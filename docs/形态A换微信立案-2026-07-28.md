# 形态 A（候选人主动发起换微信）修复立案 —— 待甲方裁决

状态：**立案，未获批，实现已冻结**。本文按 AGENTS.md「增量交付、提交与停止纪律」第 12 条并列提交旧约束、拟议文本、当前可达场景与收益成本；获批后才按「规范先行 → 实现与生成产物同步」落地。

## 一、背景：两种形态与三层判定

换微信在智联上有两条路：

- **形态 B（我方发起 → 对方同意）**：已于 2026-07-28 修复并真机验收通过（补收号触发器，两单成功）。
- **形态 A（对方主动发起 → 我方同意）**：本立案对象，当前**全线不通**。

形态 A 的链条需要三层判定，其中前两层今天都是断的：

| 层 | 问的问题 | 时效要求 | 现状 |
|---|---|---|---|
| 动作层（即时正证） | 我方点的那一下成了吗？ | **必须即时**（原语内定论，不重试） | ❌ 断：契约锚定与真机相反 |
| 业务层（账本事件） | 微信线该不该推进到「已换号」？ | 可延迟 | ❌ 断：手侧谓词与真机相反 |
| 数据层（权威取号） | 号是多少？ | 可延迟 | ❌ 断：依赖上两层 |

## 二、真机事实（2026-07-28 生产页面直读，两个样本）

| | 请求消息 | 结果消息 | 微信字段 |
|---|---|---|---|
| 形态 A（样本：对方主动发起） | `105 / in / originType=2` | `259 / **out** / originType=2` | `userWeChat` + `staffWeChat` 齐全 |
| 形态 B（样本：我方发起） | `105 / out / originType=1` | `259 / in / originType=1` | 齐全 |

规律：`originType` 恒等于发起方（1=我方、2=对方）；`flow` 表示消息归属方，结果消息**归属点同意的一方**。故两形态的 259 方向相反。

另外同一样本上，DOM 已就地改造（`is-wx-done` + 「复制微信号」按钮），其 `data-clipboard-text` 与 259 的 `userWeChat` **给出同一个号**。

## 三、与旧项目结论的关系（不构成矛盾）

旧项目注释与 `已知问题.md` 称「场景 A 不产生 259，号只在 DOM」。经核对，该说法**不承重**：它唯一来源是 20 秒轮询的否定观察，且旧项目全链靠 DOM 取号成功，从未依赖也从未回头验证「259 不存在」。其谓词 `hasAcceptedCandidateWechatCard` 并不按方向过滤，故不是「看漏了方向」。

最省事且使两边观察同时成立的解释：**259 由服务端异步生成推回，到达晚于 20 秒窗口**——不需要假设平台改过行为。

结论：直接正面观察优先于短窗口否定推断；但「259 可能不即时」这一风险由该观察佐证，是本方案拆分三层的直接依据。旧项目 DOM 路线在生产上反复成功，是即时正证的可靠依据。

## 四、立案：契约规范性修改

### 4.1 `chat.readWechatExchangeOutcome@1` 的 origin2 锚定（协议规格 §186 + contract note）

- **旧约束**：`requestSourceKey` 只允许锚定两种已证实请求：`105 + in + originType=2 + success` 后唯一的 **`259 + in + originType=2`**，或 `105 + out + originType=1 + success` 后唯一的 `259 + in + originType=1`。
- **拟议文本**：把 origin2 分支的结果消息方向由 `in` 改为 **`out`**（`105 + in + originType=2 + success` 后唯一的 `259 + **out** + originType=2 + success`）。origin1 分支**不动**——真机验证正确，且 2026-07-28 已两次成功收号。
- **当前可达场景**：候选人主动发来换微信请求、我方同意后，锚定永远匹配不上，`confirmed` 恒为 false，号永远收不到。
- **收益与成本**：收益＝形态 A 的取号链路可用。成本＝一处方向常量修正，无新字段、无新原语；属对真机事实的纠正，不扩大原语能力。

### 4.2 `chat.acceptWechat@1` 的成功正证与 data 结构

- **旧约束**：note 规定「成功只接受相对基线唯一新增的 `259/in/originType=2/success` 稳定消息，该行必须同时具有候选人与招聘方微信字段」；`ChatAcceptWechatData` 把 `exchangeSourceKey` 与 `peerWechat` 定为**必填**。即：**拿不到号就不算点成功**。
- **拟议文本**：
  1. 即时正证改为**可见后置状态**——同一张请求卡上的标准同意动作消失、变为「复制微信号」形态（按**可见文本**判定，类名只作定位提示）。该形态是 AGENTS.md「可见后置状态原则」明列的合法正证，且天然幂等。
  2. `259` 由必需降为**可选加成**：若在原语执行窗口内已到达且方向、originType、双字段齐备，则一并返回；未到达不影响成功判定。
  3. `ChatAcceptWechatData` 的 `exchangeSourceKey`、`peerWechat` 由必填改为 **optional**，并增加约束：两者要么同时出现、要么同时缺席。
  4. 号的权威来源改由既有 `chat.readWechatExchangeOutcome@1` 延迟收编（与形态 B 2026-07-28 已上线的收号触发器同一模式）。
- **当前可达场景**：若维持旧约束，点击即使真实成功、平台也已交换，只要 259 晚到就判「未确认」→ 转人工；而按安全内核「阴性禁止第二次动作」，该次接受此后不会再自动重试，等于每次形态 A 都要人工兜底。
- **收益与成本**：收益＝把「动作成没成」与「号是多少」解耦，二者各自失败不牵连；不再押注于未验证的 259 即时性。成本＝一处 data 结构由必填改可选（首客前允许破坏性修订），脑侧正证事务需处理「已确认但暂无号」分支；即时正证改用可见文本判定，脆性由「样式类名」降为「可见文本」（按防护成本预算第 2 条属低脆）。

### 4.3 不需要修改的部分

AGENTS.md 无需改动（本立案不新增出站、不扩载荷）；`docs/沟通逻辑规格-v4.md` 无需改动（「他主动发起换微信 → 无条件同意、收号、通知运营、AI 承接」本就是既有条款，本立案只是让它可执行）。

## 五、手侧改动（非规范性，随实现批）

`plugin/src/program/platform/zhilian.ts` 的 `isCandidateWechatAccepted` 目前要求 `from === target(in) && originType === 1`，形态 A 的 `out + originType=2` 两个条件都不满足，导致该 259 在账本里连「微信卡」都不算、状态机永远收不到「已换号」事件。需增加形态 A 分支：`259 + out + originType=2 + 双微信字段齐全`。

## 六、观测项（不进硬闸）

## 八、出口四项

1. **本轮最小可交付出口**：契约与手侧改动合入并通过全门禁；真机有人值守下，一次真实的形态 A 接受走通「点击 → 即时正证 ok → 账本迁入已换号 → 延迟收号 → 运营通知」全链。
2. **必须立即阻断的损害**：同一请求被点击两次（重复副作用）；即时正证误判为成功而平台实际未接受；号取错（两来源不一致却仍收编）；形态 B 既有链路受影响（origin1 锚定与谓词不得改动）；DOM 通道被当作授权来源。
3. **允许重试/人工兜底的失败**：259 未到达或字段不齐（下轮巡检重试，readonly 无副作用）；即时正证读不到（转人工，不再点击）；两来源不一致（转人工）；截图或通知失败（缺图降级）。
4. **独立审查与后置项**：冒烟绿并提交后一轮定向审查。后置项：DOM 抽号是否转正为硬兜底（凭观测数据另行裁决）、`confirmed=false` 的细分原因需扩契约字段、全库 `deferred` 终态清点。
