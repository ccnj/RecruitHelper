# 平台通知上报设计（2026-09-02 甲方裁决，第十一项云端出站）

条款见 AGENTS.md「全局约定·平台通知上报」；本文是实现底稿与真机事实记录。

## 一、真机事实（2026-09-02 GPT Chrome 只读考古）

页面：`https://rd6.zhaopin.com/app/personal`（个人中心，与微信配置开工闸同一页）。

1. 页面下半区是「面试 / 通知」两页签，默认停在「面试」。DOM 锚点：
   - 页签容器 `.todo-notification__tab__header`，页签项 `.todo-notification__tab__header-item`，激活项内 label（`.todo-notification__tab__header-item-label`）带 `.active`；容器激活通知时带 `.active_notification`。
   - 通知列表 `.notification > .notification__list`，每条 `.notification__list-item > .notification-item`，子节点 `__time`（`8月2日 09:50`，**无年份**）、`__title`、`__content`（内含「查看详情」按钮）。列表下方 `.notification__view-all`「查看全部通知」是另一个页面，不进。
2. 点「通知」页签时页面自行发三个请求：
   - `GET /api/app/notice/center/getNoticeList?pageSize=10&pageNo=1`——列表数据；
   - `POST /api/app/notice/center/updateNoticeExposeTime`——**服务端副作用**：登记"通知已被看过"，红点随之消失；
   - `GET /api/app/notice/center/checkWhetherShowDot`——红点状态。
   点页签之前列表数据不在页面里（组件 `noticeList` 在页签激活后才装载）。
3. 列表数据在 Vue 组件（`.notification` 元素的 `__vue__`，计算属性 `noticeList`；`$store.state.notice.noticeList` 同源）。每条字段：`id`(数字字符串)、`logo`、`time`(毫秒字符串)、`title`、`content`、`isRead`、`href`（如 `job/detail?jobNumber=…`）、`forcePush`、`messageType`(整数)、`propertyContext`、`srccode`。`hasMore=true`，`isShowDot=false`。
4. 本账号第一页 10 条的 `messageType` 全集：5「职位审核通过」、6「职位审核未通过」、1「求职者举报通知」、123「招聘工具箱搬家通知」。
5. 考古：旧工作区（`../AutoZhilian`）零代码触及通知中心；`html定位/` 样本里的 `notice` 状态块 `noticeList` 全空、`hasMore: true`——**这就是装载前的初始态**，所以"数组为空"不能直接当空箱。候选清单只有今天真机这四种。

## 二、实现

### 手（plugin）
- 原语 `account.readNotices@1`，intrusive，`platformSideEffect=idempotentReadReceipt`，60s/120s/30s。
- 复用微信闸的个人中心导航与账号核对（抽出 `ensureZhilianPersonalTab`）；页签未激活则点一次 label；两段条件轮询各最长约 20 秒（页签栏就绪 → 列表装载）；从 Vue 组件读第一页；不翻页、不点「查看详情」、不进「查看全部通知」。
- 装载完成判据：`noticeList` 非空且 DOM 条目数与之相等；数组为空只有 `hasMore===false` 才算真的空，否则视为初始态继续等。
- 归一：`noticeId` 缺失即整体失败留痕（服务端无法幂等）；`messageType`/`time` 换不出记 null 不丢条目；标题/正文按契约上限截断（256/4000 字）。
- data：`{notices[], observedAt}`；未见 `messageType` 原样携带。

### 脑（client/service）
- 开始入口 `productapp.Controller.Start`（人工与每日自动开始共用，完整流程与仅回复均含）：`gateWechatConfigured` 通过后、创建工作流前，`collectNoticesBestEffort` 同步派 `account.readNotices`（`appbridge.NoticeCollector`，同账号串行域，上限 90 秒）。同步是硬要求——它要导航页面，必须在批次读推荐流之前收束。
- 前置与微信闸共用 `startsNewWork`（无活跃运行、无未终局采集批次）；不满足不派发。
- 读到即经 `noticereport.Reporter` 异步 POST `/api/v1/client/platform-notices`；读失败、手离线、上传失败只记日志（`noticeCollectFailed` / `noticeReportFailed`），不拦开始、不重试、不建发件箱。
- 载荷由独立结构体逐字段抄（白名单由 `noticereport` 测试钉住）：`machineId`、`licenseToken`、`clientVersion`、`platform`、`observedAt`、`notices[]{noticeId,messageType,title,content,noticeTimeMs,isRead}`。空列表不上传。

### 旧后台（xq-resume-backend，分支 dev-wmt-0703-platform-notices）
- 迁移 `0029_platform_notices.sql`：表 `platform_notices`，唯一键 `(customer_id, platform, notice_id)`；永久留存。
- 路由 `POST /api/v1/client/platform-notices`（`client_platform_notices.py`），verify_client 鉴权，`extra="ignore"`，回执只 `{"ok": true}`。
- 仓储 UPSERT：冲突只刷新 `is_read`、`last_observed_at`、`last_seen_at`、来源机器与版本；**标题与正文不回改**。
- 部署顺序：后台先行（先跑迁移再重启），客户端后发版；客户端先到时上传 404 只记日志，不影响任何业务。

### 管理前台
- 查看面板后置（甲方 2026-09-02 裁决）。数据已落表，可用 SQL 直查：`SELECT notice_time, message_type, title, content FROM platform_notices WHERE customer_id=? ORDER BY notice_time DESC`。

## 三、边界与代价（甲方 2026-09-02 知情接受）

1. 每次开始都会清掉招聘方账号的通知红点（曝光时间 POST 是平台自己发的，点页签即触发）。
2. 开始多花约 3～5 秒（切页签 + 等列表），最坏两段各 20 秒超时后照常开始。
3. 通知正文是平台原样文案，可能含候选人姓名（举报通知类），不做内容级脱敏、不主动回查装配任何额外身份。
4. 数据源是 Vue 内部状态（高脆感知通道，与 `chat.readList` 同类）：平台改版即读不到，失效方向=不上报，不影响开始。
5. 只上行；本通道不复用于其他上报。
6. 新增一个 intrusive 原语 = 契约永久负债。

## 四、挂账与真机待验

- **真机首验**：客户机开始一次，看脑日志「平台通知已上报旧后台」与服务端 `platform_notices` 行；确认红点被清的观感。
- **空箱账号未验**：账号一条通知都没有时，组件 `hasMore` 是否变为 `false` 未经真机证实；若平台在空箱下仍保持 `true`，手侧会等满 20 秒后以 `notice_list_empty_unsettled` 失败，每次开始留一条 warn（不影响开始）。遇到空箱客户时按日志修判据。
- **未见 `messageType`**：日志与表里出现新值时补进本文第一节。
- **管理前台查看面板**：后置。
