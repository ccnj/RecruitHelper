# 智联负反馈形态考古(2026-08-11)

候选人对我们说"不"在智联上有两种超出打字的形态:在换微信邀请卡上点拒绝、直接拉黑。两种形态平台各自长什么样、我们现在把它们解析成了什么、正确实现该注意什么——本文是真机事实底稿,供「拒收换微信形态」与「拉黑感知」立案用。**本文只记事实,不是开工授权;立案仍须按防护成本预算三问与出口四项另行呈报。**

取数路径(两章共用):GPT Chrome 只读,Vuex `im/timeline` getter 与 `im.sessions` 会话列表——与插件 `chat.readThread` 两级取数的同一数据源(引用相等,见 `plugin/src/program/platform/zhilian.ts` readRowsOrNull 注释)。平台 IM 行是网易云信形态,业务负载在 `row.content`(JSON 字符串)里,`envelope = parse(row.content)`,`inner = parse(envelope.content)`。

## 一、拒收换微信

标本会话:2026-08-10 真机,conversationRef `c1532d3cd6d63e176e525aa6b515bbb7`(即 2026-08-11 语义闸战役的验收会话)。候选人 14:27 收到我方换微信邀请卡,14:30 打字回复,14:37 左右在卡上点了拒绝。

**1. 拒收行的完整形态(真机已见):**

```
row.type   = "custom"
row.status = "success"
row.from   = 候选人侧账号(即卡的接收方;点拒绝的人)
row.idServer 存在(可派生 sourceKey)
envelope.type = "99"(字符串)
inner = { "msgb": "对方拒绝与您交换微信", "msgc": "已拒绝交换微信", "type": 2 }
envelope.fallbackText.receiverText = "当前版本不支持显示该内容,请将APP更新至最新版本查看"
envelope.lastMessage.receiverText  = "对方拒绝与您交换微信"(招聘方视角)
envelope.lastMessage.senderText    = "已拒绝交换微信"(候选人视角)
```

页面把它渲染成居中灰字「对方拒绝与您交换微信」。

**2. 邀请卡本身不翻状态。** 同会话 105 邀请卡(`scene:"EXCHANGE_WECHAT"`,originType:1)的负载只有静态内容:`aiOperate/detail/icon/originType/pushContent/pushTitle/staffContent/userContent`,**没有任何状态字段**。拒收发生后卡负载不变。⟹ 拒收事实只存在于独立的 99 行;实现必须仿照 259 交换成功的既有套路——产出一张**新的** `cardState='rejected'` 卡片行(自有 idServer/sourceKey),不是改旧卡状态。

**3. 99 行不引用卡。** 拒收行负载里没有 requestId/cardId/交换请求引用。行与卡的配对做不到消息级,只能由脑按会话级微信线状态裁决(同 v4 对 259 的处理方式)。

**4. `inner.type` 是本次新见的结构判别子,老项目无先例。** 老项目(`../AutoZhilian/xq-resume-program/src/apps/workbench/utils/zhilianMinimumCollect.ts:4146`)把 99 当**通用通知族**处理:显示文本取 `msgb ?? msgc`,不区分子类型。99 族在本仓库账本里 26 条,上下文各异(8 条紧跟 pending 微信卡、有跟在"人才投递"后的、有连续两条的);已见判别子清单见文末汇总,**未见值不得实现**,归并到保守分支时保留原始类型进日志。

**5. 老项目微信卡族全表(考古候选清单):** `105`=交换请求(ASK_FOR_WX)、`259`=交换结果(WX_CARD)、`280`=查看微信号卡(IM_CHECK_WX_CARD)、`281`=系统自动交换微信(OPEN_AUTO_CHANGE_WECHAT)。280/281 本仓库真机未见。老项目的卡信息抽取器还认 `wxCardState/wxSwitchState/state/status` 四个状态字段——本次 105 标本一个都没有,列作核对清单,不作实现依据。

**6. 老项目整族丢弃 `104/169/266`**(同文件 4194 行)。本仓库账本有 19 条 `[系统消息:104]`,保守 system 分支处理是对的,暂无业务价值证据。

**7. 旁支发现:148 = 「标记不合适」事件。** 标本会话 14:09 的 148 行负载:`userInappropriateScene:"ASK_FOR_CONTACT"`、`prefix:"已标记不合适"`、`staffText` 为平台代发的模板拒绝话术。即:那句「很抱歉,我暂时不考虑这个机会,感谢您的认可~」不是候选人打字,是他点「不合适」按钮后平台代发的。现有 148 分支把它解析成入站文本、进拒绝判定,行为正确;记录在此以免日后误当真人措辞分析。

### 现有解析的缺口(实现时要改的点)

当前 system 兜底链(`zhilian.ts` 三处复制体,约 8360/9287/9991 行):

```
details.staffText ?? details.userText ?? details.title ?? details.content
?? envelope.msgb ?? envelope.msgc ?? envelope.text ?? row.text
```

`msgb/msgc` 实际在 **inner(=details)层**,链里却写在 envelope 层——恒漏,所以 99 全部落成 `[系统消息:99]`。这也是 2026-08-10 化石文本漂移的近因之一(修链本身也会再变一次兜底文本;语义闸已豁免 system 行,`main` 合并节点 `0a29a44`,不会再卡会话)。

### 设计提示(供立案,非结论)

- 判别子建议:`customSuccess && customType===99 && inner.type===2 && from===候选人侧`;`msgb` 文本是平台文案、会改版,只进 evidence 不作判别。
- 产出形态仿 259:`kind='card', cardType='wechatExchange', cardState='rejected'`,contentHash 用既定常量配方 `sha256("card\x1fwechatExchange")`,text 用 `[微信交换被拒]` 之类兜底占位。
- 脑侧连带:v4 微信线 invited→rejected 的状态语义、催2/邀请余额的后续行为,属沟通逻辑规格 v4 修订面,规格先行。
- 存量:26 条 `[系统消息:99]` 化石与 8 张实际被拒但记 pending 的卡,甲方 2026-08-11 裁"直接忽略",不迁移。
- 契约:`cardState` 枚举早含 `rejected`,零新增契约面。

## 二、拉黑(被候选人屏蔽)

标本会话:2026-08-11 真机,测试候选人会话 `52ba3e7491d9c9a42932a0d5157b1228`(该候选人已约面、已换微信)。候选人侧主动拉黑招聘方账号后,我方从平台页手动试发消息两次,分别观察"刚发完"与"刷新后"两种页面状态。

**1. 会话列表元数据带结构化拉黑布尔位(真机已见):**

```
sessions[i].blocked  = true    ← 对方把我们拉黑
sessions[i].blocking = false   ← 我们拉黑对方(未见 true 形态)
sessions[i].mute     = false
```

**页面没有任何可见横幅或提示条**——结构化字段先于可见 UI 存在。检测拉黑不必读时间线、不必试发消息,会话列表数据自带。

**2. 拉黑后发送,消息本体不落服务端。** 两种页面状态形态不同:

- **刚发完(未刷新)**:时间线尾部出现乐观本地行——`status:"fail"`、**无 idServer**、`idClient` 为空、`time` 是**空对象**(Number 化为 NaN)、带 `sendMessageId` 与 base64/progress 等本地上传字段。
- **刷新后**:该行整个消失,平台历史接口不保留失败发送。

**3. 每次尝试插入一条 99 族通知,且新鲜/刷新两态文本不一致。** 通知服务端落行(有独立 idServer):

```
envelope.type = "99"
inner = { "msgb": "对方拒收您的消息,消息发送失败", "msgc": "", "type": 34 }
```

**新鲜时 `row.text` 回显被拒正文;刷新后 `row.text` 变空**(此时解析落 `[系统消息:99]` 兜底)。同 sourceKey 文本漂移的第二个实例(第一例是 2026-08-10 插件换代化石),已由协议规格 §4.5 的 system 行语义闸豁免(2026-08-11)结构性覆盖,不会卡会话。**铁律:通知行的 `row.text` 是易变渲染态,永远不可作耐久判据。**

**4. 现有系统对拉黑发送的行为链(2026-08-11 逐层代码核实,无缺陷、方向安全):**

- 发送原语的发后观察 `mainObserveStableOutbound` 对窗口每行硬性要求 idServer 且 time 可数值化,fail 行双重不满足→每轮观察阴性→原语收场 suspect;
- fail 行滞留期间(直至页面刷新),该会话 `chat.readThread` 撞"out 方向 status 非 success"整读抛 `outbound_delivery_unconfirmed`——感知冻结仅限该会话,失效方向是"少做";
- 发后验证读的 2026-08-03 乐观判成功例外判据是**精确错误串** `thread_page_source_unavailable`(`dispatch/verification.go`),`outbound_delivery_unconfirmed` 不在内→recordMiss→suspect 转人工。**无假成功路径、无自动重发路径。**
- 代价:每次向被拉黑者发送=一张 suspect 人工票据(冷催预算使其每人有界);脑对拉黑事实无感知,会话在其视角持续"活着"。

**5. 会话列表元数据顺带的结构化业务状态字段(存在性记录,供候选清单):** `candidateState`(见 `"APPOINTED"`)、`wxSwitchState`(见 `"DONE"`)、`userWeChat`(候选人微信号明文)、`speakTimes/replied/lastActiveTime/topped` 等。平台在列表层已结构化这些状态,将来有需要不必从时间线推。

### 设计提示(供立案,非结论)

- 检测通道建议:会话列表 `blocked` 布尔投影(结构化、读列表时白捡、零额外平台交互),优于识别 34 通知行(渲染态、兜底文本、晚一拍),更不得用"发送失败"反推(核验失败不得反推副作用语义是既有红线;且 suspect 已兜住该路径)。需契约在列表读数上加一个布尔字段,开发期契约可破坏性修订。
- 状态机语义、假阳性方向(错误归档=少做+可唤醒恢复)见立案时的规格修订文本。
- 在途 suspect 不因拉黑发现而自动收敛,照旧人工裁决(安全内核不动)。
