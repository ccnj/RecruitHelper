## 1. 想要什么

客户机装在客户办公室，我方看不见。现在想知道「那台机器今天在干活吗、干了多少」，只有两条路：

- 打电话让客户截图或口述；
- 用现场数据上报把全库拉回来，解包、开 SQLite、敲 SQL。

第一条不可靠，第二条滞后（每天 00:10 一次，或者有人现场点一下）且只有我方能读懂。两条都答不了「此刻这台机器是不是卡住了」。

这个功能把它变成：客户机每 5 分钟主动报一行状态，运营打开管理前台就看到每台机器一行——最后上报时刻（判断在不在）、现在跑到哪个阶段、今天采了多少人、招呼多少条、换到几个微信、约成几场面试。

## 3. 撞上的旧约束

### 3.1 云端出站白名单——必须加第六项

AGENTS.md 开篇列了五项获准出站（旧后台 bind/job-config、LLM provider、运营通知 webhook、版本更新源、现场数据上报），末尾一句「除此之外仍视为不连云端」。这是第六项。

### 3.2 `metrics`/`heartbeat` 被逐字点名

同一段里两处：

> 不得因此接入 verify/heartbeat/session/task/metrics/alert 等其他控制面或**上报接口**

> `client_metrics`/`client_alerts`/`client_sessions`/`client_ai_model_logs` 等既有上报面仍不接入、不复用

这个功能就是 metrics + heartbeat。**要做它，这句必须为它开一个口子。**注意第二句仍应原样保留：旧产品那四张表继续不碰、不复用，本次新建独立的表与路由。

### 3.3 旧后台改动许可要再放宽一次

开篇现文是「旧后台在客户交付前只允许为本仓库明确获批的用途改动」，现有获准用途三个（bind、job-config(s)、现场数据上报）。这是第四个。代价与上次相同且不减：**每次发布会重启 `console-server.service`，而那个进程正在给 AutoZhilian 的存量客户服役。**

### 3.4 新增跨层机制立法四问（防护成本预算第 10 条）

这是常驻定时器 + 跨层 + 新持久化，四问必答：

**（一）当前可达的具体事件序列与实际损失。** 已经发生过的形状：2026-08-05 客户机一条 suspect 把同批其余 32 人冻结 72 分钟——这件事是事后翻库才发现的，而 5 分钟粒度的「阶段停在 sendingGreetings 且待裁决条数 = 1」会当场把它顶到台面上。同类还有采集撞底、职位配置没同步、插件掉线、掉登录：共同点是**客户机静默，而静默在我方这边和「今天没成果」长得一模一样**。

**（二）为什么现有机制不够。** 现场数据上报是每天 00:10 一次或人工点一下，粒度是天，且产物是要解包查库的原始库，运营看不了。运营通知 webhook 只在换微信/约面成功时响一次——机器死了它也不响，静默不可分辨。人工电话问不成规模。

**（三）是否以最小状态闭合。** 关键设计选择：**上报的是当前累计快照，不是增量事件。**由此得到——丢一次包下一次自愈，不需要发件箱、不需要重试、不需要游标、不需要「补报关机期间」；客户端零新增业务持久化状态；服务端一张追加表。这不是把歧义推给下一层，是这类数据本身允许丢。

**（四）总代价。** 客户端一个 goroutine + 一份只读聚合；旧后台一次改动与重启；管理前台一页；服务端每天约 288 行/机器（10 客户 90 天约 26 万行，PostgreSQL 无压力，仍配留存清理）。协议表面零增加——不走脑手 contract。

### 3.5 与「手的禁令」无关

「不得有业务定时器」约束的是插件。这个定时器在脑里，脑本来就是节奏的唯一来源。插件对此功能零参与。

## 4. 上报什么（PII 审查逐字段）

原则：**只出计数、枚举、时刻，与我方自己的标识。**候选人的一切——姓名、微信号、`profileId`、`platformUserRef`、消息正文、简历——一个字节都不出去。这条不是「注意一下」，是代码层白名单：载荷用一个专门的结构体拼装，不复用产品投影的类型（那些类型里有 `DisplayName`），字段全部显式赋值。

### 4.1 身份与时刻

| 字段 | 内容 | 说明 |
|---|---|---|
| `schemaVersion` | 整数 | 载荷版本，服务端据此宽容解析 |
| `machineId` | 我方机器标识 | 与现场数据上报同源，已有先例 |
| `appVersion` | 客户端版本 | |
| `reportedAt` | 客户端本地时刻（带时区） | |
| `localDate` | 客户端本地日期 | **服务端按这个切天，不按服务器时区**——客户端库里两种时间格式混用过，切天只信客户端自己算的结果 |
| `brainUptimeSec` | 脑启动至今秒数 | 频繁重启是一种故障信号 |

客户身份不自报：服务端从 `licenseToken` 解析，与现场数据上报同轨。

### 4.2 当前在做什么

| 字段 | 内容 |
|---|---|
| `job.backendJobId` / `job.name` | 当前绑定职位（后台职位名） |
| `job.syncStatus` / `job.lastSyncedAt` | 职位配置同步状态 |
| `workflow.status` / `stage` / `mode` | 枚举，不是自由文本 |
| `workflow.startedAt` / `pausedAt` / `endedAt` | |
| `workflow.endReason` | 原样上报 |
| `workflow.failureReason` | 原样上报（见下） |
| `batch.targetCount` / `capturedCount` / `scoredCount` / `selectedCount` / `sentCount` | 当前批次进度 |
| `account.bound` / `account.platform` | 有没有账号在跑；**不报 `accountRef` 原文**（报了没用，少一个字段少一份风险） |

**失败与结束原因原样上报（2026-08-06 甲方裁决）。** 立案初稿曾要求把这些字段映射成封闭枚举，甲方裁定不必，直接报原文。

支撑这个裁决的事实（本仓库实查）：`SourcingBatch.Reason`、`ProductWorkflowRun.FailureReason` 及动作层的同名字段类型上都是 `string`，**但实践上写入的全是驼峰码**——`recommendationFeedChanged`、`sourcingTargetReached`、`noNewCandidates`、`startInterruptedBeforeBatch`、`effectResolvedFailed`、`payloadLimit`、`handManualReview` 之类；`resumeFailureReason()` 是一个把协议错误码翻成固定码的 switch，没有拼接现场文本的分支；store 层另有 256/512 字符的长度上限。全仓库找不到把候选人姓名或正文拼进这些字段的写入点。

因此代价是「将来若有人往这些字段里拼候选人信息，会随本通道带出去」，而不是「现在就会带出去」。甲方知情接受，不做映射、不做过滤。**载荷仍不含**候选人姓名、微信号、`profileId`、`platformUserRef`、消息正文与简历——那几项是结构化字段，与本条无关。

### 4.3 今天的战果

`todayCaptured`（跨批次，新查询）、`todayCapturedByJob`（职位名 + 人数，甲方点名的「采集了什么职位」）、`todayRated`、`todayConfirmed`、`todayGreeted`、`todayReplies`、`todayWechat`、`todayInterviewInvites`、`todayAppointments`、`todayGreetingGenerationFailed`、`todayGreetingSendFailed`、`todaySuspects`。

累计：`totalGreeted`、`totalWechat`、`totalInterviewed`。

（生成失败与发送失败必须分两个字段——投影层已经因为合并过一次而误显示，注释里写着教训。）

### 4.4 运行健康

`handOnline`、`handContractMatch`、`extensionVersion`、`lastHeartbeatAgoMs`、`witnessJournalOpen`、`witnessOutboxPending`、`pendingManualVerdicts`（待人工裁决条数）、`manualRequiredProfiles`（已转人工的候选人数）、`llmProviderConfigured`。

`witnessJournalOpen` 特别值得报：证词 journal 打满曾经直接把发送打瘫，那次是事后才知道的。

### 4.5 多账号说明

今日计数按当前活跃账号（`platform` + `accountRef`）口径。客户端同一时刻只有一个活跃工作流槽，所以现在等价于「这台机器的今天」。若将来出现多账号并行，本载荷会只反映活跃那个——记在这里，不为它提前设计。

零账号时（全新安装、未登录）照常上报：职位与健康字段有值，今日计数全零，`account.bound = false`。**不能因为没账号就不报**——那正是最需要被看见的状态。

### 几项裁决的理由备查

- **恒定 5 分钟、不做夜间降频**：心跳的价值一半在「我还活着」，降频会让离线判定的阈值跟着变复杂。每天 288 次、载荷不到 2KB，服务器无感。
- **留存 90 天且与接口同批**：10 客户约 26 万行。现场数据上报的教训是留存清理不能后置。跨月趋势暂不做，需要时再补每日收盘快照。
- **离线判定 15 分钟**：连丢三次才标红，只是前台显示口径，不产生任何客户端行为。
- **日志降噪**：常开 + 5 分钟一次，后台连不上时一天 288 条 ERROR 会淹掉 32MB 轮转的 `brain.log`。

## 6. 若获批：技术方案

### 6.1 脑侧（本仓库）

新增 `client/service/internal/statusreport`：

- **一个 goroutine，`time.Ticker` 5 分钟**，与 `report` 包的每日调度器同轨（函数注入依赖，不认识 store/workflow 类型）。脑启动即起，不看业务运行窗口。
- **采集**：调一次现有的 `AppOverview` 投影（复用，不重写口径），加一句今日跨批次采集 count，加一次 `handHealth` 快照，加一次 suspect count。
- **拼装**：**独立的 payload 结构体，字段显式赋值**，不把投影类型直接序列化。这是白名单的实现方式——投影类型里带着 `DisplayName`，直接序列化就等于把候选人姓名发出去；配一个单元测试断言序列化结果里不出现候选人姓名、微信号、`profileId`、`platformUserRef`、消息与简历字段。
- **上传**：一次 POST，超时 15 秒，失败只记日志（按第 5 节降噪口径）。**不重试、不入库、不建发件箱。**
- **响应处理**：只解析 `ok`。**代码里不提供任何把响应内容转成本机行为的路径**——这是「只上行」的实现保证，审查时重点看这一处。
- **未激活时跳过**：没有 `licenseToken` 就不报，静默跳过（不刷日志）。

关于 5 分钟一次聚合抢 `SetMaxOpenConns(1)` 那唯一连接：产品首页轮询已经在跑同一份投影，边际成本是已知的零头；但上报是常驻的，所以实现时要测一次单轮耗时，写进验收记录。若单轮耗时超过 1 秒，再考虑把总计数改成低频。

### 6.2 服务端（旧后台，不在本仓库，分支 `dev-wmt-0703`）

照 `client_reports.py` 的形状：

- `app/api/client_status.py` — 新 router，挂 `/api/v1/client/status`，`routes.py` 注册。鉴权走 `verify_client`（与 `client_auth.py` 同轨），**不是** admin token。
