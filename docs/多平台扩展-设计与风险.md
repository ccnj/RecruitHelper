# 多平台扩展 · 设计与风险

> 目标:系统能轻松从智联扩展到别的招聘平台(Boss 直聘、前程无忧…)。
> 本文记录支撑这一目标的设计约束、尚未验证的风险、以及正确的扩展路径。

## 已落地的三道墙(平台脏东西被关住)

多平台成败只看一条:**平台的脏东西(DOM/selector/接口/页面时序)有没有被关进盒子,不渗进协议与业务。** 已由宪法/协议强制:

1. **协议意图级、平台无关**(AGENTS.md 大方向 2;协议规格 §1 公理 7、反模式 3/11)。脑说 `readThread(threadRef)`,不说"点智联那个 div"。DOM/selector/tabId/平台专有 id 只许进 evidence 与日志,脑逻辑不得读 evidence 做分支。命令必须声明式。
2. **脑完全平台无关**。业务逻辑(状态机、沟通 v4、巡检)对平台一无所知;加新平台,脑一行不动。
3. **base/program 分层 + 手侧实现注记**(C 卷 §6.4)。平台特定实现只活在 program 原语里;智联专有细节压进"实现注记",不进协议语义。

结论:接缝干净,方向对——比旧系统(DOM 知识缠进客户端)强一个数量级。

## 尚未验证的风险(现在没暴露,因为只建了智联的假原语)

**铁律:对着单一实现建的抽象几乎总是错的——不知道正确接缝在哪,直到第二个实现逼你看清。** 目前"平台无关"是被强制的约束,不是被证过的抽象。具体待验证/待补:

- **协议数据 schema 的真中性**:`chat.readThread` 返回的会话快照,字段名中性但骨子里仍是"智联形状"。第二平台若 IM 模型不同(消息结构、卡片类型、已读语义),会暴露泄漏——届时要么泛化契约,要么脑被迫加平台分支(后者破坏平台无关,禁止)。
- **平台路由**:`cmd.context.platform` 字段已留,但 domainOf 目前写死 `debug:`。多平台需脑按平台路由命令、管每平台账号与串行域——脚手架在,未跑过。
- **能力声明按平台**:脑靠 capabilities + context.platform 判断一只手能做哪个平台。机制在,未设计透。
- **业务逻辑里的平台假设**(最易忽略):沟通 v4 的"邀面卡""换微信卡"不是每个平台都有。缺此机制的平台,沟通逻辑要分叉。这是业务层埋着的平台耦合。

## 正确的扩展路径(别过度抽象)

**陷阱**:现在就建通用"平台适配框架"。单数据点猜抽象必错,还徒增复杂度。

**纪律**:
1. 守住接缝(宪法已强制:平台脏东西只进 program 与 evidence)。
2. 先把智联建成真的(M2),不为想象中的第二平台留抽象(YAGNI)。
3. **第二平台必须建立在真实账号与真机验证上。** 在取得其他平台真实账号前,M2 及后续阶段只做智联,不建虚假的 Boss 适配层。未来拿到第二平台真实账号后,再尽早做一条薄感知竖切——两个真实实现摆一起,才知道正确接缝;那时再一次性重构 contract 的数据 schema。

一句话:**架构选对了,接缝也守住了;但"多平台"靠早点撞第二个真实平台换来,不靠现在堆抽象。** 第二平台上线那一刻,是这套架构最值钱的验收,也是它最可能需要小修一次的地方(优先修 contract 数据 schema,不是脑)。
