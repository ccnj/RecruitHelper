# 里程碑 2 · 智联感知与对账实施计划

> 状态：执行基线，2026-07-17。
> 上游约束：`AGENTS.md`、`contract/协议规格-v1.md`、`docs/沟通逻辑规格-v4.md`、`docs/协议设计/C-感知同步模型.md`。
> 真机许可：见 `docs/真实账号测试授权记录.md`。
> 连接威胁模型（2026-07-17 裁决）：同机本地环境可信；脑手连接不做人工配对或 token 鉴权，只保留 127.0.0.1 监听、`chrome-extension://` Origin 前置边界、插件本地随机稳定 `handId`、主版本/caps 门禁与 10 秒 helloTimeout。`contractHash` 是公开漂移摘要，不是签名或凭据。

## 一、目标与边界

M2 只做一件大事：**把智联从三条 debug 假原语推进为真实、可重复、可恢复的感知与巡检对账闭环。**

完成时，用户每天手动开启一个智联账号 actor 后，脑能通过同一正式命令通道驱动手完成：

1. 识别真实智联页面、登录态与 content script 健康；
2. 建立或复用 IM 页面；
3. 读取会话列表并建立轻量索引；
4. 对脑侧明确标记为 tracked 的会话判脏并读取有界快照；
5. 对 tracked 会话完成首次收编、最大重叠对齐、卡片状态更新和“本轮新增”投影；
6. 在协议列举的确定性故障模型内，即使事件全部丢失、插件失忆或脑同日重启，仍由下一轮巡检恢复 tracked 会话账本；连续相同消息恰落窗口边界的理论歧义保留审计、深读和长跑观测，不作无条件“零漏”承诺。

M2 的正确性来源只有巡检对账。事件和心跳传感只能拉前巡检、打开静默窗或更新健康状态，不能直接触发业务判断或发送动作。

`tracked` 是脑侧正式业务状态，不是测试模式：用户首次选择一个会话为 tracked 时创建收编意图，首轮深读并设置 adoptedBoundarySeq；untracked 会话只维护列表索引，不宣称其消息账本完整。未来由系统自己成功发出招呼建立的会话自动进入 tracked。

### 本里程碑不做

- 不做 Boss、前程无忧等第二平台；触发条件是未来具备该平台真实账号与真机验证条件。
- 不做通用“平台适配框架”；只守住脑平台无关、智联细节只在 program 的接缝。
- 不接云端，不改旧后台，不做授权、企微通知或远程 program 交付。
- 不把 `chat.sendMessage`、`chat.sendGreeting`、AI 回复或完整沟通状态机塞进 M2；它们属于后续 `[X]` 批次。
- Windows 真机与安装包仍是 M1 发布尾巴，单独收尾，不阻塞智联感知主线。

## 二、工作方法

每一批都按同一顺序推进：

1. **先核真实页面事实**：只把旧代码和旧文档当线索，在当前已登录 Chrome 真机验证域名、接口、DOM、时序和平台副作用。
2. **再改唯一契约**：需要变更时先改 `contract/协议规格-v1.md` 与 `contract/contract.v1.json`，随后运行 codegen；禁止脑、手各自补字段。
3. **做最窄端到端竖切**：一条原语同时贯通契约、手、脑、UI、自动测试和真 Chrome，不一次写完四条原语后再联调。
4. **自动验证后真机验证**：纯算法、错误路径和极端样本由自动测试覆盖；真实账号只证明页面提取、页面驱动和平台实际效果。
5. **事实固化**：经真机确认的智联实现事实写入本仓库；脱敏 fixture 走生产解析代码，不建立测试专用分支。
6. **故障响亮**：账号错配、DOM 不确定、快照截断、零重叠、重复投影和未知副作用都不能静默兜底。

每批完成后执行适用的全量回归并记录证据：

```bash
go run ./contract/codegen -check
go test ./...
go test -race ./client/service/...
CGO_ENABLED=0 GOOS=windows go build ./client/service
pnpm --dir plugin typecheck
pnpm --dir plugin build
pnpm --dir client/ui build
```

需要真脑的 Node E2E 与真实 Chrome 验收按该批能力追加。实现批次未通过自动测试和真机门禁前，不进入下一条真实原语。

## 三、开工门禁：先闭合六个协议与身份问题

### 0. 本地可信握手修订

M1 曾验收过“60 秒配对窗 + 脑签发 handId/token”，但该证据对应的威胁模型已经在首个客户安装前被明确取代，不得把历史复杂度继续带入 M2：

- 插件首次运行用密码学安全随机源生成 `handId`，按 Chrome profile 稳定保存在 `chrome.storage.local`；它只标识手实例，不证明招聘账号身份；
- hello 的 `handId` 必填且不可空，不含 `auth`；welcome 不含 `issued`，脑不维护待配对项、配对窗口或 `paired_hands` 凭据；
- Go 服务只监听 127.0.0.1，WebSocket 升级前拒绝非 `chrome-extension://` Origin；该边界不声称防恶意本地进程；
- hello 必须在 10 秒内得到 welcome/bye，不再存在人工等待期、pre-session ping 或配对专属 bye code；
- `contractHash` 仅作 warn-only 漂移诊断，不得作为鉴权签名或硬拒依据。

如未来引入远程手、不可信本地用户或云端监听，必须先重新冻结安全威胁模型与协议版本，不能恢复旧字段冒充完成安全设计。M1 报告保留原配对测试作为历史证据，并明确标注已被替代。

### 1. 长命令的 progress、租约与 cancel

协议推迟表规定：首个典型时长超过 15 秒的业务原语上线时，progress、租约与 cancel 到期。`chat.readList` 的 DOM 兜底可能运行数十秒至数分钟，M2 已触发这个截止点；当前 `progress` 标为 `[S]`、`cancel` 仍标为 `[X]`，实现前必须正式裁决并统一规格、机器契约和代码，不能默默只靠长 deadline。

按现行触发条款，M2 默认同批激活 progress、租约与 cancel：`chat.readList` 和深读 `chat.readThread` 都上报 progress，stage 只供人读、禁止程序分支，ping/progress 均刷新 lastSeen；绝对 deadline 始终是硬上限，cancel 与 result 赛跑时 result 赢。灰度门禁分别协商 `progress/1`、`lease/1`、`cancel/1`（或契约冻结的等价版本能力），脑不得向未宣告能力的手启用对应语义。批次 0 的时长测量是参数输入，不是继续拖延的理由；若最终决定不启用租约/cancel，必须先正式修改推迟表并写出可验证的论证。

### 2. 快照大小与 blob

C 卷要求大文本或大结果走 blob，但正式协议把 blob 实现推迟到 `[X]`。现有四个阈值含义必须分清：单消息文本 >2KB 是 C 卷的 blob 建议线，welcome.inlineBytes 默认 32KB 是内联建议线，result.data >64KB 是 C 卷的数据面建议线，WS maxMsgBytes 256KB 是硬帧上限。M2 不能静默截断会话内容，也不能突破硬上限。

推荐方向：先真机测量 50 条窗口的典型和极端体积；只要合法快照可能超过内联上限，就把无业务语义的 blob 通道提前到 `[S]`，并同批验收脑侧取回、内容哈希校验、失败语义、权限和生命周期。若不提前，契约必须定义分页/分块等可证明不丢内容的有界返回策略；禁止临时发明字段或悄悄裁剪。

冻结裁决（2026-07-17）：M2 不提前实现 blob，改用协议级 opaque cursor 分页。`chat.readList` 每页最多 32 项、`chat.readThread` 每页最多 64 条，两者 `result.data` 均有 64KB 运行时硬门禁；`complete=false` 必带 `nextCursor`，脑只在聚合到 `complete=true` 后入账。单个条目仍无法在内联边界表达时响亮返回 `PAYLOAD_LIMIT`，不得截断。该裁决已经进入 `contract/协议规格-v1.md`、机器契约、Go/TS 生成类型和双端 validator。

### 3. C 卷旧命名翻译

C 卷仍有 `probePlatform`、`hb`、`hello_ack` 等推导期旧名。实施只认正式规格中的 `probe.platform`、`ping`、`welcome` 和结构化错误码；C 卷提供算法与 schema 意图，不能原样复制报文。

### 4. codegen 与运行时校验

当前 codegen 主要生成枚举、元数据和字段清单，Go body、插件 `CmdBody`、原语结果仍有手写结构。M2 的消息、卡片、游标和事件 schema 已复杂到不能继续手抄。

本批先把机器契约升级为可判定 schema，并让 codegen 至少生成：

- welcome、ping、progress、event、cmd/result 的 Go/TS 类型；
- 四条 M2 原语的 args/data 类型；
- pageKind、loginState、direction、messageKind、cardType、cardState 等复用枚举；
- required、nullable、枚举、数值上下限、版本和未知字段策略的运行时校验；
- 合法/非法样例的双端一致性测试。

`go run ./contract/codegen -check` 必须覆盖所有生成产物。

未知加法字段的策略必须是主版本内 must-ignore；contractHash 只是契约公开字节的摘要而非签名，必须只告警，不能因无害加法或摘要不同硬拒连接。

### 5. `[S]` 错误码与 ack/result 边界

正式规格已点名但机器契约尚未闭合 `USER_ACTIVE`、`CONVERSATION_NOT_FOUND` 等 `[S]` 错误。批次 1 前必须：

- 裁决 `CONVERSATION_NOT_FOUND` 与现有 `TARGET_NOT_FOUND` 的边界，只保留一套明确语义，不制造同义码；
- 规定协议、session、caps、schema 和队列类拒收才走 `ack(rejected)`；接收时已过 deadline 的命令进入执行队列的“不可执行终局”分支，`ack(accepted)` 后立即回 `result(expired)`，但绝不调用原语 handler；命令 accepted 后才发现页面、用户或目标问题，一律走 `result(failed)`；
- `CTX_NOT_READY.data.reason` 复用 notReadyReason；
- 为 CTX_NOT_READY、CTX_LOST_DURING_EXEC、USER_ACTIVE、TARGET/CONVERSATION_NOT_FOUND、ELEMENT_UNRESOLVED、ACCOUNT_MISMATCH 写手侧构造与脑侧处置测试。

### 6. 当前登录账号的身份确证

登录态为 `in` 不能证明 Chrome 仍登录着脑所绑定的同一个账号。M2 必须在契约中增加平台无关、只用于相等比较的 opaque 身份指纹；指纹不得暴露平台 userId，脑不得解析其内容。

用户首次绑定时脑保存该指纹，之后每条 intrusive/effectful 命令都在 context 携带 expectedPrincipalFingerprint。手必须在第一次驱动页面前复读当前身份并比较，返回数据或进入不可逆动作前再次复核；不一致回机器可读的 `ACCOUNT_MISMATCH`（名称以契约冻结结果为准，sideEffect=none，manualOnly），不得执行或交付跨账号数据。SW 失忆不影响期望值下发，但身份状态须区分三态：

- 已绑定但因 pageAbsent/contentScriptDead 暂不可观测：保留绑定，只允许 probe 和 `nav.ensureSurface` 这个恢复例外，不允许读会话或发送；
- 新 hand session/boot 或身份健康过期：第一次驱动命令前必须 fresh probe，一致后才恢复已验证状态；
- 观察到明确 fingerprint mismatch 或 logout→login：绑定立即失效，只允许 probe，必须真人重新确认。

账号一致性必须是每条命令的运行时门禁，不能只靠最终人眼验收。

## 四、实施批次

### 批次 0：真机侦察与事实档案

使用当前已登录的真实智联 Chrome，验证并记录：

- 实际域名、页面路由、登录态特征和 content script 注入边界；
- canonical 标签页的可判定条件；
- 会话列表接口的字段、分页、排序、未读与摘要语义，以及隔离世界是否需要 MAIN-world bridge；
- 通过 conversationRef 导航与真人点击是否同样产生已读；
- 消息方向、文本/图片/语音/文件/系统消息的 DOM 形态；
- 卡片身份、状态和状态跃迁是否在会话尾产生系统提示；M2 只观察既有历史样本、真人在页面上手动发出的卡片和候选人自然产生的操作，不得为造样本提前实现 `chat.send*` 产品原语；
- 当前招聘方登录身份的稳定来源：跨刷新/重连是否稳定、切换账号是否必变、取不到时如何机器失败；不得把 Cookie/token 或明文平台账号 ID 写入契约和仓库；
- 稳定的 platformUserRef 来源，明确不锚 resumeNumber；
- 50/500 条快照与列表分页的真实时长和载荷体积。

产物是本仓库内的智联实测实现注记和脱敏 fixture。没有真机证据的 selector/API 仍标“未验证”，不得进入产品判断。

### 批次 1：M2 类型、账号与派发接缝

先不写业务 selector，闭合所有基础接缝：

- 落实第三节的契约与 codegen 门禁；
- 建本地智联账号记录，由脑生成稳定 `accountRef`，并把第三节定义的 opaque 登录身份指纹显式绑定到在线手；不把平台 userId 直接当脑内 accountRef；
- 派发入口改为结构化命令请求，完整持久化 `{platform, accountRef, expectedPrincipalFingerprint}`，重连重发和重派不得丢 context；
- intrusive/effectful 串行域改为 accountRef，并在中心派发器增加“域内已有非终局驱动命令”的原子闸，不能只依赖 actor 自觉串行；
- 增加逻辑派发链等待接缝：保存 replacement/lineage，覆盖 rejected、expired、void、重派新 msgId、重连收编和重派封顶；每条物理命令的终局都必须先持久化，但逻辑等待者只在整条 replacement chain 最终收束时唤醒，不能因中间命令 void 提前返回，也不能只等待原始 msgId 的单条 result；脑重启后 readonly/intrusive 由新巡检自然重算；
- 手端补真正的 FIFO、队深 16、QUEUE_FULL、inFlight、execBudget、deadline 双查和 generated args 校验；
- 脑在 welcome 下发 sensors 参数，手使用下发值而非内置业务策略常量；hello 用 feature 分别协商 `progress/1`、`lease/1`、`cancel/1`，原语继续以 capability@ver 门控；
- Hub 接入 `[S]` 的 event、progress、ping.contexts 与 ping.sensors；ping 只运缓存现货，progress 同样刷新 lastSeen，IM ready 但 sensors 持续 null 时进入能力级告警。
- 在任何 readList/readThread 竖切前，把脑侧 WebSocket 读上限显式设为协议 maxMsgBytes，手侧发送前按完整 envelope 的 UTF-8 字节数检查；冻结超限时返回小型 PROTO_MSG_TOO_LARGE 结果还是关闭连接的行为，并覆盖 `limit-1` / `limit+1` 双端测试，不能依赖库默认约 32KB 上限。

验收门槛：debug 三原语回归不退化；context 在首次发送、重连重发、重派和账本查询中完全一致；同账号跨手不能并发两条驱动命令。

### 批次 1B：长命令与大载荷基础设施

本批必须在 `chat.readList` / `chat.readThread` 之前完成，不能只停留在门禁文档：

- progress：逐页/逐滚动批上报，刷新执行活性但 stage 不参与程序分支；
- 租约：冻结起始锚点、progress 续租条件、gap 超时动作与绝对 deadline 的关系，并覆盖脑/手重启和迟到 progress；
- cancel：覆盖 queued、executing、已过取消安全点三态，ack/ref 关联明确，和 result 竞态时 result 赢；
- feature：`progress/1`、`lease/1`、`cancel/1` 均独立门控，旧手不宣告就不得启用；
- blob 分叉：若批次 0 证明快照会触发大载荷需求，同批交付 HTTP endpoint、会话 token、上传/取回、内容哈希校验、大小限制、失败语义、TTL/清理与 `blob/1` 能力门禁；若不交付，必须先把经过证明的分页/分块方案写进正式契约并修改推迟条款。

验收门槛：长命令在 progress 丢失、cancel/result 赛跑、连接重建和绝对 deadline 到期时均有唯一状态推进；大载荷要么完整可取回并校验，要么在执行前响亮拒绝，绝不静默截断。

### 批次 2：`probe.platform` 竖切

- 基于真机确认后的最小 host allowlist 增加 content script 与 SW 页面桥；
- base 统一注册 Chrome/DOM 监听，program 只提供纯实现模块；
- 建 canonical 标签页协调器；
- `probe.platform` 稳定返回 pageKind、contentScriptOk、loginState、surface；
- 同时返回第三节冻结的 opaque 登录身份指纹，指纹变化立即让账号绑定失效；
- UI 展示智联账号、绑定手、页面/登录/content script 健康；人工派发仍走正式 dispatcher。

通过标准：不驱动页面、不读取或记录凭据；页面不存在、未登录、脚本失活和页面正常四种状态都能机器区分。

### 批次 3：`nav.ensureSurface` 竖切

- 复用正确账号的现有标签，必要时创建并导航至 IM；
- 等待 SPA 和 content script 就绪，绝不自动登录；
- 多标签只允许 canonical 执行驱动命令，tabId/windowId 只留在手侧证据和日志。

通过标准：复用、创建、刷新、用户关闭、登录失效和多标签切换均有确定结果；重复执行不产生可叠加平台副作用。

### 批次 4：`chat.readList` 竖切

- 真实验证后的页面 API 为主路径，DOM 分页为兜底；
- 实现 8 天截止、maxSessions、complete、稳定身份、摘要和未读“可见才算 + 两次一致”；
- 长读逐页 progress，不在原语内部自主重试；
- 列表结果落成轻量会话索引并在 UI 展示。

M2 没有候选人/职位来源，不能把近 8 天所有陌生会话都自动打开并清已读。本批建立 Conversation/ListIndex/TrackedIntent；初期只允许在 UI 明确选定少量 tracked 会话，选择动作创建正式收编意图，不是测试分支。未来由系统自己成功发出招呼建立的会话自动 tracked。

通过标准：真实页面与返回快照抽样一致；重复读取不产生重复索引；API 失败时 DOM 兜底响亮可观测；超限或不完整时 `complete=false`，不能伪装全量。

### 批次 5：`chat.readThread` 与同步账本

先完成纯 Go 对齐算法和表驱动测试，再接真实 DOM：

- 正序提取有界消息快照，规范化内容并计算 contentHash；
- 支持 anchorTail、deep、reachedTop、anchorMatched；
- 卡片 identity hash 与 cardState 分离；
- 正确标记打开会话产生的一次性已读效果；
- 在批次 1 的 Account、批次 4 的 Conversation/ListIndex/TrackedIntent 基础上，新建 Message 和必要的 PatrolRound/Audit 表；正式键全部带 platform/accountRef 维度；
- message 同时记录 `origin{self|external}` 与 firstSeenRound；M2 观察到的真人手发 out 标 external，未来 `[X]` 经系统意图成功发出的消息才标 self；
- 单事务完成最大重叠、卡片状态更新、卡片跃迁追加事实 outbox、新消息 append 和会话尾更新；跃迁事实的正式键包含 platform/accountRef/conversationRef/messageSeq 及 from/to，并记录 roundId/contentHash/cardType/createdAt；
- 卡片跃迁 outbox 跨脑重启保留，下游只能先列出 pending、再显式幂等 acknowledge；确认只写确认时间而不删除追加事实，读取不得隐式消费；
- 首次存量会话整体收编并设置 adoptedBoundarySeq，边界前历史只作语境，不触发业务事件；
- 零重叠自动深读，仍零重叠则收编并审计，不静默吞。
- 列表摘要脏检测比较 direction + kind + 由账本末条派生的同规则规范化/截断 preview；禁止把完整 contentHash 与 textPreview 直接比较。

算法与存储测试至少覆盖：重复快照、连续相同文本、窗口切边、迟到快照、零重叠、事务回滚、卡片 pending→accepted/rejected 只入账一次、重启后 pending 仍可读、ack 幂等且不删除事实、事实写入失败与 Message.CardState 整单回滚、首次收编不误报历史。

### 批次 6：账号 actor、传感与操作 UI

脑侧账号 actor 是唯一业务节奏源，顺序程序固定为：

`按需 probe → readList → 脏检测 → 逐个 tracked 脏会话 readThread → 对齐入账`

probe 在首次绑定、hand session/boot 变化或身份健康过期后必须执行；同一已验证 session 内可复用新鲜结果，不做每轮固定 probe。

同时完成：

- 每天 8:00 后由真人点“今日开启巡检”，最晚运行至 24:00，次日必须重新开启；enabledDate、enabledAt、stoppedAt、pausedReason 持久化到 SQLite，同日脑重启自动恢复 actor，午夜后旧开启状态失效；
- 手离线时当前 tick 跳过，不在手侧或离线队列囤业务命令；
- CTX_NOT_READY 时惰性派 `nav.ensureSurface`，不做每轮固定前导；它是 ready=false 门禁的唯一 intrusive 自愈例外，仅 pageAbsent/contentScriptDead 且 actor 已开启时允许，同轮至多一次；loginRequired 不自愈，只暂停转人工；
- 连续三轮 ensure 后页面又被用户关闭，由脑侧 actor 计数并暂停账号，不把“轮”的概念塞进原语；
- unreadBadge、pageNavigated、loginStateChanged、manualInteraction 四类 QoS0 事件；
- content script 的稳定传感值只缓存于 SW 内存，ping 只运现货，心跳到点禁止反向采 DOM；
- 未开启时事件只记脏；unread 增大只拉前；减小/清零永不取消巡检；
- 25 秒合并窗、距上一轮至少 60 秒；manualInteraction 打开/续 45 秒静默窗，在途命令不撤销；
- base 在内存标记命令自身触发的导航窗口：pageNavigated 仍照常上报，只有 isTrusted 的真实用户输入/导航才能产生 manualInteraction，避免命令给自己续静默窗；
- UI 提供账号绑定、今日开启/停止、立即暂停、页面与传感健康、上/下轮时间、当前阶段、静默剩余、tracked 会话、消息新增投影和审计查看。

“立即执行一轮”只能调用同一个 actor 生产入口，并继续受开启、静默、能力和串行闸约束，不能成为测试旁路。

“停止”或“立即暂停”默认只阻止新派发，在途命令自然结束；只有第三节正式激活 cancel 后，才允许经同一协议发送尽力而为取消，不能为 UI 另造取消旁路。

### 批次 7：真机故障、长跑与验收报告

真机按由浅到深的顺序验收：

1. 当前 Chrome profile、智联账号与脑内绑定一致；
2. probe、ensure、readList、readThread 逐条人工核对；
3. 一个 tracked 存量会话首次收编不触发旧事件；
4. 人工发送唯一文本或等待真实回复，下一轮只投影一次新增；
5. 手动读清未读后，列表摘要差仍能判脏；
6. 用户在任意智联页操作时静默窗生效，脑不抢页面；
7. 重载插件、杀 SW、刷新/关闭页面、断网、同日重启脑后，tracked 会话在确定性故障模型内不产生重复投影，actor 按持久化的今日开启状态恢复；
8. 多标签、页面被驱赶、登录失效、content script 失活均按规格暂停或自愈；
9. 事件全部丢失时，原定巡检仍能发现变化；事件存在时只改善延迟；
10. 逐项验证 C 卷的卡片状态、列表语义、重复文本歧义、参数和 platformUserRef 五类真机风险。卡片接受/拒绝依赖候选人侧动作：只有存在足够历史样本或找到真人配合时才能声称销案；条件不具备时必须登记为未销风险，写明影响、止损和再次验证的触发条件。

每个用例保留四层证据：命令身份、cmd/ack/result 生命周期、同步前后账本差分、必要的脱敏真机截图或文字摘要。最终新增 `docs/里程碑2-验收报告.md`，逐条给出自动测试和真实 Chrome 证据。

## 五、M2 完成定义

以下条件缺一不可：

- 四条 `[S]` 原语全部从账号 actor 经正式 dispatcher 到真实 Chrome 执行；
- 契约、generated 类型与运行时校验一致，codegen check 通过；
- 对 tracked 会话，重复快照、迟到快照、断线、插件失忆、同日脑重启和首次收编在协议确定性故障模型内不产生重复投影；已知同文窗口边界歧义有审计、深读、长跑数据和明确残余风险，不作不可证明的无条件零漏承诺；
- 事件全丢不影响正确性，用户操作优先于自动化；
- 真实智联页面事实均有本仓库内证据，未验证旧资料未进入产品判断；
- 全套 Go/race/Windows 交叉编译、TS typecheck/build、Node E2E 和真实 Chrome 验收通过；
- 形成 M2 验收报告，未销风险有明确影响、止损和后续触发条件；
- 没有第二平台代码、云端对接、AI 决策或真实自动发送混入本里程碑。

## 六、M2 之后的顺序

真实账号许可已具备，但发送能力必须在安全轨道完备后再进入产品：

1. `[X0]`：query/report、journal/outbox、guards、evidence 强制、验证闭环和 blob（若 M2 未提前触发）。
2. `[X1]`：先做既有 tracked 会话的 `chat.sendMessage`；首轮限定一个明确会话、一个 intent、真人在场，用唯一测试文本验证“一个 intent 只产生一次外部消息”，并演练点击前断线、点击后失联、result 丢失和 SW 重启。
3. `[X2]`：再做 `chat.sendGreeting`，验证新会话建立、候选人绑定和招呼后置条件。
4. `[X3]`：再做邀面/换微信等卡片原语。
5. 最后接确定性沟通状态机；AI 只提供分类或文案建议，状态推进仍由确定性代码裁决。

任何 `[X]` 用例出现 `sideEffect=possible`、回读不一致或后置条件无法确认，都只进 suspect，不自动重发。老板允许真实测试不改变这条红线。
