# 完整沟通引擎：夜间验收报告

日期：2026-07-23

## 一、结论

本轮达到获批的夜间出口：给定合法、平台无关的入站消息账本，纯脑侧可以按以下唯一主链确定地归约出下一建议、动作计划、明确无动作或转人工：

`message ledger -> normalized business event -> deterministic v4 state/reducer -> optional AI advice -> stable action plan / no action`

AI 不是必经层。状态机先按《沟通逻辑规格-v4》选择业务分支；只有普通对话、服务回复、沉默催问和拒面回执等规格明确要求生成或分类的分支才开放对应 AI 建议。固定话术、卡片事实、时钟、终态、未知事件和无动作分支不会为了统一流程而调用 AI。

本轮完成的是**可重放的 v4 纯决策层**，不是完整生产无人值守沟通系统。新聚合状态、时刻表和动作计划尚未接入生产巡检、数据库持久化、provider 调用或 WAL 派发；因此本轮没有以新引擎向真实候选人发送消息。

时钟语义已按 v4 穷尽定义：招呼、对话回复、挽留、收场属于正文；卡片、冷催、跟催、回执不是正文。所有已发动作都会滑普通时钟，只有正文滑七天兜底时钟。自动文本缺少脑侧动作语义时不按文本外形猜测，而是把正文时钟置为不确定并停止自动调度。

## 四、新增事实与保守边界

1. 智联 `customType=105` 只有同时满足“发送者是当前会话候选人”和内层 `originType` 为数字 `2` 或字符串 `"2"` 才提升为待处理换微信请求；招聘方、第三方、缺字段及其他值继续作为保守 system 形态。
2. 未经验证的状态接口不再覆盖 105 的请求语义。读取、发送基线和最终 evaluator 使用同一收窄条件；未知类型普通日志只保留去重后的类型码，不含正文或身份。
3. 当前固定话术包可无损解析并执行四个已确认映射：拒绝挽留、冷催2、换微信成功回执、约面接受确认。旧 `actions` 字段只校验形状后丢弃，不获得行为授权。
4. 当前配置没有独立拒绝收场话术，`meetingInvitePending` 也不足以提供三档跟催文案；这些分支转人工，不拆数组或猜造文案。
5. 177/259/313 仍须经过真机事实门后才能提升；343 继续保守。

以上事实记录不含候选人正文、平台身份或其他 PII。

## 五、独立审查与修复

按计划只执行了一轮限定范围独立审查。审查发现并关闭两个当前阻断链：

1. 原实现把冷催、跟催和回执误算为正文，可能让第六天催问把第七天兜底继续延期。现已集中唯一正文分类，并覆盖“第六天催1、第七天仍按原正文兜底”。
2. 同一拒绝轮在挽留正证后重放，原实现可能按已发标记升级成收场。现已按 `messageSeq + turnID` 冻结本轮阶段与动作键；同轮只恢复原键，只有更高消息序号的新拒绝轮才能升级。

两项修复后只做对应 diff 的定向复核，均通过；未重开全量审查，也未扩张其他机制。
