> 当前可达场景 / 收益与成本**。获批前不动实现。本文只是底稿，不构成任何授权。
>
> 起因：批 D（`b54aee7`）落地后甲方问「后台的某个客户，是绑一个平台，还是两个都能用」；

## 〇、三个模型与现状

| 模型 | 客户记录与平台的关系 | 职位与提示词 | 一台机器 |
|---|---|---|---|
| 1 客户绑平台 | 一条客户记录 = 一个平台上的一个账号 | 各客户记录自己配 | 一个平台 |
| 2 职位级归属 | 一条客户记录两平台都能用，职位表带平台列 | 按职位分平台 | 两平台各跑一份计划 |
| 3 账号级选择（批 D 现状） | 客户记录不绑平台，哪个平台跑取决于开始时登的是谁 | 两平台共用 | 一次一个平台 |

**现状是模型 3**：后台客户记录与职位都没有平台字段；客户端一切按（平台，登录指纹）建账本根；
两平台同时登录时脑不猜、界面让人选。审查（批 D 合并说明）确认了它对存量客户的可达代价：
只跑智联的老客户若同一 Chrome 也登着 BOSS，每次开始都要先选平台，每日自动开始当日失败且不自愈。

**现网运营形态已经是模型 1 的等式**：一个真实客户的多个平台账号在后台是多条客户记录、多台
机器（杨小七 5 账号 = 5 条客户记录 = 5 台机器）。BOSS 只是多一种账号，不改变这个等式。

## 一、拟议（五条）

### 1.1 后台客户记录加平台列，随客户快照下发

**旧约束。** 旧后台 `customers` 表无平台概念；`app/api/client_auth.py` 的 `_customer_block`
向 bind 与 job-config(s) 响应输出 `customerId/customerName/status/subscriptionEndsAt` 四项。
AGENTS.md「旧后台授权与职位配置面」把 job-config(s) 定位为「授权入口与职位配置面」，客户级
字段先例有客户名（2026-08 客户名刷新）与 `smartAi/subSmartAi`（2026-08-24）。

**拟议文本。**
- `customers` 表新增 `platform VARCHAR(32) NOT NULL DEFAULT 'zhilian'`，取值当前只有
  `zhilian` / `boss`（与脑手契约 `context.platform` 同一自由串，不做枚举列，未来平台是加法）。
- `_customer_block` 增输出 `"platform"`；bind 与 job-config(s) 三个响应同形带出。
- 管理前台客户表单加「平台」下拉，默认智联；存量客户由默认值覆盖，零迁移动作。
- AGENTS.md「旧后台授权与职位配置面」条款增一句：**客户记录的平台归属（`platform`）随客户
  快照下发，是配置面字段而非控制指令；客户端只用它决定「开始」探测并绑定哪个平台的账号。**

**当前可达场景。** BOSS 首客交付时，后台必须有一条客户记录说明「这条授权是给 BOSS 的」，
否则客户端无从区分；不加字段就只能靠模型 3 的登录探测，而那条路对存量客户有上面写的
可达代价。

**收益与成本。** 收益：平台归属有唯一事实来源，工作状态/日报/周报/职位状态上报不需要任何
改动就天然不混（一条客户记录一个平台）。成本：后台一列一处装配一处表单，部署顺序后台先行
（客户端缺席即默认智联，见 1.4，顺序错了也不坏）。

### 1.2 客户端以客户平台为「指定平台」，人工开始与自动开始同一入口

**旧约束。** 批 D 2.1：「开始」对手声明的每个平台各探一次，恰一在线用它，多于一个由 UI
显式选择；每日自动开始一律传空平台、遇歧义当日失败。`productapp.Controller.Start` 的
`platform` 参数由 apphttp 请求体传入。

**拟议文本。**
- `jobconfig.Customer` 增 `Platform` 字段，随 bind 与 `refreshCustomerSnapshot` 落
  `legacy-job-config.json`（与客户名同一通道、同一失效方向：拿不到就不更新）。
- `Controller.Start` 不再从请求体取平台，改为读本地客户快照的 `Platform` 作为指定平台传给
  `ResolveCurrent(ctx, platform)`（批 D 已有的「指定平台只探它」分支）。人工点击与每日自动
  开始因此走完全相同的路径，符合「每日自动开始复用与人工点击完全相同的入口与全部前置闸」。
- 指定平台未登录 → 既有 `ErrLoginRequired`（文案按平台分：智联/BOSS，顺带修掉审查记录的
  「文案钉死智联」）；不偷换成另一个在线平台。

**当前可达场景。** 同 1.1 第一条；另：存量智联客户同机登 BOSS 的场景在本条下完全消失——
指定平台是智联，BOSS 登不登都不问。

**收益与成本。** 收益：平局问题整个消掉，前一份底稿里的「平局规则」提案作废。成本：客户端
十来行加用例；`Start` 签名回到三参数（apphttp / autostart 两个接口与桩同批改回）。

### 1.3 砍掉批 D 为「让人选」配的界面与参数

**旧约束。** 批 D `e3466f2`（UI 选择控件、`PlatformChoiceRequired`、localStorage 记忆）与
`705602a` 中 apphttp 请求体 `platform` 字段、409 带 `platforms` 候选列表、
`productapp.PlatformAmbiguousError`。

**拟议文本（二选一，交甲方）。**
- **甲（推荐，砍概念）**：回退 `e3466f2` 全部与 apphttp 的 `platform` 请求字段；解析器删去
  「各探一次 + 歧义」分支，只保留「指定平台只探它」——`PlatformAmbiguousError`、
  `HandPlatforms` 的解析用途一并退役（`HandPlatforms` 留给诊断面）。
- **乙（保留后备）**：只回退 UI 与请求字段，解析器保留多探与歧义分支作为「本地快照缺平台」
  时的后备，歧义时报清楚的失败、不猜。

**当前可达场景。** 1.2 落地后，生产上没有任何路径会让脑报歧义（指定平台恒有值，见 1.4），
这些代码要么是死代码（甲），要么是只在开发机假后台不发字段时才活的后备（乙）。

**收益与成本。** 甲：少 ~200 行与 12 条用例，界面回到批 D 前；代价是开发机切平台只能改假后台
或本地快照文件。乙：多留一条永远不该走到的分支。大原则第 4 条倾向甲。

### 1.4 本地快照缺平台字段时默认智联

**旧约束。** 无（字段是新的）。批 D 已有同性质先例：手未声明 `platforms` 时
`fallbackPlatforms = ["zhilian"]`。

**拟议文本。** 客户端本地快照无 `platform` 或为空时按 `zhilian` 处理，与 `fallbackPlatforms`
同源、同注释（"本产品此前只随智联交付，缺席即旧世界"）。这是部署默认值，不是业务判断。

**当前可达场景。** 客户端先于后台升级、或后台字段尚未部署：所有存量客户必须逐字保持今日行为。

**收益与成本。** 收益：部署顺序错了也不坏，不需要"先后台后客户端"的硬约束（仍建议后台先行）。
成本：脑里多一处 `"zhilian"` 字面量；它与 `fallbackPlatforms` 是同一个事实，建议共用一个常量。

### 1.5 底稿 2.1 修订与一句事实同步

- 《BOSS第一刀裁决底稿》2.1「职位配置对两平台共用（同一客户、同一批职位）」与「多于一个则
  产品 UI 要求用户显式选择」两句作废，改为「一条客户记录一个平台；平台由后台客户快照下发」。
- 「不做职位级平台归属（模型 2）」维持：它是模型 1 之上的加法，真有客户要一台机器同跑两平台再立案。

## 二、不在本包、但要知情的

| 项 | 说明 |
|---|---|
| 一个生意两平台 = 两条客户记录 + 两台机器 | 与今天每个智联账号一台机器相同，不是新负担；一台机器只绑一个 licenseToken 是既有事实 |
| 改平台是运维动作 | 后台把某客户从智联改成 BOSS，客户端下次开始即切平台；改之前应先结束该机的运行。是否加「运行中禁改」的后台校验，建议不加（大原则第 4 条），写进运维手册 |
| BOSS 客户的完整流程 | 当日职位计划的职位在线闸要 BOSS 版 `job.readPublishedList`（BOSS 职位管理页零考古），属第二刀；在那之前 BOSS 客户只能跑「仅回复」，闸的方向是不开工 |
| 上报面 | 工作状态、日报、周报、职位状态、聊天记录、类别审计、平台通知七路上报零改动；聊天记录上报本就带平台 |
| 管理前台 | 客户表单加下拉是 xq-resume-admin 的改动，与后台列同批部署 |
