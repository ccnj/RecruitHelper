## 一、身份

### 候选人 id：在 DOM 上

会话列表项 `.geek-item` 同时带两份：`data-id="{uid}-{friendSource}"` 与
`id="_{uid}-{friendSource}"`。这是**候选人的服务端 id**，稳定可用。

### 消息 id：Snowflake，而且不在 DOM 上

```
mid = ((unix_ms - 1695139200000) << 12) | 低12位
```

epoch `1695139200000` = 2023-09-20 00:00 北京时间。**22 个会话的 `lastMsgId` 全部吻合**，
解出的时刻与消息自带 `time` 差 0~20ms（更早样本偏差达数百 ms，因其 `lastTS` 被舍到整秒）。

低 12 位**不是**全局递增序列：观测值密集聚在 769~777，另见一个 8，像「机器位 + 序列」
的复合。**具体位宽未验，不要依赖。**

**mid 全局分配、按全站时间穿插，所以同一会话内相邻消息必然跳号**：
同一人 7ms 内连发差 2；另一会话相邻两条差 1；又一会话差 4093。
**「id 连不连续」不能用来证明历史没窟窿。**

可用的部分：mid 严格单调于服务端时间，且能**独立于 `time` 字段**解出服务端毫秒。

**`mid` 完全不在 DOM 上**：66 个 mid 与整页 `outerHTML` 比对，命中 0；
属性里的长数字全是 SVG 路径坐标。消息行只有 `data-v-*`（Vue scoped CSS 标记）。
这是走 MAIN world 而非 DOM 的直接原因。

### `cmid`：客户端生成、服务端回显

双向都有。格式因客户端而异——我方 web 端生成雪花状值，对端生成 unix 毫秒。

**若发送接口允许指定 `cmid`，它就是天然的幂等键载体**，发后核验可按 id 对而非内容匹配。
**「能否自定义」「服务端是否据此去重」均未验证。**

## 二、消息形状

MAIN world 读到的是 Vue 归一化后的对象，**与 HTTP 线上形态不同**，适配器认前者：

| | MAIN world（`list$` 元素） | HTTP 线上（`historyMsg`） |
|---|---|---|
| 发送方 | 扁平 `fromId` / `fromName` / `fromAvatar` | `from: { uid, name, avatar, … }` 对象 |
| 类型 | `type: "text"` 等字符串 | `type: 1/3/4` 数字 |
| 其余 | `mid`/`cmid`/`time`/`status`/`bodyType`/`messageType`/`bizType`/`body`/`isSelf` 大体一致 | |

按形状搜索 Vue 树时判据要**兼容两层**（`'mid' in e && 'body' in e && ('from' in e || 'fromId' in e)`）
——只认线上形状会搜不到，这个坑已实际踩过一次。

### 方向判据（两个坑）

**只能用 `from.uid === 我方uid`（MAIN world 层是 `fromId`）。**

- **`type` 不是方向**：`type=3/body.type=1` 在两个方向都出现（IN 18 条、OUT 3 条）；`type=1` 同样两向都有
- **`flag` 也不是方向**：`65537` 与 `1` 都是两向都有

照 `type` 写方向判据会静默错一半。

### 已见枚举（真机已见，未见不得实现）

`bizType`：

| 值 | 含义 |
|---|---|
| `101` | 普通聊天文本（双向） |
| `14` | 对方请求发送附件简历（dialog，带 拒绝/同意） |
| `21050004` | 牛人简历卡 |
| `21050060` / `21050070` / `21120018` | 平台提示（hyperLink） |
| `21050177` | 候选人发简历时的伴随文本 |
| `21050220` | 带「了解详情」按钮的 dialog |
| `21130009` | **面试邀请卡**（写） |
| `21130010` / `21050071` | 系统行，`body.type=4`，内容为空 |
| *缺席* | 早期普通文本没有 `bizType` 字段 |

`body.type`：`1` 文本 / `4` 系统 / `7` dialog / `9` 简历卡 / `12` hyperLink / `14` 面试卡

`status`：`1` 已送达未读 / `2` 已读 / `3` 已撤回
（邀面卡发出时 `1`，候选人读后变 `2`，实测跃迁；撤回行 pushText 为「XX撤回了一条消息」）

`uncount`：`0` 计入未读 / `1` 不计入（平台系统消息与简历卡）

## 三、完整性判据（有一处未验证，是决策的代价）

MAIN world 层的终止标志是 `message-list` 组件的 **`isToTop`**，DOM 上对应
`.chat-message-list.is-to-top`。

**但 `isToTop` 的翻转没有观测过。** 测试账号里最长的会话只有 8 条，而页大小是 20，
所以 `isToTop` 从一开始就是 `true`，从未见过 `false → true` 那一跃。
要验证需要一个 >20 条的会话，账号里没有，也不该为了造一个去给真人连发二十条。

**这是取数通道决策的一笔真实代价**：被降级的那个判据（附录 A 的 `c=100` 法）
是验证过的，接替它的这个不是。上生产前必须补验。

## 四、面试是独立于聊天流的实体（结构上最重要的一条）

写操作实测：发出一张线下面试邀请卡，随后用「修改」改期。

- 聊天流里只有**一张** `body.type=14` 的卡：
  `body.interview = { condition: 1, text: "发送了面试邀请", url }`
- **卡里不含时间与地点**，只有一个 url
- **改期不产生任何消息**：详情从 `09:00-11:00` 改为 `14:00-16:00` 成功，
  但会话流条数不变、卡的 `mid` 与 `condition` 均不变
- 面试有独立 API 面 `/wapi/zpinterview/*` 与独立 `encryptInterviewId`

**因此「消息账本 = 全部事实」这个假设在 BOSS 上不成立。** 智联那边邀面卡就是消息、
状态跃迁落在消息上；BOSS 这边不是。凡「已发卡不再邀面」这类判据，
在 BOSS 上不能只看消息流。

### 可见后置状态（安全内核前置）

| 层 | 定位 | 取值 |
|---|---|---|
| 会话工具栏 | 按钮文案 | 发卡前「约面试」→ 发卡后「查看面试」 |
| 面试详情面板 | `.interview-detail-dialog-ui .interview-detail-header .title` | 「等待对方接受」 |
| 卡片消息体 | `body.interview.condition` | `1` ↔「等待对方接受」 |

三者都是平台明确呈现的可见状态，`.title` 是可见文本、脆性低。

**尚缺：候选人真正接受/拒绝后 `condition` 与 `.title` 变成什么。** 不受我方控制，
需等真实候选人动作。本轮候选人做的是**反提议**（要求改时段），卡片停在 `condition:1`。

**成功弹窗不构成成功**：改期那次弹出「面试邀请已发出」，但 8 秒后会话流零新增
（详情里的时间确实变了）。既有裁决「命令返回值与『点了按钮』不构成成功」当场应验。

## 五、邀面表单（写）

模态框根类 `interview-invite-dialog-ui`。字段：

- **面试类型** radio：`线下面试` / `线上面试` ← 对应我方契约的 `onsite` / `wechatVideo`
- 招聘职位（下拉，隐藏 input 存 jobId）
- 面试地址（`readonly`，预填）
- 备注事项（textarea，≤140 字）
- **面试时间**：日期 + 时间，两者皆 `readonly`，只能点开选
- 联系人（下拉，带手机号）

**时间有两种模式**（页签 `.time-title` 内 `.selected`）：

| 模式 | 形态 | 粒度 | 范围 |
|---|---|---|---|
| 精准时间 | 单个时刻 | 小时 × 5 分钟 | 08–20 时 |
| 宽松时间 | **区间** | 30 分钟 | 开始 08:00–20:00，结束 09:00–21:00 |

宽松时间的结束列在选定开始后**重新过滤**，最早为开始 + 1 小时。
我方契约的「面试起止时间」在 BOSS 上走**宽松时间**可表达；精准时间只有起点。

其他实测行为：

- 日历只放开今天及以后
- 「修改」重开的是同一个表单，且**不预填**原时间
- 「修改」的二次确认原话：**「更新后会取消原有面试，并向牛人重新邀约」**——
  它是「撤销 + 重发」，不是原地编辑

**坑**：`input.radio-input` 的 `checked` 两个选项恒为 `false`，
选中状态只在 label 的 `.radio-checked` 类上。按 `input.checked` 读面试类型会永远读错。

## 九、DOM 能读到什么（降级路径的边界）

正式取数走 MAIN world，但 DOM 仍是降级与交叉校验的来源：

| 选择器 | 含义 |
|---|---|
| `.geek-item[data-id="{uid}-{src}"]` | 会话列表项，候选人服务端 id |
| `.chat-message-list.is-to-top` | 历史到顶标志 |
| `.message-item` | 消息行 |
| `.item-myself` / `.item-friend` / `.item-system` | 方向 |
| `.status.status-read` | 已读回执 |
| `.message-card-wrap.blue` / `.boss-green` | 卡片及配色变体 |
| `.message-card-buttons > .card-btn` | 卡片按钮 |
| `.message-time > .time` | 时间，是「08-25 14:31」这种**文本，不是时间戳** |

**DOM 是数据层的真子集，会整条漏行**：实测数据层 11 条 / DOM 9 行，
漏的是 `bizType=21130010`、`21050071` 这类 `body.type=4` 的空内容系统行。
已读标记也不全：两条 OUT 消息同为 `status=2`，DOM 只在其中一条渲染「已读」。

## 十、IM 传输：MQTT over WebSocket

`wss://ws6.zhipin.com/chatws`，跑在 Worker 里（`geek_chat_sdk_worker_version`）。
localStorage 里的 `Sent:ws6.zhipin.com:443:/chatws:…` 是 Paho MQTT 客户端的存储格式。

**消息态不落盘**：`indexedDB.databases()` 为空；localStorage 46 个键中无任何 mid。
这是「消息只活在 JS 内存里」的原因，也是本地存储路不通的直接证据。

## 附录 A：HTTP 历史接口（推导来源，正式取数不用）

本节记录事实的取得方式，供日后交叉验证与排障；**正式实现不走这条**
（理由见取数通道决策文档）。

```
GET /wapi/zpchat/boss/historyMsg?src={friendSource}&gid={候选人uid}&maxMsgId={游标}&c={条数}&page=1
→ zpData: { hasMore, messages[], type, minMsgId }
```

真机验证（8 条历史的会话，`c=1` 逐页走完 vs `c=100` 一次拿全）：

| 事实 | 证据 |
|---|---|
| `maxMsgId` 是权威游标，`page` 参数被忽略 | 全程 `page=1`，8 页链式走完 |
| 游标**排他**，按 mid 降序 | 每页返回严格小于 `maxMsgId` 的记录 |
| 下一页游标 = 响应 `minMsgId` | 8 步吻合 |
| 两条路径**同集合、零重复、零遗漏** | 集合比对通过 |
| `hasMore` **不携带服务端额外知识** | 它等于「返回条数 == 请求条数」：拿到最老一条时仍为 `true`，再请求才空 |

**推论**：一次 `c=100` 返回不足 100 条即证明该会话全部历史到手。
页面自己用 `c=20`，我方不控制 `c`，故走 MAIN world 后这个证明失效，
完整性改押 `isToTop`（见第三节，未验证）。

## 附录 B：其他已见接口

- `GET /wapi/zpmsg/history/pull?type=0&lastId={mid}&secretId=…` —— 全账号增量拉取，
  `lastId` 就是 mid 做水位，形状正是巡检想要的；**但 `secretId` 铸不出来**
  （缺参时 `code:17 缺少必要参数`），多半来自 WS 握手。**线索，未打通。**
- `/wapi/zpinterview/boss/interview/info.json?geekId=&geekSource=` —— 面试详情面板的数据源，
  但直接 fetch 返回 `{}`，加 `X-Requested-With` 无变化，**取数条件未摸清**
