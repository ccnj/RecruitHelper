## 一、身份

### 候选人 id：在 DOM 上

会话列表项 `.geek-item` 同时带两份：`data-id="{uid}-{friendSource}"` 与
`id="_{uid}-{friendSource}"`。这是**候选人的服务端 id**，稳定可用。

### 消息 id：Snowflake，而且不在 DOM 上

```
mid = ((unix_ms - 1695139200000) << 12) | 低12位
```

epoch `1695139200000` = 2023-09-20 00:00 北京时间。**22 个会话的 `lastMsgId` 全部吻合**，
解出的时刻与消息自带 `time` 差 0~20ms（更早样本偏差达数百 ms，因其 `lastTS` 被舍到整秒）。

低 12 位**不是**全局递增序列：观测值密集聚在 769~777，另见一个 8，像「机器位 + 序列」
的复合。**具体位宽未验，不要依赖。**

**mid 全局分配、按全站时间穿插，所以同一会话内相邻消息必然跳号**：
同一人 7ms 内连发差 2；另一会话相邻两条差 1；又一会话差 4093。
**「id 连不连续」不能用来证明历史没窟窿。**

可用的部分：mid 严格单调于服务端时间，且能**独立于 `time` 字段**解出服务端毫秒。

**`mid` 完全不在 DOM 上**：66 个 mid 与整页 `outerHTML` 比对，命中 0；
属性里的长数字全是 SVG 路径坐标。消息行只有 `data-v-*`（Vue scoped CSS 标记）。
这是走 MAIN world 而非 DOM 的直接原因。

### `cmid`：客户端生成、服务端回显

双向都有。格式因客户端而异——我方 web 端生成雪花状值，对端生成 unix 毫秒。

**若发送接口允许指定 `cmid`，它就是天然的幂等键载体**，发后核验可按 id 对而非内容匹配。
**「能否自定义」「服务端是否据此去重」均未验证。**

## 二、消息形状

MAIN world 读到的是 Vue 归一化后的对象，**与 HTTP 线上形态不同**，适配器认前者：

| | MAIN world（`list$` 元素） | HTTP 线上（`historyMsg`） |
|---|---|---|
| 发送方 | 扁平 `fromId` / `fromName` / `fromAvatar` | `from: { uid, name, avatar, … }` 对象 |
| 类型 | `type: "text"` 等字符串 | `type: 1/3/4` 数字 |
| 其余 | `mid`/`cmid`/`time`/`status`/`bodyType`/`messageType`/`bizType`/`body`/`isSelf` 大体一致 | |

按形状搜索 Vue 树时判据要**兼容两层**（`'mid' in e && 'body' in e && ('from' in e || 'fromId' in e)`）
——只认线上形状会搜不到，这个坑已实际踩过一次。

### 方向判据（两个坑）

**只能用 `from.uid === 我方uid`（MAIN world 层是 `fromId`）。**

- **`type` 不是方向**：`type=3/body.type=1` 在两个方向都出现（IN 18 条、OUT 3 条）；`type=1` 同样两向都有
- **`flag` 也不是方向**：`65537` 与 `1` 都是两向都有

照 `type` 写方向判据会静默错一半。

### 已见枚举（真机已见，未见不得实现）

`bizType`：

| 值 | 含义 |
|---|---|
| `101` | 普通聊天文本（双向） |
| `14` | 对方请求发送附件简历（dialog，带 拒绝/同意） |
| `21050004` | 牛人简历卡(**2026-09-03 更正**:账本实证它也是会话开头那张「N月N日 沟通的职位-职位名」职位卡,入站;两种形态是否同一 bizType 待真机分辨。适配器一律投 system) |
| `21050060` / `21050070` / `21120018` | 平台提示（hyperLink） |
| `21050177` | 候选人发简历时的伴随文本 |
| `21050220` | 带「了解详情」按钮的 dialog |
| `21130009` | **面试邀请卡**（写） |
| `21130010` / `21050071` | 系统行，`body.type=4`，内容为空 |
| *缺席* | 早期普通文本没有 `bizType` 字段 |

`body.type`：`1` 文本 / `4` 系统 / `7` dialog / `9` 简历卡 / `12` hyperLink / `14` 面试卡

`status`：`1` 已送达未读 / `2` 已读 / `3` 已撤回
（邀面卡发出时 `1`，候选人读后变 `2`，实测跃迁；撤回行 pushText 为「XX撤回了一条消息」）

`uncount`：`0` 计入未读 / `1` 不计入（平台系统消息与简历卡）

## 三、完整性判据（有一处未验证，是决策的代价）

MAIN world 层的终止标志是 `message-list` 组件的 **`isToTop`**，DOM 上对应
`.chat-message-list.is-to-top`。

**但 `isToTop` 的翻转没有观测过。** 测试账号里最长的会话只有 8 条，而页大小是 20，
所以 `isToTop` 从一开始就是 `true`，从未见过 `false → true` 那一跃。
要验证需要一个 >20 条的会话，账号里没有，也不该为了造一个去给真人连发二十条。

**这是取数通道决策的一笔真实代价**：被降级的那个判据（附录 A 的 `c=100` 法）
是验证过的，接替它的这个不是。上生产前必须补验。

## 四、面试是独立于聊天流的实体（结构上最重要的一条）

写操作实测：发出一张线下面试邀请卡 → 用「修改」改期 → 候选人接受 → 人工取消。

### 生命周期由**三条独立消息**表达，每条一次跃迁

| 时刻 | `bizType` | `condition` | 方向 | `body.interview.text` |
|---|---|---|---|---|
| 19:24:40 | `21130009` | `1` | OUT | 发送了面试邀请 |
| 19:36:43 | `21130008` | `3` | IN | **接受了面试邀请** |
| 22:27:50 | `21130006` | `5` | OUT | 取消了面试 |

取消时另有一条 `21130011`/`body.type=1` 的 OUT 文本承载原因（「取消原因：已招到人员」）。

`body.interview.extend` 携带 **`{"interviewId":<数字>,"isVideo":0}`**——
这是消息与独立面试实体之间的**关联键**。

### `condition` 是快照，永不回写（关键）

第一张卡在**接受之后、取消之后**读取，`condition` **仍然是 `1`**。
三条消息各记各的跃迁，互不影响。

**推论：当前面试状态不能从消息流读出来。** 消息流只能给出「发出→接受→取消」的历史，
读不出「此刻是什么状态」——那必须读面试实体本身（详情面板 / 已约面列表）。

`condition` 已见值：`1` 待接受 / `3` 已接受 / `5` 已取消。
`2`、`4` 未见（推测为拒绝一类），按枚举面事实门**不得实现**。

### 卡里不含时间地点，改期不产生消息

- `body.interview` 只有 `condition`/`text`/`url`/`extend`，**没有时间与地点**
- **改期不产生任何消息**：详情从 `09:00-11:00` 改为 `14:00-16:00` 成功，
  但 19:26 到 19:36:35 之间会话流零新增，而改期就发生在这中间；
  第一张卡的 `mid` 与 `condition` 也都不变
- **「对方能否无声感知到改期」未验证**：实测序列是「我方发文字说明改到下午」→
  25 秒后对方回「好的👌」→ 8 秒后接受。无法区分他是看到卡片变了还是看到了我方的文字。

**因此「消息账本 = 全部事实」这个假设在 BOSS 上不成立。** 智联那边邀面卡就是消息、
状态跃迁落在消息上；BOSS 这边不是。凡「已发卡不再邀面」这类判据，
在 BOSS 上不能只看消息流。

### 可见后置状态（安全内核前置）

| 层 | 定位 | 取值 |
|---|---|---|
| 会话工具栏 | 按钮文案 | 发卡前「约面试」→ 发卡后「查看面试」 |
| 面试详情面板 | `.interview-detail-dialog-ui .interview-detail-header .title` | 「等待对方接受」 |
| 会话级 | `relationType` | 已约面后观测到 `9` |
| 卡片消息体 | `body.interview.condition` | `1` ↔「等待对方接受」（快照） |

三者都是平台明确呈现的可见状态，`.title` 是可见文本、脆性低。
**尚缺：接受/取消后详情面板 `.title` 的文案**（本轮读到时面板已随取消关闭）。

**成功弹窗不构成成功**：改期那次弹出「面试邀请已发出」，但 8 秒后会话流零新增
（详情里的时间确实变了）。既有裁决「命令返回值与『点了按钮』不构成成功」当场应验。

## 五、邀面表单（写）

模态框根类 `interview-invite-dialog-ui`。字段：

- **面试类型** radio：`线下面试` / `线上面试` ← 对应我方契约的 `onsite` / `wechatVideo`
- 招聘职位（下拉，隐藏 input 存 jobId）
- 面试地址（`readonly`，预填）
- 备注事项（textarea，≤140 字）
- **面试时间**：日期 + 时间，两者皆 `readonly`，只能点开选
- 联系人（下拉，带手机号）

**时间有两种模式**（页签 `.time-title` 内 `.selected`）：

| 模式 | 形态 | 粒度 | 范围 |
|---|---|---|---|
| 精准时间 | 单个时刻 | 小时 × 5 分钟 | 08–20 时 |
| 宽松时间 | **区间** | 30 分钟 | 开始 08:00–20:00，结束 09:00–21:00 |

宽松时间的结束列在选定开始后**重新过滤**，最早为开始 + 1 小时。
我方契约的「面试起止时间」在 BOSS 上走**宽松时间**可表达；精准时间只有起点。

其他实测行为：

- 日历只放开今天及以后
- 「修改」重开的是同一个表单，且**不预填**原时间
- 「修改」的二次确认原话：**「更新后会取消原有面试，并向牛人重新邀约」**——
  它是「撤销 + 重发」，不是原地编辑

**坑**：`input.radio-input` 的 `checked` 两个选项恒为 `false`，
选中状态只在 label 的 `.radio-checked` 类上。按 `input.checked` 读面试类型会永远读错。

## 六、换微信（写，已跑通）

点「换微信」的完整链路：

1. 内联二次确认 `.exchange-tooltip`（**不是模态框**，锚在工具栏按钮上），
   按钮 `span.boss-btn-primary`（确定）/ `span.boss-btn-outline`（取消）
2. 确定后弹模态框 `.add-wx-wrap`（外层 `.dialog-wrap.active`，
   body 加 `.boss-layer__lock-scroll`），**要求先填我方自己的微信号**
   （6-20 位大小写字母、数字、下划线、减号，不支持中文）。
   **这是 BOSS 独有的前置**：招聘方账号需已配置微信号
3. 填完确定，请求发出

### 发出后

| 层 | 观测 |
|---|---|
| 新消息 | `bizType=21050024`、`body.type=4`、`body.action.aid=32`、`type="action"`、`isSelf=true`、`status=1`，文案「请求交换微信已发送」 |
| 会话级 | `requestWeiXin: 0 → 1`；`relationType: 5 → 6`；`weixin` 仍为 `null`、`weixinVisible: 0` |
| 工具栏 | **「换微信」置灰**，其余三个仍亮 —— 可见后置状态 |
| DOM | 居中系统行「请求交换微信已发送」 |

### 对方接受后（2026-08-29 实测，请求发出 6.5 小时后）

| 层 | 观测 |
|---|---|
| 新消息 | `bizType=12`、`body.type=1`、`type="text"`、`isSelf=false`，正文形如「<对方昵称>的微信号：<号码>」——**号码直接嵌在文本里，不是卡片、没有结构化字段** |
| 会话级 | `weixin` 由 `null` 填为号码；`weixinVisible: 0 → 1` |
| 会话级 | **`requestWeiXin` 由 `1` 回落到 `0`** |
| 会话级 | `relationType` **不变**（仍为 `6`） |

**两个坑：**

1. **`requestWeiXin` 的语义是「有一个待答的请求」，不是「曾经请求过」。**
   发出时 `0→1`，对方应答后回落 `0`。拿它判断「是否已换过微信」会直接错——
   判据必须用 `weixin != null` 或 `weixinVisible == 1`。
2. **权威值取 `conversation$.weixin`，不要去解析那条文本。**
   文本是给人看的，号码嵌在中文里；结构化值平台已经给了。

列表层「已交换微信」页签的判别键**未查清**——不是 `relationType`（实测未变）。

**NLP 联动**：我方文本里出现换微信意图时，BOSS 会在输入框上方弹出
「⊗ 交换微信」快捷条。属平台自动行为，非我方触发。

## 七之二、账号身份与登录态（只读，零 HTTP）

Vue 根上挂着四个可观测：`user$`、`privilege$`、`connect$`、`chatLayoutType$`。
**MAIN world 一次性读即可拿到，不需要任何请求。**

### 账号身份（够做身份绑定）

**更正（2026-08-30 实测）：`user$` 不在 `$root` 上。** 它挂在一个 `$options.name === 'app'`
的组件实例上（`isRoot: false`）。从任一带 `__vue__` 的元素沿 `$parent` 上行都能碰到它，
但一路走到 `$root` 反而**读不到**——原写法「Vue 根上挂着四个可观测」是错的。

取数判据因此必须用**形状**而不是组件名：找 `user$` 为对象且 `userId` 为正整数的实例。
组件名是平台私有内部，拿它当判据是高脆的（防护成本预算第 2 条）。整棵树 2584 个元素里
340 个带 `__vue__`，走一遍是毫秒级。

`user$` 里可用的锚：

| 字段 | 用途 |
|---|---|
| `userId`（数字） | **身份锚**。与消息信封里的 `from.uid` / `to.uid` 是同一个空间，实测两处一致 |
| `encryptUserId` | 加密 id（跨会话稳定性未验） |
| `name` / `showName` | 招聘方姓名 |
| `brandName` / `encryptComId` | 公司名与公司加密 id |
| `identity` / `doubleIdentity` / `trueMan` | 身份类别标志 |

DOM 上的可见姓名：`.top-profile-logout .ui-dropmenu-label .label-name .user-name`。

**`user$` 里同时有 `token`、`wt`、`wt2` 三个凭据字段,还有 `clientIP`、`phone`、`email`。**
取数路径正好经过它们,**必须逐字段取用,禁止把整个 `user$` 塞进 evidence、
日志或任何上报** —— 那会一次性把凭据与出口 IP 带出本机。

### 登录态：只知道一半

- `root.connect$` 是个布尔,当前为 `true`,形似连接态
- DOM 上存在「退出登录」入口 —— 已登录的可见标志
- **cookie 里读不到认证凭据**(多半 httpOnly),所以**判登录态不能靠 cookie**

**掉登录后的形态未验证。** 需要真的退一次登录才能看清:`user$` 是变 null、
还是页面整体跳转登录页、还是弹登录框。智联那边掉登录是一条独立的即时停机通道
(`contentSensor` 的 `armLogin` 双读),BOSS 上对应的判据**目前是空的**。

**这是上生产前必须补的一项**:账号身份绑定与掉登录停机都在安全侧,
判错的方向是**错靶**(把 A 客户的话术发给 B 客户的候选人)。

## 附录 A：HTTP 历史接口（推导来源，正式取数不用）

本节记录事实的取得方式，供日后交叉验证与排障；**正式实现不走这条**
（理由见取数通道决策文档）。

```
GET /wapi/zpchat/boss/historyMsg?src={friendSource}&gid={候选人uid}&maxMsgId={游标}&c={条数}&page=1
→ zpData: { hasMore, messages[], type, minMsgId }
```

真机验证（8 条历史的会话，`c=1` 逐页走完 vs `c=100` 一次拿全）：

| 事实 | 证据 |
|---|---|
| `maxMsgId` 是权威游标，`page` 参数被忽略 | 全程 `page=1`，8 页链式走完 |
| 游标**排他**，按 mid 降序 | 每页返回严格小于 `maxMsgId` 的记录 |
| 下一页游标 = 响应 `minMsgId` | 8 步吻合 |
| 两条路径**同集合、零重复、零遗漏** | 集合比对通过 |
| `hasMore` **不携带服务端额外知识** | 它等于「返回条数 == 请求条数」：拿到最老一条时仍为 `true`，再请求才空 |

**推论**：一次 `c=100` 返回不足 100 条即证明该会话全部历史到手。
页面自己用 `c=20`，我方不控制 `c`，故走 MAIN world 后这个证明失效，
完整性改押 `isToTop`（见第三节，未验证）。

## 十一、聊天输入区（2026-09-01 只读实测，为打字线做的考古）

在真实登录页上只读取得，未点击、未输入、未导航。视口 1470×662。

### 输入框

```
div#boss-chat-editor-input.boss-chat-editor-input
  contenteditable="true"     tabIndex=-1
  role / aria-label / spellcheck 均无
  810 × 126 @ (579, 490)
  祖先：.conversation-editor → .conversation-operate → .conversation-box → .chat-conversation
```

**全页唯一**：`#boss-chat-editor-input` 命中 1 个，`.boss-chat-editor-input` 也命中 1 个。
两个锚点各自唯一，用 id 更稳（id 是公开且按定义唯一的，属低脆锚点）。

**它是 `contenteditable` 的 div，不是 `textarea`。** 所以读写都走 `textContent`，
不是 `.value`——这条错了会静默读到 `undefined`，而 `undefined === ''` 为假，
“输入框空不空”的判据会永远说非空。

### 空态是真的空

```
innerHTML   ""
textContent ""
childNodes  0
```

**没有 `<br>` 哨兵**。很多富文本编辑器空态会留一个 `<br>` 或 `<p><br></p>`，
那会让 `textContent === ''` 仍然成立但 `innerHTML` 不为空；这里两者都干净，
所以 `composer.empty` 的判据就是 `textContent === ''`，不需要额外归一化。

### 发送控件

```
div.submit-content > div.submit      文本「发送」     74 × 36 @ (1295, 596)
```

**它不是 `<button>`。** `.conversation-editor` 里 `button`、`[class*=btn]`、
`[class*=send]` 三种选择器一个都没命中——「发送」是个 div。

推论（给将来的发送原语）：**没有 `type` / `disabled` 这类标准 DOM 语义可核对**。
按「守卫只核对世界状态与动作接口的公开语义」，动作接口那一半在这里是空的，
所以发送的授权只能落在世界状态那一半（路由、身份、目标绑定、composer 内容）
与发后正证上。空态下它有没有禁用态 class 未测——那需要先往框里打字。

### 焦点：页面自己会给

读取时 `document.activeElement` **已经是输入框本身**，我们没有点过。
BOSS 在打开/切换会话时会主动把焦点放上去。

这条改变了打字链的设计：**焦点不是必须靠我们点击拿到的**。真人在这个页面上也是
打开会话就直接开始敲，不必先点一下。所以「打字前先 OS 点击输入框」应当改成
**「焦点不在输入框时才点」**——那既更省一次动作，也更贴近真人。

注意 `tabIndex=-1`：Tab 键聚焦不到它，只能由页面程序或真实点击给。所以焦点丢了之后
我们确实需要点击来拿回，`.focus()` 不在选项里（那会造出一个没有前置点击的焦点，
是真人身上不存在的形状）。
