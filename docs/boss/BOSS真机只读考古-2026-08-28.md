## 一、消息 id：Snowflake，连续性判据不可用

```
mid = ((unix_ms - 1695139200000) << 12) | 低12位
```

epoch `1695139200000` = 2023-09-20 00:00 北京时间。**22 个会话的 `lastMsgId` 全部吻合**，
解出的时刻与消息自带 `time` 差 0~20ms（更早的样本偏差达数百 ms，因为其 `lastTS` 被舍到整秒）。

低 12 位不是全局递增序列：观测值密集聚在 769~777，另见一个 8。像是「机器位 + 序列」的复合，
**具体位宽未验，不要依赖**。

**结论：mid 全局分配、按全站时间穿插，同一会话内相邻消息必然跳号。**
- 同一人 7ms 内连发两条 → 差 2
- 另一会话同一人相邻两条 → 差 1
- 又一会话相邻两条 → 差 4093

用「id 连不连续」证明「历史没窟窿」这条路**不通**。

可用的部分：mid 严格单调于服务端时间，且**能独立于 `time` 字段解出服务端毫秒**。

## 二、历史接口与分页契约（完整性判据的替代）

```
GET /wapi/zpchat/boss/historyMsg?src={friendSource}&gid={候选人uid}&maxMsgId={游标}&c={条数}&page=1
→ zpData: { hasMore, messages[], type, minMsgId }
```

真机验证（8 条历史的会话，`c=1` 逐页走完 vs `c=100` 一次拿全）：

| 事实 | 证据 |
|---|---|
| `maxMsgId` 是权威游标，`page` 参数被忽略 | 全程 `page=1`，8 页链式走完 |
| 游标**排他**，按 mid 降序 | 每页返回严格小于 `maxMsgId` 的记录 |
| 下一页游标 = 响应 `minMsgId` | 8 步吻合 |
| 两条路径结果**同集合、零重复、零遗漏** | 集合比对通过 |
| `hasMore` **不携带服务端额外知识** | 它等于「返回条数 == 请求条数」：拿到最老一条时仍为 `true`，再请求才空 |

**推论（重要）：一次 `c=100` 的请求若返回不足 100 条，即证明该会话全部历史已到手。**
智联那套「无游标、最多 32 项、move=reset/next」给不出这个证明。

## 三、消息信封（接口原始形态）

```
{ mid, cmid, from:{uid,name,...}, to:{...}, type, time, status, flag,
  offline, pushSound, pushText, received, securityId, taskId, uncount,
  bizType, bizId,
  body: { type, templateId, headTitle, text?, extend?, dialog?, hyperLink?, resume?, interview?, style? } }
```

注意：**接口原始形态与页面 Vue 层归一化后的形态不同**（原始 `type` 是数字，Vue 层给的是
`"text"` 这类字符串）。适配器认原始的。

### 方向判据（有坑）

**只能用 `from.uid === 我方uid`。**

- `type` **不是方向**：`type=3/body.type=1` 在两个方向都出现（IN 18 条、OUT 3 条）；`type=1` 同样两向都有
- `flag` **也不是方向**：`65537` 与 `1` 都是两向都有

照 `type` 写方向判据会静默错一半。

### 已见枚举（真机已见，未见不得实现）

`bizType`：

| 值 | 含义 |
|---|---|
| `101` | 普通聊天文本（双向） |
| `14` | 对方请求发送附件简历（dialog，带 拒绝/同意） |
| `21050004` | 牛人简历卡 |
| `21050060` / `21050070` / `21120018` | 平台提示（hyperLink） |
| `21050177` | 候选人发简历时的伴随文本 |
| `21050220` | 带「了解详情」按钮的 dialog |
| `21130009` | **面试邀请卡**（写） |
| `21130010` / `21050071` | 系统行，`body.type=4`，内容为空 |
| *缺席* | 早期普通文本没有 `bizType` 字段 |

`body.type`：`1` 文本 / `4` 系统 / `7` dialog / `9` 简历卡 / `12` hyperLink / `14` 面试卡

`status`：`1` 已送达未读 / `2` 已读 / `3` 已撤回
（邀面卡发出时 `1`，候选人读后变 `2`，实测跃迁；撤回行 pushText 为「XX撤回了一条消息」）

`uncount`：`0` 计入未读 / `1` 不计入（平台系统消息与简历卡）

### `cmid`：客户端生成、服务端回显

双向都有，且历史接口里也在。格式因客户端而异——我方 web 端生成雪花状值，
对端生成 unix 毫秒。**若发送接口允许指定 `cmid`，它就是天然的幂等键载体**，
发后核验可按 id 对而非内容匹配。**「能否自定义」「服务端是否据此去重」均未验证。**

## 四、面试是独立于聊天流的实体（本轮最重要的结构发现）

写操作实测：发出一张线下面试邀请卡，随后用「修改」改期。

- 聊天流里只有**一张** `body.type=14` 的卡：
  `body.interview = { condition: 1, text: "发送了面试邀请", url }`
- **卡里不含时间与地点**，只有一个 url
- **改期不产生任何消息**：详情从 `09:00-11:00` 改为 `14:00-16:00` 成功，
  但会话流条数不变、卡的 `mid` 与 `condition` 均不变
- 面试有独立 API 面 `/wapi/zpinterview/*` 与独立 `encryptInterviewId`

**因此「消息账本 = 全部事实」这个假设在 BOSS 上不成立。** 智联那边邀面卡就是消息、
状态跃迁落在消息上；BOSS 这边不是。凡「已发卡不再邀面」这类判据，
在 BOSS 上不能只看消息流。

已见接口（取数条件未完全摸清，`info.json` 直接 fetch 返回 `{}`，加 `X-Requested-With` 无变化）：

- `GET /wapi/zpinterview/boss/interview/info.json?geekId=&geekSource=` ← 详情面板打的就是它
- `GET /wapi/zpinterview/boss/interview/getInterviewByChat?geekId=&jobId=&geekSource=`
- `GET /wapi/zpinterview/boss/interview/valid/list.json`
- `POST /wapi/zpinterview/boss/interview/invite.json`
- `GET /wapi/zpinterview/common/interview/getInterviewContact?encryptInterviewId=`

## 六、邀面表单（写）

模态框根类 `interview-invite-dialog-ui`。字段：

- **面试类型** radio：`线下面试` / `线上面试` ← 对应我方契约的 `onsite` / `wechatVideo`
- 招聘职位（下拉，隐藏 input 存 jobId）
- 面试地址（`readonly`，预填）
- 备注事项（textarea，≤140 字）
- **面试时间**：日期 + 时间，两者皆 `readonly`，只能点开选
- 联系人（下拉，带手机号）

**时间有两种模式**（页签 `.time-title` 内 `.selected`）：

| 模式 | 形态 | 粒度 | 范围 |
|---|---|---|---|
| 精准时间 | 单个时刻 | 小时 × 5 分钟 | 08–20 时 |
| 宽松时间 | **区间** | 30 分钟 | 开始 08:00–20:00，结束 09:00–21:00 |

宽松时间的结束列在选定开始后**重新过滤**，最早为开始 + 1 小时。
我方契约的「面试起止时间」在 BOSS 上走**宽松时间**可表达；精准时间只有起点。

其他实测行为：

- 日历只放开今天及以后
- 「修改」重开的是同一个表单，且**不预填**原时间
- 「修改」的二次确认原话：**「更新后会取消原有面试，并向牛人重新邀约」**——
  它是「撤销 + 重发」，不是原地编辑

**坑**：`input.radio-input` 的 `checked` 两个选项恒为 `false`，
选中状态只在 label 的 `.radio-checked` 类上。按 `input.checked` 读面试类型会永远读错。

## 九、isolated world 可达性（决定架构分叉）

`javascript_tool` 跑在 MAIN world，页面的 `__vue__` / RxJS 流（`list$`、`conversation$`）
**插件够不着**——要够着就得注入 MAIN world，等于造 window 全局，
正好撞 BOSS 的 `Object.keys(window)` 白名单 diff（上报码 99003）。

### DOM 能读到什么

| 选择器 | 含义 |
|---|---|
| `.geek-item[data-id="{uid}-{src}"]`（另有 `id="_{uid}-{src}"`） | 会话列表项，**候选人服务端 id** |
| `.chat-message-list.is-to-top` | 历史到顶标志 |
| `.message-item` | 消息行 |
| `.item-myself` / `.item-friend` / `.item-system` | 方向 |
| `.status.status-read` | 已读回执 |
| `.message-card-wrap.blue` / `.boss-green` | 卡片及配色变体 |
| `.message-card-buttons > .card-btn` | 卡片按钮 |
| `.message-time > .time` | 时间，是「08-25 14:31」这种**文本，不是时间戳** |

### DOM 读不到什么

- **消息服务端 `mid` 完全不在 DOM 上**：66 个 mid 与整页 `outerHTML` 比对，
  命中 0；属性里的长数字全是 SVG 路径坐标。消息行只有 `data-v-*`（Vue scoped CSS 标记）
- **DOM 是 API 的真子集，会整条漏行**：实测 API 11 条 / DOM 9 行。
  漏的是 `bizType=21130010`、`21050071` 这类 `body.type=4` 的空内容系统行
- 已读标记不全：两条 OUT 消息同为 `status=2`，DOM 只在其中一条渲染「已读」

DOM 路唯一顶不掉的是**消息身份**（mid），而 mid 是去重与账本的锚。

## 十一、检测面实测：MAIN world 注入的足迹（2026-08-28 晚补）

起因是取数架构的分叉：DOM 拿不到 mid,要么 MAIN world 读 Vue 内部,要么扩展自己调
HTTP 接口。后者把风险从"可测的前端面"挪到"不可测的服务端日志",故先量前者的足迹。

用插件自己的 `chrome.scripting.executeScript({world:'MAIN'})` 实测(不是 CDP,
两者注入机制不同,CDP 的数不作数):

| 量什么 | 结果 |
|---|---|
| 连打两枪之间新增的 `window` 全局 | **0**(全局数三次都是 332) |
| `func` 形式注入在 `performance.getEntries()` 里的条目 | **0**(总条目三次都是 205) |
| `files` 形式注入(从扩展加载 js)的条目 | **0** —— Chrome 对页面隐藏扩展注入的脚本加载 |
| 按数据形状搜整棵 Vue 树 | 282 个组件,**0.9~1.2 ms**,连打五次产生 0 个 `long-animation-frame` |
| 同一动作页面自己的 longtask | **86 ms**(比例约 1:57) |

**扩展 origin 的 fetch 技术上可用**:`Origin: chrome-extension://<id>` 下
`/wapi/zpjob/interview/job/list` 返回 `HTTP 200 / code 0 / 641 字节`,服务端接受。
但可用不等于该用——它在服务端日志里留下精确可归因、且全机队共用一个的标识,
而那一面我们没有任何观测能力。

### 阳性对照:BOSS 的未知全局检测确实在跑

一个刻意不留痕的探针没法自证跑过("零足迹"与"没执行"观测上等价),故做了反向实验:
用 `document_start` 的 MAIN world 内容脚本故意种一个可枚举全局
`__rhCanary_20260828`,然后刷页面。

**实证结果**:页面 21:55:17 加载,**21:55:27**(约 10 秒后)的上报里,
`800001` 的 `p6` 原样带出了这个名字。三件事同时得证——他们的检测在跑、
判据就是"可枚举 `window` 全局 ∉ 白名单 → 按名字原样上送"、我们的埋点观测抓得住。

**但同一条 `p6` 里另有 12 个名字**:

```
crashReport, viewport, initWarlockData, loadFallbackScript, loadLastbackScript,
apmVueErrorHandler, __originalFetch, litHtmlVersions, litPropertyMetadata,
litElementVersions, BOPI, __xbcw
```

其中 `crashReport`/`viewport`/`initWarlockData`/`apmVueErrorHandler` 是 **BOSS 自己页面的全局**
—— 他们的白名单陈旧到盖不住自家页面。**这份名单是噪声很大的**,单条命中的信号价值
因此有限;但一个稳定、独特、在多台机器同时出现的名字仍然可聚类,所以"别留全局"
这条不放宽,只是理由从"会被抓"改成"别给跨机器可聚类的特征"。

`__originalFetch` 在名单里,意味着有人 patch 了 `fetch` 并留了原引用 —— 正是
"持久化 hook 会留痕"的现成反面教材。

**除故意种的金丝雀外,名单里没有任何一项来自我方插件。**

金丝雀已注销、页面已刷新清除,可枚举全局回落到 329。
