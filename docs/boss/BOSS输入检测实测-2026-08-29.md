# BOSS 输入行为检测实测（2026-08-29）

真机测量 BOSS 对**打字行为**的检测，以及 CDP 合成输入在其中的表现。

结论先行：**CDP 输入被满命中。** 而其中一项（`composition`）**不是时序问题，
是结构性缺失，调参数糊不过去**——这是 OS 注入战役「打字必须自研 TIP」那条挂账的
实证依据，此前它只是假设。

---

## 一、检测账本在哪

`localStorage['_ZP_CNT_']`，16 个计数器 + 一个写盘时间戳 `t`。
**批量延迟写盘**，不是每次输入立刻落盘——本轮两次误读都源于读得太早。

计数语义取自本地既有研究（`../hiBoss/lab/extension/popup.js`，
其源头是 `report/behavior-layer-checks.md` 与反混淆的 sec 脚本）：

| 计数器 | 含义 | 日内只增不减 |
|---|---|---|
| `input_count` | 总输入次数 | 是 |
| `speed_abnormal_count` | 打字太快（<100ms/字） | 是 |
| `composition_abnormal_count` | **中文没走输入法** | 是 |
| `keyboard_abnormal_count` | **有文字却没按键** | 是 |
| `key_word_ratio_abnormal_count` | 按键数远少于字数 | 是 |
| `flimbot_abnormal_0_count` | 更宽的规整度网（>0） | 是 |
| `gobbledygook_count` | 上一项的孪生计数器 | 是 |
| `input_rhythm_abnormal_count` ★ | 每一下都极短（全 ≤15ms） | 否 |
| `input_rhythm_abnormal_200_count` | 剔掉停顿后仍每字 ≤200ms | 否 |
| `input_trait_abnormal_count` ★ | 每次上屏都是单字 | 否 |
| `quorble_abnormal_count` | 节奏太规整 | 否 |
| `flimbot_abnormal_count` ★ | 剔掉停顿后仍太规整（>0.6） | 否 |
| `flimbot_kd_abnormal_count` | 每个键按得太一致（dwell） | 否 |
| `flimbot_kr_abnormal_count` | 按键间隔太规整 | 否 |
| `keycode_abnormal_count` ★ | 键码全是 0（合成事件默认值） | 否 |
| `keycode_abnormal_count_2` ★ | 某个物理键占比 >0.7 | 否 |

★ = 会触发聚合上报的五项。触发条件：`input_count % 25 == 0` 且五项任一非 0；
届时其余九个非「只增不减」项会被清零。

另有 `localStorage['__local__sec__store___']` 记 rAF 帧率
（`recent` 全 60、`max`/`min`、屏幕 `scw`/`sch`）。

## 二、实测：CDP 输入的画像

三次输入（一次中文并发送、一次模态框里的纯 ASCII、一次聊天框里打了不发的 ASCII），
全部计入 `input_count`——**模态框输入算，打了不发也算**。

| 计数器 | 结果 |
|---|---|
| `composition_abnormal` | **1**（仅中文那次） |
| `keyboard_abnormal` | 2 |
| `speed_abnormal` | 1 |
| `input_rhythm_abnormal` ★ | 1 |
| `input_rhythm_abnormal_200` | 1 |
| `input_trait_abnormal` | 1 |
| `keycode_abnormal` ★ / `_2` ★ | 0 |
| `key_word_ratio_abnormal` | 0 |
| flimbot / quorble 族 | 0 |

**一次中文输入，六项异常同时开火。**

### `keyboard_abnormal`（有文字却没按键）说穿了机制

`keycode` 族与 flimbot/quorble 族全部为 0，**不是因为表现正常，
而是因为压根没有按键事件可供分析**——CDP 的 `computer.type` 走
`Input.insertText`，一个 `keydown`/`keyup` 都不产生。

BOSS 看到的画像是：**凭空出现 N 个字、零次按键、瞬间完成、
中文却没有任何输入法组合过程。**

### `composition` 只对中文开火（对照已成立）

三次输入里只有第一次是中文，而 `composition_abnormal` 全程停在 **1**——
两次 ASCII 输入一次都没触发它。

> **`composition_abnormal` 只对「中文没走输入法」开火，ASCII 不触发。**

## 三、对 OS 注入战役的结论

| 族 | OS 注入能不能解 | 理由 |
|---|---|---|
| `keyboard` / `keycode` / `key_word_ratio` | **能** | OS 注入产生真实键盘事件与真实键码 |
| 时序族（speed / rhythm / trait / quorble / flimbot） | **能** | 时间分布由我方控制 |
| **`composition`** | **不能** | 中文不经输入法就是没有 composition 事件 |

**因此 TIP（输入法组件）是硬需求，不是优化项。** 这是本轮把它从假设变成实测的地方。

## 四、当前账号状态与运营含义

测试账号 `input_count` 已到 **3/25**，五项上报触发条件里**已中两项**
（`input_rhythm_abnormal`、`input_trait_abnormal`）。
再有 22 次 CDP 输入即触发一次聚合上报。

**任何用 CDP 打字的真机操作都在推高这个计数。** 需要长时间真机验证时，
要么改用 OS 注入，要么接受计数增长并知道阈值在哪。

## 四之二、账本不随日界清零（2026-08-30 补测）

诊断面板接入后复读：**账本写盘于 08-29 14:42，落后读取时刻 25.5 小时，
`input_count` 仍是前一日的 3。**

即跨了一整个自然日界也没有清零。二手语义里「日内只增不减」的说法隐含着
存在日界重置，**实测未观测到**。目前唯一有依据的归零时机是聚合轮
（`input_count % 25 == 0` 且 ★ 五项任一非 0 时，其余九项清零）。

推论：**这个账号上的异常计数是长期累积的**，不会睡一觉就干净。

   判据可能要求更长样本或不同触发条件——**未查清**
2. 十六项各自的精确阈值只有二手描述，未对反混淆源码逐条复核
3. 计数器的清零周期：日界已排除（见四之二），会话界/登录界仍未查
4. 这些计数**实际被上送时的载荷形态**——插件的埋点观测当前**未接入 `_ZP_CNT_`**
   （埋点战役里明确挂账延后的一项），本轮数据是直接读 localStorage 取得的

## 附：本轮的两次误读

留档，因为它们会重复发生：

- **「计数器只在发送时更新」——错。** 它是批量延迟写盘，读早了看不到。
- **「模态框输入不在监控范围」——错。** 同一个误读造成；模态框输入照样计入。

两次都是「读得太早 → 得出机制性结论」。**下次读 `_ZP_CNT_` 要等足够久或反复读。**
