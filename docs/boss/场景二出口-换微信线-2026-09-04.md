## 〇、两条判据原则（2026-09-04 甲方定，本出口全部按此写）

1. **判据用「或」不用「与」。** 每个判定只挑一两个最稳、最标志性的平台反应，出现即成立；其余反应只进 evidence / 日志当观测。
2. **信号必须在两个读取时机都可见。** 原语刚做完动作立刻回读，与巡检后来重新点开会话再读，读到的是同一样东西。
   只选服务端持久化、两次都渲染的证据；淘汰只在当场闪一下的（tooltip、快捷条）和要重载才刷新的（`weixinVisible`）。

## 一、脑侧零改动的依据

读过 `communication/events.go`、`v4_state.go`、`appbridge/effect_verifier.go`、`patrol/m7_wechat_collect_patrol.go`：脑只认
`ThreadMessage` 的 `kind/cardType/cardState/direction` 与三条原语的 typed data，全部平台无关：

- 入站 `card/wechatExchange/pending` → `EventWechatRequested` → 脑铸 `acceptWechat(requestSourceKey=该行 sourceKey)`；
- 出站 `card/wechatExchange/pending` → `EventWechatInvited`；任一方向 `accepted` → `EventWechatExchanged` → 微信态 Exchanged；
- `sendWechatInvite` 的验证读走 `readThread` 窗口找「出站 card/wechatExchange/pending、contentHash=常量配方、时间不早于派发」；
- `acceptWechat` 的验证读走 `readWechatExchangeOutcome` 带锚形态，要 `confirmed + exchangeSourceKey + peerWechat`；
- 微信态 Exchanged 后 `m7` 巡检先 `readThread`（BOSS 上会自行点开会话）再 `readWechatExchangeOutcome` 无锚形态收号。

所以只要 BOSS 手侧把三种平台形态投成上述三种契约形状、三条原语按契约 data 回值，脑侧一行不改。

## 二、手侧改动面（本轮全部）

### 2.1 `readThread` 投影增量（`projectBossMessage` + MAIN world 抽字段）

MAIN world 的 `mainReadBossThread` 多抽三个原始字段：`body.templateId`、`body.dialog.operated`、`body.dialog.buttons[].url` 里的 `aid` 列表。
投影表新增两行，其余不动：

| 平台形态 | 投影 | 脑侧事件 |
|---|---|---|
| `bizType=12` + `body.type=7` + buttons aid 含 33（入站） | `card/wechatExchange/pending`，text 固定「[交换微信请求]」，hash 常量配方 | `EventWechatRequested` |
| `bizType=12` + `body.type=1` + `templateId=5`（入站） | `card/wechatExchange/accepted`，text 固定「[微信交换成功]」，hash 常量配方 | `EventWechatExchanged` |

- 请求卡 `operated=true` 后**仍投 pending**（与智联同构：智联的 105 请求卡也不带完成态，完成由独立的 259 表达）。
  这样 Exchanged 只由微信号消息触发一次；`operated` 只作 `acceptWechat` 自己的前置与正证，不进投影。
- **微信号不进 text**：`templateId=5` 那条的正文含号码，投影用固定文案；号只经 `readWechatExchangeOutcome` 的 `peerWechat` 走
  ContactAsset 边界。这是 AGENTS「AI provider 数据边界」对候选人微信号去处的硬要求。
- 其余 `bizType=12`/`body.type=1` 文本照旧投 `text`。

### 2.2 `chat.sendWechatInvite`（两步，零打字）

- **前置**（世界状态核对，全部低脆）：账号身份当前；目标绑定 = `conversation$.uid+name` 与 `conversationRef` 一致（复用场景一 `ensureBossThreadOpen`，
  不是当前会话就点开一次）；`bothTalked=true`；工具栏「换微信」`span.operate-btn` 无 `disabled` 且文本恰为「换微信」——
  文本「换微信 请求中」= 已有我方待答请求、「查看微信」= 已换成，两者都**干净失败不点**（detail 带读到的文本）。
- **并发前置**：消息数组里存在 `operated=false` 的入站请求卡（判据表第二行）→ `GUARD_FAILED` 干净拒绝、不点。
  理由见 §四 第 5 条。
- **动作**：`osClick`「换微信」→ 条件等待 `.exchange-tooltip`（display block、`.text` 含「交换微信」）出现（封顶 60 秒的条件轮询，不是固定等）
  → 若出现 `.add-wx-wrap` 模态（己方微信号未配）→ `manualOnly` 干净失败、不填不点 → 证词 attempting → `osClick` 该 tooltip 的
  `.boss-btn-primary`「确定」（取可见那份，index 由命中测试兜底）→ 至多一次。
- **正证**（判据表第一行，条件轮询复读）：新增 aid=32 出站行且 `time` 不早于派发 → ok，`sourceKey=mid`，`contentHash=sha256("card\x1fwechatExchange")`，
  `tsApprox=time`；或 `weixin` 由空变非空（并发前置漏网的兜底）→ **未确认**（detail「对方待答请求已被本次确定接受，微信已落值」），
  由脑走验证读→suspect→人工，见 §四 第 5 条。两者都没有 → 未确认。

### 2.3 `chat.acceptWechat(conversationRef, requestSourceKey)`

- **前置**：目标绑定同上；消息数组里 `mid==requestSourceKey` 的行存在、是入站 dialog、buttons 含 aid 33、`operated=false`；
  卡内 `div.message-card-buttons > span.card-btn`「同意」无 `disabled` 且在视口内可见（≥24px）。任一不成立 → 干净失败不点
  （已 `operated` 或按钮 `disabled` = 已答过，detail 说明；不在视口 = retryable，本轮不滚）。
- **动作**：证词 attempting → `osClick` 卡内「同意」（expectText「同意」）→ 至多一次。靶子选卡内不选快捷条：卡内按钮长在该消息 DOM 里，
  与 `requestSourceKey` 绑定；快捷条是页面级通知，多条待答时显示哪条未知。
- **正证**：`conversation$.weixin != null` 或该行 `dialog.operated=true`（条件轮询复读）。
- **data**：`exchangeSourceKey` = 锚之后最新一条 `templateId=5` 入站行的 mid、`peerWechat` = `conversation$.weixin`，两者齐才带，
  否则一并缺席（契约「要么同时出现要么同时缺席」），号由验证读延迟收编。

### 2.4 `chat.readWechatExchangeOutcome(conversationRef, requestSourceKey?)`

- 零点击、不定位：要求当前打开的会话与 `conversationRef` 绑定一致，否则按契约拒绝（脑的两个调用方都会先把会话点开：
  验证器复用原命令会话，`m7` 先 `readThread`）。
- **判据**：`conversation$.weixin != null`。
- 带锚：锚行存在且为入站请求卡，取锚之后最新一条 `templateId=5` 入站行为 `exchangeSourceKey`；无锚：取当前可见消息里最新一条 `templateId=5` 入站行。
  `weixin` 有值但找不到 `templateId=5` 行 → `confirmed=false`（本轮正证不足，不猜）。
- `confirmed=true` 只带候选人 `peerWechat`，永不带招聘方微信。

### 2.5 门禁同步

`unit.mjs`「BOSS 表恰为…」用例从 4+5+7 改为 4+5+10，适配器声明面用例同步；`projectBossMessage` 新增三条投影单测
（请求卡 pending、`operated=true` 仍 pending、`templateId=5` → accepted 且 text 不含号码）；三条原语各一组"前置拒绝零点击"用例。

## 三、出口四项

### 1. 本轮最小可交付出口

上面 2.1～2.5 全部落地、`pnpm typecheck` + unit 绿、Windows 交叉编译过，然后 **Mac 真机两条链各跑通一次**（换微信线零打字，不需要 Windows TIP）：

- **链 A（脑主动）**：测试候选人说话 → 脑意向判断 → AI 建议「发起换微信邀请」→ `sendWechatInvite` 正证收编 → 候选人端接受 →
  巡检 `readThread` 投出 accepted → Exchanged → `m7` 收号 → ContactAsset → 运营通知发件箱入队。
- **链 B（对方主动）**：候选人端发请求 → 巡检投出 pending → `EventWechatRequested` → `acceptWechat` 点卡内「同意」→ 验证读 confirmed → ContactAsset。

通过判据：候选人端各恰好收到一次；两条链意图终局成功、零 suspect；ContactAsset 恰一条且号码正确；埋点「踩雷」行零新码；人工介入零次。

### 2. 必须立即阻断的损害

- **错靶**：三条原语动作前都核 `conversation$.uid+name` 与 `conversationRef`；`acceptWechat` 额外核 `mid==requestSourceKey`。
- **二次不可逆点击**：证词 attempting 写在「确定」/「同意」前；前置读「请求中」/「查看微信」/`operated`/`disabled` 即拒；原语内不重试。
- **对真人发请求**（开发期）：只在交接日之后建档的会话上跑，脑账本 `data-boss4` 现有真人会话一律不进沟通线（`RECRUITHELPER_INBOUND_HANDOVER_DATE` 已设）。
- **微信号外泄**：投影 text 用固定文案；号只进 `peerWechat` typed data；不进 evidence、detail、手侧日志。

### 3. 允许重试或人工兜底的失败

- 前台闸、标定、落点、tooltip 未出现、卡不在视口 → 干净失败 retryable，脑按既有节奏重派。
- 己方微信号未配（出现填号模态）→ `manualOnly`，人去平台配一次。
- 正证零匹配（含 §四 第 5 条并发漏网）→ 未确认 → 脑验证读 → suspect → 人工；绝不补动作。
- 验证读 `weixin` 有值但 `templateId=5` 行未到 → 本轮 `confirmed=false`，下一轮再读。

### 4. 审查轮次与后置项

- 冒烟 commit 后一轮独立出口审查，只对阻断级做定向复核。
- 后置（各自另立）：`acceptWechat` 卡不在视口时接 `osScroll`；「拒绝」与「请求中」回落形态考古；`selectedIndex` 语义；

  1.4 已于 09-02 批为勘误级，随本包同批落还是后置，请甲方定）。
