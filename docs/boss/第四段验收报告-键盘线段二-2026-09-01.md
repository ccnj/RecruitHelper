# 键盘线段二验收 · Windows 真机首验

2026-09-01。客户端基线 `c159759`，TIP 源码 `hiBoss@6e60bff`。

**整条线通了。** 三条文案全部 `matched=true`——键序、上屏词、回读逐字相同。
自研 TIP 存在的唯一理由(从根上消掉候选词随机性)在真机上兑现。

## 三条文案

| 文案 | 键 | 排版 | 滞后峰值 | TIP | 回读 |
|---|---|---|---|---|---|
| 你好，方便加个微信聊聊吗 | 82 | 1 次重采 7 词 1ms | 13us | 7/7 | 逐字相同 |
| 岗位是Java后端，Base深圳，方便聊聊吗？ | 128 | 3 次重采 12 词 8ms | 585us | 12/12 | 逐字相同 |
| 薪资20到30万，3年经验 | 66 | 1 次重采 11 词 1ms | 172us | 11/11 | 逐字相同 |

三条都停在草稿状态,一次发送都没有。

### 第一条把 macOS 那次的病治好了

```
mac  期望「你好，方便加个微信聊聊吗」  实得「你好，方便价格微信聊聊吗」
Win  期望「你好，方便加个微信聊聊吗」  实得 逐字相同
```

段一在 mac 上七词错一个且是同音异形(`jiage`),说明切分、上屏键、组字周期全对,
只有候选词那一层不同——**而那正是自研 TIP 唯一要解决的**。现在解决了。

### 后两条堵的是两个「在 mac 上原理上验不了」的洞

**英文段。** 上游 2026-09-01 放行英文时**全部是离线证据、零真机**,而 macOS 上
结构性验不了:走系统输入法的话 `b,a,s,e` 会被当拼音处理,上屏的是汉字——
不是"选错候选词",是结构性不同。现在 `Java`、`Base` 大小写都对,
坐实了「按什么键」与「出什么字」分开这个设计。

**数字。** 上游自记的活账:真微软拼音下数字走 `insertText`(type1),而 TIP 的
classify 把空格、数字、OEM 标点键一律当上屏键吃掉走 composition(type2);
2026-08-23 那份真机计划里**一个直接数字段都没有**。`20` 还会被拆成 `2`、`0` 两段。
现在 `20`/`30`/`3` 全对。

### 排版器的闭环自验第一次在真机上可见

混排那条 **3 次重采**。排版器把自己算出的计划合成成事件流、再量一遍参数,
与真人基线对不上就换种子重来(最多 40 次)。两份不合格的形状被它自己否掉了。

## 时钟:Windows 比 macOS 好一个量级

```
macOS  5839us      Windows  13 / 172 / 585us      上游 Windows  790~2490us
```

`clocksrc_windows.go`(QPC)在真机上头一次跑,量级与上游对得上。
这也印证了当初那条判断:**不能用 `time.Now()` 测**——它在 Windows 上粒度 15.625ms,
量什么都是梳状,三种等待策略会被一律报成量化、结论完全相反。

## 鼠标线:两个靶子都过了,这条线收官

```
只移不点  landed  · 2 趟 · 落点偏差 122px · 标定就绪     · 滞后 598us · 3574ms
真点一次  clicked · 1 趟 · 落点偏差 0px   · 就绪(热路径) · 滞后 385us · 4596ms
  1. 靠近#1 靶「全部(点前 选中=收藏 列表=0)」瞄点(233,74) 抖动(-4,-1) 落(233,74)
     偏0 标定=就绪 命中=是(靶子(span))
  2. 点后 isTrusted=true 命中靶子=true 事件偏差=5 后置=选中=全部 列表=0 靶子「全部」已选中
```

冷启动两趟收敛,与上游「实测两趟就够」一致;122px 是**第二趟学的时候**的偏差,
学完即 armed,不是命中精度。**命中精度是热路径那条的 0px。**

`isTrusted=true` 是整条 OS 注入线存在的全部理由——BOSS 查这个,页面内合成的事件
在它这儿不成立。后置状态真的翻了(收藏 → 全部),可逆靶子的正证成立。
排轨迹 0ms 说明前一条学出来的标定直接复用上了。

**至此鼠标线在 Windows 上的验收判据补齐**(此前只有 macOS,而 scale=1 是所有档位里
最容易的一档——上游在 Windows 上那一趟照出两个 bug,两个在 macOS 上都完全不可见)。

## 埋点:十五项异常计数全 0,但样本只有 6 次且无基线

整条键盘线的**目的**是让 BOSS 的 `_ZP_CNT_` 不报输入异常。首读:

```
平台没记下任何输入异常
input_count 6    十五项 abnormal 计数全部 0(含触发聚合上报的五项 ★)
读取 17:49:14 · 平台写盘 17:42:51(落后 383 秒) · 未设基线
```

三项尤其要紧,它们正是 CDP 打不过去的地方:

| 计数器 | 值 | 含义 |
|---|---|---|
| `composition_abnormal_count` | 0 | 中文**走了**输入法——我们的 TIP 被平台认作真输入法 |
| `keyboard_abnormal_count` | 0 | 有文字**也有**按键 |
| `keycode_abnormal_count` ★ | 0 | 键码不是合成事件的默认 0 |

对照 2026-08-29 的 CDP 打字:**只 3 次输入就已中两项 ★**
(`input_rhythm_abnormal`、`input_trait_abnormal`)。

### ⚠ 三条让这份读数还不能当结论

1. **没设基线。** 面板的「设为基线」没按过,所以这些 0 归因不到我方这几次运行——
   也可能只是这台新机器的 Chrome profile 干净(`_ZP_CNT_` 存在 localStorage,
   换机器/换 profile 就是空的)。08-29 那两项非 0 现在变 0,**最可能的解释正是这个**,
   而不是被清零:考古记录明确写了这个账本**不随日界清零、异常计数长期累积**,
   唯一有依据的归零时机是聚合轮。
2. **`input_count` 才 6,聚合阈值是 25。** 6 次没中确实是好信号(CDP 3 次就中两项),
   但离说服力差一截。
3. **写盘落后 383 秒**,最后一两次运行可能还没进这份快照。

### 坐实它只需一步

**设基线 → 连着跑到 `input_count` 过 25 → 再读。**

安全:聚合上报的触发条件是 `input_count % 25 == 0` **且** ★ 五项任一非 0。
★ 全 0 时跨过 25 什么都不会上报——而"干净跨过阈值"本身就是最强的证据。

## 这一趟改掉的两个 bug

**一、管道建一次就不能关。** 第一条命令全绿,第二条**整条 6ms、一个键都没发**。
6ms 是线索:等 TIP 的超时是 8 秒,所以它压根没走到等待,是建管道当场失败。
三条撞在一起——go-winio 建监听用 `FILE_CREATE`(同名管道有实例就建不出)、
关监听只关监听句柄(已接受的连接还开着)、而 TIP「连上就一直连着」。
根因是照搬了上游 `play.go` 的形状:那是一次性 CLI,"每次"等于"每进程",
永远撞不上第二次;我们的脑是常驻的。修复 `e56c138`。

**二、失败时不说原因。** 手服务把「起管道失败(…):拒绝访问」放在响应体里,
插件在非 2xx 分支直接扔掉,现场只有「手服务返回 500」。
「错误收敛必须留痕」禁的正是这个。修复 `c159759`。

**第一个修复已由甲方真机连跑数次确认**(2026-09-01):同一脑进程内连续多条打字命令
不再报错。那正是修复前必死的路径。
