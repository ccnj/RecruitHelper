## 一、为什么 BOSS 必须走这条线

BOSS 装了输入行为检测：页面 `localStorage._ZP_CNT_` 记打字的异常特征，
CDP 打字六项全中（`docs/boss/BOSS输入检测实测-2026-08-29.md`）。

更硬的一条：**`composition` 事件只对中文开火**。这不是可以绕过的门槛，是结构性
缺失——不走真正的输入法就造不出中文输入该有的事件序列。所以自研 TIP 是硬需求，
不是优化。

## 二、三层分工

```
┌─ 插件 (TS + vendored .mjs) ──────────── 产出数据 ─────────┐
│  排版器 compose(text) → Plan                              │
│  Plan = { startTime, words[] }                            │
│    word = { text:"你好", keys:[{code,down,up,shift}],     │
│             commit:{code:"Space"}, splits:[2], direct }   │
└───────────────────────────────────────────────────────────┘
                          ↓ HTTP /handinput/type（整份 Plan）
┌─ 脑进程的手服务 (Go) ────────────────── 执行过程 ─────────┐
│  ① 命名管道 → 告诉 TIP 这轮按顺序上屏哪几个词             │
│  ② Plan.Flatten() → 按时刻排序的 down/up 事件             │
│  ③ SendInput 发真实虚拟键码                               │
└───────────────────────────────────────────────────────────┘
                          ↓ Windows 输入栈
┌─ 自研 TSF 输入法 (Rust DLL，被 TSF 加载进 chrome.exe) ────┐
│  收到按键 → 走完整 ITfComposition → 上屏指定的词          │
└───────────────────────────────────────────────────────────┘
                          ↓
                    Chrome → BOSS 页面
```

## 三、分界线是「数据 / 过程」，不是「JS / Go」

**插件产出数据（一份带时刻的序列），Go 执行过程（按时刻把它播出去）。**

这条比「JS 归插件」更本质，因为它同时钉死了两边：

**生成必须在插件。** 决定性依据是上游打字线那条 LCG 跨语言不等价：

```js
s = (s * 1103515245 + 12345) & 0x7fffffff     // hiBoss lab/engine/compose/timing.mjs
```

`s` 接近 2^31 时乘积到 2.37e18，**超过 2^53**。JS 用 double 算完再截 32 位，
**精度丢失是结果的一部分**。用 Go 的精确整数照抄同一个公式：

```
前 10 步中不一致 9 次，第 1 步就分叉
JS = 377401600      精确整数 = 377401575
```

要跨语言一致只有两条路：在 Go 里复刻同样的浮点精度丢失（脆，且错了不报错，
只会让分布悄悄偏），或者换 RNG——那就跟上游全部基线、种子、AUC 验收脱钩重来。
**hiBoss 自己没讨论过这一点**，是 2026-08-28 实测出来的。

诚实补一句：鼠标线的 RNG 是 mulberry32，走 `Math.imul` 与 `|0`，精确 32 位，
跨语言可以逐位复刻。所以严格说这条只锁死打字那半。但把两半劈到两种语言里是最差
的组合——两套语言、两套验收，换不来任何东西。

**播放必须在 Go。** 注入时序相对计划的偏差实测 0.79~2.49ms，MV3 的 service worker
定时器做不到这个量级；且上游那句「引擎里一旦出现『等一下再走下一步』，它就搬不走」
同样成立。

## 四、搬运纪律

```
vendor/*.mjs     逐字复制，一行不改（连注释一起搬，那是纪律的载体）
vendor/*.d.mts   我们手写，只声明实际用到的导出——上游改签名当场编译红
plan.ts          我们写的，唯一对外入口
```

**不是「移植成 TS」。** 改过的文件对不上上游，对不上就意味着 hiBoss 那边的判别器
跑分不再能说明我们真机跑出来的东西。需要什么就在 `plan.ts` 里包一层。

### vendor/ 里的东西是谁写的

（2026-08-31 甲方问过一次，记在这儿免得再查。）

**全部是 hiBoss 项目自己的，没有一行来自 BOSS 网站。** 但分两类：

| 文件 | 性质 | 来源 |
|---|---|---|
| `route.mjs`、`engines.mjs` | hiBoss 手写的**生成算法** | `hiBoss/lab/engine/mouse/` |
| `route.bjh.mjs`、`press.bjh.mjs` | **生成文件**，真人行为的数据池 | `hiBoss/lab/probe/baseline/` |

数据池是从真人的手量出来的（同事真实重度使用 BOSS 的那段会话），**量它用的字段
是 BOSS 自己上送的 `p6.x/p6.y/p6.z/p6.w`**。准确说法：格式借的是 BOSS 的埋点通道，
内容是真人的行为。BOSS 只提供了一把尺子，没提供任何代码。

反混淆出来的 BOSS 代码住在 hiBoss 的 `evidence/` 与从它推出的判别器里，
**一个字都没进 `vendor/`**。

两个池子的头注释都写了同一条设计取向，搬的时候别丢：

> **等概率抽一个，别拟合分布。** 手写的模型这一季度错过五次，而池子只会错在采样上。

## 五、上游已完成的部分（真机验证过）

| 位置 | 内容 | 状态 |
|---|---|---|
| `hiBoss/lab/engine/tip/` | Rust 自研 TSF 输入法 | 三步全 ✅ Windows 真机 |
| `hiBoss/lab/engine/inject/tip_windows.go` | 命名管道 TipServer / SendWords / DriveWords | ✅ 真机 |
| `hiBoss/lab/engine/compose/` | 排版器（planner/pinyin/lexicon/segment/params/timing） | ✅ |

2026-08-23 Windows 11 / Chrome：9 字计划 6 个词，**6/6 全部上屏**，文案一字不差，
注入滞后均值 0.001ms，逐键间隔与计划完全吻合。

自研 TIP 的意义是**从根上消掉候选词随机性**：借来的微软拼音自己决定出哪个词，
实测 36 个 IME 段错 3 个（8%），且同一个 `liaoliao` 有时出「了了」有时出「聊聊」
——候选词错误不是拼音的纯函数，规则式规避不成立。自研 TIP 不查词库，上屏什么由
外部指定。

### 三条铁律（`hiBoss/lab/engine/tip/README.md`）

1. **必须走完整的 `ITfComposition`**，不能图省事直接 `InsertText`。网页看到的
   `keyCode 229` 是 Chrome 的 `TSFTextStore::DispatchKeyEvent` 伪造的；
   `has_composition_range_` 为假时按键只被缓存不派发，**吃了键却不建 composition
   等于网页一个 keydown 都收不到**，对 BOSS 的 keyboardAbnormal 是直接送人头。
2. **注入器必须继续发真实虚拟键码**，绝不用 `KEYEVENTF_UNICODE`——否则
   `ITfKeyEventSink` 收到的 WPARAM 恒为 `VK_PACKET`，拿不到按了哪个键。
3. **`pfEaten` 在四个回调里必须自洽**。实测 chrome.exe 只发 `OnKeyDown`，
   notepad / explorer 只发 `OnTestKeyDown`。

## 六、一次打字的完整流程

```
1. 脑 → 手：chat.sendMessage（意图级，只有文本，零坐标）
2. 插件：爬 DOM 找到输入框矩形
3. 插件：走已有的鼠标线点进输入框
4. 插件：compose(文本) → Plan
5. 插件 → Go：POST /handinput/type {整份 Plan}
6. Go：管道送词表给 TIP；同时 SendInput 按计划播键
7. TIP：n-i-h-a-o + Space → composition → 上屏「你好」
8. 插件：回读输入框的值，核对 == 期望文本
9. 放行判定 → 发送（本轮竖切不做这一步）
```

**第 3 步不是可选的。** `SendInput` 打的是前台窗口的焦点元素，所以打字依赖鼠标线
先点进输入框。用 DOM `.focus()` 会造出「没有前置点击的焦点」——那是真人身上不存在
的形状，方向与整条线的立论（让它照发，把发出去的内容做成人的样子）相反。

**打字不需要标定。** 搭车标定、散开、热路径那一整套是坐标的事，键盘线一个坐标都
没有。这条线比鼠标线简单。

## 七、要建的东西

| # | 建什么 | 从哪来 |
|---|---|---|
| 1 | `osengine/vendor/compose/*.mjs` + 手写 `.d.mts` | hiBoss 逐字搬 6 个文件（约 45KB） |
| 2 | `pinyin-pro` 依赖 | npm（353KB 词典） |
| 3 | `handinput` 的 TIP 命名管道 | 搬 `tip_windows.go` 的 TipServer（390 行） |
| 4 | `keymap`（code → 虚拟键码） | 搬 |
| 5 | `POST /handinput/type` | 我们写 |
| 6 | `debug.osType@1` 原语与编排 | 我们写 |
| 7 | TIP DLL 的交叉编译与注册 | crate 已有 |

Plan 在 Go 侧的类型（`hiBoss/lab/engine/inject/injector.go`）：

```go
type PlanKey struct {
    Code     string; Down, Up float64
    Shift    bool   // 本键是在 Shift 按住时按下的
    Modifier bool   // 本键就是修饰键（ShiftLeft）
}
type PlanWord struct {
    Text   string; Direct bool
    Keys   []PlanKey; Commit *PlanKey
    Splits []int     // 音节边界，只影响 TIP 组字区的显示，注入器只负责转交
}
type Plan struct { StartTime float64; Words []PlanWord }
```

`shiftGuard = 40.0`：Shift 必须在下一个键按下前至少这么久松开。2026-08-21 真机
教训——「？」之后 x 在 Shift 仍按住时按下，输入法收到大写 X 当成英文，
**「薪资」变成了「Xin子」**。时序职责在排版器（只有它有全局视野），注入层只在
排不开时显式报 `ShiftConflict`，不静默出错字。

## 八、三条已知残留（2026-08-28 记下，仍未处理）

1. **`pinyin-pro` 从没在 service worker 里跑过。** 353KB 的 `dict1` 是硬依赖、
   tree-shaking 去不掉，冷启动约 37.5ms。SW 靠 20 秒心跳常驻，一个浏览器会话只付
   一次，所以结构上不是问题——但要顺手验一次。
2. **池子怎么携带、怎么随基线更新，上游没定**（`route.mjs` 只说「从外部注入」）。
   搬打字池时要定一个版本冻结的规矩：**池子换了轨迹就变了**，必须跟引擎版本一起冻结。
3. **接口不能只收按键序列。** Go 既要按计划播键，又要经命名管道告诉 TIP 出哪个词，
   所以 `/handinput/type` 一次收整份 Plan，含 `words[].text` 与 `splits`。

## 九、两个尚未解决的真问题

**一、TIP 怎么装到客户机。** `regsvr32` 注册需要管理员权限，而本产品的交付方式是
「客户端整包携带 + 首次人工远程协助」（`docs/插件交付与更新决策-2026-07-25.md`）。
这条从没想过，**它是键盘线能不能落地的最终关卡**。

**二、一切只能在 Windows 上做。** TIP 是 Windows DLL、命名管道是 Windows、
`SendInput` 是 Windows。macOS 上除了交叉编译，一行都验不了。

推论：**推进键盘线自动把「鼠标线 Windows 重跑」做了**——那是鼠标线唯一缺的验收
判据，而键盘线无论如何都需要那台机器。
