# BOSS 场景一实现说明（2026-09-03）

场景一 = 「测试候选人在已有会话里说一句，系统在 BOSS 上回一句」，仅回复流一轮闭环。
本文记实现按什么分工写、哪些地方与智联不同、出口审查留下的挂账，以及 Windows 真机首验必看项。
事实依据全在 [`BOSS平台事实-2026-08-28.md`](BOSS平台事实-2026-08-28.md) §二/§十一/§十二；
读取分工裁决在 [`BOSS取数通道决策-2026-08-28.md`](BOSS取数通道决策-2026-08-28.md) §十之二。

## 一、七条原语各读什么、点什么

| 原语 | isolated DOM 读 | MAIN 内存读 | OS 点击 |
|---|---|---|---|
| readUnreadTotal | 侧栏角标 `.menu-chat-badge` 文本 | — | — |
| readList | 页签/小页签/职位下拉文案与矩形 | 会话数组（形状：uid+friendSource+newMsgCount+encryptUid，取与 DOM 行顺序对齐的一份） | 页签不是「全部」或小页签不对时各点一次 |
| identifyCurrentConversation | — | `conversation$`（自有属性，按形状找） | — |
| openConversation | 行定位、selected 类、未读气泡、视口内 | — | 目标行未 selected 时点一次 |
| readThread | 行定位/selected（点开时） | message-list 的 `list$` + `isToTop` + 同一注入里的 `conversation$` 绑定核对；`user$.userId` 只在页面内判方向 | 普通巡检行未 selected 时点一次 |
| sendMessage | 输入框、发送钮、发送前最后一道闸（钮+选中行+输入框内容一次注入） | 当前会话对象、发送前基线、发后正证 | 焦点不在才点输入框；发送钮一次 |
| captureThreadScreenshot | 选中行、`.chat-message-list` 矩形与滚动指标 | — | — |

引用格式：`conversationRef = uid-friendSource`，`platformUserRef = uid`。两层都有，DOM 行的
`data-id` 就是它，点击定位一句选择器即到。

身份复核：按标签页缓存指纹，导航代数（`base/tabGeneration.ts`）变、后台进程重启、超 30 分钟
任一即重读；`probe.platform` 永远新鲜读。

### 一之二、candidate.readResume（2026-09-03 下午补，甲方选 B）

建档后脑要先补采简历（规格 §12.16「补采成功才进入正常沟通」），BOSS 没这条能力时每轮"本轮跳过"、
永不进沟通——这是 Mac 首跑前发现的阻断。甲方在「脑侧放宽跳过补采」与「手侧实现 readResume」里选了后者。

| 项 | 做法 |
|---|---|
| 数据源 | 当前会话对象 `conversation$`（MAIN 一次读），打开会话即有，**零点击**；行未 selected 时与 readThread 同款先点开 |
| basic | 姓名 / 年龄 / 工作经验 / 最高学历 / 现居地 / 活跃时间，值空整行省略（标签与智联对齐：脑侧评分把「工作经验」映射成工作年限、「现居地」映射成现居） |
| workExperiences | 每段 `时间 公司 · 职位`，段间空行；**没有描述文字**——面板正文画在 canvas 上（平台事实 §十三） |
| education | 每段 `时间 学校 · 专业 · 学历` |
| expectations | 空数组：`conversation$` 的 toPosition/salaryDesc 是我方沟通职位与薪资，不是候选人期望；候选人期望只在面板 canvas 上 |
| selfEvaluation | 空串（智联缺它时同款） |
| 性别 | 不给：`gender` 是数字码，与文案的对应未真机验证（枚举面事实门） |
| 失效 | 摘要除姓名外全空 → `ELEMENT_UNRESOLVED/afterRecovery`，不返回空简历冒充读到 |

挂账：沉默追问（silenceFollowup）的提示词要「性别」这个基本事实，BOSS 简历里没有，那条链在 BOSS 候选人上会缺参
失败——场景一是回复不是追问，不阻断；性别码对应关系真机验一次即可补上。描述文字与个人优势只能走图
（面板 canvas 同源、像素可导出，识别另立案）。

### 一之三、清场：白名单关闭 + 通用识别留痕（2026-09-03 甲方裁决）

不是新原语，是 `readList(move=reset)`（每轮第一条命令）起手的一趟尽力而为，与智联的
`dismissGlobalPromoModalsBestEffort` 同一位置、同一纪律。

- **关闭只走白名单** `BOSS_DISMISS_WHITELIST`（平台事实 §十三 真机见过、语义确认无害的三处：列表顶营销卡、
  左下客户端下载横幅、右栏意向沟通引导气泡）。每项至多一次 OS 点击、可见且关闭控件在视口内才点，
  点前命中测试只认那个关闭控件；点完条件等待容器消失（封顶 3 秒）。关掉记 `promoModalDismissed`（warn），
  关不掉记 `promoModalDismissFailed`（error），拒点记 `promoModalDismissRefused`；任何失败只留痕不拦。
- **识别面通用**：三处命中测试（页签、会话行、发送钮）被遮时，`found` 带出遮挡物签名——四层类名链、尺寸、
  文本头几个字；`osClickOnce` 据此记 `clickTargetCovered`（warn），签名同时在错误 detail 里。人在诊断台
  看一眼是营销位就往名单加一行；平台新增弹窗的代价是「多失败一轮、加一行」，不是「点错一次」。
- 「不合适」（`.not-fit-wrap .operate-btn`）与一切没见过的叉号永远不在名单里；单测钉住名单内容。
- 未验：三处关掉后刷新会不会再弹。会的话每轮起手都要付三次点击，不会就只有第一轮。

## 二、与智联不同、且是刻意的

- **readList 的未读筛选真实切「未读」小页签并回读**（甲方 2026-09-03 裁定）。切过去未读行浮到
  顶上、处理完离开列表，不需要滚动就能逐条点到；本地 `newMsgCount>0` 只作交叉核对。回读判据：
  小页签 `active` 落在「未读」，再条件等待窗内全部行未读数>0（服务端查询异步回，封顶 20s），
  超时照常返回并留痕（规格 §12.6 零值不得单独导致整窗失败）。
- **职位范围只回读不切**：下拉是两次点击、选项 DOM 没考古；不是「全部职位」按 `GUARD_FAILED/manualOnly`
  停账号等人。
- **move=next 显式拒绝**（`ELEMENT_UNRESOLVED`，retryable=no）：BOSS 尚无滚轮注入，窗口以数据层
  前 32 条为界。脑侧把它按部分遍历收束（见挂账 O4），前 32 行照常处理。
- **readThread 单页交付、不签游标**：已加载的（点开只拉 20 条）既未到顶又未对齐锚尾即失败，不伪造
  `complete`。
- **sendMessage 打字后回读逐字相同才点发送**，回读不同、闸不放行、手服务半途失败一律 `manualOnly`
  ——草稿留在框里，机器没有清空它的手段，人来清。换行换成空格而不是删掉：脑侧 contentHash 把换行
  当空白折叠，删掉会让发后正证永远零命中。
- **截图单帧不滚动**：程序化滚动在 BOSS 上会产生没有滚轮事件的 scroll，留痕形态未验；历史超一屏
  `truncated=true`。
- **未见 bizType 归并 system 并把原始类型进日志**；邀面卡 contentHash 暂按消息身份投影（本地账本锚），
  契约包 1.2 落地后改常量配方。

## 三、出口审查（2026-09-03）的处置

阻断级 B1（发送前最后一道闸缺目标绑定复核）与优化级 O1（正证只认 status 1/2）、O2（未读窗口
条件等待）、O3（换行换空格）已各自一个 commit 修掉。以下挂账：

| # | 内容 | 处置 |
|---|---|---|
| O4 | `move=next` 拒绝让全量扫描每轮以 failed 收场 | 脑侧按部分遍历收束（本批 Go 侧 commit） |
| O5 | `chat.*` 用 `TARGET_NOT_FOUND` 与契约注记「chat.* 不得使用」冲突；智联 11 处同款、脑侧只把它归 skipRound | 既有冲突，沿用实践；待一次裁决勘误注记或补脑侧映射 |
| R1 | 历史>20 条且账本为空的会话读不到顶也对不齐锚 → 每次 `afterRecovery/possible`；脑侧验证读不带锚尾，对这类会话永远失败 | 滚轮注入落地前的已知代价；首验用短会话 |
| R2 | `condition=5` 映射 `expired`；接受/取消各投影成一张 `interviewInvite` 卡 | 底稿 1.5 已批的模型；场景三前再裁 |
| R3 | 入站方向判据 `fromId === conversation.uid` 未真机验证；不成立则入站全归 system、脑失聪 | **首验必看**，第一轮 readThread 即可证伪 |
| R4 | 职位范围不是「全部职位」→ 暂停整个账号 | 行为诚实，知情即可 |
| R5 | sendMessage 预算 60s×2.0 对 OS 打字链偏紧 | 首批真机拿到耗时后按条款同批放大 |
| R6 | requireCurrent 路径与正证循环的 MAIN 读次数 | 读取隐形已实测，登记 |
| R7 | 手服务半途死掉草稿留框、`afterRecovery` 让下轮撞 `USER_ACTIVE` 静默跳过 | 低概率，登记 |
| R8 | 撤回行投影会改 hash，锚尾含它则永不对齐 | 叠加 R1，登记 |

## 四、Windows 真机首验必看项

0. **Chrome 必须在最前面**（2026-09-03 Mac 首跑教训：客户端窗口盖着 Chrome，整轮零点击）。鼠标线移动前先读窗口焦点/最小化/标签激活/页面可见，不在前台就**条件等待人切过来**（每 500ms 复查，封顶 20 秒且不超命令 deadline，进度报「等待 Chrome 切到最前」），等不到才拒并在 detail 里报原因；发键前的前台闸同款等待。点「开始」之后有 20 秒把 Chrome 切到最前、鼠标放到页面上。
1. **入站方向**（R3）：readThread 结果里候选人那句是 `in` 不是 `system`。
2. **切「未读」后的数据层**：小页签翻了之后 `list$` 多久变成未读子集；有没有 `unreadWindowHasReadRows` 留痕。
3. **打开后行是否立刻离开「未读」列表**（openConversation 后置的第二条路）。
4. **侧栏角标零态**：清完未读后节点是消失、清空还是留 0。
5. **发送链耗时**：基线读 + 打字 + 靠近 + 正证，对照 60s×2.0 预算（R5）。
6. **发后 `status`**：新行是否先以非 1/2 出现、多久变 1（O1 的 500ms 是否够）。
7. **营销弹窗**：撞见即记 DOM（清场原语因无事实未写，命中测试遇遮挡只会拒点）。
8. **埋点五项 ★ 仍 0**，`input_count` 增量 = 打字次数；无安全验证跳转。
