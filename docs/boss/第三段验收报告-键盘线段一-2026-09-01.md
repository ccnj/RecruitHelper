# 第三段验收：键盘线段一（macOS，2026-09-01）

出口是「在 macOS 上把一句中文打进 BOSS 的输入框」。**达成。**

一句话：**链路里除自研 TIP 之外的每一环都通了，而 TIP 只能在 Windows 上验。**

## 一、真机结果

```
outcome    typed
keys       82          82 次按键
tries      1           排版一次就中
planMs     10ms
lagMaxUs   5839us      注入滞后最大 5.8 毫秒
matched    False
elapsedMs  8035ms

点前 焦点=在 窗口=在前台 矩形=810x126
排版 1 次重采 7 词 10ms
发了 82 次按键 滞后最大 5839us
回读 不同：期望 12 字、实得 12 字
```

### 那一个字的差别恰好是最好的证据

```
期望   你好，方便加个微信聊聊吗
实得   你好，方便价格微信聊聊吗
                ^^^^
```

`加个` → `价格`。**两个都是 `jiage`**，系统输入法选了另一个候选词。

七个词逐个看：

| 词 | 结果 | 说明 |
|---|---|---|
| 你好 | ✓ | 拼音切分与上屏键都对 |
| ， | ✓ | 标点走 direct 键入 |
| 方便 | ✓ | |
| 加个 | **✗ 价格** | 同音异形，候选词选错 |
| 微信 | ✓ | |
| 聊聊 | ✓ | **上游点名的那个不稳定词**（liaoliao 时而出「了了」），这次对了 |
| 吗 | ✓ | |

**错的方式比错本身重要。** 如果拼音切分错了，字数不会是 12 对 12；如果上屏键错了，
会有拼音字母残留在框里；如果 `ITfComposition` 周期没走完，网页一个 keydown 都收不到。
这些全对，**只有候选词那一层不同**——而候选词正是自研 TIP 存在的唯一理由。

量级也对得上：上游实测借来的微软拼音 36 个 IME 段错 3 个（8%），我们 7 词错 1 词（14%）。

## 三、两个要记的数

**一、`lagMaxUs = 5839`（5.8 毫秒）。** 上游在 Windows 上量到 0.79~2.49ms，我们差一个
量级。这与鼠标线当初的发现一致：macOS 有 OS 级调度抖动，`LockOSThread` 压不住。
打字的键间隔是 80~300ms，5.8ms 占 2~7%，不致命——**但这个数必须在 Windows 上重量**，
那才是判据。

**二、`background.js` 从 963KB 涨到 1.6MB。** `pinyin-pro` 那笔账在 `bossOsType` 调
`planType` 之后付了（此前整条 import 链被 tree-shake）。冷启动实测：首次 import
含词典初始化 26.5ms、第一次 compose 10.9ms、第二次 0.6ms。SW 靠心跳常驻，一个浏览器
会话只付一次。

## 四、准备冒烟时发现并修掉的一个真缺陷

**键盘没有鼠标那道「零观测」闸。**

鼠标那半有个天然的：页面没观测到 mousemove，就说明光标不在页面上，拒绝。键盘是
**盲发**——发完才回读。而 `document.activeElement === 输入框` 只说明**页面内部**的焦点
在那儿：Chrome 退到后台时它照样为真，可 `CGEventPost` / `SendInput` 打的是**最前台的
那个窗口**。

少了这道闸，Chrome 不在前台时这条命令会把拼音字母敲进用户正在看的别的应用——终端、
编辑器，什么都可能。判据用 `document.hasFocus()`（标准 DOM API，只在文档所在窗口是
系统活动窗口时为真），放在**发键之前现读**，不用开头那次的值：中间可能刚做过一次
OS 点击拿焦点，而点击本身会改变哪个窗口在前台。

**它是在发出第一条命令之前拦住的，不是事后补的。**

## 五、路上被门禁拦下的两次（都拦对了）

**一、适配器能力名单。** 那条用例写死「只有两条（probePlatform、osProbe）」，依据是
「坐标被证明对之前不实现任何真业务原语」。加 `osType` 时它红了。**没有默默把数字加一**
——名单变长的理由写进了用例：坐标已由 08-30 四趟真机证明，`osType` 是键盘线出口里
明列的一条；而且三条仍全是 `debug.*`，**BOSS 上至今没有任何真业务原语**。

**二、`composer.empty`。** 第二次派发时输入框里还留着第一趟打的字，当场拒绝。
那道闸与发送原语用的是同一个，不为调试放宽。

## 六、一个从上游带回来的收获

本仓库实测「好的」40% 排不出来、「嗯嗯」100% 排不出来，报给 hiBoss 后查出根因**比
「阈值太严」深得多**：`localCheck` 抄 BOSS 判据时把**前置门丢了四处**，于是我们在
平台根本不评估的区间里否决计划。

铁证是上游那两份真人基线自己都过不了本地预检（Windows 真人卡在
`quorble(keydurations) 0.354 > 0`）——**判据严到把真人判成机器**。

同批还修掉一个我方没发现的静默 bug：`pinyin-pro` 给「嗯」的 `ng` 是**词典注音**，
真人打的是 `en`。排成 `KeyN,KeyG` 之后自研 TIP 走 `commit(word)` 直接上屏、屏幕上
完全看不出问题，**一旦回落到系统输入法就上不了屏**——而那正是我们的 macOS 开发环境。

修完（上游 `84c1a22`）：全部文案 0/30 失败，且**重采次数普遍下降**（长文案从 4.2 次
降到 1 次）。只放宽闸的话失败会变少但重采不会变——判据对了。

## 八、追记（2026-09-01 晚）：英文段上游已通，本仓库已同步至 `70de0a8`

本报告 §七 原本把「英文字母打不出来」列为限制真实文案的真问题。上游当天解决了，
**而且解法比预期干净：不需要「切输入法模式」那个状态机。**

### 关键在于前提变了

原来拒绝英文的理由是「英文字母需切换输入法模式」——那个理由的前提是**借来的**输入法：
打英文要切模式，而「输入法状态」是个状态机，当时判定不值得建。

自研 TIP 落地之后前提没了：**上屏什么由词表指定**，于是 `Base` 就是一个普通的 ime 段，
键序 `b,a,s,e` + 一个上屏键，上屏的文本就是这个词。**TIP 一行没改**，改的全在排版器。

```
岗位是Java后端，Base深圳，方便聊聊吗？
  → 岗位 是 Java 后端 ，(直) Base 深圳 ，(直) 方便 聊聊 吗 ？(直)

"Java"  direct=false  splits=[]  KeyJ,KeyA,KeyV,KeyA,Digit2
```

四个刻意的取舍（都已在 `unit.mjs` 钉住）：

| 取舍 | 理由 |
|---|---|
| **键序全小写，不排 Shift** | 大写由上屏的词带出来。现有 shift 时序取自打全角标点的样本（句读位置的动作），套到词中间会把 `B→a` 顶到几百毫秒 |
| 上屏键沿用中文段那张 | 英文词在候选里排第几本来就浮动，固定一个键反而是在编确定性 |
| 无音节分隔 | 真输入法打英文时也不画那个撇号 |
| **不排回车上屏** | 见下 |

### 「不排回车上屏」那条论证值得抄下来

真输入法里回车上屏字母原文，是英文段最常见、也是量过最像真人的一条打法。上游放弃了它：

> TIP 现在无条件透传回车，而「本该被吃的键透传出去」是一条**正常代码路径**（组字失败时
> `OnKeyDown` 会主动改口透传；宿主也会掐断组字）。那一下回车漏出去是**把半截话发给
> 候选人**，空格漏出去只是多一个空格。**失败模式不对称，所以这条不做。**

放弃一个更像真人的做法，理由不是实现麻烦，是**失效方向**。

### 两条对我方的直接影响

**一、英文段在 macOS 上验不了「打对了」。** 这条设计的前提是 TIP 决定上屏内容。
macOS 走系统输入法，`b,a,s,e` 会被当拼音处理，上屏的是汉字——**不是「选错候选词」，
是结构性不同**。macOS 开发环境从此只能验英文文案「发出去了」，验不到「打对了」。

**二、数字那个洞是活的，而我方文案一定有数字。** 上游自记的账：真微软拼音下数字走
`insertText`(type1)，而 TIP 的 `classify` 把空格、数字、OEM 标点键一律当上屏键吃掉、
走 composition(type2)。**离线判定算的分布不是真机那一个**，正是标点段踩过的同一个坑；
2026-08-23 那份真机计划里一个直接数字段都没有，所以**至今没被真机照过**。

```
3年经验可以吗   → 3(直) 年 经验 可以 吗
薪资20到30万    → 薪资 2(直) 0(直) 到 3(直) 0(直) 万      ← 「20」还被拆成两段
```

根治要给管道协议加「这个词透传、别吃」的标记，上游明说不在那一轮。**段二真机要专门
覆盖含数字的文案。**

### 还有一条别顺手做的

上游在放行英文时特意在原地留了说明：**半角标点留在拒绝表里，理由和当初的英文一模一样，
别看见英文能过了就顺手把它也放进去。** 两者的理由现在已经不同——英文那个理由（要切模式）
随 TIP 作废了，半角标点的是真实行为差异（真输入法直接上屏，TIP 会当上屏键吃掉）。
本仓库为此单立了一条用例钉住「半角仍拒绝」。

### ⚠ 英文段零真机

上游那一轮全部是离线证据（真 wasm 跑 compose 16 项全 PASS、连发 30 条零上报）。

**要量的只剩一条，而且不是 keyCode（2026-09-01 更正）。** 本文初稿照抄了 `ca82931`
列的三个观察项，但上游在下一个提交 `70de0a8` 就把它们过了一遍——**判据是「量出来的
结果会不会改变我们的动作」**：

| 原观察项 | 上游裁决 |
|---|---|
| 候选窗第几个是 `base` | **砍掉**。位置本来就浮动，量出一个也固定不下来；加权随机的 `commitKeys` 正是对这件事的建模 |
| 回车上屏的是不是字母原文 | **砍掉**。是，但这从来不是决策输入——不做回车的理由是**失败模式不对称**，量出「是」也不做 |
| 数字键 keyCode 51 还是 229 | **留下，但问法要改**（见下） |

数字那条原来问错了两处：

**一、真人那一半早就量过了**，不该再占真机时间。2026-08-21 基线 416 个 keydown 里
390 个是 `Process`，其余是 Backspace / Shift / 数字——**真微软拼音不吃数字键**。
未知的是**我们自己 TIP 那一半**：跑我们的 TIP 时一个直接数字段实际展开成什么。

**二、只看 keyCode 不够**，那只是入口。要对的是整条流：离线说一条
`input(insertText, isComposing=false)`，读代码推断说两对 update+input 加一条
`compositionend`——**差的是 `rhythms` 项数与 `typingFragment` 形状，而被判定的正是它们**。
上游明说「事件流在这仓库被真机打脸过两次，推断不算数」。

改后的量法：排一份带数字的计划（如「岗位薪资20到35，13薪」），跑完拿事件流跟 `synth`
预测对账，走已有的 `verify-capture` / `roundtrip` 姿势，**不需要新工具**。

**英文段本身仍是零真机**，那条 ⚠ 只活在 `ca82931` 的 commit message 里、没进上游的
HANDOFF——顺手一起量。
