# 第三段验收：键盘线段一（macOS，2026-09-01）

出口是「在 macOS 上把一句中文打进 BOSS 的输入框」。**达成。**

一句话：**链路里除自研 TIP 之外的每一环都通了，而 TIP 只能在 Windows 上验。**

## 一、真机结果

```
outcome    typed
keys       82          82 次按键
tries      1           排版一次就中
planMs     10ms
lagMaxUs   5839us      注入滞后最大 5.8 毫秒
matched    False
elapsedMs  8035ms

点前 焦点=在 窗口=在前台 矩形=810x126

发了 82 次按键 滞后最大 5839us
回读 不同：期望 12 字、实得 12 字
```

### 那一个字的差别恰好是最好的证据

```
期望   你好，方便加个微信聊聊吗
实得   你好，方便价格微信聊聊吗
                ^^^^
```

`加个` → `价格`。**两个都是 `jiage`**，系统输入法选了另一个候选词。

七个词逐个看：

| 词 | 结果 | 说明 |
|---|---|---|
| 你好 | ✓ | 拼音切分与上屏键都对 |
| ， | ✓ | 标点走 direct 键入 |
| 方便 | ✓ | |
| 加个 | **✗ 价格** | 同音异形，候选词选错 |
| 微信 | ✓ | |
| 聊聊 | ✓ | **上游点名的那个不稳定词**（liaoliao 时而出「了了」），这次对了 |
| 吗 | ✓ | |

**错的方式比错本身重要。** 如果拼音切分错了，字数不会是 12 对 12；如果上屏键错了，
会有拼音字母残留在框里；如果 `ITfComposition` 周期没走完，网页一个 keydown 都收不到。
这些全对，**只有候选词那一层不同**——而候选词正是自研 TIP 存在的唯一理由。

量级也对得上：上游实测借来的微软拼音 36 个 IME 段错 3 个（8%），我们 7 词错 1 词（14%）。

## 三、两个要记的数

**一、`lagMaxUs = 5839`（5.8 毫秒）。** 上游在 Windows 上量到 0.79~2.49ms，我们差一个
量级。这与鼠标线当初的发现一致：macOS 有 OS 级调度抖动，`LockOSThread` 压不住。
打字的键间隔是 80~300ms，5.8ms 占 2~7%，不致命——**但这个数必须在 Windows 上重量**，
那才是判据。

**二、`background.js` 从 963KB 涨到 1.6MB。** `pinyin-pro` 那笔账在 `bossOsType` 调
`planType` 之后付了（此前整条 import 链被 tree-shake）。冷启动实测：首次 import
含词典初始化 26.5ms、第一次 compose 10.9ms、第二次 0.6ms。SW 靠心跳常驻，一个浏览器
会话只付一次。

## 四、准备冒烟时发现并修掉的一个真缺陷

**键盘没有鼠标那道「零观测」闸。**

鼠标那半有个天然的：页面没观测到 mousemove，就说明光标不在页面上，拒绝。键盘是
**盲发**——发完才回读。而 `document.activeElement === 输入框` 只说明**页面内部**的焦点
在那儿：Chrome 退到后台时它照样为真，可 `CGEventPost` / `SendInput` 打的是**最前台的
那个窗口**。

少了这道闸，Chrome 不在前台时这条命令会把拼音字母敲进用户正在看的别的应用——终端、
编辑器，什么都可能。判据用 `document.hasFocus()`（标准 DOM API，只在文档所在窗口是
系统活动窗口时为真），放在**发键之前现读**，不用开头那次的值：中间可能刚做过一次
OS 点击拿焦点，而点击本身会改变哪个窗口在前台。

**它是在发出第一条命令之前拦住的，不是事后补的。**

## 五、路上被门禁拦下的两次（都拦对了）

**一、适配器能力名单。** 那条用例写死「只有两条（probePlatform、osProbe）」，依据是
「坐标被证明对之前不实现任何真业务原语」。加 `osType` 时它红了。**没有默默把数字加一**
——名单变长的理由写进了用例：坐标已由 08-30 四趟真机证明，`osType` 是键盘线出口里
明列的一条；而且三条仍全是 `debug.*`，**BOSS 上至今没有任何真业务原语**。

**二、`composer.empty`。** 第二次派发时输入框里还留着第一趟打的字，当场拒绝。
那道闸与发送原语用的是同一个，不为调试放宽。

## 六、一个从上游带回来的收获

本仓库实测「好的」40% 排不出来、「嗯嗯」100% 排不出来，报给 hiBoss 后查出根因**比
「阈值太严」深得多**：`localCheck` 抄 BOSS 判据时把**前置门丢了四处**，于是我们在
平台根本不评估的区间里否决计划。

铁证是上游那两份真人基线自己都过不了本地预检（Windows 真人卡在
`quorble(keydurations) 0.354 > 0`）——**判据严到把真人判成机器**。

同批还修掉一个我方没发现的静默 bug：`pinyin-pro` 给「嗯」的 `ng` 是**词典注音**，
真人打的是 `en`。排成 `KeyN,KeyG` 之后自研 TIP 走 `commit(word)` 直接上屏、屏幕上
完全看不出问题，**一旦回落到系统输入法就上不了屏**——而那正是我们的 macOS 开发环境。

修完（上游 `84c1a22`）：全部文案 0/30 失败，且**重采次数普遍下降**（长文案从 4.2 次
降到 1 次）。只放宽闸的话失败会变少但重采不会变——判据对了。
