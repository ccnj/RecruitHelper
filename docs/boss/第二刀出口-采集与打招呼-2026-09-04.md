## 一、事实到设计的六条推论

1. **身份一条线**：推荐卡 `geekId / geekSource / encryptGeekId` 与 IM 侧 `uid / friendSource / encryptUid` 逐字相等。`platformUserRef = String(geekId)`（与场景一 readList 的 uid 同空间），`conversationRef = "{geekId}-{geekSource}"` 在首击当场就能算出并随 `sendGreeting` data 返回；脑侧晚到回绑（`LateBindGreetedConversations`）照旧可用但不再是必经之路。`positionRef = encryptJobId`（职位选择器 `.job-item[value]` 与卡片同值；平台自己的聊天参数也用它）。
2. **首击是零正文的不可逆动作**：建关系（列表出现该人、按钮变「继续沟通」、IM 出现会话），平台没有代发任何招呼语；正文要人（或键盘线）在快捷窗或 IM 页打字发送。所以「招呼」在 BOSS 上天然是两步，且**第一步本身已经是候选人可见动作**（BOSS 会通知候选人被打招呼，候选人端形态未验）。契约 §4.3 对 `sendGreeting` 的成功定义正是「关系未建立→关系已建立」，正文行只是丰富正证——这条定义在 BOSS 上比在智联上更贴。
3. **推荐页与 IM 页不共用内存态**：快捷窗有自己的 `geek` 与消息数组（同形），但顶层没有 `list$/conversation$`。要么给快捷窗另写一套读/写/正证（编辑器 `#boss-chat-global-input`、发送 `.submit`、消息从 `message-component.message` 读），要么把正文发送交给场景一在 IM 页的 `chat.sendMessage`（全套安全轨已在）。左栏 SPA 切到 IM 页再回来推荐列表原样保留，所以后者不破坏推荐流。
4. **筛选只有非 VIP 组可用**：年龄（滑块，只能拖）、性别、活跃度、人才范围（近期未看 / 同事已聊）整块被 `.vip-mask` 盖住（`paid=false`）。契约六组里只有求职状态 / 学历能按图索骥（经验、薪资契约里没有）。脑侧 `m6_sourcing_batch.go:158` 要求回读 `Filters` 与配置 `reflect.DeepEqual`，BOSS 上任何 VIP 组非「不限」的配置都会让批次停在 filtersApply。
5. **简历只有摘要**：详情正文在嵌套 iframe 的 canvas 上，DOM 零文本；卡片 `geekInfo` 已含 `geekDesc / geekEdus / geekWorks / viewExpect / ageDesc / geekDegree / geekWorkYear / salary`，详情右栏只多一份「经历概览」。打开详情除了留下「看过」记录什么都不多给。
6. **推荐页整张在 iframe 里**：定位、内存读、OS 坐标、落点观察都要过 `contentDocument`（探针三条修复已合 main：e807499 / 21d5b04 / 61846d5），生产原语照同一口径写；快捷窗盖住卡片按钮列，每次用完必须关。

执行方原推荐方案二（契约成功语义本就是关系跃迁、正文复用场景一安全轨、Mac 可验到底）。**甲方裁决取方案一**：正文必须在推荐页的快捷聊天窗里发，与真人操作同路（真人不会绕去 IM 页）；第一版从简，脑与契约零改动。执行方据此把方案一的部分失败形态钉死如下，不再含糊：

- 首击未确认（`isFriend` 数秒内没翻、按钮没变）：不进快捷窗、不打字，result `failed`、`sideEffect=possible`，交脑验证读。
- 首击已确认、快捷窗打不开 / 打字回读不等 / 发送键点不到：**不重试、不补动作**，result `failed`、`sideEffect=possible`，detail 写明「关系已建立，正文未发出」并留手侧日志；脑的验证读会以卡片「关系已建立」自动补记 ok（契约 §9.4.2 正是这么定的），候选人这一次只收到平台的「打招呼」通知、收不到正文，24 小时后由既有催问链接上。这是甲方知情接受的代价，不为它加机制。
- 发送键已点、快捷窗消息数组没读到我方行：`failed`、`sideEffect=possible`，同上交验证读；绝不第二次点发送。
- 全部成功：`ok`，data 带 `conversationRef`（首击当场可算）与 `contentHash = HashText(正文)`（与脑侧 `SendFingerprint` 同配方），最后关窗（关不掉只留痕）。

## 三、改动面（方案二口径；方案一另算）

### 3.1 手侧（`plugin/src/program/platform/boss.ts`）

- 基础：推荐页 iframe 感知的定位/内存读/点击/滚动 helper（同探针口径：`contentDocument`、偏移、观察器）；`verifiedBossTab` 复用。
- `job.readPublishedList`：左栏「职位管理」→ iframe `/web/frame/job_v2/list` → 逐行 `.job-name` + `.status-box` 文案；分区语义按页签文案（开放中 / 待开放 / 审核未通过 / 已关闭），脑侧「在线中」口径在脑侧映射到「开放中」（待裁决第 4 件）。
- `candidate.selectSourcingPosition`：单职位时核 `.job-item.curr[value]` 与 label；多职位时展开 `.ui-dropmenu` 点 `.job-item`（切换后置未验，后置项）。
- `candidate.applySourcingFilters`：点「筛选」→ 逐组点 `div.option` → 「确定」→ 重开回读 → 再点「筛选」收起；VIP 锁定组只回读不点。
- `candidate.readSourcingWindow`：从 `CardList.pageList` 按 DOM 顺序取 `geekId`（1～32）；`move=next` 用 `debug.osScroll` 同款滚 iframe 文档一屏；`reset` 滚到顶；`finished=true` 只留观测。
- `candidate.readSourcingTargetResume`：按 `geekId + encryptJobId` 在 `pageList` 唯一匹配，从 `geekInfo` 投影五分区；是否开详情见待裁决第 6 件。
- `chat.sendGreeting`（方案一，一条做完）：目标绑定（`pageList` 唯一 + `.card-inner[data-geekid]` 相等）→ 快捷窗若开着先关 → 点前读 `isFriend=0` 且按钮文本「打招呼」→ 证词 → `osClickOnce`「打招呼」→ 轮询同卡 `isFriend` 0→1 / 按钮「继续沟通」（首击正证；没翻即止）→ `osClickOnce`「继续沟通」→ 等顶层 `chat-global-conversation` 出现且其 `geek.uid` 等于目标 → 编辑器 `#boss-chat-global-input` 按 2026-09-03 裁决清空再打（键盘线 `osType` 同款：真实按键全选删除、回读为空、逐字打入、回读逐字相等；焦点判据 `document.hasFocus()` 现读，必要时先点编辑器）→ 最后一道闸：编辑器文本 == 正文、发送键 `.submit-content .submit` 可点 → 证词更新 → `osClickOnce`「发送」→ 轮询快捷窗消息数组出现我方文本行（`isSelf`、正文相等、`time` 不早于派发）→ 关窗 `.chat-global-top .iboss-close`（关不掉只留痕）→ data `{platformUserRef, positionRef, conversationRef, contentHash=HashText(正文), observedAt}`。全程两个不可逆点击（首击、发送），证词紧贴各自的点前一刻；相邻动作照既有 1～1.8 秒节奏。
- `chat.readGreetingOutcome`：只读推荐页同卡（`pageList` 按 `geekId` 找 → `isFriend` / 按钮文本）；找不到卡即 `confirmed=false`（不切 IM 页，第一版不加）。
- 快捷窗读写 helper：顶层 `chat-global-conversation` 的定位、`chat-global-message-list` 消息数组读（从各 `message-component.message` 取，形状同 IM）、编辑器与发送键定位；与 IM 页那套分开写，不混用。
- 能力表与声明面：unit.mjs「BOSS 表恰为 N 条」+7；纯函数用例（五分区投影、筛选映射、pageList↔DOM 一致性、快捷窗消息行匹配）。

## 四、七件事（1、5、7 已定，2、3、4、6 待批）

1. **原语切法**：**已定方案一**（甲方 09-04 夜：正文在快捷窗发，与真人同路；第一版从简，脑与契约零改动）。
2. **筛选 VIP 锁的处置**：执行方推荐**运营侧约定**——BOSS 职位的「候选人筛选」文档年龄/性别/活跃/人才范围一律配「不限」，手侧对 VIP 组只回读不点，回读恒「不限」与配置相等，脑侧 `DeepEqual` 自然过；零代码。备选是契约增量（`applySourcingFilters` data 加 `unsupported` 维度列表、脑侧只比支持的维度），日后账号买了 VIP 再立。代价：BOSS 上年龄不控（评分提示词见得到年龄，靠提示词）、性别只靠脑侧男性比例闸、活跃度不控。
3. **`platformUserRef = String(geekId)`、`positionRef = encryptJobId`**：与 IM 侧 uid 同空间；`encryptJobId` 是平台自己的职位绑定键。
4. **职位在线判据文案**：BOSS「开放中」= 契约/脑侧「在线中」。映射放手侧（投影成「在线中」）还是脑侧（按平台配一张表）——执行方推荐手侧投影，脑保持平台无关。
5. **`readGreetingOutcome` 是否切 IM 页读列表行**：**已定不加**（甲方 09-04 夜：第一版简单一点）。第一版只读推荐卡；卡不在即本轮未取得正证，按既有 suspect 路径。代价：批内推荐页被刷新后的未确认首击会落人工票，频率待真机。
6. **`readSourcingTargetResume` 不开详情**：详情正文是 canvas、右栏只多一份经历概览，卡片 `geekInfo` 已够投影五分区；不开详情就没有「看过」副作用、也省 2 秒停留。契约 data 形状不变，`platformSideEffect` 可按实际声明。
7. **首击后候选人先开口的处理**：随方案一消解——正文在首击后数秒内于同一原语发出，没有窗口可言；候选人若恰在那几秒插话，快捷窗消息数组会多一条入站行，只作观测（`expectedTail` 观测模式同款），正文照发。

## 五、出口四项

### 1. 本轮最小可交付

手侧七条原语 + iframe / 快捷窗 helper 落地，typecheck / unit / build 绿，Windows 交叉编译过；脑与契约零改动。真机（data-boss4，职位 178）：完整流程开始 → 读职位管理页 → 单职位直通 → 筛选（非 VIP 组，配置全「不限」）→ 首窗 15 张 → 目标简历投影 → 评分筛选 → 首击 2～3 人各恰一次 → 快捷窗打字发送 → 账本 `greeted` + `conversationRef` 当场绑定 + 正文行可见。Mac 只能验到快捷窗打字前（系统输入法不精确），发送与正证在 Windows（TIP）验；零 suspect、埋点「踩雷」零新码。

### 2. 必须立即阻断的损害

- **错靶**：首击前按 `geekId + encryptJobId` 在 `pageList` 唯一匹配并核 `.card-inner[data-geekid]`；点前最后一次命中测试核按钮文本「打招呼」；快捷窗或任何顶层浮层盖住时在顶层 `elementFromPoint` 一层就拒。
- **二次首击 / 二次发送**：证词分别紧贴首击与发送的点前一刻；点前读到 `isFriend=1` 或「继续沟通」即不再首击；发送键至多点一次；脑账本 idemKey 照旧。
- **发错正文 / 发错窗**：打字后回读逐字相等才允许点发送；快捷窗 `geek.uid` 必须等于目标，不等即止。
- **跨职位重复**：脑侧建档查重按人；首窗 `isFriend=1` 投影为 `contactState=established`，永不授权 `sendGreeting`。
- **推荐流中断**：批内不重载插件、不刷新页面；快捷窗每次关闭；`readGreetingOutcome` 切 IM 页只用左栏 SPA。

### 3. 允许重试或人工兜底的失败

- iframe 未挂、列表空、卡片 vm 未挂、滚不动、面板未展开、职位管理页未就绪 → 干净失败 `afterRecovery`，脑侧既有批前重试 / 跳过职位链。
- VIP 锁定筛选组 → 不点、回读「不限」、留痕；不失败。
- 首击已点但 `isFriend` 数秒内没翻 → 未确认 → `readGreetingOutcome` 验证读（推荐卡 → IM 行）→ 仍读不到才 suspect 人工；绝不第二次点。
