## 先记住四个「看起来成功了其实没有」

这四条是整份单子里最值钱的部分。它们的共同点是：**正常路径与失败路径在屏幕上长得一模一样**，
不专门去查就查不出来，而查错方向会白跑一整趟。

| 现象 | 真相 | 唯一判据 |
|---|---|---|
| `regsvr32` 弹「成功」、输入法出现在列表里、**能切过去、能打字** | COM 键名若不带花括号，`CoCreateInstance` 永远失败，**DLL 从来没被加载过** | `tasklist /m hiboss_tip.dll` |
| 「能用它打字」 | **不构成反证**——TIP 没加载时按键落到底层美式键盘，打出来的字母一模一样 | 同上 |
| ~~`matched=false`，以为是"候选词选错了"~~ | ~~可能 TIP 压根没加载~~ **这一条 2026-09-01 已被代码堵掉**，见下 | — |
| 坐标算得对、点下去偏，偏移随缩放率变 | DPI 感知没生效，Windows 对本进程撒谎（`GetCursorPos` 返虚拟化坐标、`SendInput` 被偷偷缩放） | 虚拟桌面报 `2560×1440` 而不是 `1707×960` |
| `SendInput` 返回 0、什么都没发生 | UIPI：目标窗口完整性级别比我们高（浏览器以管理员身份运行） | 两边同权限运行 |

上游原话：**「一旦踩上会先怀疑坐标换算，最后才想到 DPI。」**

### 第三条陷阱已被代码堵掉，但堵法要知道

原本的陷阱是：`matched=false` 有两个输出完全相同的原因——

```
TIP 加载了,但系统/TIP 选了别的词   →  matched=false
TIP 从来没加载,按键落到底层键盘     →  matched=false
```

现在分得开了，因为**管道连接本身就是加载证明**：TIP 的 DLL 跑在 chrome.exe 里才连得上
管道，没加载就没有连接，而**没有连接我方就不打**（`tip_windows.go` 的 `DriveWords`）。
所以那种情况的输出不再是 `matched=false`，而是：

> 等了 8s 没有 TIP 连上来 —— 输入法切到我们这个了吗?Chrome 是在 regsvr32 之后启动的吗?

**`tasklist /m hiboss_tip.dll` 因此降为佐证，不再是唯一判据**——但它仍值得抄，
因为它能分开「DLL 没加载」与「DLL 加载了但管道那半没起来」，两者的提示语一样。
它不占额外往返，跟 `detail` 一起抄即可。

**上面表里的前两条没被堵掉，原样成立**：`regsvr32` 报成功、能切过去、能打字，
这三样都不构成 DLL 被加载的证据。区别只是我们现在不会拿它们当判据了。

## 第 2 段 · 鼠标线首验｜**零新代码** `[我方未验]`

先跑它，理由有三：一行代码不用写；它是鼠标线**唯一缺的验收判据**；坐标链不通的话后面全等着。

       抄下:scale 六位小数、吸到哪一档、每趟的靶点与落点、偏差

### 这一段专门要盯的

**`scale` 不是 1 时才会现形的两个 bug。** hiBoss 踩过：`Piggyback.Seed` 少乘 scale
（150% 下种子偏 227 物理像素）、九点标定混用 CSS 与物理（150% 下每跑丢 2/9 个点）。
上游的结论是**「凡是碰坐标换算的，Mac 上绿了不算数」**。我方 `SeedCalib` 的 Windows
分支（收 pixel 要乘 dpr）**至今只有 macOS 那半被真机验过**。

**`scale` 吸到相邻的错档。** 系统缩放 × 浏览器 zoom 的乘积集合，最近两对相对间距只有
0.444%/0.568%，小于吸附容差 0.5% 的两倍。**吸错了是个精确数字，后面所有自检都会以为它对。**
所以要抄六位小数，不是抄结论。

**`lagMaxUs` 要和 macOS 对照。** mac 上量到 5839us，上游 Windows 是 790~2490us。
Windows 定时精度实际比 macOS 好（无 15.625ms 梳状），如果我们量出来更差，
那是我们的问题不是平台的。

### 做不了：Windows 上没有 TIP 就不打

所以切到微软拼音再点「开始打字」，得到的会是

### 也不必做：那个拆分现在一次跑就有

第 4 段的一次运行会同时给出两半的答案，因为 `detail` 里多了一句 TIP 对账：

| 现场 | 断在哪一半 |
|---|---|
| `按键 0` + 「没有 TIP 连上来」 | TIP 没装上/没切过去/Chrome 启动太早 |
| `按键 82` + 「TIP 上屏 0/7 词」 | 键发出去了，但 TIP 一个词都没提交——TIP 那半 |
| `按键 82` + 「TIP 上屏 7/7 词」+ 回读逐字相同 | ✅ 全对 |
| `按键 82` + 「TIP 上屏 7/7 词」+ 回读不同 | 词提交了却不是这些字——排版/词表那半 |
| `按键 82` + 「上屏 4/7 词」 | 打到一半断了，看流水里最后一段 |

## 第 5 段 · 量埋点｜**整条线的目的**

前四段证明的都是「打得出来」，**这一段才回答「BOSS 认不认」**。用诊断台那个埋点观测页读。

```
□ 5.1  清空埋点 → 只跑注入 → 刷新读
□ 5.2  三类文案分别量(它们走的路不同):
       纯中文   cnTextCount 恒为 0,整族判据不启动
       含英文   [上游零真机] 闸门会开,dwell 的 0.6 开始计数
       含数字   [上游零真机] 离线按 type1 算,真机走 type2
□ 5.3  抄下:za 分布、五项 ★ 计数器、上报码
```

### 三条会改变结论的告诫

**一、`cnTextCount` 恒为 0 不是安全边际，是运气。** 只要有一个字符不经输入法直接落进去
（半角标点、emoji、粘贴、英文），8 项计数器全部醒过来。**我们目前的余量主要来自这道闸。**

**二、Windows 真人 dwell 的 quorble 是 0.354，不是 0。**「真人天然落在安全区」是
**纯 macOS 结论**；短消息 n=20 的窗口有 **11.4%** 概率越过 0.6。

**三、数字那条是唯一值得占真机时间的观察项**，而且**要量的不是 keyCode**：
真人那一半 2026-08-21 已量过（真微软拼音不吃数字键），未知的是**我们自己 TIP 那一半**——
它的 `classify` 把数字当上屏键吃掉走 composition(type2)，而真输入法是 type1。
要对的是整条事件流（`rhythms` 项数与 `typingFragment` 形状），不是入口那个数。
排一份带数字的计划（如「岗位薪资20到35，13薪」），跑完拿事件流跟预测对账。

## 不在这份单子里的两件事

1. **TIP 怎么装到客户机。** 本单只管开发机上手动装。真交付要怎么办（`regsvr32` 要管理员，
   而交付方式是整包携带 + 首次人工远程协助）——**那是键盘线能不能落地的最终关卡**，
   但不该卡住这一趟。
2. **注入中途被打断没有保护。** 切窗口、弹窗抢焦点、授权被撤，都会留下半句话。
   上游从 2026-08-21 就记着，至今未做。我方的 `/handinput/type` 有「半途失败放开按住的键」，
   但那只管键盘状态，不管**已经打进去的半句话**。
