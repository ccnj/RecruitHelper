# Windows 真机操作单：键盘线（2026-09-01）

那台机器不在手边，**每一趟都贵**。

> ## ⚠ 2026-09-01 甲方裁决：本单降级为「失败时的排查树」，不是执行顺序
>
> **一次跑到底，不做前置校验；跑不通再拆开定位。**
>
> 依据有二。其一，大部分环节已经验过：鼠标链上游 2026-08-27 在 Windows 上跑过两趟
> （100% 与 150% 两档），TIP 端到端上游 2026-08-23 跑通（6 词 6/6 上屏，滞后均值
> 0.001ms），我方 macOS 那半 2026-09-01 打进了真实 BOSS 输入框。
>
> 其二——**`debug.osType` 的 `detail` 字段本身就是分段报告**：
>
> ```
> 点前 焦点=在 窗口=在前台 | 取焦点 clicked | 排版 1 次重采 7 词
> | 发了 82 次按键 | 回读 不同：期望 12 字、实得 12 字
> ```
>
> 分阶段的主要价值是隔离故障，而这个字段已经隔离好了。把一次往返拆成五次，
> 换来的信息它本来就给。
>
> **所以：下面的分段照旧有用，但用法是「detail 说停在哪一段，就翻到那一段照着查」。**
>
> 有一类失败 `detail` 给不出——`SendInput` 被 UIPI 静默拦截时返回 0 而不报错，
> 那会产生**假成功**（报「发了 82 次按键」而实际一个都没发）。已确认我方鼠标侧
> 检查了返回值（`inject_windows.go:158`），键盘侧实装时照搬同一检查。
> 假成功比假失败贵得多——它把人引向错误方向。

体例照 hiBoss `HANDOFF.md:831-864` 的鼠标线操作单——那份是他们排过多趟才定下来的，
TIP 一直没有等价物，这份是串出来的。

> **出处约定。** 标 `[hiBoss 已验]` 的是上游在 Windows 11 / Chrome 151 真机上跑过的；
> 标 `[我方未验]` 的是本仓库写了但从没在 Windows 上跑过的代码。两者的失败含义不同：
> 前者失败多半是环境，后者失败多半是我们的 bug。

## 先记住四个「看起来成功了其实没有」

这四条是整份单子里最值钱的部分。它们的共同点是：**正常路径与失败路径在屏幕上长得一模一样**，
不专门去查就查不出来，而查错方向会白跑一整趟。

| 现象 | 真相 | 唯一判据 |
|---|---|---|
| `regsvr32` 弹「成功」、输入法出现在列表里、**能切过去、能打字** | COM 键名若不带花括号，`CoCreateInstance` 永远失败，**DLL 从来没被加载过** | `tasklist /m hiboss_tip.dll` |
| 「能用它打字」 | **不构成反证**——TIP 没加载时按键落到底层美式键盘，打出来的字母一模一样 | 同上 |
| `matched=false`，以为是"候选词选错了" | **可能 TIP 压根没加载**。两种情况的输出**一模一样** | 同上 |
| 坐标算得对、点下去偏，偏移随缩放率变 | DPI 感知没生效，Windows 对本进程撒谎（`GetCursorPos` 返虚拟化坐标、`SendInput` 被偷偷缩放） | 虚拟桌面报 `2560×1440` 而不是 `1707×960` |
| `SendInput` 返回 0、什么都没发生 | UIPI：目标窗口完整性级别比我们高（浏览器以管理员身份运行） | 两边同权限运行 |

上游原话：**「一旦踩上会先怀疑坐标换算，最后才想到 DPI。」**

### `tasklist /m` 不是前置校验，是**读结果的一部分**

一次跑到底之后，`matched=false` 有两个完全不同的原因，而它们的输出**完全相同**：

```
TIP 加载了,但系统/TIP 选了别的词   →  matched=false
TIP 从来没加载,按键落到底层键盘     →  matched=false
```

不查这一条，失败时会往「候选词、词表、管道」方向查，而真因可能在 `regsvr32` 那一步。
它不占额外往返——跟 `detail` 一起抄下来即可。

## 第 0 段 · 出发前（在 mac 上做完）

```
□ 本仓库门禁全绿：go vet / go test ./client/... / codegen -check / 插件 typecheck + 单测
□ CGO_ENABLED=0 GOOS=windows go build ./client/service   通过
□ 打一个 Windows 客户端安装包（整包携带插件）
□ 编 TIP：cd hiBoss/lab/engine/tip
          cargo build --release --target x86_64-pc-windows-gnu
          → target/x86_64-pc-windows-gnu/release/hiboss_tip.dll
```

**产物不在 git 里。** hiBoss 的 `.gitignore` 排除了 `tip/target/` 与 `inject{,.exe}`，
clone 过去必须自己重编。工具链：`rustup target add x86_64-pc-windows-gnu` +
`brew install mingw-w64`。

两个不能省的配置（都在 `hiBoss/lab/engine/tip/.cargo/config.toml`，已经配好，别动）：

- **linker 用 mingw-w64 的 gcc** —— rustup 给 windows-gnu 只自带 `crt2.o`/`dllcrt2.o`，没有完整 sysroot
- **`-C target-feature=+crt-static`** —— 不静态链接的话产物依赖 `libgcc_s_seh-1.dll` 等，
  而这个 DLL 要被加载进 chrome.exe，**那里找不到这些依赖，加载直接失败**

## 第 2 段 · 鼠标线首验｜**零新代码** `[我方未验]`

先跑它，理由有三：一行代码不用写；它是鼠标线**唯一缺的验收判据**；坐标链不通的话后面全等着。

```
□ 2.1  DPI 感知自检
       判据:虚拟桌面报 2560×1440(按实际分辨率),不是 1707×960
       **不过就地停** —— 后面所有坐标数据都不可信

□ 2.2  osProbe viewportSpread
       判据:两趟散开之后标定收敛
       抄下:scale 六位小数、吸到哪一档、每趟的靶点与落点、偏差

□ 2.3  osProbe reversibleToggle
       判据:命中靶子、isTrusted=true、后置状态翻转且可逆
       抄下:lagMaxUs
```

### 这一段专门要盯的

**`scale` 不是 1 时才会现形的两个 bug。** hiBoss 踩过：`Piggyback.Seed` 少乘 scale
（150% 下种子偏 227 物理像素）、九点标定混用 CSS 与物理（150% 下每跑丢 2/9 个点）。
上游的结论是**「凡是碰坐标换算的，Mac 上绿了不算数」**。我方 `SeedCalib` 的 Windows
分支（收 pixel 要乘 dpr）**至今只有 macOS 那半被真机验过**。

**`scale` 吸到相邻的错档。** 系统缩放 × 浏览器 zoom 的乘积集合，最近两对相对间距只有
0.444%/0.568%，小于吸附容差 0.5% 的两倍。**吸错了是个精确数字，后面所有自检都会以为它对。**
所以要抄六位小数，不是抄结论。

**`lagMaxUs` 要和 macOS 对照。** mac 上量到 5839us，上游 Windows 是 790~2490us。
Windows 定时精度实际比 macOS 好（无 15.625ms 梳状），如果我们量出来更差，
那是我们的问题不是平台的。

### 一条死规定

**必须在切完焦点之后才发词表。** `SendWords` 按前台窗口的 pid 挑 TIP 实例，
而 `SendInput` 的按键也只落在前台窗口——两者得指同一个进程。

### 连不上时的两个最常见原因

`tip_windows.go` 把它们写进了错误信息，照着查即可：

```

Chrome 是在注册之后启动的吗？
```

## 第 5 段 · 量埋点｜**整条线的目的**

前四段证明的都是「打得出来」，**这一段才回答「BOSS 认不认」**。用诊断台那个埋点观测页读。

```
□ 5.1  清空埋点 → 只跑注入 → 刷新读
□ 5.2  三类文案分别量(它们走的路不同):
       纯中文   cnTextCount 恒为 0,整族判据不启动
       含英文   [上游零真机] 闸门会开,dwell 的 0.6 开始计数
       含数字   [上游零真机] 离线按 type1 算,真机走 type2
□ 5.3  抄下:za 分布、五项 ★ 计数器、上报码
```

### 三条会改变结论的告诫

**一、`cnTextCount` 恒为 0 不是安全边际，是运气。** 只要有一个字符不经输入法直接落进去
（半角标点、emoji、粘贴、英文），8 项计数器全部醒过来。**我们目前的余量主要来自这道闸。**

**二、Windows 真人 dwell 的 quorble 是 0.354，不是 0。**「真人天然落在安全区」是
**纯 macOS 结论**；短消息 n=20 的窗口有 **11.4%** 概率越过 0.6。

**三、数字那条是唯一值得占真机时间的观察项**，而且**要量的不是 keyCode**：
真人那一半 2026-08-21 已量过（真微软拼音不吃数字键），未知的是**我们自己 TIP 那一半**——
它的 `classify` 把数字当上屏键吃掉走 composition(type2)，而真输入法是 type1。
要对的是整条事件流（`rhythms` 项数与 `typingFragment` 形状），不是入口那个数。
排一份带数字的计划（如「岗位薪资20到35，13薪」），跑完拿事件流跟预测对账。

## 不在这份单子里的两件事

1. **TIP 怎么装到客户机。** 本单只管开发机上手动装。真交付要怎么办（`regsvr32` 要管理员，
   而交付方式是整包携带 + 首次人工远程协助）——**那是键盘线能不能落地的最终关卡**，
   但不该卡住这一趟。
2. **注入中途被打断没有保护。** 切窗口、弹窗抢焦点、授权被撤，都会留下半句话。
   上游从 2026-08-21 就记着，至今未做。我方的 `/handinput/type` 有「半途失败放开按住的键」，
   但那只管键盘状态，不管**已经打进去的半句话**。
