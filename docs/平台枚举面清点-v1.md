## 1. 结论摘要

1. 在 15 份库存档中按指定客户取最新的 `dxc-0712`、`wyl-0714`、`zhq-0714`，共得到 565 条入站消息。按顶层平台消息 ID 跨库去重后仍为 565 条：无重复，也无缺失 ID 的行。
2. 入站顶层 `contentType` 共见 7 个数值：`99`、`105`、`148`、`177`、`259`、`313`、`343`。另有 202 条普通文本没有 `contentType` 字段。
3. 所谓“`null contentType`”已查清：**0 条显式 JSON `null`，202 条是字段缺席**。SQLite `json_extract`等查询会把“缺席”也折叠成 SQL `NULL`，因而之前看起来像是 `null`。其真实行为是普通 NIM 文本通道，不是未知卡片。
4. **存在对方主动发起换微信的案例**：`ASK_FOR_WX` 在 wyl 最新库中 4 条，三库共 7 条。wyl 的 21 条微信交换卡片由 4 条 `ASK_FOR_WX` 和 17 条 `WX_CARD` 组成。
5. 批次 0B 的 32 条候选规则扫描全部 565 条入站文字后，若按“简历标记 > 拒绝正则 > 短拒绝”优先级模拟，得到简历 67 条、拒绝正则 217 条、短拒绝 21 条、无命中 260 条。这些规则仍全部是 `productionEnabled=false`，本清点不改变该状态。
6. `contentType=148` 共 217 条：目标拒绝正则命中 217，漏掉 0，在非 148 中命中 0。这只能证明它在当前三库样本上的区分度，不自动构成生产开启授权。

### 2.2 “已见”的三种含义

- **库存已见**：三份最新客户库的入站顶层样本中存在。
- **真机已见**：本仓库已有当时真实登录页面的只读观察记录，或本次在 wyl 已登录页面直接复核到。
- **当前显式映射**：新系统当前 program 有专门分支；否则即使库存已见，也只会落入保守 `system`分支。

“库存已见”不能替代真机事实门；老项目常量更只是候选清单。
