# 智联主动微信请求接受事实记录（2026-07-24）

## 一、目的与边界

本记录只回答一个问题：候选人主动发起微信交换请求后，我方点击一次平台“同意”，
页面与实时消息源会出现什么可复核结果。

探针只读取当前已打开的智联 IM 会话，没有点击、发送、滚动、切换账号或读取其他
候选人；仓库只记录平台类型码与布尔结论，不记录候选人姓名、会话标识、微信号、
消息正文或平台消息身份。

## 二、枚举候选清单

按 `AGENTS.md` 的平台枚举面事实门，先考古旧项目微信相关候选值全集：

| 类型码 | 旧项目候选语义 | 本次处置 |
|---|---|---|
| `99` | 平台提示；旧库存同时包含拒绝换微信与拒收消息 | 已见但语义多态，不作为接受成功 |
| `105` | 微信交换请求 | 真机已见并按方向与 `originType` 收窄 |
| `259` | 微信交换结果 | 真机已见并按 `originType` 区分两种发起方向 |
| `280` | 查看微信号卡片 | 真机未见，不实现 |
| `281` | 自动交换微信 | 真机未见，不实现 |

旧项目曾记录“接受候选人请求后原卡就地变为 done、没有新增 `259`”的旧页面形态。
本次真实页面明确新增 `259`，因此旧结论只保留为考古候选，不授权当前实现。

## 三、动作前事实

在当前精确 IM 会话路由中，只读双采样得到：

- 消息行顶层类型为 `custom`；
- 自定义类型为 `105`；
- `direction=in`；
- `originType=2`；
- 平台状态为成功；
- 存在稳定服务端消息身份；
- 不存在独立的 `requestId`、`id` 或 `cardId`；
- 不携带候选人或招聘方微信字段；
- 两次采样的类型、状态、身份集合与结构一致。

同一时刻 DOM 投影为：

- 当前会话只有一个可见微信请求卡；
- 卡内只有一个可见且未禁用的“同意”动作；
- 请求卡尚未进入 done 形态；
- 尚无候选人微信复制值。

## 四、动作后事实

真人此前对上述同类请求执行过一次平台标准“同意”动作。本次在该已完成会话中只读
双采样，稳定观察到：

- 原 `105 + in + originType=2` 请求行仍在；
- 其后新增一条顶层 `custom`、自定义类型 `259` 的消息行；
- 新行 `direction=in`、`originType=2`、平台状态成功；
- 新行存在独立稳定服务端消息身份；
- 新行同时存在候选人微信字段与招聘方微信字段；
- 两次采样的类型、状态、身份集合与结构一致；
- 原请求卡进入 done 形态；
- done 卡存在符合微信号字符约束的候选人复制值。

请求卡完成后仍保留 `.imc-wx-request__actions-success` 容器，因此实现不得仅凭该类名
判断“仍可同意”；必须同时排除 done 形态并确认动作的当前公开文本与可用状态。

## 五、与既有 `259` 的区分

仓库已有真机事实：

- `259 + direction=in + originType=1`：候选人接受我方主动发起的微信邀请；
- `259 + direction=in + originType=2`：我方接受候选人主动发起的微信请求后，平台新增
  的交换结果。

两种结果都携带双方微信字段，但发起方向不同。不得把所有 `259` 合并成同一个动作
来源，也不得把我方点击后的结果再次解释为候选人执行了一次接受动作。

## 六、允许实现的最窄判据

本事实门只授权以下能力：

1. `chat.acceptWechat` 只接受当前精确会话中、由指定请求 `sourceKey` 锚定的
   `105 + in + originType=2 + success`；
2. 最终点击前复用字面同一 evaluator，要求该请求仍是唯一可见 pending 请求卡、
   唯一“同意”动作可用、卡片未进入 done，且消息尾基线未变化；
3. 只调用一次平台标准 click；
4. 成功只认相对动作前基线唯一新增的
   `259 + in + originType=2 + success`，且新行同时具备稳定服务端身份与双方微信字段；
5. 联系方式只收编候选人字段，招聘方字段只作为交换完成的布尔正证；
6. `259 + originType=1` 沿用既有“候选人接受我方邀请”语义，不触发
   `chat.acceptWechat`；
7. 类型、方向、字段、基线或卡片关联任一缺失或歧义，都只记未确认并转人工，不再次
   点击。
