# 里程碑 6：正式采集批次规格

日期：2026-07-22

状态：甲方已批准。本文细化《端到端业务主线计划》中“完整批量采集后再统一评分”的脑侧领域语义；脑手线上字段仍以 `contract/协议规格-v1.md` 与 `contract/contract.v1.json` 为准。

## 一、出口与边界

本阶段建立可恢复、可计数、不会跨职位串批的正式采集批次，并以“推荐列表窗口扫描 → 脑选未处理稳定身份 → 定点读取完整简历”替代 32 项排除数组。

本阶段不应用后台筛选、不生成列表耗尽结论、不评分、不选人、不生成招呼语、不发送消息。普通页面失败、滚动停滞和暂时没有新身份允许阻塞后由真人恢复；重复成员、跨职位收编、超过目标继续采集和批次事实被覆盖必须立即阻断。

## 二、批次事实

1. `SourcingBatch` 是脑侧业务事实，固定包含随机 `batchId`、`platform`、`accountRef`、不可变 `contextRevisionHash`、显式 `targetCount`、平台职位绑定、状态、原因与时刻。一个账号同时最多存在一个非终态批次。
2. `targetCount` 必须由启动请求明确给出，创建后不可修改、没有隐藏默认值。它不从旧后台“候选人筛选”的 `targetMin/targetMax` 推导；后两项只用于统一评分后的确定性选人。
3. 批次启动时真人已经选择目标推荐页；脑先创建 `preparing` 批次，再用首个 `candidate.readSourcingWindow` 正结果把当前页面唯一 `positionRef` 原子绑定到批次，随后进入 `collecting`。职位标题只供展示，不参与身份或绑定。
4. 后续窗口与简历结果的 `positionRef` 必须与批次绑定完全相等；不一致时停止新派发，禁止把结果并入本批。
5. 批次成员唯一键是 `(batchId, platformUserRef)`；候选人人根仍唯一为 `(platform, platformUserRef)`。`resumeNumber`、姓名、页码、滚动位置与 DOM 顺序均不得作为身份或去重键。
6. 只有完整简历、持久命令正结果与批次成员在同一事务内核对并提交成功，`capturedCount` 才增加。命令尝试、局部读取、重复观察与失败均不计数。
7. 同一批次再次观察同一 `platformUserRef` 不新增成员、不增加完成数，也不再次进入本批评分或招呼生成；新的页面观察仍保留在命令账本中，不物理删除。

## 三、状态与停止

批次状态固定为：

- `preparing`：尚未取得并冻结当前平台职位；只允许窗口读取。
- `collecting`：职位已绑定且成功成员数小于目标；允许窗口读取和定点简历读取。
- `blocked`：账号、职位、身份或窗口推进证据不充分；禁止自动派发，真人处理后才可显式恢复。
- `completed`：唯一成功成员数达到 `targetCount`；终态。
- `stopped`：用户显式终止；终态且保留原因。

普通账号暂停只阻止新派发，不改变 `preparing/collecting` 批次状态；重新启用后恢复同一批次。达到目标的那条成员事务必须同时把批次改为 `completed` 并停止当前采集 actor，下一轮不得派发第 `targetCount+1` 条简历读取。

当前版本没有 `exhausted` 状态。真机事实只证明推荐页触底后继续异步扩展和回收 18～22 个卡片 DOM 窗口，尚未观察到可信平台终点。`moved=false`、空 DOM、等待超时或若干轮没有新身份都只能进入 `blocked`，不能推导列表耗尽。

## 四、持久化与恢复预算

1. 新成功采集事实必须携带非空 `batchId`，并受 `(batchId, platformUserRef)` 数据库唯一约束；已有冒烟历史行保持原样、允许 `batchId=NULL`，不伪造批次归属，也不迁移或删除。
2. 批次状态、成员与终态都是业务事实，禁止物理删除。用户放弃当前批次时写 `stopped + reason + endedAt`；继续采集必须新建批次。
3. 不新增通用 in-flight 恢复槽。脑若在 intrusive 命令已经终局、但成员事务尚未提交的极窄窗口崩溃，重启后允许再次读取该候选人；批次唯一键保证它至多成为一个成员。这只会多产生一次可恢复的已查看记录，不会发送候选人消息，当前有人值守阶段接受该成本。
4. 管理 API 只返回批次随机引用、配置 hash、目标数、聚合计数、状态、原因和时刻；不得返回 `platformUserRef`、展示名、职位标题或简历正文。

## 五、窗口调度

1. `candidate.readSourcingWindow` 只感知当前可见稳定身份窗口及平台职位。脑保存已完成成员集合，并从窗口中选择第一个未完成身份；手不接收、不保存业务批次。
2. `candidate.readSourcingTargetResume` 只读取脑指定的当前窗口目标。目标不在窗口、重复、职位换绑或完整简历读取失败时不搜索替代者，由脑决定下一次窗口动作。
3. 当前窗口全部已处理时，脑才派 `move=next`；页面重载或手失忆后可从 `move=reset` 重新扫描，依靠批次成员唯一键吸收重复。
4. 后台筛选配置的应用与回读另立事实门；本批不得把筛选点击偷渡进窗口读取或定点简历原语。

## 六、机制立法四问

1. 当前可达损失：第 33 人起排除集合丢掉旧身份会重复收编；相同 revision 重启会混算历史；页面切职位会把错误职位简历并入同一配置；没有目标数会持续采集。
2. 现有机制不足：logical dispatch 只去重同一命令，账号级开关可被覆盖，32 项排除既不是全批账本，也不能表达窗口推进。
3. 最窄闭环：一张正式批次表、采集事实上的批次外键与唯一成员约束、一个窗口感知原语和一个定点简历原语；不造通用任务框架、不声明耗尽。
4. 成本：一次数据库加法迁移、两条 intrusive 原语、管理 start/stop/status 和相应测试。代价直接服务当前批采目标，且不增加 effectful 面、候选人消息风险或旧后台改动。
