## 2. 真机事实

### 2.1 本次线下卡（type 355）负载形状

外层 `row.content` 是 JSON 字符串，解析得信封；信封的 `content` 字段是**对象**（不是字符串），插件 `parseObject` 首行对对象短路返回，故 `details` 正确取到内层 22 个字段：

```
staffInterviewTimeString, userIconUrl, companyName, jobTitle, needBack,
orgId, jobId, userTitle, interviewId, staffIconUrl, resumeId,
userInterviewTimeString, interviewType, staffTitle, jobResumeId,
interviewStartTimeString, rootCompanyId, startTime, endTime, state,
interviewAddress, jobNumber
```

判定相关取值：

| 字段 | 实际值 | 说明 |
|---|---|---|
| `interviewType` | `"ATTENDANCE"` | 到场面试 |
| `interviewPlatform` | **字段不存在** | 线下面试无「会议平台」概念 |
| `interviewAddress` | 非空 | 线下地址，线上卡此字段为空串 |
| `startTime` | `"1785448800000"` | 换算本机时区 2026-07-31 06:00 |
| `endTime` | **`"0"`** | 线下面试不给结束时间 |
| `state` | `0` | 数值 0 |
| `interviewId` | 非空 | — |
| `interviewPlatformDescription` | **字段不存在** | 线上卡有（见 2.4） |

## 3. 当前可达场景与实际损失

### S1（阻断级）线下卡不推进「已邀面」，冷催误归档已约面试的候选人

事件序列：运营手工发线下邀面卡 → 插件归为 system → 主线停在「沟通中」→ 「沟通中」在沉默轨上 → 候选人若未点接受，24h 冷催1、36h 归档「沉默」。

实际损失：已经约好线下面试的候选人被系统当作失联，收到催促消息并被归档。归档同时清零冷催预算（含催2），唤醒后永无冷催。运营侧无任何异常提示——console 那行 `zhilian_unrecognized_message_type 355` 不进产品 UI。

现有机制为何不覆盖：`EventSystemNotice` 是显式 no-op，不触发 manualRequired；355 未识别不产生 `EventUnknownPlatform`，因为兜底分支在插件侧就把它降级成了 system。

### S2（优化级）线下卡的面试时间不入库，运营通知与客户端均无面试时间

`NotificationRenderSnapshot.InterviewStartsAtMs` 只从 `messages.interview_starts_at_ms IS NOT NULL` 的最新行取（[`notification_store.go:394`](../client/service/internal/store/notification_store.go)），而该列仅在插件返回 `ThreadMessage.interview` 时写入；线下卡未被识别，该列从未写过。

实际损失：即使 S1 之后候选人点了接受、约面成功通知照常发出，通知正文的面试时间渲染为字面量 `未获取到,请在客户端核对`（[`render.go` `formatInterviewTime`](../client/service/internal/notify/render.go)）。而客户端同样没有该时间，运营去客户端核对也查不到，只能回智联页面人工查。

### S3（优化级，存量）腾讯会议线上卡「已邀面」可推进，但面试时间同样丢失

按 2.4 样本对现行代码求值：`interviewPlatform="TENCENT"` 非空，`endTime` 有效，故 `isStaffInterviewInvite` **通过**，主线能推进「已邀面」；但 `interviewMethod` 求值为 `null`（只认 `WECHAT_VIDEO`/`4`），故 `interview` 详情不填充，`interview_starts_at_ms` 仍为 NULL，落入与 S2 相同的损失。

该缺口独立于线下卡，比 S1 更隐蔽（状态推进正常，只有时间丢失），且**本仓库尚未真机复现**——旧样本不构成本仓库事实。

## 4. 旧约束（现行规范原文）

以下为拟修改处的现行文本，修改前视为有效约束：

## 5. 拟议文本

### 5.1 `contract/contract.v1.json`

**(a) 扩 `interviewMethod` 枚举**（append-only，不删值）：

```
/enums/interviewMethod: ["wechatVideo", "onsite"]
```

仅加 `onsite`（真机已见）。`tencentVideo` **不在本次实现**——旧样本已见但本仓库真机未见，按事实门不得实现，列入保留清单待本仓库真机复现后另案。

**(b) `InterviewDetails.endsAt` 改为 optional：**

```
InterviewDetails: {
  startsAt: {type: int64, minimum: 1},
  endsAt:   {type: int64, minimum: 1, optional: true},
  method:   {type: string, enumRef: enums.interviewMethod}
}
```

理由：线下卡 `endTime` 平台恒给 `"0"`，`minimum: 1` 无法表达；规格第 4 章第 3 条明令「不得猜值」，故不得合成 `startsAt + 默认时长`。发送方向的必填由 `ChatSendInviteCardArgs` 的 note 单独约束（见 5.2c），不因读取侧放宽而放宽。

### 5.2 `contract/协议规格-v1.md`

**(a) 改 §4.5 第 250 行：**

> `ThreadMessage.interview` 是 optional 的平台无关邀面参数 `{startsAt,endsAt?,method}`，只可用于 `kind=card && cardType=interviewInvite`；时间为 Unix epoch 毫秒。`endsAt` 为 optional：平台明确给出结束时间时必须填写且 `endsAt > startsAt`；平台对该形态不提供结束时间（当前已知：线下到场面试，平台恒返回 `0`）时必须省略，**不得由 startsAt 合成**。当前 `method` 开放 `wechatVideo` 与 `onsite`。其余参数无法从真实平台事实可靠映射时，整个 `interview` 字段仍必须省略，不得猜值。

**(b) 改 §4.5 第 246 行 contentHash 配方：**

> 已可靠归一化的 `interviewInvite`：`sha256("card\x1finterviewInvite\x1f" + startsAt + "\x1f" + (endsAt ?? "") + "\x1f" + method)`。

`endsAt` 缺席时投影为空串，保持分隔符位数稳定；`method` 由字面量改为取实际值。

**(c) 第 179 行补一句，明确发送侧不随读取侧放宽：**

> 本次放宽只作用于 `chat.readThread` 的归一化读取方向。`chat.sendInviteCard@1` 的 args 仍要求 `startsAt/endsAt/method` 三项必填、`endsAt > startsAt`、`method` 只开放 `wechatVideo`；发送线下卡不在本次授权范围。

**(d) 第 524 行邀面正证判据**：维持原样。发送侧未扩，正证配方随 5.2b 的通用化自动一致（wechatVideo 卡的投影结果与旧配方逐字节相同）。

### 5.3 插件实现（非规范面，列出供审查）

`plugin/src/program/platform/zhilian.ts`：

- `interviewMethod` 求值扩为：`VIDEO`+`WECHAT_VIDEO`/`4` → `wechatVideo`；`ATTENDANCE` → `onsite`；其余组合仍为 `null`（含 `TENCENT`，走保守分支）。

## 7. 收益与成本

### 收益

- 消除 S1：已约线下面试的候选人不再被冷催并归档为「沉默」。这是本立案唯一的阻断级收益。
- 消除 S2：运营通知与客户端拿到真实面试时间，运营不必回智联页面人工查。
- 为 S3 留出接口：`method` 通用化后，`TENCENT` 真机复现时只需加一个枚举值与一条分支。

### 成本

- **契约破坏性修订**：`InterviewDetails.endsAt` 由必填改 optional、contentHash 配方改写。当前处于首客前，按「悬置决策·契约 append-only 冻结点」允许破坏性修订，但须同 commit 重生成两端产物、通过全量门禁，并按硬切换生效（暂停派发 → 重启脑 → 重载插件 → 确认 contractHash 一致后恢复命令，mismatch 状态禁发 effectful）。
- **存量消息重对账风险（需甲方知情接受）**：同一条 355 消息此前以 `kind=system` 落库、contentHash 为文本哈希；改动后同一 `sourceKey` 将归一化为 `kind=card` 且哈希不同。`m2_store` 的卡片状态变更路径对 `ContentHash` 不一致会返回 `ErrConversationVersionConflict`。已持久化记录按「派发时契约」视为不可变审计快照，但**当前会话（本次测试会话）在下一轮巡检对账时的具体行为需要在实现批次内先写针对性测试确认**，不能假定平滑。这是本立案最不确定的一处，也是我建议独立审查轮次盯住的点。
- **`onsite` 卡进入「已邀面」后的下游行为未验证**：`addV4InterviewGroup` 会为其建跟催组，跟催三档话术是否适配线下面试（例如话术是否提及会议链接）未经检查，属明确后置项。
- 实现规模估计：插件侧约 4 处判定 + 1 处投影；契约 2 处 + codegen 产物；协议规格 3 段。回归测试需覆盖线上微信视频卡不回归、线下卡新通过、TENCENT 仍保守、`endsAt` 缺席时的哈希稳定性。
