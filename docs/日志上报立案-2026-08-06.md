## 1. 想要什么

客户机上出了事——某个环节报错、AI 连不上、证词库触发处置、产生一条要人裁决的 suspect——当场推一条到后台，我方在管理前台几分钟内就看得见：哪个客户、哪台机器、什么时候、什么事、卡在哪个候选人哪一步。

不是要把日志全搬上去，是要**及时知道有事发生**。

## 2. 现状事实（本机核实，2026-08-06）

**「事后查得到」已经解决了，缺的是「及时」。** 第五项现场数据上报已经在跑：诊断台点一下、或开了每日自动上传后每天 00:10，脑把 `brain.log` + `brain.db` + `ai-traces.db` 打成 15–20MB 的包传到旧后台，管理前台能下载。所以今天的排障路径是：客户报障 → 让他点上传（或等次日凌晨）→ 下载 → 解包 → 翻 60MB 日志。

| | 现有整包上报 | 本次日志上报 |
|---|---|---|
| 我方发现故障 | 最快次日凌晨，还得有人翻整包 | 分钟级，带类型和分类 |
| 触发 | 人点 / 每日一次 | 出事就推 |
| 单次体量 | 15–20MB | KB 级 |
| 客户机没开自动上传 | 完全看不到 | 照样看得到 |
| 客户没报障 | 我方不知情 | 我方主动知道 |

**当前可达的具体损失场景**（「新增跨层机制立法四问」第一问，不用假想未来用户）：

- 2026-08-05 客户机一条招呼 suspect 把同批其余 32 人冻结 72 分钟。我方是事后才知道的。suspect 一产生就推一条上来，人当天就能去裁决。
- 证词库读回校验失效已分三档处置（AGENTS.md 防护成本预算第 1 条）。哪一档真在客户机上触发过、触发了几次，现在只能靠翻包，翻不到就当没发生。
- 旧后台配置拉不到、AI provider 连不上、自动更新失败——这些都会让客户机静默半天不干活，客户往往以为是自己网络问题，不报障。

**脑侧日志现状**：`slog` 单点初始化在 [main.go:47](client/service/main.go:47)，TextHandler 直写 stdout，Electron 汇到 `{userData}/logs/brain.log`（32MB 轮转一代）。没有分级过滤、没有结构化事件、没有任何出站。在这里挂一层 handler 是干净的单点改动。

**插件侧日志现状**：只有 `console.error` / `console.warn`，落在扩展自己的控制台里。脑看不到，`brain.log` 里没有，整包上报里也没有。也就是说**手侧自身的故障现在完全不可观测**——除非它同时导致某条命令失败，才会经 `result` 间接在脑侧留痕。

**协议侧**：`event` 是唯一的手→脑非应答通道，QoS0、lossy、可批。当前只有四个事件（`unreadBadge`、`pageNavigated`、`loginStateChanged`、`manualInteraction`）。`EventBody` 已有自由形态的 `data` 字段，加一个事件类型只需在 `events` 枚举加一项加一个 dataSchema，改动面很小。

**后台侧**：旧后台 `xq-resume-backend` 已经为第五项加过一整套（`client_reports.py` + `admin_field_reports.py` + 仓储 + migration + 留存清理），分支 `dev-wmt-0703`。本次照同一形状再做一套，路子已经趟过。另有 `client_alerts.py` / `client_metrics.py` / `client_ai_model_logs.py` 是旧产品在用的上报面，规范逐字点名不得接入、不得复用——本次**不碰它们，另建 RecruitHelper 自己的表**。

## 3. 撞上的旧约束（逐条）

### 3.1 云端出站白名单——必须新增一项

开篇列了五项获准出站，末尾「除此之外仍视为不连云端」。这是新增的一项，没有别的解释路径。

（立案时是第六项。同日另一个会话并行做的「工作状态上报」先合入 `main` 占了第六项，本条合并时改列**第七项**。两条通道职责不同：那条报「在不在跑、跑了多少」，本条报「出了什么事」。）

**挂不进第五项**：第五项条款写死「触发方式限两种：同机诊断台的人显式点击，以及……每日 00:10 自动触发。除此之外不得由业务事件触发」。本次要的正是业务事件触发。

### 3.2 旧后台那条被逐字点名的禁令

现文（开篇）：

> 除「全局约定·现场数据上报」明确获批的上报接口外，不得因此接入 verify/heartbeat/session/task/**metrics/alert** 等其他控制面或上报接口；旧产品正在使用的既有接口、表与行为一律不得改动，`client_metrics`/`client_alerts`/`client_sessions`/`client_ai_model_logs` 等既有上报面仍不接入、不复用。

本次功能形状上就是 alert 上报，被点名的正是它。这句必须改。

需要注意的是这条禁令有两半，**只改前半，后半原样保留**：新建 RecruitHelper 自己的表和路由是本次要开的口子；碰旧产品既有接口、表与行为，依然一步都不许动。

### 3.3 候选人姓名与聊天正文出本机——性质与第五项不同

甲方选定上报带「定位用的标识」（含候选人 displayName），2026-08-06 追加裁决**聊天正文也可以带**，仍不带简历正文、微信号、API key。

相关现文（「AI provider 数据边界」）：

> 普通日志、审计 detail、`brain.db` 的诊断面、管理 API、验收报告和**未来上报**只允许 capture/snapshot/invocation/turn/action 随机引用、用途、provider/model、配置 hash、输入输出 hash、字节/token 数、延迟、状态、错误分类与估算费用；禁止记录 API key、base request/response、**聊天正文**、简历正文、完整 prompt 或**候选人明文身份**。

**聊天正文这条比姓名硬，因为它在四处被重申，其中一处直接点名了本次功能：**

- 「同机产品 UI 业务投影例外」：前端不得把这些响应写入 localStorage、IndexedDB、普通日志、**错误上报**、支持包或导出文件。——「错误上报」四个字说的就是本次要做的东西。
- 「开发者 SQL 控制台例外」：边界仍然收在同机……不得进入普通日志、审计 detail、stdout、支持包、验收报告、运营通知 webhook、旧后台、AI 请求或**任何远程渠道**。
- 「开发者诊断台明文边界」：本条**只放宽 `/admin/*` 这一个面**——stdout、普通日志、审计 detail、验收报告、`/app/*` 产品 API、运营通知 webhook、旧后台、AI 请求与**任何远程渠道**一律不因本条放宽。

四条现文合起来的意思是：聊天正文至今只在同机的三个面上可见（产品 UI、诊断台、SQL 控制台），加上第五项的整包。本次是**第一次让它以自动、实时的方式经业务事件出本机**。

第五项确实已经让候选人明文（含聊天正文）出过本机（整包里含 `brain.db`），但两者性质要分清，这是本立案最该讲明白的一点：

| | 第五项整包 | 本次日志上报 |
|---|---|---|
| 触发 | 人点击（在场知情）/ 每日一次（开关默认关，只能人在诊断台开） | 出事自动推，无人在场 |
| 频次 | 每天至多一次 | 事件级，全天候 |
| 知情 | 点的人知道自己传了什么 | 没有人知道某一刻传了什么 |

所以这是**第二次**开口，不是第一次口子的延伸。甲方需要单独知情接受。

### 3.4 一个连锁后果：日志行本身不能开始带姓名或正文

这点必须在设计里挡住。如果做法是「让 ERROR 日志行开始打候选人姓名和聊天正文，上报直接搬运日志行」，后果是 `brain.log` 从此长期在客户机磁盘上留着姓名与聊天记录，并随每日整包一起传——**等于顺手把「普通日志」这条边界也改了**，影响面远超本需求。

因此本方案的做法是：**日志行原样不变，上报时另附结构化的定位上下文与正文字段**。要改的只有「上报」这一个面，「普通日志」的边界一个字不动。这个区分写进拟议文本。

### 3.5 「不去取」而不是「要滤掉」——2026-08-06 甲方定的方向

这条决定了实现形态，必须先讲清楚，否则规范文本会被误读成一个过滤器需求。

甲方的方向是：**保护隐私靠「不主动去上报」——不专门回查、不专门装配隐私字段。但隐私信息如果本来就混在错误日志或聊天正文里，无所谓，直接传。**

所以「不带微信号」的准确含义是：**装配载荷时不去查权威 `ContactAsset`**。它不意味着要在聊天正文上跑正则把微信号洗掉——候选人在聊天里自己打出的手机号、微信号、身份信息，一律原样上传。

这个区分不是文字游戏，它是两种完全不同的实现：一个是「少写一次数据库查询」，另一个是「上线一个内容扫描器」。后者成本高、必然误伤，而且删掉的往往正是排障要看的那句话。

口径与 AGENTS.md 既有条款一致：「简历与候选人自由文本可能自含姓名、电话等身份，甲方知情授权……系统不承诺内容级脱敏」。甲方明示本条不必写进 AGENTS.md，此处记录以免实现走偏。

### 3.6 契约新增事件——永久负债

甲方选定插件端同批做、经脑转发，需要在 `events` 枚举加一项 `handLog`。

「防护成本预算」第 6 条要求：向 append-only 契约加枚举/字段/原语前，先回答「evidence 文本或日志是否足够」。本条的诚实回答是**不够**——手侧自身的故障（连接层异常、分发器抛错、DOM 读取崩溃）今天既不进 `result` 也不进 `brain.log`，没有任何现存通道能承载。首个真实客户已安装，契约已进入 append-only 期，加枚举是合法的 append，但它此后不可删除。

同时 `event` 通道现有的权力描述要放宽。现文（`contract.v1.json`）：

> QoS0 提示;唯一权力=调整巡检开跑时刻/静默窗/健康档

日志事件的权力是「进上报队列」，不在这三项里。这句要改。

### 3.7 手的禁令——不改，但设计要绕开

- 「不得有业务定时器」：手侧不攒批、不设 timer，出错即时 `event`，节流靠比较上次发送时间戳（不是定时器）。
- 「不得持久化业务状态」：手侧不落 `chrome.storage`，连不上脑就丢——`event` 本来就是 QoS0/lossy。

### 3.8 不需要改的

- 「Chrome 插件永远不连接旧后台」——甲方选定经脑转发，这句原样保留，插件「无云端出站能力」仍是构造性事实。
- 微信号的五处白名单、简历正文「收在同机」——本次不回查这两样，不碰（聊天正文另按 3.3 开例外；正文里候选人自曝的微信号按 3.5 不过滤，不属于对白名单的放宽）。
- 统一业务运行窗口——上报不是候选人可见动作，照第五项写法排除。
- 「业务事实行禁止物理 DELETE」——见 5.1，脑侧不落库，不产生业务事实行。

## 5. 若获批：技术方案

### 5.1 脑侧（本仓库）

新增 `client/service/internal/logreport`：

**采集**。在 [main.go:47](client/service/main.go:47) 的 `slog` 上套一层 handler：原有 stdout 输出一字不动（`brain.log` 照旧），同时把符合条件的记录喂给上报器。两类来源：

- **命名事件**：一份显式登记的封闭清单，调用点主动报，带结构化定位字段。首批建议：脑启动失败、手长时间掉线、AI provider 不可用、suspect 产生、转人工、巡检轮异常中止、旧后台配置拉取失败、自动更新失败、证词库三档处置触发、运营通知发送失败。**不含任何形如「脑已启动」「我还活着」的周期性事件**——那是 heartbeat，规范禁止。
- **ERROR 兜底**：级别 ≥ Error 的日志行全收，保证没预料到的故障也能上来。

**上下文补齐**。命名事件由调用点带上 `profileId` / 会话引用 / 命令名 / idemKey / 原语名这类非明文引用；上报器按这些引用回查本地库，补上候选人姓名、职位名与聊天正文。**姓名与正文只存在于上报载荷，不回写日志行**（见 3.4）。ERROR 兜底行能从 attrs 里认出 `profileId` 的就补，认不出就只发日志行。

**聊天正文带多少**（我的默认，甲方可否）：**与本次事件直接相关的那个会话的最近 20 条消息**，按发生顺序，含双方，带方向与时刻。理由是排障要看的正是上下文——AI 为什么这么回、为什么判成 suspect、候选人到底说了什么导致状态跳变——一两条不够用；整会话又等于把 `messages` 表往外倒，且大多数行与本次故障无关。20 条能覆盖绝大多数场景，单条上报仍在 KB 级。

**不主动装配的字段**：简历正文与简历快照、权威 `ContactAsset` 微信号、API key、`ai-traces.db` 里的 provider 请求/响应原文与完整 prompt。最后一项要单独强调——AI 调用的 prompt 里嵌着简历正文，且 `ai-traces.db` 的「任何远程渠道」禁令只在第五项整包上开过例外，本次不扩及。

**不做任何内容级脱敏**（见 3.5）。上报器不扫描、不跑正则、不剔除载荷里的任何文本；日志行和聊天正文里出现的手机号、微信号、身份信息一律原样上传。守的是装配环节「不去数据库捞隐私字段」，不是「把已有文本里的隐私洗掉」。

**节流**（必要，不是可选）：

- 同指纹（事件类型 + 错误分类 + 调用点）在 5 分钟窗口内合并成一条，带 `count` / `firstAt` / `lastAt`。
- 全局每分钟上行条数上限，超出部分丢弃并计数，丢弃数本身作为一条上报——宁可告诉后台「这里丢了 400 条」，也不要静默。

**发送**。攒批 30 秒或满 20 条发一次；崩溃类事件同步立即发。走已有的 `licenseToken` 身份，跟第五项同一套鉴权，不新增配置面。

**可靠性做成尽力而为**：内存队列，失败重试两次后丢弃并计数，**不建持久化发件箱、不建重试表、不落库**。理由（「立法四问」第四问）：第五项整包每天兜底，事件上报只负责「快」不负责「全」；为了不丢几条诊断日志而新增一张表、一套恢复路径、一套迁移，代价不相称。副作用是不产生任何业务事实行，绕开禁止物理 DELETE 那条。

**开关：没有开关**（2026-08-06 甲方当日修订，理由是「只是上报日志，不干过分的事」）。立案时写的是「默认关闭、只能人在诊断台点开」，实现到诊断台那一步时甲方改判常开。代价已陈述并记入 AGENTS.md：装了新版的客户机自此持续自动外传候选人姓名与聊天正文，本机没有任何手段关掉它；这与同为常开的工作状态上报不同——那条载荷是纯计数。诊断台保留一栏状态显示（上次结果、累计发出/丢弃条数），那是状态不是开关。

### 5.2 契约（本仓库）

- `events` 枚举加 `handLog`，dataSchema 定义 `level`、`code`（封闭错误分类）、`message`、可选的非明文定位引用。**手侧不带候选人姓名**——手不该知道也不需要知道，姓名由脑补齐。
- `EventContext` 现为必填（`platform` + `accountRef`），而手侧日志可能发生在还没有账号身份的时刻（连接刚建立、登录态未知）。**2026-08-06 核实结论：`EventBody.context` 改为可选**，与 `CmdBody.context` 同例——那里已经为同一个问题（`probe.platform` 的 `contextOptionalBeforeBinding`：绑定前尚无 `accountRef`）这么解过。放弃哨兵值方案的理由是它会在管理前台显示成一个假账号名，误导排障的人。

  这个改动有一处必须配套，否则是净损失：`context` 变可选后生成的 Go 类型是 `*EventContext`，而 Go 对指针自动解引用字段访问——**编译器不会报错，nil 会在运行时让脑 panic**。等于把一个 schema 拦得住的错误换成了崩溃。因此拦截责任显式迁移到脑的事件分流处：`handLog` 在账号解析之前分流，其余事件缺 `context` 一律拒收并留痕。三处消费点（`main.go` 两处审计、`manager.go` 的 `HandleEvent`）已全部改为 nil 安全。
- `event` 通道的权力描述加上「及进入日志上报队列」。
- 明确 `brainMay`：**只记录与外发上报，不得触发任何业务命令**。
