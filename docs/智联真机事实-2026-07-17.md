# 智联真机事实（2026-07-17）

本文只记录在当前已登录真实智联招聘方 Chrome 中实际观察并复核过的事实，作为里程碑 2 智联 program 的实现依据。候选人姓名、招聘方姓名、企业名、手机号、微信号、职位编号、账号 ID、会话 ID、token 和消息正文均不进入仓库。

## 1. 证据边界

- 观察日期：2026-07-17（Asia/Shanghai）。
- 页面：当前用户 Chrome 中已经登录的真实招聘方账号。
- 主站 host：`rd6.zhaopin.com`。
- IM 路由：`/app/im`；选中会话后 URL 为 `/app/im?sessionId=<opaque>`。
- 账号页路由：`/app/personal`。
- 页面运行时公开加载的三个脚本也用于静态复核：
  - `app._route_.im.web.a480807d6f2a87d367d112aeb9c664cb.js`，SHA-256 `9ee07db0749391256a1218c48470f8afeb03ea8737c114dd5b76c0d1da799ed2`；
  - `im-base.web.911a7ee28fee13f27deb4a0bd812bf79.js`，SHA-256 `85500bbbb3755f0430e38c788c35c415447af9b376c7d1a3ce09150f9f0a218a`；
  - `app-store.web.6ac72d412b46c420f4735f0dee0407ee.js`，SHA-256 `b2eb4b64da37936589f261e843447da3130a469f4974d9dd6e6e5dc1c30a477c`。
- 上述 hash 只定位本次观察到的页面版本；智联发版后必须重新侦察，不能把文件名或 selector 当永久契约。

## 2. 页面、登录与账号身份

### 2.1 可观测页面状态

- 正常登录页面存在 `#root`，并有主导航 `/app/job`、`/app/recommend`、`/app/search`、`/app/im`、`/app/personal`。
- 页面 HTML 内有一个以 `__INITIAL_STATE__=` 开头的 JSON 启动脚本。
- 登录信号是 `session.session.isLoggedIn === true`，同时 `session.session.staff.staffId` 与 `session.session.org.orgId` 可用。
- 浏览器隔离执行环境中 `window.imEngine`、`window.$session`、`window.__INITIAL_STATE__` 和 `window.Vue` 都不可见；但启动脚本的 DOM 文本可见。因此动态调用页面 IM 引擎需要显式 MAIN-world bridge，不能假定普通 content script 能直接访问页面全局变量。

### 2.2 opaque principal fingerprint

最终扩展重载后，当前 IM 页确认以下三个字段同时存在：

- `session.session.staff.staffId`
- `session.session.org.orgId`
- `session.session.staff.defaultLoginPoint`

同页的 `personal.imUserInfo` 实际为空对象，因此早期依赖 `rootCompanyId` 的实现会得到 `loginState=in` 但 fingerprint 为 null；正式绑定真机因此被正确拒绝。现行 program 以 session `orgId` 为主锚，只在旧页面缺少它时才用 `personal.imUserInfo.rootCompanyId` 作为保守兼容兜底。字段在 MAIN world 用固定版本前缀和无歧义长度编码形成输入，再做 SHA-256，只把摘要返回给脑：

```text
sha256(join("|", [byteLen(value) + ":" + value for value in
                   ["zhilian-principal-v2", staffId, orgId, defaultLoginPoint]]))
```

脑只比较完整摘要，不解析内容。任一字段缺失时身份状态为 `unobservable`，不能退化为姓名、公司名、手机号、Cookie 或 token。真机已证明该摘要能完成零配对正式绑定；尚未用第二个账号实测“切换账号必变”，在有第二账号前将该项保留为未销风险，并以三字段中任一变化即 mismatch 作为止损。

## 3. 会话列表

### 3.1 启动状态字段

`__INITIAL_STATE__.im.sessions` 是当前首批会话。每条已确认包含：

- `sessionId`：32 字符 opaque 会话标识；
- `peerPartnerId`：稳定候选人平台引用，作为 `platformUserRef`；
- `userId`、`typeUserId`：页面内部其他候选人引用；
- `jobNumber`、`jobTitle`；
- `unreadCount`、`isUnRead`、`unreadReminderType`；
- `lastSentence`、`lastMessageReadTime`；
- `sortTime`、`createdDate`、`modifiedTime`；
- `resumeNumber`，但它只可作证据，禁止作为候选人主键。

首屏实测 20 条，`pageNo === 2`、`hasMoreSession === true`，`sortTime` 降序。页面代码调用 `im/session/list`，参数含 `pageNo`、`pageSize: 20`、`activeSessionId`、筛选条件等。

### 3.2 DOM 与虚拟滚动

已验证的当前页面结构：

```text
.im-session-list
  .im-session-list__virtual
    .im-session-list__virtual--box
      .im-session-item
        .im-session-item__name-title
        .im-session-item__msg
        .im-session-item__time
        .im-session-item__unread
```

- 首屏虚拟容器高约 907px、内容高 1440px，对应 20 条、每条约 72px。
- 第一次滚动加载后内容高从 1440px 增至约 2922px；继续滚动后依次增至约 5769px、7218px。
- DOM 只保留约 32 个挂载项，不能用“当前 DOM 元素数”判断总条数或 `complete`。
- 首批消息很多，仅滚动到约 100 条时可见日期仍在前两天。因此 8 天窗口可能需要多页，`chat.readList` 必须逐页/逐滚动上报 progress，并由 cutoff、`maxSessions` 和真实 `hasMore` 共同确定 `complete`。

### 3.3 未读语义

- `.im-session-item__unread` 的文本和 `sessions[].unreadCount` 一致，可为字符串呈现的 `0`。
- 左侧主导航总未读徽章已验证为 `div.app-im-unread.app-menu-item__im-unread`，父节点为 `.app-menu-item-content-normal__tip--count`；当前版本是纯数字文本。元素缺失能否一律解释为 `0` 仍须双读与导航状态共同判定，不能单次缺失即发零值。
- 顶部全局未读徽标不是强一致信号：打开会话后行内未读已从 `1` 变为 `0`，顶部徽标仍短暂保持旧值；刷新后才反映新状态。
- 因此列表结果以每条会话的 `unreadCount/isUnRead` 为准；顶部徽标只作 QoS0 提示，不作账本。

## 4. 线程读取与已读副作用

### 4.1 页面真实实现

智联页面的时间线主路径是：

```text
window.imEngine.getHistoryMsgs({
  to: activeSession.peerPartnerId,
  lastMsgId: oldest.idServer,
  endTime: oldest.time,
  scene: "p2p" | "team"
})
```

失败时页面回退到：

```text
POST im/getSessionMsgs {
  targetType: activeSession.sessionType,
  targetId: activeSession.userId,
  endTime
}
```

页面用 `idServer` 去重并按 `time` 正序合并；回退路径还用 `sendMessageId` 做第二次去重。历史区页面明确显示只提供近 90 天消息。

最终真机重验还确认了当前生产页的实际兜底形状：

- 时间线容器是 `.im-timeline__wrapper .im-timeline`，不是旧版 `.km-list`；
- Vue2 `__vue__` 数据在当前生产构建中不可用；
- 同一路由启动状态的 `im.timelineMap[sessionId].timeline` 含稳定消息身份，可作为 MAIN 引擎不可用时的只读数据证词；
- 明确边界节点是 `.im-timeline-ending`，当前文案为“以下是90天内的聊天消息”；
- MAIN runtime 的 `$session` 可能暂时为 `null`，此时招聘方 `staffId` 必须回退到同一份已解析的 `__INITIAL_STATE__`，不能猜方向。

program 只有在该显式 90 天边界存在且当前 eligible 行数不超过本页上限时才声明 `reachedTop`；超过上限时继续生成排他 cursor，没有边界或数据身份不稳定时响亮失败，不把可见窗口伪装成完整历史。

### 4.2 首次打开会话会产生外部可见语义

页面在首次时间线读取后会调用/触发：

- `window.imEngine.sendMsgReceipt(...)`；
- `im/send/lastMsgRead`；
- 条件满足时 `im/send/refreshMsgRead`；
- `im/session/markRead` 与 IM SDK session ack。

真机实测：打开一个未读数为 `1` 的既有会话后，该行未读立即变为 `0`，刷新后仍为 `0`。所以 `chat.readThread` 已在正式协议中定为 intrusive：只允许 tracked 会话、受账号串行域和用户静默窗约束，平台副作用声明为 `idempotentReadReceipt`。不得为了索引未知会话而逐个打开。

如果 MAIN-world bridge 后续能证明“只调用 `getHistoryMsgs` 且不调用 receipt/markRead”不会改变平台状态，可以增加无已读路径；在真机证明前不得假设无副作用。

## 5. 消息形状

### 5.1 时间线基础字段

`im.timelineMap[sessionId].timeline[]` 已确认包含：

- `from`、`to`、`scene`、`sessionId`；
- `idServer`（样本为 14 字符）与 `sendMessageId`（样本为 32 字符）；
- `time`、`status`、`type`；
- `text`、`file`、`content`。

方向以 `from === current staffId` 判定为招聘方发送，否则为候选人发送。M2 入账的 `origin` 仍是产品语义：历史和真人手发均记 `external`；只有未来系统 intent 成功产生的消息才记 `self`。

### 5.2 DOM

线程根与消息节点：

```text
#im-session-detail.im-session-detail
  .im-timeline__wrapper
    .im-timeline
      .im-message
```

文本消息使用 `.im-message__bubble`、`.im-message__text`，招聘方气泡带 `.im-message__bubble--me`，已读状态带 `.im-message__read-state`。系统提示使用 `.im-message__toast`。DOM 只作 MAIN-world/API 失败时的兜底与证据，不应成为消息身份主来源。

### 5.3 已见 custom 类型

当前历史样本已验证以下 custom `content.type`：

| type | 已观察语义 | 关键子字段 |
|---|---|---|
| `104` | 当前沟通上下文 | `job`、`resume`、`sessionOriginType` |
| `169` | 沟通职位系统提示 | `jobNumber`、`jobTitle`、`rootOrgId`、`title` |
| `131` | 招呼消息 | `greetingText` |
| `105` | 换微信请求卡片 | `scene: EXCHANGE_WECHAT`、`staffContent`、`userContent` |
| `99` + `content.type: 2` | 对方拒绝换微信 | `msgb`、`msgc`、`type` |

普通文本的 NIM `type` 为 `text`，正文在 `text`。未知 custom 类型必须保留稳定 hash，并按正式枚举归为 `system`（文本使用不含隐私的稳定类型占位或页面可见摘要），不能静默丢弃或误判为普通文本。

页面当前换微信卡片组件还会以 `{sessionId, messageId}` 调用只读接口 `im/getWxCard/state`，返回数字状态用于渲染 `EXCHANGING/DONE/REFUSED`。这说明卡片当前状态不能只从尾部拒绝提示推导；正式 program 应以原始请求卡片的稳定 identity hash 为身份、接口状态为可选状态证据。该接口的直接 `fetch` 仍待本插件 MAIN-world 真机验证，失败时只能返回 `unknown`，不能伪造终态。

## 6. 当前实现裁决

- `probe.platform`：DOM 判断 host/route/content script；MAIN-world bridge 读取登录状态与身份三元组，只返回 SHA-256 fingerprint。
- `nav.ensureSurface`：复用 `rd6.zhaopin.com/app/im`；无页面时才创建；绝不自动登录。
- `chat.readList`：优先 MAIN-world 调用页面已有 `imEngine.getSessions`；平台请求可使用更小内部页，协议对外页最多 32 条且 data≤64KB。每条 conversationRef 以 opaque `sessionId` 表示，platformUserRef 以 `peerPartnerId` 表示。已实现保守 DOM 虚拟列表兜底：首窗只接受启动状态，动态窗只接受带稳定身份的 Vue source；只有按降序越过 8 天 cutoff 才宣告 complete，到可见底部但没有平台 hasMore 证词时响亮失败。正式 actor 已在最终插件上连续分页并建立 509 条轻量索引。
- `chat.readThread`：优先 MAIN-world `getHistoryMsgs`；按 `idServer`、`sendMessageId` 做手内去重，脑只看 direction/contentHash 做最大重叠。协议对外页最多 64 条且 data≤64KB；引擎不可用时只接受目标路由上具有稳定消息身份的 Vue 数据或同一启动状态 `timelineMap`，并要求显式 90 天边界才声明 `reachedTop`。最终正式 actor 首次读取收编 7 条历史并把收编边界设为 7；第二轮以 5 条锚尾完成重叠证明，消息总数仍为 7、本轮新增仍为 0。直接引擎路径不调用页面 Vuex 的 receipt 方法，但在真机证明 unread 不变前仍保留 intrusive 分类。
- 页面脚本 hash、selector、custom type 都属于智联 program 实现事实，不进入平台无关协议语义。

最终真机还验证：扩展重载后稳定 `handId` 重新连入、页面暂不可用时 actor 经一次 `nav.ensureSurface` 恢复；真实用户点击事件在长 `chat.readList` 途中建立 45 秒静默窗，并在列表结束后阻止新的 `chat.readThread`，轮次以 `USER_ACTIVE` 响亮终止，既有 7 条账本不变。同一持久化数据库重启脑后，插件在两个同时打开的 IM 标签下只建立一条 hand session，actor 按持久化的“今日开启”状态自动恢复完整巡检，`chat.readThread` 再次终局 `ok`，消息仍为 7 条且新增投影仍为 0。

唯一增量验收时，脑先优雅退出，招聘方再由真实页面人工发送一条自然文本，页面确认只出现一条；随后关闭发送所在标签，只保留另一个 IM 标签。因为手端事件没有持久 outbox，脑离线期间的发送/导航提示必然全部丢失。重启脑时账号 `dirtyHint=false` 且原定 5 分钟巡检已经到期，因此轮次以 `timer+surfaceRecovery` 触发，经一次 `nav.ensureSurface`、完整 `chat.readList` 和 `chat.readThread` 后把账本从 7 条推进到 8 条，本轮新增恰为 1。距上一轮满 60 秒后从同一 actor 入口复读，列表尾已与账本一致，没有再次打开会话，账本仍为 8 条且本轮新增为 0。该链同时证明事件全丢、发送页关闭、同日脑重启和重复对账不增生；不证明 M2 已具备产品自动发送原语。

## 7. 尚未销案的真机项

- 无第二个真实账号，尚未实测账号切换后的 fingerprint 变化。
- 尚未找到“同意换微信/接受卡片”的可控历史样本；拒绝样本已验证。接受状态在有历史样本或候选人配合后再销案。
- 图片、语音、文件消息的真实历史样本尚未逐类验证；未知类型必须保真保存并报告。
- 50/500 条完整线程快照的体积与时长尚未测得；协议在测量前必须使用分页/分块，禁止静默截断。
- 当前真实样本已覆盖一条普通文本增量；卡片接受、媒体、第二账号和长线程等未销项以验收报告的残余风险矩阵为准。
