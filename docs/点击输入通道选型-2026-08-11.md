# 点击输入通道选型(2026-08-11)

**本文档只陈述事实与选项,不构成任何授权。** 据此做出的决定须另行记录。

全文严格区分三类结论:**[实测]** 当日真机验证得出;**[读码]** 从平台前端代码逻辑推出,未单独验证;**[未知]** 无可见性,不得当作依据。

## 一、问题

智联页面挂着一段名为 `environment-check` 的脚本,全局监听 `click` 与 `keydown`,凡 `event.isTrusted === false`(即代码合成的事件),就把**企业 ID、员工账号 ID 与被点元素的 DOM 路径**上报平台服务端。

它不拦截,是记账。我方当前 45 处 `element.click()` 全部落在这个判据的错误一侧,只要事件冒泡到 `document` 就产生一条实名记录,客户机一天数百条。平台据此掌握的不只是"这个账号在用自动化",而是完整的操作模式与节奏。

本文档比较三条应对路径,供裁决。

## 二、平台侧事实

### 2.1 isTrusted 检测 [读码 + 实测]

脚本 `https://fecdn5.zhaopin.cn/rd6_zhaopin_com/environment-check.web.<hash>.js`,16KB。除 core-js polyfill 外业务代码只有环境检测一件事,IM 主 bundle 中无人引用其导出对象——**整个文件对页面功能无贡献**。

关键逻辑(压缩后原文,变量名为混淆结果):

```js
function n(payload) {
  post('/security/environment', {
    rootOrgId: window.$session.org.orgId,
    staffId:   window.$session.staff.staffId,
    content:   JSON.stringify(payload)
  }).catch(...)
}
function u() {
  document.addEventListener("click", t => {
    if (!t.isTrusted) n({ eventName: "web-event-click", xpath: i(t.target) })
  })
  document.addEventListener("keydown", t => {
    if (!t.isTrusted) n({ eventName: "web-event-keydown", xpath: i(t.target) })
  })
}
```

`i()` 自被点元素逐级向上拼路径,含 `#id` 与 `.class`。

同一脚本在页面加载时另判无头环境:UA 含 `Headless`/`PhantomJS`、`navigator.webdriver` 为真、或 `outerWidth`/`outerHeight` 非正数,任一命中即上报 `web-load-headless`。

**[实测]** 上报的完整路径是 `POST https://rd6.zhaopin.com/api/security/environment`,**带 `/api` 前缀**——仅读代码看不出,baseURL 是运行期拼的。返回 200。

### 2.2 另外两套防护 [读码,未验其行为]

- **瑞数 VMP**:`https://rd6.zhaopin.com/<随机路径>/<随机名>.<hash>.js`,170KB。特征为 `$_ts` 全局对象、大量 `_$` 前缀混淆变量、文件尾部成段字节码数组。检测逻辑全在自定义字节码内,静态搜不到任何明文关键词。**[未知]** 它查什么、查到会如何处置,我方无可见性;追进去需逆向 VMP,按「不审计平台实现」的信任边界应在此止步。
- **数美设备指纹**:`device-fingerprint-sdk` 加载数美 `fp.min.js`,上报端点名含 `reportShuMeiDevice`,种 `x-zp-device-sn` cookie。**它认的是机器,与点击方式无关**,任何方案都消除不了。

### 2.3 一个边界事实 [实测]

`outerWidth`/`outerHeight` 为 0 的窗口上下文会被 2.1 判成无头并上报。**同窗口的后台标签页不受影响**(实测 `visibilityState: hidden` 时 `outerHeight` 仍为正常值)。若将来让自动化在最小化或异常窗口中运行,须重新确认此值。

## 三、CDP 验证结果 [实测,2026-08-11]

方法:最小临时扩展,只声明 `debugger` 权限,只调 `Input.dispatchMouseEvent`,**不 enable `Runtime`/`DOM`/`Page` 任何 domain**(最著名的 CDP 检测手法以 `Runtime.enable` 为前提)。在智联真实登录页面上验证。

三条路互不冲突。拦截上报与点击方式完全解耦,加删都是一条规则的事,**是天然退路,随时可加**。

### 4.1 拦截路径的两次形态:先拦端点,后改为拦脚本 [实测,2026-08-11]

**第一版拦端点,被真机否决。** 初始实现拦 `POST /api/security/environment`(提交 `221989a`/`2a35544`/`82559bc`),本机验收当时判定通过:规则命中、请求消失、同域埋点未见误伤。

但随后在真机上发现:请求被拦后,**平台 `http` 模块会把这次失败连同身份一并送进它自己的异常上报通道**,载荷形如

```
scene:   "接口请求异常"      message: "服务异常: Network Error"
request: { url: "/security/environment" }
staffId: <员工账号 ID>       pageUrl: <当前页面>
```

**这比不拦更糟。** 正常用户的点击 `isTrusted` 为真,`environment-check` 根本不发这个请求,也就无从失败;因此"某 staffId 的 `/security/environment` 持续 Network Error"同时暴露两件事:该账号在产生合成事件,且有人在拦截。原方案未达成目的。

**第二版改为拦脚本加载**,把链条掐在源头:脚本不加载 → 监听器不注册 → 请求不产生 → 没有失败 → 没有异常上报。规则改为 `urlFilter: "environment-check"`、`resourceTypes: ["script"]`、`requestDomains: ["zhaopin.cn","zhaopin.com"]`。

**本机验收(第二版)**:该脚本的 window 标记不存在(从未执行)、`transferSize` 为 0、**无 CDN 换域重试**;派发 4 次合成事件后新增请求为 **0**(并经"主动 fetch 一条即被记录"的阳性对照确认记录功能正常);页面推荐列表 20 条正常渲染,Vue 实例、Vuex、router 均在。资源加载失败虽会触发平台捕获阶段的 `error` 监听,但其上报函数首行 `if (!t.message) return` 把没有 `message` 的资源错误挡在上报之前——实测未产生任何上报。

**方法教训(值得记一笔)**:第一版之所以漏判,是因为当时用 `performance.getEntriesByType('resource').length` 前后比对判断"有无新增请求",而 **resource timing 缓冲区默认上限恰为 250 条**,页面早已饱和,新请求根本不再记录——250→250 被误读成"零新增"。此后凡用该 API 做有无判断,必须先 `setResourceTimingBufferSize` 扩容并 `clearResourceTimings`,且**附带阳性对照**。

**遗留**:平台若统计该脚本的加载成功率,可发现本机从不加载它。该痕迹弱于"安全埋点接口持续失败"(脚本加载失败在真实世界常见),接受。客户机验收待发版后进行。本节不改变 CDP 与 OS 的选型,两者仍悬置。

## 五、我方现有点击路径与改造形态

### 5.1 现状 [实测]

- **45 处 `.click()`,分布在 32 个顶层函数**,全部集中于 `plugin/src/program/platform/zhilian.ts`。
- 全部在 **MAIN world** 执行:经 `runMain` 以 `chrome.scripting.executeScript({ world: 'MAIN' })` 序列化注入。该入口是唯一注入通道,交互节奏闸收口于此。
- **MAIN world 的必要性来自感知而非动作**:为读 `__vue__`(Vue 组件实例)进而取 Vuex getter 拿消息数组;该 expando 属性在 isolated world 不可见。点击本身不需要 MAIN world。
- **44/45 处点击的定位是纯 DOM 选择器**。唯一依赖 `__vue__` 的是 `mainClickConversationOnce`(点开会话即选人):它经 `__vue__`/`$nuxt` 反查每行对应的候选人,要求每行唯一确定一人,选出目标行,并在点击前最后再核一次身份。

### 5.2 改造形态

现每处点击是一次原子注入:定位 → 前置检查 → 点击 → 等后置条件,全在同一 JS tick。CDP 与 OS 的派发都必须自 background 发起,故该原子操作必须拆开:

```
1 定位段  MAIN world    定位 + 业务前置检查 + 算视口坐标 + elementFromPoint 预检 + 存 handle
2 派发段  background    按后端派发
3 确认段  MAIN world    等后置条件(选人那处另核一次身份)
```

要点:

- **第 3 段是现有代码平移**,点击后的等待循环本来就在,不是新增。
- **命中确认由后置条件承担,无需新机制**——后置条件("弹窗真的关了""选项真的选中了")比"目标收到了 click 事件"是更强的判据,合「可见后置状态原则」。
- 真正新增的只有两样:第 1 段末尾的算坐标 + 预检 + 存 handle,以及 `mainClickConversationOnce` 的身份复核。
- `handle` 指 MAIN world 中保存元素引用的下标——`executeScript` 之间无法传递 DOM 对象,只能传可序列化值。`intrinsic` 后端靠它点对象(而非坐标仿制品),OS 靠它比对光标落点;CDP 用不到。
- **第 1 段的尾部(算坐标、预检、handle、将来的窗口指标)必须抽成共用函数**;若任由 45 处各自实现,升级 OS 时将被迫改动 45 处。

改造后"点击"收敛为三个共用件:坐标准备函数、派发函数(含降级决策)、编排层。45 处调用点只余各自的定位与业务前置检查。

### 5.3 三个后端在该形态下的差异 [判断]

|  | CDP | OS |
|---|---|---|
| 派发段是否经 WS | **否**,全在插件内(`executeScript` + `debugger.sendCommand`),脑手协议完全透明 | **是**,每次点击穿两次 WS |
| 派发段是否碰页面 | 否,只需坐标 | **是**,需窗口指标做换算,并注入监听做光标闭环 |
| 编排段数 | 3 | **5**(定位 / 移光标 / 落点确认 / 派发 / 确认) |

因此"派发段平台无关、只知坐标"这一性质**对 CDP 成立,对 OS 不成立**。切换后端的成本:`intrinsic` ↔ `cdp` 只改派发函数;转 OS 还须改编排层段数与坐标准备函数,但**不扩散到 45 处调用点**——这是本形态的主要价值,而非"换后端零成本"。

### 5.4 固有代价 [判断]

定位与点击不再处于同一 JS tick,"我检查过的就是我点的"由**构造性保证降为"预检 + 后置确认"**。最尖锐处在 `mainClickConversationOnce`:其点击前的最后一次身份核对与实际点击之间隔了一个跨进程往返。

后果被下游守卫兜住:点错行只导致**误标一次已读加一张人工票据**,而 `conversationRef→peer` 目标绑定作为发送硬前置可阻断错靶发送。方向为少做。

拆步不可逆:即便日后换回 `intrinsic`,每次点击仍是三段往返。实际影响可忽略——多出的往返为数十毫秒量级,而交互节奏下限为 1 秒起、同批抖动 2.5~5 秒。

### 5.5 待验证 [未知]

`chrome.scripting.executeScript` 注入 async 函数时,Chrome 是否等待其返回的 Promise resolve。OS 的光标闭环依赖此;本项目未验证。

## 六、未决与未知

1. **瑞数是否检测 CDP** [未知]。只能上线后观察,窗口可能数周。可观测信号:发送成功率下降、开始出验证码、平台侧功能受限、网络请求中出现新的上报端点。
2. **OS 在 Windows 上的坐标换算未验**。Mac 与 Windows 的窗口装饰、DPI 缩放模型、多显示器坐标系均不同,Mac 上验通不能推及 Windows。定 OS 前须在 Windows 上重验。
3. **行为统计层三条路都够不着**。严格 08:00–24:00 活动、相邻候选人 4~8 秒均匀间隔、每份简历恰好停够 2 秒、每天数百条、从不点错从不回退——这些在平台服务端业务日志里一览无余,不需要任何前端检测。**"一劳永逸不被识别"不成立**;要动这一层只能拿产能换隐蔽,属另一议题。
4. **平台已有的识别能力与处置之间隔着一层**。设备指纹、业务统计、明文上报三样平台都有,而客户账号至今未被处置。三条路降低的是证据的直白程度,不是"从被发现变为不被发现"。

## 七、建议

**先 CDP。** 理由:

1. 已实证可行,今日即可动工;
2. OS 买到的是"消除一个未证实存在的风险",代价是一个数量级的工程复杂度与一批新失效模式(窗口被挡、坐标算偏、点到页面外);
3. **先 CDP 更快拿到决定性信息**:瑞数有无反应是"要不要 OS"的唯一判据,而先做 OS 须先付完整工程才能开始观察——花更大的钱,却更晚知道那笔钱该不该花;
4. **沉没成本量级不同**:转换时作废的代码,CDP 侧约小几百行,OS 侧为大几百行加一次协议修订;
5. **失效模式的危险程度不同**:CDP 最坏是被平台知道(而平台本已知道,伤害增量近零),OS 最坏是点击落在页面之外、别的程序上,方向正对第零条红线。危险的那个应后做。

**一条曾据以推荐的理由已被证伪,在此更正**:原稿称"先做 OS 若需回退,已付的协议面改动难以撤回"。该前提不成立——开发阶段 contract 不受 append-only 约束、允许破坏性修订,`main` 上刚完成过一次(`manualInteractionKind` 三值收窄为单值,`6a6c199`)。纯代码角度 OS→CDP 反而是减法(删多加少)。推荐结论不变,依据换为上述第 3~5 条。

若采纳 CDP,两条设计要点须写进实现:

- **`canceled_by_user` 不自动重连**,降级回 `intrinsic click` 并上报给脑。客户点掉横幅是明确表态,与之拉锯(点掉→重连→再弹)比不上 CDP 更糟。代价是客户一键即可使本方案失效。
- **坐标点击必须两道闸**:点前等 rect 连续若干帧稳定 + `elementFromPoint` 确认该坐标上即目标(或其后代);点后在目标元素上确认确实收到本次 click。两道任一不过即不算点击成功。

裁决权在甲方。

## 八、前置状态(已落地)

以下两项是本决策的前置,已在 `main` 上完成,理由不在此重复:

- **`isTrusted` 已从系统清零**(`ad3d860`)。手侧不再监听真人 DOM 输入,`manualInteraction` 收窄为推荐流换代信号,判据改为 Chrome `webNavigation.onCommitted` 公开确认的推荐页主框架 `reload`——**与事件真假无关,CDP/OS 接入后照常工作**。条款见《协议规格-v1》「manualInteraction 收窄为推荐流换代信号(2026-08-11 甲方裁决)」。
- **`sendGreeting` prepare 段的 `humanTouched` 真人探测已移除**(`53fe8fb`)。防覆盖用户草稿改由"编辑器内容与本命令正文精确相等"核对承担——核对结果而非推测意图。条款见《协议规格-v1》「编辑器准备阶段不监听真人操作（2026-08-11 甲方裁决）」。

当前系统中 `isTrusted` 不参与任何判断,三条路均无此项阻碍。
