## 一、触发事实(当前可达场景)

2026-07-28 11:47,档案 `p-c1e2d6391629ee531de2a159`(职位"家庭资产配置顾问")在招呼后一轮内连发 3 条:文字提问 → 在线简历卡 → 文字提问。v4 冻结路径 `FreezeCommunicationV4Turn` 建 turn 后,`ReduceV4InboundTurn` 判定"特殊事件与普通消息混合"为 `unsupportedSemantic`,整轮转人工:意向 AI、回复 AI 均未调用,候选人的两个问题无人应答;聚合 `automation_status=manualRequired`,该档案自此离开自动化轨道。

同型个案:会话 `989f76876cfc…` 对应档案(2026-07-26)同样是"文字+简历卡"混合被拦。

**频率:** 全库 52 个入站段(两条出站之间的连续候选人消息段,忽略 system 行)中:

| 形态 | 段数 | 现状 |
|---|---|---|
| 纯文字 | 41 | 自动处理 |
| 纯在线/附件简历卡 ×1 | 4 | 自动处理(businessEvent 分类=interested,直接回复) |
| **文字 + 简历卡混合** | **2** | **转人工,零响应(本案)** |
| 简历卡 + 换微信成功卡(±文字) | 2 | 混合被拦;两例均为收编导入的历史段,未进实时自动轨 |
| 纯换微信 pending / accepted / 邀面 accepted 卡 | 3 | 各有确定性处理 |

混合段占 4/52 ≈ 7.7%;老项目生产同口径为 13.1%(见第八节)。混合输入是常态,不是长尾。

**放大效应:** 轮级 `unsupportedSemantic` 会把聚合 `automation_status` 冻为 `manualRequired`,此后该候选人的一切新消息都不再自动处理。现存恢复路径仅两条一次性定向 CLI(配额废除解冻、`outboundBoundaryMissing` 边界恢复),`unsupportedSemantic` 无恢复入口——单轮的保守判定实际是档案级永久退出自动化。

## 二、旧约束(现状条文与代码封锁点)

规格层:《沟通逻辑规格-v4.md》未明文禁止混合轮;拦截的授权依据是 M5-A/B 剖面的"未激活能力全部转人工"。即本案是**激活范围的留白**,不是规格红线;扩展它属于剖面能力增补(本次已获甲方范围授权),不属于改安全内核。

代码层五处封锁点(改一处不够,任一处都会把混合轮打回人工):

1. `communication.ReduceV4InboundTurn`([v4_engine.go:96](../client/service/internal/communication/v4_engine.go)):`special×1 + ordinary≥1` 或 `special>1` → `unsupportedSemantic`。**v4 主路径的语义裁决点,本案实际命中处。**
2. `store.DialogueTurnInputKindOf`([m5_dialogue_identity.go:22](../client/service/internal/store/m5_dialogue_identity.go)):合法输入形态只有"全部非空文字"与"恰 1 张 resumeAttachment 卡"。被 `FreezeDialogueTurn`、`RecheckDialogueTurnCurrent`、`loadM5TurnMaterial`、`ApplyResumeBusinessClassification` 四处复用。
3. `communication.Reduce → validateFrozenTurn`([reducer.go:213](../client/service/internal/communication/reducer.go)):冻结轮消息出现任何 card → `ManualUnsupportedSemantic`(经典链;批 A 路径不经过,批 B/C 实现时按实际复用面处理)。
4. 巡检预判 `inspectM5Pending`([m5_dialogue.go:239](../client/service/internal/patrol/m5_dialogue.go)):复用第 2 处。
5. `m5ai.RenderIntentPrompt`([render.go:547](../client/service/internal/m5ai/render.go)):本轮消息必须全部为 inbound text(批 A 跳过意向 AI 后不在路径上)。

已具备、无需新建的能力:历史/本轮信封已把简历卡渲染为固定占位文本"候选人已投递简历";纯简历卡轮已有"businessEvent 分类=interested、跳过意向 AI、直接回复"语义;换微信 pending 单卡已有"无条件接受→收编→承接 AI"链(2026-07-26 例外);交换成功单卡已有"收号+运营通知+固定回执"动作;邀面接受单卡已有"已约面推进+固定确认语"链;v4 状态机已有"动作后对话"(`DialogueAfterActions`)骨架。

## 三、已获批裁决与拟议规格文本

**2026-07-28 甲方已拍板三项:**

1. **简历卡裁决规则:** 轮内含简历卡(不论有无文字、卡数几张)整轮判 `interested`(businessEvent 来源),跳过意向 AI,直接生成回复;"文字形似拒绝+简历卡"也按有意向,沿用 2026-07-22 冒烟裁决"简历事件 > 拒绝正则族 > 短语族"优先级。
2. **范围:三种混合全做**(简历卡混合、换微信卡混合、邀面接受卡混合),分批交付。
3. **存量档案:甲案**——落地后提供一次性定向解冻 CLI。

**拟议规格文本(混合输入轮总则,获批后并入《沟通逻辑规格-v4.md》§五;批 A 部分为已批裁决的如实固化,批 B/C 细则待甲方确认):**

> **混合输入轮(2026-07-28)**:同一候选人输入轮内,普通非空文字与下列特殊卡可以任意混合、任意排序、各自任意条数:在线/附件简历卡、换微信请求卡(pending)、微信交换成功卡(accepted)、邀面接受卡。轮内出现图片/语音/文件或未知卡型时,整轮仍转人工。裁决规则:
> 1. **状态推进与确定性动作照旧、逐事件应用**:接受换微信、联系方式收编、运营通知、已约面推进、截图等既有事件动作不因混合而增减或改序;安全前置(接受正证→收编完成→才可承接)不变。文字部分合成一次真实表达(轮次 +1、滑动沉默锚点)。
> 2. **意向分类**:轮内含任一上述特殊卡即跳过意向 AI——简历卡与换微信请求按已批裁决视为强意向;交换成功与邀面接受是服务事实,无需分类。分类落 `interested`(businessEvent 来源)或按服务态处理。
> 3. **候选人可见回复(单轨,至多一次对话建议)**:轮内**无文字**时沿用各单卡既有语义(固定回执/固定确认语/承接 AI)。轮内**有文字**时,该轮的固定回执/固定确认语由**一次 AI 承接调用替代**(reply 或 serviceReply 用途,按主线状态定;上下文含全部事件与文字,AI 自然完成确认+回应),多气泡仍逐项走独立安全轨;已批组合资格(如确认正文+换微信邀请 → AI 正文+换微信邀请)照旧由确定性代码裁决。**AI/解析/前置失败一律转人工,不自动回落固定话术、不补发**——沿用本规格"回复失败立即转人工"纪律。
> 4. **对话用途选择**(确定性,一轮一次):主线已约面 → serviceReply(禁承诺纪律照旧);轮含换微信请求且接受链完成 → 既有承接用途;其余 → reply(interested 已定)。多类特殊卡同轮时动作取并集、对话仍只一次。

## 四、分批实施方案

设计原则:**不新增动作类型、预算、持久化结构或契约表面;不改安全内核。** 所有批次的可见动作仍走既有 WAL/idemKey/证词/正证轨;`dialogue_turns` 无新列,`contract/` 无改动。

### 批 A:简历卡混合(最小,先行)

| # | 位置 | 改动 |
|---|---|---|
| 1 | `v4_engine.go` `ReduceV4InboundTurn` | special 全为 `EventResumeSubmitted` 时与 ordinary 合成单一轮事件(seq=段尾),Kind=`EventResumeSubmitted` → 既有 `ReplyKnownInterested`。v4 聚合主路径与 M5 试运行路径同经此函数,一处改动两径受益 |
| 2 | `m5_dialogue_identity.go` `DialogueTurnInputKindOf` | 合法形态:全文字;简历卡 ≥1 张;文字+简历卡混合(后两种归并同一形态,裁决语义相同)。其余照旧拒绝 |
| 3 | `m5_dialogue.go` `reduceM5ResumeTurn` 断言 + `ApplyResumeBusinessClassification` 校验 | 从"恰 1 条且为卡"放宽为"≥1 张简历卡、其余全为非空文字" |
| 4 | 回复信封(现状确认,预期零改动) | 简历卡占位文本已进 `throughTurn`/`history`;回复 prompt 无 `{回复}` 槽。以测试钉死 |

测试:单元回归 + 本案三消息序列(text, card, text)端到端重放 + "卡在段尾"“多卡”“文字形似拒绝仍判有意向”“含其他卡仍拒(批 A 阶段)”边界用例。

### 批 B:换微信卡混合

- **pending + 文字**:既有"无条件接受→正证→收编→承接 AI"链照旧;文字自然进承接上下文(消息账本天然提供),轮次合成推进。预计主要是 v4 引擎混合分派 + 形态判定扩展,动作链零改动。
- **accepted + 文字**:收号+运营通知照旧;固定回执由 AI 承接替代(§三.3),`WechatReceiptSent` 在承接正证后置位(防未来重复回执)。
- 覆盖 e191 型历史形态(简历卡+文字+交换成功卡):动作并集 + interested + 一次承接。

### 批 C:邀面接受卡混合

- 已约面推进、截图、约面成功运营通知照旧;固定确认语由服务态 AI 承接替代(§三.3);"+换微信邀请"组合资格照旧由确定性代码按已批清单裁决(AI 正文+换微信邀请为已批组合形态)。

### 批 D:存量解冻 CLI(甲案)

仿 `m5_v4_budget_unblock.go` 模式:独立 CLI、停脑后运行、仅匹配 `manual_reason=unsupportedSemantic` 且轮输入经新形态判定合法的档案;turn 按已冻结事实回 `collected`,聚合回 `active`,留审计。真人已插话会滑动沉默锚点,既有语义覆盖,安全。

**实施顺序:A → D(解冻两个存量档案,含真机验收)→ B → C。** 每批独立出口、独立 commit 与验收;批 B 实现中若确认逐形态枚举难以维护,判定点收敛重构(第七节债 1)升格为批 B 前置,另行报出口。

## 五、每批出口四项(纪律第 1 条;批 A 已细化,B/C/D 开工前按同格式补齐)

**批 A:**
1. **最小可交付出口:** 规格 §三总则(批 A 部分)合入 → 4 处改动+测试一绿 → 本案序列测试走通"冻结→businessEvent 分类→回复建议"→ 逐因果 commit。真机验收:下一个自然混合轮(或授权测试账号构造一例)自动产出回复。
2. **必须立即阻断的损害:** 放宽波及其他卡型或媒体轮;一轮产生多于一次回复建议调用或多条候选人可见动作计划外新增;存量 `manualRequired` 档案被隐式复活(只允许批 D 显式 CLI)。
3. **允许重试/人工兜底的失败:** 回复 AI 失败沿用既有转人工;形态拿不准照旧转人工——方向永远是"读不懂→不确认→转人工",不多发。
4. **审查轮次与后置项:** 冒烟 commit 后一轮独立审查,阻断项修复后仅定向复核。后置项:批 B/C/D、恢复入口通用化(第七节债 2)。

## 八、老项目考古结论(2026-07-28 子代理调研,已核对代码证据)

按"文档信任边界"纪律,以下结论全部落在老工作区代码与生产日志上,旧文档仅作线索;仅摘对本提案有直接影响的部分。

**老项目对混合轮没有专门设计,也没有"转人工"概念,硬着头皮走同一条链。** 结构性裂缝:事件检测按"本轮全部新入站"扫,判意向只取"最后一条消息"(`chat_reply.py:358`,全仓库唯一判意向调用点)。后果:

- **文字+简历卡完全无感知**:简历卡以平台文案混进普通消息;RSM 简历 marker 只在卡恰为段尾时命中(顺序运气);生产 216 次意向 LLM 调用 0 次见过简历卡文案。
- **换微信+文字是唯一被事故逼着专门处理的混合**(其问题 24:确认语分支吞同轮文字→消息已消费→候选人永久已读不回、双闸互锁僵死,SQL 手工解救)。修复= "固定话术+AI 承接" + "本轮除卡片外是否还有真实文字"谓词。
- **邀面接受+文字至今吞文字**,官方口径(待办 F6)"已知会丢,明确接受"。
- **量级**:947 轮中多消息轮 124(13.1%),含卡 33 轮。
- **无"看不懂→搁置"机制**:空消息/LLM 失败/非法信号全部默认中性放行。

**对本提案的影响:** (1) 批 A 采用"简历事件短路扫整轮"正是老项目 RSM 顺序缺陷的正解,且为已批优先级;(2) 问题 24 与新系统"manualRequired 后档案永冻无恢复"同构,坐实第七节债 2 与批 D;(3) 批 B/C 的"有文字→AI 承接替代固定话术"移植自老项目验证过的修复方向,但失败语义按本仓库纪律收紧为转人工(老项目是回落固定话术);其"插件丢弃 99% 卡片类型、下游靠文案全等匹配"的坑已被本仓库平台枚举面事实门与 contract 枚举挡住。
