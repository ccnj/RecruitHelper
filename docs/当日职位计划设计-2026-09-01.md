# 当日职位计划设计（2026-09-01 甲方裁决）

## 一句话

原来一天只给一个职位打 80~90 个招呼；现在把同一份总量按当天真正在线的职位数分摊，每个职位各跑一个小批次，顺序打完，总量不变。

## 甲方裁决清单（2026-09-01，对话裁决，本文固化）

1. **总量**：跟原来一样，从后台配置的 [targetMin, targetMax] 里取一个数；配置取计划序第一个职位的「候选人筛选」文档，运营侧约定同一客户各职位配成一致。
2. **人工确认闸撤销**：候选确认改为编排器自动确认；控制律（精确全选集合一次性消费）保留，只换触发者。
3. **回复延迟接受**：批次串行，早批招呼的回复要等全部批次跑完才开始处理，甲方知情接受。
4. **少发不挪**：任何职位跳过或采不满，份额不挪给其他职位。
5. **旧机制不管**：后台「当前职位」字段与定时轮换保留原样，不再驱动职位选择。
6. **采集系数**：首轮 ≈ 1.5×份额、续采步进 ≈ 0.5×份额、整批上限 ≈ 3×份额（甲方改定，取整向上）。
7. **当场打出**：切到下一职位前，上一职位的计划招呼必须全部终局（甲方点名的硬约束，源自推荐页刷新后旧候选人不可找回的平台事实）。

对应 AGENTS.md 修订：「统一业务运行窗口」增补授权单位段，新增「当日职位计划与招呼配额分摊」条目。

## 可执行职位判别（两层）

**后台层（定名单）**：复数同步（job-configs）返回、且配置文档齐全能导入为可执行上下文的职位。复用既有"有效职位集"机制（`SaveEffectiveLegacyJobAIContexts`），不合格职位本来就进不了这个集合。计划序 = 后台职位 ID 升序（确定性，不依赖响应顺序）。

**平台层（定 N）**：复用既有开批前状态闸。第一批开批前必须跑的那次 `job.readPublishedList`（读全部分区）同时用于计划定稿：N = 后台合格职位 ∩ 平台「在线中」分区，职位名归一化口径与发布幂等同一套。N 定稿后当天不变；中途上线的职位不追加。

之后每个职位轮到开批时照旧复核状态（既有闸原样），发现下线/未见 → 跳过该职位。

## 总量抽取与配额分摊

- 总量 T：以（本地日期 + 计划标识）做稳定哈希，在计划序第一职位的 [targetMin, targetMax] 内抽取，手法与既有 `stableSourcingSelectionTarget` 同款。**必须可重放**：脑重启后重算得同一个 T，否则配额漂移。
- 份额：基数 = T ÷ N 向下取整，余数 r = T mod N，计划序前 r 个职位各 +1。总和恰等于 T，永不向上取整。
- T < N 边缘：计划序靠后职位份额为 0，不开批，方向少发。
- 份额是**选中目标 override**：批次筛选的 targetCount 直接取份额，不再从该职位配置 [min,max] 抽取；批次自洽校验按"有计划条目则 targetCount == 份额"分支，无计划条目（存量批次、管理面显式批次）沿用旧规则。

## 最低分数与男性比例（2026-09-01 甲方质询确认）

两个闸都是批次内闸，零代码改动：评分与 minScore 钉在各批冻结的职位配置上；男性上限 = 份额 × 比例 / 100 向下取整。甲方知情接受小份额量化收紧：份额 17@50% → 上限 8；份额 1@50% → 上限 0（该批只选女性，池子全男则该职位当天发不出）。全天男性合计 ≤ 原单批取整值。

## 跨职位不重复招呼（既有闸，加回归钉住）

1. 筛选建档查重按人不按职位：同平台同账号下任何非淘汰档案都算占用（`sourcingCandidateAlreadyProfiledTx`），职位 A 发过的人在职位 B 的批次判 `ExistingProfile` 跳过；批次严格串行，无竞态窗口。
2. 平台层兜底：打过招呼按钮变"继续沟通"，contactState=unknown 永不授权 sendGreeting（协议规格 §614）。

## 运行编排

### 阶段机改动（2026-09-01 实现侦察后修正：不新增阶段）

侦察发现批前状态闸本来就在批 actor 里（`runSourcingBatch` 的 preparing 分支：读 `job.readPublishedList` → 上报 → 核对本职位在线），计划定稿直接挂在**当日第一次成功的闸读取**上，不需要新增 planning 阶段：

```
Start（人工/每日自动开始）
  → 复数同步（必须成功）→ 建计划（草稿态：后台合格职位序列 + 总量 T 落库）
  → StartFull(首条目 revision)：批次规模按“临时份额”（以草稿职位数 N₀ 计）
  → 批 actor 既有状态闸读取 → 钩子：计划定稿（N=在线∩合格，份额落库，离线条目标跳过）
    （首批因 N₀≥N 可能少采，由既有续采轮 +0.5×份额 自愈；上限 3×临时份额
      在过线率低于五成时可能提前封顶，方向少发，接受并留观）
  → 既有漏斗：采集→评分→筛选（份额 override）→生成→自动确认→发送
  → 发送全部终局 → stage=communication
  → 计划还有待跑条目：编排器自动登记 PendingActionSourcing（复用「再采一批」机器）
  → 巡检边界消费：标记当前条目完成 → 完结当前 run（endReason=additionalBatch）
    → 按下一条目开新 run（份额已定稿，规模精确；批前状态复核走既有批内闸）
  → …循环…
  → 最后一个条目的 run 停留在 communication，开启巡检回复，至当日收场
```

条目的批次未能正常终局时（批前闸拦下：jobNotOnline / jobStatusReadFailed / positionSelectFailed=重名歧义族 / recommendPageNotReady / filtersApplyFailed；或采集中途 blocked：windowReadFailed / targetReadFailed / positionChanged 等）批次终局、run 失败，收口扫描一律标记条目跳过（原因「batch:<原因码>|<判定现场>」）并接续下一条目；只有计划级故障（dailyPlanFinalizeFailed、运行失败时根本没有批次=重启落在空档）→ 计划终止。（2026-09-07 甲方裁决：此前只有跳过类枚举内的原因跳过、其余原因终止计划；俞炳冬01 09-05～07 连续三天因 windowReadFailed 终止整日计划、末两职位未发，甲方裁定单个职位的失败无论如何不得终止整个计划。）份额 override 的可重放性由筛选汇总行新增 `plan_quota` 列自证，不依赖计划表长期在场。

### 「当场打出」的保证

会刷新推荐流的两个动作（状态读取导航去职位管理页、`selectSourcingPosition` 切职位）都只发生在下一批的开批流程里，而下一批的开批被阶段机钉死在上一批发送阶段 `progress.Completed`（全部计划招呼终局，含 suspect 计入已处理）之后。suspect 的收敛与发后正证走 IM 会话窗口，不依赖推荐页，切换后照常可查。批内续采（+0.5×份额）是同一推荐流内继续下探，不切换不刷新。

### 自动确认

生成完成且确认投影就绪后，编排器计算既有"精确全选集合"并直接消费确认（等价于机器执行 ConfirmAll），不再进入等待人工的停靠态；集合校验、一次性消费、批次锚定全部原样。存量停在 `awaitingConfirmation` 的运行升级后由同一路径自动收敛。

### 恢复与终止（全部朝少发）

| 场景 | 处置 |
|---|---|
| 脑重启在某批漏斗中途 | 既有批次恢复机制原样续跑，计划游标随批次状态 |
| 脑重启落在批间空档（旧 run 已完结、新 run 未建） | 收口扫描发现"无活跃 run + 计划有待跑条目"→ 计划终止（chainInterrupted），当日不再续，次日重来 |
| 用户点结束 | run 完结，收口扫描随之终止计划 |
| 用户暂停/恢复 | 只作用于当前 run，计划不动 |
| 漏斗跨 24:00 挂起（waitingDailyWindow） | 次日恢复后继续当前批与计划余下条目（计划跟随运行，不跟随日历日） |
| 沟通态跨日终局（dailyWindowClosed） | 计划随之收口：无待跑条目记完成，有待跑条目记终止 |
| 计划条目轮到时职位下线/未见/歧义/状态读取失败 | 跳过该条目并留痕，继续下一条目 |
| 批次因职位状态之外的任何职位级原因 blocked/stopped（窗口读取失败、简历读取失败、职位漂移等；账号级故障如掉登录、手离线也会以这些原因表现） | 跳过该条目并留痕，继续下一条目（2026-09-07 甲方裁决；此前就地终止）。该批已采未招呼的人随批次作废。账号级故障时逐职位盲试约十分钟才收场，甲方知情接受 |
| 计划定稿失败（dailyPlanFinalizeFailed）、运行失败且没有批次 | 计划级故障，就地终止，不自动重试 |

收口扫描：编排器每 tick 在无活跃 run 时核对活跃计划——有待跑条目记 `aborted(chainInterrupted)`，无待跑条目记 `completed`。同一把 advanceMu 下执行，不与接续竞争。

## 留痕与可见性

每个计划条目的状态（待跑/进行/完成/跳过）、份额、实发、跳过原因持久化并经 `/app` 产品 API 投影到产品 UI；跳过原因必须带判定现场（哪一层、读到了什么），按「错误收敛必须留痕」条款执行。工作状态上报照旧按当前批次投影当前职位，不新增上报字段。

## 存量与入口兼容

- 存量单批次运行、管理面显式批次（`/admin` m6 start）不属于任何计划，沿用旧配额规则与旧采集常量。
- 产品「开始」不再要求携带职位：完整流程一律按当日计划跑；活跃运行期间重复点击开始为幂等空操作。
- **「沟通期再采一批」入口随本设计停用**（活跃 run 存在时 Start 一律幂等返回）：其旧语义是在当日配额之外再发一整批 80~90，与分摊模型直接冲突。这是执行方按少发方向的处置，**待甲方追认**；如需"人工追加一批"的能力另行立案，恢复成本低。
- 每日自动开始不再读"当前职位"，直接发起计划；开关、触发时刻、前置闸全部不变。

## 后置项（本轮明确不做）

- 采集系数（1.5/0.5/3）真机标定后调优。
- 批间插巡检窗口（甲方已裁接受回复延迟）。
- 后台「当前职位」/定时轮换机制的清理（甲方已裁不管）。
- 确认页 UI 的删减美化（本轮只保证计划进度可见与自动确认后不再误导等待）。

## 验收清单（本轮真机出口）

1. ≥2 个在线职位的账号完整跑一天：计划定稿 N/T/份额与配置一致，各职位实发 ≤ 份额，合计 ≤ T。
2. 无跨职位重复招呼（抽查建档与平台会话）。
3. 人为制造一个职位下线：该条目跳过、原因 UI 可见、其余条目照跑。
4. 全部批次终局后巡检回复正常开启；次日每日自动开始接新计划。
5. 回归用例：发送未全部终局时下一职位批次开不出来（排序硬约束）。
