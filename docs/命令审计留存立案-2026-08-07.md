> 停止纪律」第 12 条提交裁决材料，批准后按"规范先行 → 实现同步"落地：条款进
> AGENTS.md「全局约定·命令审计留存」（`ef3079e`），实现见 `b3c32b5`。
> 第六、七节记裁决结果，其余各节保留立案当时的原始材料。

且已经在往外溢——本机磁盘、每日诊断包、服务器留存三处同时被拖着涨。

## 一、现场事实

数据源是客户机「戴相成03」2026-08-07 11:57 的诊断包（`brain.db` 354MB，
本机使用 10 天，7-29 至 8-07）。

### 1.1 库被什么占满

| 层级 | 占用 |
|---|---|
| `cmd_records` 一张表 | **280MB（79%）** |
| └ 其中 `chat.readList` 一个原语 | **143MB** |
| └ 其中 `chat.readThread` | 13MB |
| 其余全部表加起来 | 约 40MB |

作为对照：真正的业务事实——全部聊天消息（`messages`）——只有 **2.2MB**。

### 1.2 这 143MB 是怎么产生的

`chat.readList` 是巡检的只读对账命令，读一次会话列表。它的返回值被全文存进
`cmd_records.result_body`，单条约 9.6KB：约 30 个会话，每个带会话引用、对方
姓名、职位、未读数与最后一条消息正文。

它跑得极密——业务时段每小时 250～500 次，**约每 7～15 秒一次**：

| 日期 | 次数 | 体积 |
|---|---|---|
| 7-29 ~ 8-01 | 每天 400～900 | 每天 5～10MB |
| 8-04 起（装 1.7.2 之后） | 每天 3300～4800 | **每天 33～46MB** |

8-04 有个明显跳变：整体命令量从每天 1200～2000 条涨到 5900～6900 条，
`readList` 在其中的占比也从 34% 升到 69%。跳变原因未查，本立案不依赖它。

### 1.3 信息密度（8-05 全天实测）

全天 4774 次读、45.7MB。其中：

- 与上一条**完全相同**的占 37%；去重后只剩 1076 份不同快照
- 全天出现过 635 个不同会话，其中 **616 个被记录了 100 次以上**
- 而同一会话身上真正发生的字段变化，**全天合计只有 163 次**
  （最后一条消息 66 次、未读数 50 次、活跃时间 47 次）
- **98% 的读取 `complete=False`**，是滚动分页的中间态，属读取过程而非读取结论

**为了记住这 163 次变化，存了 45.7MB。**

### 1.4 内容是否冗余：不完全是

`conversations` 表（1322 行）逐字段覆盖了 `readList` 返回的每一项：

| readList 返回 | conversations 表 |
|---|---|
| `conversationRef` | `conversation_ref` |
| `peer` | `peer_display_name` |
| `unreadCount` | `unread_count` |
| `lastActivityTs` | `last_activity_ms` |
| `lastMessage` | `last_message_preview` / `_direction` / `_kind` |
| `positionTitle` | 经 `platform_user_ref` 关联 |

没有任何字段只存在于 `cmd_records` 里。**但 `conversations` 是覆盖写的**，
只保存"现在什么样"；`cmd_records` 保存的是"每个时刻看到的世界什么样"。
排查确实用得上后者——例如「这条消息为什么没被处理」，需要知道当时那一轮
列表里有没有它。因此这批数据**不是纯冗余，是价值随时间急剧衰减的取证材料**。

### 1.5 只增不减

`cmd_records` 无任何清理机制。按当前速度：

| | |
|---|---|
| 现在（10 天） | 354MB |
| 一个月 | 约 1.2GB |
| 一年 | 约 14GB |

## 二、当前可达场景与实际损失

不是推演，三处都已经在发生：

**（一）客户机磁盘。** 每天 +40MB，永不回收。

**（二）每日诊断包。** 该客户机的每日自动上传是开启的（`field_report_settings`
`auto_upload_enabled=1`，最近一次 8-07 00:10 成功）。整个 `brain.db` 每天凌晨
上传一次，压缩后的包大小随库同步膨胀：

```
8-03  18M      8-06  38M
8-05  28M      8-07  48M      ← 每天约 +10M
```

**（三）服务器留存。** 服务器（40G 盘，已用 8.6G，剩 29G）现有 4 个客户
共 45 个包、588M。因为库本身在涨，每天的包越来越大，14 天保留窗口的总量
**是个持续上升的值，不收敛**。AGENTS.md「现场数据上报」条款里那句"每日自动
上传若不设上限，十客户规模下一年即耗尽当前服务器磁盘"，当时的估算尚未计入
库本身会膨胀这一层。

（顺带记录，与本立案无关的独立事项：`/srv/console/rh-updates/pkg` 堆了 33 个
历史安装包共 3.0G，客户端只认 `latest.json` 指向的那一个。清理与否另行请示。）

## 四、拟议方案

### 4.1 规则

- **48 小时内**的 `cmd_records.result_body` 全量保留，一个字不动。
- **超过 48 小时**的置空（`result_body=''`）。**行不删**：`msg_id`、原语名、
  时间、状态、错误码、`args`、`guards`、`idem_key` 等全部保留。
- 每天 **00:05** 执行一次，置空后紧接 `VACUUM`。
- 前置检查：没有活跃工作流、没有未收束命令，不满足即跳过当天
  （与现场数据上报的自动触发前置条件同一套）。
- **不分存量与增量**，同一套逻辑；首次运行自动收掉积压。

### 4.2 为什么是 48 小时而不是 24

诊断包自动上传**不重试、不补传**——客户端当天没开机，或到凌晨 2 点仍有活跃
工作流，当天就整个跳过。若本地只留 24 小时，漏传一天即等于那天的数据永久
蒸发。48 小时给了整整一倍余量：漏传一天，第二天的包里仍含着那天的数据，
**要连漏两天才会真丢**。

实测该客户机 8-02 至 8-07 每日 00:10 各一份，一天不缺。

### 4.3 为什么时点是 00:05

卡在 00:10 上传之前；业务窗口 `[00:00, 08:00)` 本就不允许开新活；跨 24 点
收束的尾巴按规格是"数十秒级"，到 00:05 已收干净。

### 4.4 为什么每天 VACUUM 而不是按需

实测（354MB 库，macOS）：

| 步骤 | 耗时 |
|---|---|
| 置空 12829 行 | 3.9 秒 |
| `VACUUM` | 5.5 秒 |
| 合计 | **< 10 秒** |

原本考虑过"靠 SQLite 页复用自然平衡、不必每天 VACUUM"，或"存量单独挑停机
时机人工执行"。10 秒的操作不值得为它引入第二套机制或人工流程。**甲方裁决：
机制越简单越好**，故统一为每天一次、存量增量同路。

（客户机为 Windows，磁盘更慢时按 5 倍估算仍在 50 秒内，距 5 分钟窗口有余。）

**实测偏差校正（落地时发现）。** 上表那次实测的切点算错了 8 小时：
`cmd_records.created_at` 存的是带 `+08:00` 偏移的本地时间，而当时构造的切点用的
是 UTC 表示，SQLite 直接按字符串比较，等于**实际保留了 56 小时而非 48 小时**。
因此 5.1 / 5.2 节的 222MB 是"保留 56 小时"的结果，真正的 48 小时会略小一些，
方向上偏保守，不影响任何结论。实现里不存在这个问题——它跟随 store 包既有惯例，
把 `time.Time` 直接交给 GORM 比较，写入与查询用同一套序列化。

落地时另在对齐真机规模的合成库（255MB、2.6 万行）上交叉验证了一次，
同一台开发机：置空 2 万行 0.56 秒、`VACUUM` 0.45 秒、文件 255MB → 54MB。
两次实测都确认了同一件事：**置空之后不 `VACUUM`，文件大小一字节不少。**

### 4.5 被否掉的方案：2–7 天抽样保留

裁决过程中甲方提过一个三档设想：48 小时全留、2–7 天抽样保留、更早全清。
抽样那一档经讨论后否掉，理由有两条：

**排查是取证，不是统计。** 查 bug 的场景永远是「4 号下午那个候选人怎么漏掉
的」，要的是**那几分钟**的快照。抽 10% 意味着九成概率要的那条恰好被抹了，而
手上留着的是一堆"别的时刻的代表性样本"，一条都用不上。更糟的是它给假的安心：
以为 7 天内都能查，真去查了才发现没有——不如一开始就知道"48 小时以外查不到"，
至少会赶在窗口内取证。

**算账也不支持。** 2–7 天是 5 天，按 10% 抽样只多占约 20MB，相比 48 小时那
80MB 几乎不影响总量。为 20MB 的差别增加一整档保留逻辑、一套测试和一个"这条
到底还在不在"的不确定性，不划算。

（讨论中提过一个比随机抽样更好的维度：按"与上一条内容有没有变"来筛——1.3 节
的数据显示 37% 的快照与上一条完全相同，去掉它们是零信息损失。但同样是为不到
20MB 的收益增加一档机制，甲方明确"机制越简单越好"，故一并不采纳。）

### 4.6 拟议的 AGENTS.md 文本修改

「AI provider 数据边界」末段，把

> 不可变 `CmdRecord.ResultBody` 审计快照

改为

> `CmdRecord.ResultBody` 审计快照（保留期内；超期按「命令审计留存」条目置空）

并在「全局约定」新增一条：

> - **命令审计留存（2026-08-07 甲方裁决）。** `cmd_records.result_body` 只保留
>   最近 48 小时，超期由脑在客户端本地时间每日 00:05 置空并 `VACUUM`；执行前
>   须确认没有活跃工作流与未收束命令，不满足即跳过当天，不补做。**行本身永不
>   删除**——`msg_id`、原语名、`idem_key`、`args`、`guards`、时间、状态与错误码
>   原样保留，「业务事实行禁止物理 `DELETE`」不因本条放宽。被置空的是命令返回
>   正文这一项取证材料，其副本存在于每日诊断包中（服务器留存 14 天），48 小时
>   窗口相对 24 小时上报周期留有一倍余量，可容忍漏传一天。甲方知情接受两项后果：
>   超过服务器留存期的返回正文此后无人持有；诊断需取回服务器包解压方可查阅，
>   不再能在同机诊断台直接读到。本条不改变 `result_body` 在保留期内的既有边界
>   与去处，也不授权对其他任何表或列做同类清理。

## 五、收益与成本

### 5.1 收益（实测，非估算）

在诊断包副本上完整跑过一次：

| | 现状 | 清理后 |
|---|---|---|
| `brain.db` | 354MB | **222MB** |
| 每日增长 | +40MB，无上限 | **0，封顶** |
| 每日诊断包 | 48MB 且在涨 | 约 30MB 且稳定 |

最重要的不是一次性省下的 130MB，而是**从"一年 14GB"变成"稳定在 200MB 出头"**。
服务器侧同步受益，14 天窗口的总量随之收敛。

### 5.2 剩下的 222MB 是什么（一并记录，供日后判断是否还要动）

| | 占用 | 说明 |
|---|---|---|
| `cmd_records` 表 | 163.6MB（74%） | |
| ├ `result_body` 文本 | 89.3MB | 其中 `chat.readList` 82MB |
| ├ 其余 52 列文本 | 16.4MB | |
| └ 页碎片开销 | 约 58MB | 单条 9.6KB 跨溢出页，末页留白，放大 55% |
| 其余全部表 | 36.3MB | |
| 全部索引 | 22.1MB | |

即：**清理后 48 小时内的 `readList` 仍占全库一半**。这是"保留 48 小时"的固有
价格，不是浪费。要再瘦只有两个杠杆——缩短窗口，或降低 `readList` 每 7～15 秒
一次的频率。后者动的是巡检节奏设计，不在本立案范围。

页大小从 4KB 调到 16KB 可压掉大部分碎片，但需整库重建、引入新的迁移路径，
为几十兆不值当，**不建议**。

### 5.3 成本

- **能力损失（真实）**：48 小时以外的命令返回正文，本机不再持有；服务器 14 天
  以外的，此后**无人持有**。现在本机有 7-29 起的完整历史，改完即失去。
- **排查体验下降**：查 2 天前的现场，要 SSH 或经管理前台取回 tar.gz、解压后
  才能查，不能像今天这样在同机直接读。
- **新增机制**：一个每日定时任务 + 前置检查，需测试覆盖"有活跃工作流时跳过"
  与"跳过后次日照常执行"。
- **不可逆**：置空的内容除诊断包外无处找回。

## 六、必答项：服务器留存清理尚未验证

本方案把"48 小时以外的历史"整体托付给诊断包链路，因此那条链路是否可靠成为前提。

**服务器上 14 天留存清理一次都没有触发过**——最老的包是 7-31 的，至今 7 天，
尚未到清理时点。若清理实现有误（未运行 → 磁盘继续涨；或过于激进 → 提前删），
本方案的兜底就是空的。

建议：**在实现落地前先确认该清理逻辑确实按 14 天工作**。这是只读核查，成本很低。

请甲方一并裁决：是否要在本立案落地前完成这项核查。

**裁决结果（2026-08-07）：不核查，直接落地。** 甲方接受该不确定性——即"服务器
帮忙存着 48 小时以外的历史"这个前提尚未被实际验证过。本必答项就此结案，不作为
未决项挂起。

- **2–7 天抽样保留不做**（理由见 4.5）。甲方要求"机制越简单越好"。

  （合计约 1 秒），由每日任务的第一次执行顺带清掉，不设人工流程。

落地按"规范先行 → 实现同步"执行：`ef3079e` 改规范，`b3c32b5` 落实现与测试。
