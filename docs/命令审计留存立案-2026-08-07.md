# 命令审计留存立案（2026-08-07）

**结论先说**：`cmd_records.result_body` 只保留最近 48 小时，超期由脑每天凌晨
00:05 置空并 `VACUUM`。**行本身永不删除**。甲方 2026-08-07 批准，条款进
AGENTS.md「全局约定·命令审计留存」。

本文是那条款的完整立案底稿：数据从哪来、为什么是 48 小时、放弃了什么、
接受了什么代价。

## 一、起因：一台客户机 10 天积到 354MB

排查另一件事（采集筛选偶发失败）时顺手看了眼客户机诊断包，发现 `brain.db`
已经 354MB。拆开看，大头集中得反常：

| 层级 | 占用 |
|---|---|
| `cmd_records` 一张表 | **280MB（79%）** |
| └ 其中 `chat.readList` 一个原语 | **143MB** |
| └ 其中 `chat.readThread` | 13MB |
| 其余所有表加起来 | 约 40MB |

作为对照：**所有聊天消息（`messages` 表）只有 2.2MB**。也就是说，真正的业务
事实占的空间，还不到那个只读命令留下的返回正文的六十分之一。

## 二、机制：每 7～15 秒存一份几乎一样的快照

`chat.readList` 是巡检用的只读对账命令，读一次会话列表。它的返回值被**全文**
写进 `cmd_records.result_body`，单条约 9.6KB，结构是：

```
data.sessions[29] —— 每项含 conversationRef / peer / positionTitle /
                     unreadCount / lastActivityTs / lastMessage
```

问题在于它跑得非常密。以 8 月 5 日全天为例：

- 全天 **4774 次**，共 **45.7MB**
- 业务时段每小时 250～500 次，**约每 7～15 秒一次**
- 而同一批会话身上真实发生的字段变化，全天只有 **163 次**

也就是说，同样的 29 条会话被反复快照了四千多次，其中绝大多数字节是上一条的
复制品。这些内容在 `conversations`、`messages` 等业务表里都有覆盖写的对应列，
`cmd_records` 里这份是重复的第二副本。

**而 `cmd_records` 此前没有任何清理机制，只增不减。**

增长速率（8 月 4 日装 1.7.2 后整体命令量涨了约 3 倍）：

| 日期 | readList 次数 | 当日新增 |
|---|---|---|
| 7-29 ～ 8-01 | 400～900 | 5～10MB |
| 8-04 | 3338 | 32.9MB |
| 8-05 | 4774 | 45.7MB |
| 8-06 | 3952 | 36.3MB |

外推：**每月约 1.2GB，一年约 14GB**。

## 三、连带后果：服务器那头一起涨

这台客户机开着每日自动上传（`field_report_settings.auto_upload_enabled = 1`），
每天 00:10 把整个 `brain.db` 打包传到服务器，保留 14 天。实测包的大小：

```
8-03  18.3M      8-06  39.5M
8-05  29.0M      8-07  48.4M
```

**每天涨约 10MB，而且因为库本身在膨胀，这个数字不会收敛。** 服务器 40G 磁盘
目前已用 8.6G，四个客户的诊断包共 588M。AGENTS.md 立「现场数据上报」时估过
"十客户规模下一年即耗尽磁盘"，那次估算还没算上库本身会长这一层。

## 四、方案与被否掉的选项

### 采纳：48 小时全保留，超期置空，行不删

分三点，每点都有理由：

**为什么是置空而不是删行。** 删掉行会让 `cmd_records` 的审计骨架断掉——事后连
"这条命令是什么、什么时候发的、成没成功"都答不上来，清理就从瘦身变成了毁证。
置空只丢返回正文，`msg_id`、原语名、`idem_key`、`args`、`guards`、时间、状态、
错误码全部原样保留。这同时避开了「业务事实行禁止物理 `DELETE`」那条线——本条
明确不放宽它。

**为什么是 48 小时而不是 24。** 诊断包上传是**不重试、不补传**的：客户端那天
没开机、或到凌晨 2 点还有活跃工作流，当天就直接跳过，第二天不补。若本地只留
24 小时，漏传一天等于那天的数据永久蒸发。48 小时给了整整一倍余量——漏传一天，
第二天的包里仍含着那天的数据，**要连漏两天才会真丢**。

**为什么排在 00:05。** 上报是 00:10。清理先跑完，当天上传的包就已经是瘦身后
的，一次凌晨把本机与服务器两头的膨胀一起收掉。

### 否掉：2–7 天抽样保留

甲方最初的设想是三档：48 小时全留、2–7 天抽样、更早全清。抽样这一档在讨论中
被否，理由是**排查是取证不是统计**：

查 bug 的场景永远是「4 号下午那个候选人怎么漏掉的」，要的是**那几分钟**的快照。
抽 10% 意味着九成概率要的那条恰好被抹了，而手上留着的是一堆"别的时刻的代表性
样本"，一条都用不上。更麻烦的是它给的是假的安心：以为 7 天内都能查，真去查了
才发现没有。

算账也不支持它：2–7 天是 5 天，按 10% 抽样只多占约 20MB，相比 48 小时那 80MB
几乎不影响总量。**为 20MB 的差别增加一整档保留逻辑、一套测试和一个"这条到底
还在不在"的不确定性，不划算。**

（讨论中提过一个比随机抽样更好的维度——按"与上一条内容有没有变"来筛，那天
4774 条能降到 2991 条且每次真实变化都在。最终仍未采纳：同样是为不到 20MB 的
收益增加一档机制，而甲方明确要"机制越简单越好"。）

### 否掉：存量单独处理

曾考虑给存量那 143MB 安排一次单独的人工清理流程。甲方判断"130M 不至于清很久，
机制越简单越好"，直接由每日任务的第一次执行顺带清掉。**实测证明这个判断是对
的**（见下节：1 秒）。

## 五、实测

真机库因 macOS 磁盘权限无法复制，改用对齐真机规模的合成库（255MB、2.6 万行、
其中 2 万行带 9.6KB 正文），开发机 SSD：

| 步骤 | 耗时 | 文件大小 |
|---|---|---|
| 起始 | — | 255.0 MB |
| 置空 2 万行 | 0.56 秒 | **255.0 MB（一字节没少）** |
| `VACUUM` | 0.45 秒 | **54.0 MB** |

两条结论：

1. **合计约 1 秒**，存量不需要特殊安排，第一次自动执行就清完了。
2. **不 `VACUUM` 的话文件纹丝不动**。SQLite 只把腾出的页标成空闲留着复用，
   `brain.db` 还是原大小，诊断包照样每天传三百多兆——服务器那头一分没省。
   所以 `VACUUM` 不是可选的收尾。

预期稳态：`brain.db` 从 354MB 降到 **130MB 上下并封顶**，诊断包从 48MB 降到
**15MB 上下**。

## 六、甲方知情接受的代价

1. **超过服务器 14 天留存期的返回正文，此后无人持有。** 本地删了、服务器也过
   期了，那段历史就真没了。
2. **查两天前的现场要取回诊断包解压**，不能在同机诊断台直读。47MB 的包解出来
   400MB，不是"随手查"。
3. **置空不可逆。** 没有撤销，没有回收站。
4. 服务器侧的 14 天留存清理**至今一次未触发**（最老的包才 7 天），也就是说
   "服务器帮忙存着历史"这个前提尚未被实际验证过。甲方 2026-08-07 裁决不为此
   做前置核查，接受该不确定性。

## 七、不在本次范围

- **`chat.readList` 本身的调用频率**（每 7～15 秒一次）没有动。本次只处理"存
  下来的东西"，不碰"读得多勤"。若日后要减，那是巡检节奏的独立议题。
- **`ai-traces.db`**（35MB）不在本条款范围，其保留策略已于 2026-08-07 另行裁决
  维持现状（无限期保留、不加密、无开关）。
- **服务器上 `/srv/console/rh-updates/pkg` 堆积的 33 个旧版安装包（3.0G）**：
  排查中顺带发现，客户端只认 `latest.json` 指向的那一个，其余是纯浪费。属于
  独立的运维小事，未在本次处理。
