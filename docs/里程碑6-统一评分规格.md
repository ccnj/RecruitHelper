# 里程碑 6：统一评分规格

日期：2026-07-22

状态：甲方已批准《端到端业务主线计划》中的统一评分阶段；本文按该既有授权冻结最窄实现语义，不扩展到筛选、建档、招呼或沟通。

## 一、出口与边界

本阶段消费一个明确且已经 `completed` 的正式 `SourcingBatch`，串行评分它的全部成员。出口是每个成员都有且仅有一条终局评分调用事实：合法的 1～10 分，或明确的失败终局；全部成员终局后，批次评分进度才算完成。

本阶段不读取后台候选人筛选阈值、不产生入选名单、不建立 CandidateProfile、不生成招呼语、不打开平台页面、不调用手端原语，也不创建任何 effect intent。AI 只给分，后续确定性筛选另批实现。

## 二、批次范围与配置绑定

1. 评分入口只接受随机 `batchId`。账号、配置 revision 和成员集合只能从该批次事实反查，调用方不得另传并覆盖。
2. 批次必须是 `completed` 且 `endedAt` 非空，成员数必须恰好等于 `targetCount`；`preparing/collecting/blocked/stopped` 批次一律拒绝评分。
3. 评分只查询 `run.batchId = batchId` 的成员，固定按 `capturedAt, runId` 顺序处理；同账号、同 revision 的其他批次和 `batchId=NULL` 历史行不得进入。
4. 批次与成员已有的 `contextRevisionHash` 只记录采集实际使用的配置，不再主导评分路由。评分阶段在首条 provider 调用预留前，以 `SourcingBatch.BackendJobID` 读取该职位最近一次成功同步的 `legacyJobConfig` revision；首条预留落库后，该 revision 即成为本次评分运行的阶段事实，余下成员继续沿用，不能因 head 更新而在同一批混用配置。后续筛选阶段可以重新读取更新后的 head。
5. 第一个已预留调用的 `provider/model` 组合冻结本批后续调用；恢复时本地配置若已变更，必须在新预留前停止，不得把不同模型结果静默混入同一批次。每条调用仍如实记录自己的 provider/model、输入输出 hash、用量、费用和错误分类。

## 三、`ScoringInputV1`

旧客户端实际把插件简历对象投影成固定中文结构后替换 `{resume_json}`；正式后台 prompt 尚未用新仓库的原始 canonical JSON 真机评分。新实现因此冻结版本化 `ScoringInputV1`，不把未经验证的内部存储形态直接暴露给 prompt。

1. 输出顶层固定为 `基本 / 期望 / 自评 / 工作经历 / 教育经历 / 简历全文`。
2. `基本` 只映射快照中实际存在的标签：`工作经验→工作年限`、`现居地→现居`，其他非姓名标签原样保留；缺失的 `性别/年龄/工作年限/最高学历/求职状态/现居` 以空字符串表达。不得从姓名、称谓或其他文本推断性别等事实。
3. 候选人姓名不进入结构化模型输入；平台用户 ID、账号、职位/会话/档案引用和 `resumeNumber` 永远不进入。
4. `期望` 保留快照已有的标签和值；当前正式采集只有整块 `求职期望` 时原样保留，不把其文本猜拆成期望职位、薪资或地点。旧结构中缺失的 `期望职位/期望薪资/最近投递` 以空字符串表达。
5. `自评/工作经历/教育经历` 延续旧客户端的字符上限 1500/1500/500；当前快照没有独立“简历全文”来源，固定为空，不拿其他字段拼造替代品。这是 `ScoringInputV1` 固定业务投影的一部分，不是 token 预算补救；渲染完成后不得再按字节数、token 估算或 provider 结果动态缩减这些字段。
6. 投影以合成 fixture 固化字段名、缺失语义、截断和确定性 JSON 序列化。投影只参与 provider 输入与输入 hash，不额外持久化一份候选人正文。

## 四、一次性调用与收敛

1. `SourcingScoreInvocation.runId` 唯一约束继续充当一次性 provider 授权。预留事务必须同时重核：成员属于目标批次、批次已完成、成员采集 revision 等于批次采集 revision、成员内容 hash 未变、调用 revision 属于批次 `BackendJobID`，且等于本评分阶段首条既有预留的 revision；完全没有预留时还必须等于事务内重读的 current legacy head。
2. 只有首次成功插入预留的执行者可以调用 provider；成功、provider 拒绝、传输失败、输出无效、预算阻断和 in-flight 都禁止自动二次调用。
3. 服务启动时把崩溃遗留的 `finishedAt=NULL` 评分预留终局化为 `transportFailed + processInterrupted`，绝不重调 provider。之后再次运行同一批次只继续尚无预留的成员。
4. 单个成员失败是该成员的明确终局，不阻断后续成员；合法分数必须是 1～10 的 JSON 整数并继续通过非思考用量闸。模型返回的解释字段本阶段丢弃，业务库只保存分数和既有脱敏调用审计。
5. 进度只按目标成员聚合：`ok + failed + inFlight + pending = targetCount`。只有 `finishedAt` 非空才计入 `ok/failed`；仅存在预留不得冒充完成。
6. 评分属于 P 档非 intent 用途，输入上限固定为 provider `usage.prompt_tokens <= 16000`；该字段是 token 数和预算裁决的唯一权威来源。本地不得以请求正文 UTF-8 字节数、tokenizer 估算或其他启发式提前判定 token 超限。
7. 完整序列化请求 JSON 另受首版 256 KiB UTF-8 运输硬上限约束，它与 token 预算严格分离。越过运输上限在 provider 前终局为 `transportFailed/requestPayloadTooLarge`，usage/成本为零，不得记成 `budgetBlocked`。provider 响应缺少或携带非法 `prompt_tokens/completion_tokens` 时以 `invalidOutput/responseInvalid` 失败，模型正文不得被采用。
8. 合法响应若报告 `prompt_tokens > 16000`，仍须保存 provider 返回的真实 input/cache/output/reasoning usage、既有脱敏 hash 与据此计算的成本，再以 `budgetBlocked/inputTokenBudgetExceeded` 终局化；`score` 必须为空，且不得形成 selection、profile、招呼语、action、effect intent 或手端调用。不得为规避预算截断/缩减既定投影、换档、换模型或自动重试；M5 已发生事故的唯一 attempt 2 许可不适用于评分。

## 五、首版运行方式

首版提供本地管理端显式 `run + status`：`run` 在脑内串行执行并复用既有 provider，完全独立于账号每日巡检、手在线状态和 IM。请求取消时只收敛当前已经预留的成员并停止；再次调用从无预留成员继续。重复调用不会对任何既有成员产生第二次 provider 请求。

本阶段不先造通用后台任务框架或并发 worker。3 人真实冒烟先验证正式 prompt、输入投影、逐人成败与完整批次屏障；150 人真实耗时若证明同步本地调用妨碍可用性，再用本规格不变的账本事实另立后台化优化。

## 六、机制成本与停止条件

当前可达损失是旧账号/revision 查询混入历史或其他批次、崩溃预留永远悬空，以及旧 actor 评分后继续进入筛选/招呼。最窄闭环只增加 batch-scoped 读口、预留复核、中断终局化、聚合状态和独立脑侧 scorer；不新增脑手契约、平台原语或通用任务表。

自动化门禁必须证明：混合历史数据只评分目标批；错批次/revision/content 被拒绝；成功、provider 失败和非法输出均成为不同成员终局；进程中断不重调；provider 缺失时零预留；多字节输入不能被 UTF-8 字节数误判 token 超限；完整请求 JSON 的 256 KiB 前后分别得到正常调用与独立运输失败；缺 usage 响亮失败；provider 报告 16000/16001 `prompt_tokens` 时分别放行与保存真实计量/成本后的 `budgetBlocked`，后者 score 为空；全程 selection/profile/greeting/action/effect intent/effectful command 与手端调用均为零。

停止条件是正式 3 人批次全部得到评分或明确失败、脱敏进度可查、真实页面完全未被触碰，并完成一轮阻断级独立审查。达到后立即提交冒烟记录并转入“配置化筛选”，不在本批顺手实现下一阶段。
