### 1.3 联动与顺序约束

1. **薪资三段联动。** 空表单上薪资行只有「最低月薪」一个控件,DOM 中不存在(连隐藏的也没有)最高月薪与薪资月数节点。选定最低月薪后整行才渲染为 `[最低] － [最高] × [月数]`。
2. **最高月薪上限为最低月薪的 2 倍。** 实测最低选「1万」时,最高月薪可选项为 1.1万～2万共 10 档。**后台 `validate_publish_params` 不校验此关系**,运营可存入平台不接受的组合。
3. **职位类别必须由我们自己选,平台只是"有时会替你填"**(2026-07-30 修订,原文写作"自动生成、无法手动预填",已被证伪)。
   - 只填职位名称、不填描述:类别恒为「请选择」,且**类别选择器点了打不开**;
   - 填入工作性质、职位名称、描述并失焦后,选择器才可打开(不是立刻,要等平台加载);
   - 平台**只在自己有把握时**才自动填上一个并挂「推荐」徽标(实测 `储备总监`、`财富传承顾问` 会填,`家庭财务规划师` 不填);
   - 不自动填**不代表没有候选**——打开选择器仍有数个候选,见 §1.8。
   - 因此**职位描述必须先于任何依赖类别的操作填入**,自动化中不能把描述放在最后。
4. **职位关键词弹层同样依赖描述。** 描述未填时点击「+」无任何弹层(早期考察一度误判为控件故障);描述填入后点击即正常打开。

### 1.4 职位关键词弹层(结构随职位类别变化)

弹层标题「选择职位关键词,为您推荐『更精准』人才」。**分组数量、分组名称与词库均随职位类别变化**,实测两例:

| | 储备总监(类别=储备经理人) | 财富传承顾问-法税(类别=财务咨询顾问) |
|---|---|---|
| 分组数 | 4 组 | 7 组以上,另有「更多」折叠 |
| 分组名 | 行业经验 / 工作方向 / 证书 / 其他招聘要求 | 行业经验 / 财务管理方向 / 咨询方式 / 管理咨询方向 / 市场调研方向 / 证书·职称 / 其他招聘要求 |
| 行业组词库 | 保险·银行·投资与资产管理·信托·金融科技/数字金融·社会事业与服务·基金·课外培训与资格考试·咨询服务·证券/期货 | 财务/审计/税务·法律·咨询服务·保险·商务服务业·投资与资产管理·银行·技术服务·专利/商标/知识产权 |
| 证书组词库 | 大学英语四级 / 大学英语六级 | FRM·会计从业资格证·CPA(专业阶段通过/全科通过/非执业会员/执业会员)·ACCA·AICPA·CPAA |
| 自动预选 | 预选「保险」(占 1/3) | 无预选(已选 0/11) |

**稳定事实(两例一致)**:
- 总配额 **11**,弹层底部显示「已选: x / 11」;
- 各分组有独立子配额(观察到 3 / 3 / 2 / 3);
- 每组均有「+ 自定义」入口,可输入词库外的词;
- 已选词条可取消(点击已选区词条的 ×,计数即回落)。

**不稳定事实**:分组结构、词库内容、是否自动预选,均随职位而变。因此**关键词的匹配结果无法离线预检**。

**复合词条**:词库存在 `财务/审计/税务`、`专利/商标/知识产权`、`金融科技/数字金融`、`证券/期货` 等以斜杠合并的词条。`税务`、`审计` 这类单词与它们**不全等**,因此选词方(2026-07-31 起是大模型)想要其中之一时,拿到的是整条复合标签,不能拆。

#### 1.4.1 用完整发布参数试填后的修订(2026-07-30)

上表来自手工考察时用**短描述**触发的分组。用真实完整描述(1400 余字)经手侧原语试填后,以下几条必须修订:

1. **分组结构不只由职位类别决定,也由描述内容决定。** 同为类别「储备经理人」,短描述得到 4 组、完整描述只得到 2 组。因此上表的分组列只是样本,不是该类别的固定形态。
2. **每个分组的上限是 3(甲方 2026-07-30 确认),但并非全部为 3** ——实测「您期望候选人具备的证书是？」为 2。实现不得硬编码组内上限,只认平台的拒绝行为。
3. **兜底组「您还有哪些招聘要求？」始终存在,但 DOM 结构与其他分组不同**:它不在 `li.s-checkbutton-drilldown-multi-limit__list-item` 里,按该选择器统计分组会漏掉它,并误得出"这个职位没有兜底组"的结论(执行方一度据此误判)。可靠判据是按标题形态「……？ (已选/上限)」匹配。
4. **组内配额占满后,平台不再给出自定义输入框**,而不是给出后再拒绝。表现为"等待输入框超时",必须与"输入框尚未渲染"同样处理为该词装不下,记入 `dropped` 后继续,不能整体失败。
5. **必须先有职位类别才能操作关键词**(甲方 2026-07-30 确认)。顺序是:填描述 → 失焦 → **选定类别** → 关键词弹层才可打开。类别为「请选择」时点关键词入口无任何反应。类别现在由我们自己选(§1.8、§2.7),不再等平台自动填。
6. **分组词库随选定的类别变化**,所以我们选哪个类别会改变关键词的落点。这是选类别的连带后果,不是缺陷。

实测落点(两例均为未命中词全部进兜底组):

| 职位 | 类别 | 关键词处理结果 |
|---|---|---|
| 储备总监(管理经验优先) | 储备经理人 | 自定义 创业/销售/团队管理 —— 刚好用满兜底组 3 个位 |
| 财富传承顾问(法律/财务/税务背景优先) | 理财顾问 | 自定义 法律/税务/会计;**审计因兜底组配额已满被丢弃** |

#### 1.4.3 关键词弹层有两个组件变体(2026-07-30,由试填失败暴露)

**分组与词条的 DOM 块名随选定的职位类别变化**,不是只有词库变。实测两个变体:

| 选定类别 | 词条类名 | 分组配额 | 标题形态 |
|---|---|---|---|
| 理财顾问 / 储备经理人 | `li.s-checkbutton-drilldown-multi-limit__item` | 有,`(0/3)` | 问句 + 计数,如「您还有哪些招聘要求？ (0/3)」 |
| 财务咨询顾问 | `li.s-checkbutton-drilldown-multi__item` | 无 | 纯名词,如「财务管理方向」「咨询方式」 |

注意块名差在 `-limit`:`...multi-limit__item` 与 `...multi__item` 是两个不同的 BEM 块,不是修饰符。把 `-limit` 写死会在换类别后**整批读不到分组与词条**,表现为「关键词弹层未在期限内加载出分组」——弹层其实开着、分组也渲染了,是选择器空转。这正是 2026-07-30 `财富传承顾问(法律/财务/税务背景优先)` 换选 `财务咨询顾问` 后试填失败的原因。

可靠形态(两变体实测一致):

- 词条:`li[class*="s-checkbutton-drilldown-multi"][class*="__item"]`,必须排除 `[class*="__item__add"]`(自定义入口本身也带 `__item`)。
- 自定义入口:`li[class*="s-checkbutton-drilldown-multi"][class*="__item__add"]`,只认可见的,取最后一个即兜底组。
- **分组标题:`[class*="s-checkbutton-drilldown-multi"][class*="__list-item-title"]`。** 它比按 `(已选/上限)` 计数硬凑稳,而且天然覆盖结构与众不同的兜底组——实测标题数(6)比 `__list-item` 数(5)多一个,多出来的就是它。带配额变体的标题类名还没在真机核对过,所以实现里两条来源取并集。
- 确定按钮仍是 `.s-button` 里文案以「确定」开头的那个,总配额仍显示「已选: x / 11」。

这条是**我们接管类别选择的连带后果**:以前类别由平台自动填,实际只见过带配额那个变体;我们自己选之后才碰到另一个。

#### 1.4.2 年龄合规提示与类别无关(2026-07-30 修订,原结论已证伪)

**原结论是错的,不要再引用。** 原文写作"`家庭财务规划师(HR/培训/市场背景优先)` 的描述含年龄表述,平台因此拒绝判定职位类别"。2026-07-30 逐项验证推翻了它:

- 那句提示是**常驻静态说明**,不是校验结果:`<p class="job-required-hide-age-tip">`,由账号级接口 `POST /api/job/getJobRequiredHideAgeInfo` 驱动(实测返回 `{"requiredHideAge":true,"minAge":"16","maxAge":"16"}`),与描述内容无关。已成功发布的 `储备总监`、`财富传承顾问` 也都带这句话。
- 平台的内容校验**是通过的**:`POST /api/job/check/jobDescribe` 与 `POST /api/job/check/jobTitle` 均返回 `{"level":"SUCCESS","message":"通过"}`。
- 描述失焦后触发的推断接口是 `POST /api/job/check/reasoningDetail/new`,实测只回 `{"education":4,"workAge":null}`——**响应里没有职位类别**。整个失焦流程里没有任何一个请求在判定类别。

真实原因是平台对这个职位**不自动填类别**,而旧实现在等一个不会到来的值,30 秒轮询耗尽。打开选择器就能看到它其实给了 4 个候选。见 §1.8。

年龄规则本身确实存在且影响 C 端展示:职位管理列表页的 `家庭资产配置顾问(房地产背景优先)` 卡片挂着「职位名称/描述中不可写年龄要求、已在 C 端隐藏」与「去编辑」,即该职位虽在线但求职者看不到。**但它不阻断发布,也不阻断类别。**

### 1.5 职位管理列表页

列表页 `https://rd6.zhaopin.com/app/job`。

- 职位名选择器 `a.job-item__title--jobname`,实测提取准确。
- 状态由顶部 tab 区分:**在线中 / 未上线 / 审核中 / 未过审**,tab 文本形如 `在线中 · 2`(无数字即 0),选中态为 `is-active`。
- 顶部「全部职位」下拉是**归属筛选**(全部职位 / 我发布的职位 / 协作给我的职位),**不是状态筛选**。要覆盖全部状态只能逐 tab 遍历。
- 每个职位卡片带操作:在线职位有「修改 / 下线 / 复制」等;未上线职位有「删除 / 修改 / **上线**」。
- **已下线的职位可直接一键「上线」**,不需要重新走发布流程。
- 分页默认每页 20 条;账号显示「可上线职位数 59 个」,存在超过单页的可能。
- **「审核中」的职位会出现在我们的列表读取结果里**(2026-07-30 真机验证:`#17` 发布后进入审核中,`job.readPublishedList` 与预检立刻把它读成 `existing`,平台在架计数 4→5)。因此 `expectAbsentOnPlatform` 这道幂等闸覆盖审核中的职位,不会因为"还没上线"而放过一次重复发布。
- 发布后的落点**不固定**:`#15` 直接进「在线中」,`#17` 进「审核中」(点击忽略敏感词提示后平台跳转到 `?status=REVIEWING`)。正证判据按 §2.3 只认"同名职位出现在列表",不区分分区,所以两种落点都成立。

#### 1.5.1 下线入口与二次确认层(2026-08-13 真机实测)

为 `job.takeOffline` 立案时逐条核对,含一次对测试职位的真实下线。

- 每行的下线入口是 `a[zp-stat-id="job-action-offline"]`,位于行内 `div.job-item__sub-actions`。行是 `div.job-list > div.job-item`,职位名仍是 `a.job-item__title--jobname`(与 §1.5 同一套选择器,可整个复用)。同一操作条里另有 `job-action-share / job-action-edit / job-action-newcopy` 与 `rd_cooperation`,四项都带 `zp-stat-id`,语义明确、属低脆锚点。
- **点这个入口只打开确认层,不产生任何副作用**。副作用发生在确认层的按钮上。
- 确认层是**全局单例** `.km-modal.km-modal--open.km-modal--message-box`,文案「确定要下线该职位吗?」——**不含职位名**。确认按钮 `button.km-button--primary.km-button--filled`(文案「下线」),取消按钮 `.km-button--light.km-button--outlined.default-button`(文案「取消」);两个按钮**都没有** `zp-stat-id`。
- **页面里同时存在数十个 `.km-modal`,且数量随操作增减**(下线前 31 个、下线后 28 个)。判别"确认层开着没有"**只能靠 `km-modal--open` 且实际可见**,绝不能靠存在性或计数——隐藏的历史弹层里同样躺着「确定要下线该职位吗?」的文本。
- 确认层不含职位名,直接决定了目标绑定的位置:**绑定必须在点入口那一刻凭同一个 DOM 行锁死**,点开到点确认之间不得重读列表、不得重新定位。协议规格因此为本原语立了「『在线中』分区内同名职位唯一」的硬前置。
- 下线后的可观察变化(实测,点确认到列表更新在 1.2 秒内):「在线中」计数减一、「未上线」计数加一、分页「共 N 条」同步减一、该职位名从在线中列表消失,并出现在「未上线」分区、带一个 `手动下线` 标签。**该标签纯诊断,不作判据**。
- 无成功 toast。
- 下线**可逆**:未上线分区该行的操作是「删除 / 修改 / **上线**」(与 §1.5 一致),点「上线」即可恢复。下线不清除该职位已积累的招呼数(实测「11 新招呼」原样保留)。

## 二、甲方裁决(2026-07-29)

### 2.1 职位名来源

发布时填入平台的职位名称**必须取 `job.name`**,不得取 `发布参数.职位名称`。理由与完整条款见 AGENTS.md 相关约定与本仓库 memory;要点是 `job.name` 是系统的职位身份键(旧后台按归一化职位名去重,client/program 两侧按职位名把候选人匹配到职位配置),而发布参数中的职位名称无任何机制保证与之同步,漂移会导致平台职位与后台配置对不上号。

两者不一致时:**照常用 `job.name` 发布、不阻塞**,但须在表格/日志标出提示,让运营看得见 JSON 中该行未生效。

### 2.2 死字段

发布参数中有三个字段不参与发布:

| 字段 | 原因 |
|---|---|
| `职位名称` | 按 2.1 走 `job.name` |
| `职位类别` | 按 2.7 一律由大模型从平台候选中选定 |
| `职位关键词` | 按 2.4 一律由大模型从平台当前词库中选定 |

预检报告须明确列出"该字段不参与发布",避免运营误以为生效。

**`职位类别` 曾在此列,2026-07-30 移出,2026-07-31 移回。** 原始理由"平台按职位描述自动判定、人工不填"在 07-30 被证伪(平台只在自己有把握时才自动填,不填时会给一组候选让人选,见 §1.8),它随即改作"后台配置值与平台候选精确匹配"的首选来源。07-31 移回本表:三例真机(`销售总监`、`财务经理`、`培训经理/主管`)的配置值**全部不在平台候选里**,精确匹配三战三败,留着只是多一套失败模式与两条并存路径。

**`职位关键词` 2026-07-31 新入本表。** 原来按后台数组逐项匹配平台词库;改为由大模型看着平台当前实际词库选 3-5 个(§2.4)。后果之一是预检不再校验关键词——现在因"缺少职位关键词/关键词重复/超过 11 个"被判 `blocked` 的职位会变成可发。这是裁决的直接后果,不是疏漏。

### 2.3 幂等口径

**不依赖任何后台或本地状态,以平台实时状态为唯一真相。**

- 发布前读职位管理列表,**只比对职位名**;
- **同名职位存在即不允许重发**,不区分在线中/未上线/审核中/未过审;
- 名字比对做**归一化**(至少统一全半角括号与空格)。归一化**只放宽匹配、不放宽发布**:判断是否已存在用宽松比较,真发时仍用原始 `job.name`。误判方向因此偏向"以为已存在而跳过",即少发。

不新增任何 client → 后台的写接口;后台不记录发布状态。

**账本闸只防误重发,不禁止再次发布(2026-07-30 甲方裁决)。** 意图身份由「职位 + 发布参数 + 尝试序号」派生:同一序号内只允许发一次,HTTP 重试收编原意图,不另铸一个。既有意图**已终局**(`ok` / `resolvedOk` / `failed` / `resolvedFailed`)时,运营显式再发就递进尝试序号铸造新意图,并留一条 `job_publish_reattempt` 审计;旧意图是永久终局,不原地复活、不改写业务事实。

- **理由**:账本闸的本意是防误重发(HTTP 重试、连点两下),不是禁止一次新的业务行为。发布 → 下架/删除 → 重新发布是正常招聘动作;卡死它等于删过的职位永远发不了,一次干净失败(守卫没过、表单填不进去)也会把该职位这份参数永久锁死。
- **真正的防重复闸是 `expectAbsentOnPlatform`**——点击前的平台实读,比哈希比对强得多。职位还在时那道闸让本次干净失败(`sideEffect=none`),不会产生重复职位。
- **`suspect` 与在途(`dispatching`/`reconciling`/`verifying`)绝不许被新尝试绕过**,否则 idemKey 冻结形同虚设:结果未知必须先由人裁决。未知状态一律按未收束处理。

### 2.4 关键词处理(2026-07-31 甲方裁决整节重写)

1. 关键词一律由大模型选定,后台配置的 `职位关键词` 不参与发布(§2.2)。
2. 选词的唯一输入是**平台当前实际词库**:必须先定类别(§2.7),再打开弹层、展开「更多」、清空平台预选(消除自动预选带来的配额与不确定性),**按分组**读回全部词条与各组已选/上限。分组不能丢——组内上限是 3,模型看不见分组就会把词堆在一组里被平台拒掉。
3. 模型须返回 **3-5 个**关键词,其中不在词库里的自定义词**最多 3 个**(2026-08-16 甲方裁决由 2 改为 3,当日先短暂去掉过、随即改判为 3;原 2 的理由是"兜底组硬上限是 3,留一格余量")。这道复核是兜底组容量的唯一守卫——自定义词不属于任何分组、不计入第 6 条的组内配额复核,兜底组的 limit 在脑侧永远不会被触发。3 即贴齐该组平台容量、不再留余量:某职位的兜底组实际只放得下 2 个时,第 3 个由手侧按第 6 条记 `dropped` 继续,失效方向是关键词少一个而不是发错。
4. 返回值逐字回词库核对:在词库里的落 `matched`(点选),不在的落 `custom`,走 **「您还有哪些招聘要求？」组的「+ 自定义」**(该组无预设词条,语义上即兜底组)。两个去向沿用 `JobPrepareDraftKeywordOutcome` 既有的字段名,不另造词。**绝不模糊匹配、绝不拆分斜杠复合词条**(拆分会使 `税务` 命中 `财务/审计/税务`,顺带给职位打上财务与审计标签,超出运营本意)。
5. "选不出来"有五种:数量越界、词重复、自定义超 3、返回不是合法 JSON、provider 调用失败(第三种的阈值 2026-08-16 由 2 改为 3)。五种都重试,**至多 3 次**,仍不行则干净失败(点击前,`sideEffect=none`),把词库与失败分类报给运营。
6. 手侧填充规则不变:命中即点选(**分组无须我方决策**,词条属于哪组由平台词库结构决定),未命中走兜底组自定义,组内配额占满则丢弃并如实记 `dropped`,**不转投其他组**(转了语义即变)。
7. 打开弹层前**必须已填职位描述、且已选定职位类别**,两者缺一弹层都打不开(§1.4.1 第 5 条)。
8. 总配额 11 仍是平台硬上限,但 3-5 的约束更严,实际不会触及。
9. 词库与选词结果**不进预检**(词库随类别与描述变化,无法离线判定),作为发布过程产出记录。
10. **平台这次给出的词库必须原样回显给运营**(甲方 2026-08-01 裁决):按分组列出每个词条,并标出哪几个被选中。理由是选词的封闭候选集只有这一次机会被看见——弹层关掉就没了,而词库随类别与描述变化、事后无从复原。只显示分组标题不够:运营无法判断"模型是没选到好词,还是平台压根没给"。

**提示词硬规则**(甲方 2026-07-31 审定,2026-08-01 两次增补,2026-08-16 自定义上限由 2 改为 3):只能返回 3-5 个词;**优先选词库里已有的词**,不在词库里的自定义词至多 3 个;**不选带「保险」字样或以保险从业为核心的词**;**判据是"我们想吸引的候选人身上会有什么标签",不是"这个岗位在做什么"**;必须做决策、不许弃选。

**选词判据面向候选人,不面向岗位(甲方 2026-08-01 裁决)。** 关键词在平台上的作用是把职位**匹配给求职者**,也是求职者搜索时的入口——它匹配的是候选人的简历,不是岗位的职责书。因此选词必须先读职位描述里讲"**什么样的人适合**"的那一段(背景、行业、经历、资质偏好),把它当作我们要吸引的人群画像,再据此推测这些候选人简历上会出现哪些词,最后从平台词库里挑最可能命中的。

- 反例:岗位靠"家族传承沙龙"获客,就选一个描述岗位动作的词;正例:我们要的人做过会展销售、带过大客户、有证券从业资格,就选这些**候选人身上的**标签。
- 这条不放宽"描述里找不到依据的词不要选":人群画像本身必须出自描述,不是凭空想象一批人。
- 与既有规则的关系:它替换原来的"必须与职位名称、描述的实际内容相符",不改变数量、自定义上限、组内配额与避开保险这几条(自定义上限当时是 2,2026-08-16 改为 3)。

避开保险的理由与 §2.7 类别那条同源:关键词决定平台把职位匹配给哪些求职者,这些岗位招的是从别的行业转行来的人,打上保险标签会把职位推给已在保险业内的人,与招聘意图相反且池子更窄。**它与类别那条一样只是提示词偏好,不是闸**——确定性代码只核对数量、重复、自定义上限与组内配额,不按词面拦保险。理由:词库里没有"候选全是保险"这种死局(总能从别的分组选或自己写),但把它做成硬闸会在某个职位的词库确实偏保险时把整条链卡住,而这类岗位本来就沾保险,少一个词的损失远小于发不出去。

**数据边界**:与 §2.7 同——请求只带职位名、职位描述、选定类别与分组词库,全是职位上下文,不带任何候选人身份字段。审计只留无正文诊断,不写提示词、模型原文与选定词。

### 2.4.1 敏感词确认层自动点「忽略」(2026-07-30 甲方裁决)

出现 §1.7 的敏感词确认层时,`job.publishDraft` **自动点一次「忽略」继续发布**,不停下来等人。

- **理由**:弹层开着职位就不会创建,不处理它等于任何触发敏感词的职位都必然停在弹层上、最后落成 suspect,要人工兜每一条。
- **这不是"第二次点击发布"**,而是同一个不可逆动作的确认续做。原语内"绝不重试、绝不第二次点击发布"不变。
- **只在三个条件同时成立时点**:可见的敏感词弹层唯一、文案确属敏感词提示(含「敏感词」与「忽略」)、「忽略」按钮唯一且未禁用。任何一条不满足都不猜,直接按 `sideEffect=possible` 交给发后回读与人工。
- **绝不点「修改」**。
- 弹层原话(含敏感词与所在字段)必须带进 `platformFeedback`,否则运营不知道是哪个词触发的。它只作诊断,不参与判定。
- 正证判据不变:仍然只认发布后职位管理列表里出现同名职位。

### 2.5 客户端流程(2026-07-31 甲方裁决改为两段式)

1. **预检。** 一个按钮「全部发布前预检」:手读取职位管理列表,回报平台现存职位名;客户端按 2.3 口径逐个校验,并附加确定性参数校验(薪资 2 倍上限、必填齐全)。结论分三类:**可发布**(默认勾选)/ **平台已存在**(显示不勾选)/ **参数有问题**(置灰并写明原因)。
2. **阶段 A(零副作用)。** 分三段,不再是逐个职位串到底(2026-08-01 甲方裁决,理由见 §2.7):
   - **A1 收候选**:对全部可发职位逐个派 `job.readClassCandidates`,只收候选、不定类别。单个职位读失败即标记跳过,继续读其余。
   - **全局分配**:把收齐的候选一次性交给大模型,产出「职位 → 类别」的分配表。
   - **A2 选词**:对拿到类别的职位逐个派 `job.readKeywordVocabulary` 并选定关键词。单个失败即标记跳过。

   全程不点击任何提交控件,可以任意重跑。
3. **二次确认清单。** 每行显示职位名、选定类别(置信度/理由)、选定关键词(区分词库命中与自定义)、预检结论。**默认全选所有可发职位**,可单独取消;不可发的显示原因。**与别的职位撞上同一个类别的行必须标出来**(§2.7),人工在此改选类别时若造成新的撞车,同样即时标出但不拦——人说了算。
4. **阶段 B(副作用)。** 点击「确认发布(共 x 个)」后逐个真发。单个职位干净失败或 `suspect`,**跳过当前,继续下一个**;`suspect` 的意图按 2.3 永久冻结、等人裁决,**绝不在本批内重试或另铸同义意图**。

两段之间必须有人确认,不是为了流程仪式:类别与关键词现在都由大模型选,§2.7 的"真正的闸是发布前运营看得见类别再确认"因此同时覆盖关键词。

阶段 B 不设"连续 suspect 熔断"。若 suspect 的成因是系统性的(掉登录、平台改版),会堆出多条待裁决;甲方 2026-07-31 知情接受这一代价,以换取一次系统性故障不吃掉整批的可发职位。

### 2.6 明确接受的风险

**预检快照与实际发布之间的 TOCTOU 不做防护。** 执行方曾建议每个职位提交前重查一次平台,甲方裁决**不考虑,概率太低**。据此,循环发布期间以预检快照为准,不再逐个复查。本条为知情接受,非疏漏。

### 2.7 职位类别全批统一分配,尽量互不相同(2026-07-30 甲方裁决,2026-07-31 删去精确匹配支,2026-08-01 改为全批统一分配)

**不再等平台自动填类别,一律自己选**;平台已经预填的也重选。理由:平台什么时候会预填我们至今没摸清规律,把行为建立在没摸清的条件上会再咬一次,而且两条路径意味着两套失败模式。

**2026-08-01 甲方裁决:类别不再逐个职位单独问模型,改为收齐全部待发职位的候选清单后一次性统一分配,并要求尽量让各职位落到不同的类别上。** 理由是发多个职位的核心诉求是**扩充候选人池**:类别决定平台把职位推给哪一类求职者,若十几个职位全落进同一个类别,平台就把它们推给同一批人,多发的那些等于白发。逐个决策时模型看不见别的职位在选什么,撞车完全没人管。

决策链:

1. 职位类别由大模型**一次性为全批职位分配**,输入是每个职位的名称、描述原文与它自己的候选清单及平台释义。提示词见下。原"后台配置值与平台候选归一化精确匹配优先"已于 2026-07-31 删除,理由见 §2.2。
2. 模型返回**类别名文本**而不是序号:读候选与真正选中之间隔着若干趟,平台可能换候选,序号会错位。
3. **唯一的硬闸**:每个职位分到的类别必须**逐字出现在那个职位自己的候选清单里**。核不上一律拒绝,**绝不模糊匹配、绝不就近取一个、绝不"挑第一个"兜底**——类别选错会把职位推给错误的人群,而页面看上去一切正常。
4. **差异化是目标,不是闸。** 候选清单由平台按每个职位的名称与描述现给,不同职位的候选可能高度重叠(真机见过一个职位只有 4 个候选)。要求互不相同因此**物理上未必可满足**,把它做成硬闸会直接死锁。撞车允许发生,但必须在二次确认清单上标出来交人裁决。
5. **不选保险类同样只是提示词偏好,不是闸**(2026-08-01 甲方澄清)。候选全为保险相关时不选也得选,此时仍须返回其中一项,但置信度低于 0.3 并写明。此前实现即是如此——确定性代码只核对"在候选里",从未强制排除保险。
6. **只在本批内求不同**,不比对平台上已在架职位的类别。严格说扩池的诉求也覆盖"跟已在架的别撞",但平台职位清单只回职位名、不回类别,要拿到得新增读取能力;本轮不做,列入后置项。
7. **置信度不设闸**,只随报告显示给运营;真正的闸是发布前运营看得见类别再确认。
8. **失败粒度:整批重试至多 3 次,但不整批陪葬。** provider 调用失败、返回不是合法 JSON、分配缺职位或多职位、某个职位的类别不在它自己的候选里——都重试整批(分配相互耦合,只重一个会破坏差异化)。3 次之后若**部分职位的分配合法、部分不合法**,保留合法的那些、把不合法的标记跳过,不让一个坏职位废掉整批的类别决定。全部不合法则整批 A 干净失败(零副作用,可重跑)。
9. **单职位重选走同一条路**:运营对某一个职位重跑类别决策时,把其余职位已定的类别作为"已占用"一并交给模型,让它主动避开。因此系统里只有一套类别提示词,没有"批量版/单职位版"两份。

**为什么必须三趟填页。** 候选只有填完三项才拿得到(§1.8),关键词词库又只有定完类别才拿得到(§1.4.1 第 5 条),而手不能调大模型(插件永远不接触 key),手在原语中途也没法回头问脑。两个决策点串起来就只剩三趟:第一趟 `job.readClassCandidates` 拿候选、脑定类别,第二趟 `job.readKeywordVocabulary` 拿分组词库、脑定关键词,第三趟带着两者真发。这是架构约束推出来的,不是为了加人工闸——人工闸是顺带白拿的。

原文写作"两趟填表",那是关键词尚由后台配置时的形态,已按 2026-07-31 裁决修订。**趟数并没有变多**:原来的第二趟「试填」退出循环,只留作单职位排障。

第一、二趟之间原本还能保留表单省掉一次填表,但 2026-08-01 改为全批统一分配后,循环里这两趟中间隔着"其余职位的 A1"和一次全局决策,表单留不住,见 §2.8。

**提示词硬规则**(甲方 2026-07-30 审定,2026-08-01 增补差异化,原文见 `client/service/internal/m5ai/job_class.go`):每个职位只能从**它自己的**候选里原样返回一个;**尽量让各职位落到不同类别**,并主动避开已占用的类别,只有当某职位的候选全被占用或都明显不贴合时才允许撞车;**不选保险相关**——这些岗位实际做保险,但招的是转行的人(职位名里就写着「HR/培训/市场背景优先」),落进保险桶会把职位推给已在保险业内的人,与招聘意图相反且池子更窄;必须与职位名称、描述的实际内容最贴合,以平台释义为判据;必须为每个职位做决策、不许弃选、不许漏掉任何一个;候选全为保险时仍须选一个但置信度低于 0.3 并写明。

**输入预算例外**(甲方 2026-08-01 裁决)。全批分配一次要带上全部职位的完整描述,远超按单次回复设定的 `ReplyInputTokenLimit`(16000)。为此新增**按用途的输入上限覆盖**,批量类别决策一项放宽到 **64000 token**;其余用途不变,intent 仍收窄到 8000。

- 该上限只放宽输入,输出上限不动。
- 规模依据:按中文约 0.6 token/字估,12 个职位约 1.4 万 token、20 个约 2.2 万、40 个约 4.4 万。再往上会先撞 `maxProviderRequestBytes`(256 KB,约 45 个职位)。**那不是平台的限制,是我们自己代码里的保守自限**(2026-08-02 勘误:此处原写作"硬闸",会让人误以为碰不得);需要时凭实测依据可以调,本轮不动。
- 成本依据:按冻结的 DeepSeek 价格 cache-miss 输入 $0.435/M token,一次 2.2 万 token 约 $0.01,一批发布只调一次,可忽略。
- 为什么给完整描述而不是摘要:类别选错会把职位长期推给错误的人群,代价远高于这点 token;描述又正是平台自己判定候选的输入,截断会让模型看到的和平台看到的不是同一份。

**数据边界**:请求只带职位名、职位描述、候选清单及平台释义,全是职位上下文,不带任何候选人身份字段。批量分配只是把同类内容按职位重复若干份,不引入新的数据类别。审计只留无正文诊断(用途/尝试/结果分类/延迟/token/字节/traceStatus),不写提示词、模型原文、选定类别与理由;后两者只经 HTTP 响应交给运营看。

**首验结果**:`家庭财务规划师(HR/培训/市场背景优先)` 后台配置 `培训经理/主管` 不在候选里,模型第一次尝试即选定 `理财顾问`(置信度 0.8),理由为"排除保险顾问与保险项目策划因其以保险从业为核心、不符合招聘意图;财务咨询顾问面向企业而非个人家庭"。随后试填全过、关键词 `人力资源/培训/市场营销` 三个全进。

### 2.8 页面连贯性(2026-07-31 甲方裁决,2026-08-01 收窄适用范围)

同一职位的第一趟(读类别候选)与第二趟(读关键词词库)之间**允许保留已填表单**,第一趟不再离开发布页。这样"描述失焦后等类别选择器加载"的数十秒只付一次。

**2026-08-01 起本节在循环里不适用。** §2.7 改为全批统一分配后,阶段 A 的顺序变成"A1 收齐全部候选 → 全局决策 → A2 逐个选词":A1 跑完第一个职位就去跑第二个,第一个的表单早被覆盖,等 A2 回来找它时什么都没了。因此循环里每职位退回三趟完整填页,**每职位约多付 40~60 秒**(一次填表加一次描述失焦等待)。这是全批分配的必然代价,甲方知情接受。`keepForm` 参数保留,只在单职位排障路径(连着跑第一、二趟)仍然有用。

- 由 `job.readClassCandidates` 的可选参数 `keepForm` 显式表达,默认 `false` 保持原行为(读完就走)。旧版手按 must-ignore 丢弃该字段、照常离开页面,不会出错。
- 第二趟**不假设页面状态**:开场先回读职位名、工作性质与描述长度,对得上才接着干,对不上或读不到就当干净页面整个重填。连贯性只是优化,从不是正确性依赖。
- 阶段 A 全程表单必填不齐(缺学历、经验、薪资、月数、关键词、人数),误点「发布」平台自己会拒。`job.prepareDraft` 那条"回读完成后必须主动离开发布表单,不把一个填满的表单留在页面上等人误点"针对的是填满全表的情形,对本节的半成品表单不适用;该原语自身的这项约束**不变**。
- 第二趟结束照旧离开发布页:它后面接的是二次确认清单,人可能隔几分钟也可能隔几小时才确认。
- **第三趟(真发)不适用连贯性。** `job.publishDraft` 必须先离开发布页去读职位名全集(那是幂等闸),那一步必然丢弃表单。此为安全内核,不动。

## 三、后置项

1. **关键词规律统计(甲方 2026-07-29 提出)**:把平台弹层实际出现的分组与关键词,结合当次发布的 job,上报后台用于统计规律。**该项需要新增 client → 后台写接口,属于当前获准范围之外**,实施前须按「增量交付、提交与停止纪律」第 12 条并列提交旧约束/拟议文本/当前可达场景/收益与成本,获批后方可落地。
2. **职位改版同步**:平台列表每个职位均有「修改」入口。职位配置改版后应走编辑而非重新发布,否则平台会堆积同名职位。本轮不实现,设计上需为其留出位置。
3. **已下线职位的重新上线**:未上线职位卡片有「上线」按钮,较重新发布更合适。当前按 2.3 一律跳过同名职位,不做自动上线。
4. **跟平台在架职位的类别也求不同**(2026-08-01 立):§2.7 的差异化目前只在本批内生效。要覆盖"跟已在架的别撞",需要能读回平台已有职位的类别——`job.readPublishedList` 只回职位名。届时按新增读取能力立案。

### 1.6 控件写入的真机形态(2026-07-30 试填验证)

以下几条是经手侧原语真机跑通后固化的写入方式,与手工用键盘操作的观察不同,自动化必须按这里的方式做:

1. **职位描述(jqte 富文本)到隐藏 textarea 的同步是异步的。** 写入 `div.jqte_editor.innerHTML` 并派发 `input` 后,立刻读隐藏 textarea 仍是旧值(甚至为空),必须轮询到 `textarea.value === innerHTML` 才算写入完成——这个一致本身就是写入成功的正证。按行包 `<div>` 与真实键盘输入产生的结构一致(首行裸文本、后续每行一个 `<div>`);实测 1455 字正常。
2. **描述失焦是类别选择器可用的前提,不是"平台判定类别"。** 触发最小事件集为 `focus → input → keyup → blur → focusout`;失焦后平台要加载一段时间选择器才打得开,长描述明显更慢,实测需给到 30 秒量级。原文写作"平台判定类别"已按 §1.4.2 修订——平台只在自己有把握时才预填,类别一律由我们自己选(§2.7)。
3. **工作性质的选中态是 `km-button--primary`**(未选中为 `km-button--light`),该组按钮没有 `aria-pressed` 等标准属性可读。
4. **下拉面板挂在 body 下,与触发控件没有 DOM 父子关系**,只能按水平位置就近匹配;选项元素在普通下拉是 `li`、在薪资下拉是 `a.km-option`,用宽泛的 `[class*="option"]` 会把整张列表容器当成一个选项。上一次操作留下的面板不先收口,下一次点击会把它 toggle 关掉。
5. **薪资月数控件没有 placeholder**(平台预置默认值 12 个月),只能按当前值形态 `/^\d+个月$/` 定位。
6. **关键词自定义输入框是点开后异步渲染的**,且添加成功后**不会自动收起**;残留的打开态会让平台拒绝「确定」并提示"请先完成添加"。收起只能点与「添加」同父的那个「取消」——弹层底部还有一个同名按钮,点错会丢弃全部已选。

## 四、未验证事项

1. **发布成功后的可见后置状态形态仍未验证。** 全程未点击「发布」,因此不知道成功后是跳转、弹提示还是其他,也不知道新职位在列表中多久可见。按「成功=发后页面可见」内核,此项必须在实现发布动作前或首次真机验收时确定,预期正证为"职位管理列表中出现 name == `job.name` 的职位"。
2. **列表分页处理**:当前职位数未触发分页,超过 20 条时的翻页或每页条数调整未验证。手侧读取已用"共 N 条与实际读到的卡片数必须相等"作为完整性守卫,超页时会如实失败而不是返回残缺清单。
3. **关键词弹层「更多」折叠**的展开行为与其后的分组内容未逐一读取。当前实现只操作可见入口,折叠区内的分组不参与匹配。
4. **描述含年龄表述能否离线预检**未定。可以正则检测,但"20 年经验"之类容易误报;当前依赖试填时平台自己给出提示(见 1.4.2),代价是每个职位都要试填一次才知道。
5. **富文本特殊字符**:已验证换行与常见标点、破折号、全角括号;未验证 HTML 敏感字符之外的极端输入。
