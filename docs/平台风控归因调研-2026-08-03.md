## 2. 量级对照：新版全面更保守（这条排除了最常见的风控口径）

招聘平台最常见的风控口径是量级。这条路已经堵死：

| 维度 | 旧版 | 新版 |
|---|---|---|
| 单轮采集人数 | 150（`homeStore.ts:100`） | 150（`productworkflow/manager.go:17`） |
| 选人数 | 80–90（`selection.py:15-18,38-39`） | 80–90（`m5ai/sourcing.go:450`） |
| 每日打招呼上限 | 无 | 无 |
| 单条招呼耗时 | 3–5 秒 | **9–13 秒（更慢）** |
| 多气泡间隔 | 1–5 秒，条数无上限 | **2.5–5 秒，上限 5 条（更保守）** |
| 巡检轮次间隔 | 1 分钟 | **5 分钟（更稀）** |

**【代码事实】** 另外，页面静态痕迹方向上旧版远比新版激进，却长期没被封：

- 旧版在智联页面上挂了一个 `id="xq-root-workbench"`、`z-index: 2147483647` 的**可见 React 面板**（`appUtil.ts:160-171`、`workbench/index.tsx:66-93`）
- 旧版往平台 origin 写 sessionStorage（`zhilianMinimumCollect.ts:1073-1090`）
- 旧版在 MAIN world 用 `window.postMessage(..., '*')` 广播带自家前缀 `xq-resume-base-main` 的魔法字符串（`content-main/index.ts:118-129`）
- 旧版申请 14 项权限（含 cookies / webRequest / proxy / nativeMessaging），在 `<all_urls>` 注入两份脚本
- 新版：对页面零 DOM 写入、零 postMessage、零 storage、5 项权限、只注入 `rd6.zhaopin.com`

**结论**：「平台扫 DOM / 扫全局变量 / 扫 postMessage」这条假设基本可以排除。

## 3. 智联的检测面（全部为实测）

### 3.1 神策全埋点，且不批量发送

**【实测】** 页面加载了神策数据（SensorsData）SDK：

| **滚动热图** `heatmap.scroll_notice_map` | **`default`（开启）** |
| `batch_send` | **`false`（每事件立即单发一条请求）** |
| `use_client_time` | `false`（用服务端时间） |

**意义**：点击与滚动深度是被采集的；`batch_send: false` 意味着行为频率在网络层直接可数。

**注意边界**：神策全埋点采集 **click 和 scroll**，**不采集 `input` / `beforeinput`**。这一点直接影响第 5 节的定级。

### 3.2 `/api/security/environment`：每一次点击都上报元素路径

**【实测】** 这是本次调研最意外的发现。

**触发时机**：发消息前会调用一次。但进一步测试发现——**对任意中性元素派发 click 也会上报**，所以它是**全局点击上报**，不是发送专用。

**请求体**（XHR POST）：
```
{ rootOrgId: string(8), staffId: string(10), content: string(730) }
```

`content` 是**明文 JSON**：
```
{ eventName: "web-event-click",
  xpath: "<从 body 到被点击元素的完整祖先类名链，688 字符>" }
```

**响应**：`{ code, data: null, message(2), taskId(32), time(19), errors: null }` —— 服务端只回执，不下发结论。

**xpath 跟随 `event.target`**（零副作用的父/子/孙三级对照）：

| 派发目标 | xpath 长度 | 末端 |
|---|---|---|
| 父容器 | 319 | `...imMainPanel` |
| 子元素 | 323 | `...imMainPanel DIV`（多一段） |
| 孙元素 | 440 | 更深的路径 |

**【代码事实 + 实测】** 发送按钮的 DOM 结构是 `BUTTON > DIV`，按钮**没有直接文本节点**。

**【推断】** 真人用鼠标点"发送"时鼠标落在内层 DIV 上 → `target = DIV`；而 `button.click()` → `target = BUTTON`。**两者 xpath 末端差一层，且每次点击都上报。**

**但见第 6.3 节：这条不构成新旧差异。**

### 3.3 网络出口被页面全劫持

**【实测】** 对照实验（同一浏览器、同一扩展环境）：

| | example.com | 智联 IM 页 |
|---|---|---|
| `fetch` | 原生（34 字符） | **被包装（564）** |
| `XMLHttpRequest.open` | 原生（33） | **被包装（239）** |
| `XMLHttpRequest.send` | 原生（33） | **被包装（564）** |
| `WebSocket` | 原生（38） | **被包装（564）** |

对照组证明**不是我方浏览器扩展造成的**，是智联页面自己劫持的。fetch / send / WebSocket 三者包装函数长度相同（564），说明出自同一个包装工厂。关键词匹配未命中任何已知监控 SDK（Sentry / Aegis / ARMS / 听云 / NewRelic / Bugsnag / Datadog / 神策等），推测为自研或深度混淆。

### 3.4 百度反爬与设备指纹

## 4. 核心发现：读历史消息的方式，新旧是 0 与 N 的关系

### 4.1 代码事实

**【代码事实】** 新版直接调用页面 IM 引擎接口，DOM 只是兜底：

```
// plugin/src/program/platform/zhilian.ts:7398（原注释）
// 自包含 MAIN-world 历史读取。直接调用 imEngine.getHistoryMsgs；与 Vuex getTimeline 不同，
// 不调用 sendMsgReceipt/sendLastMsgRead

// :7480 调用点
imEngine.getHistoryMsgs({ to, limit, asc, scene?, endTime?, lastMsgId? })
```

DOM 兜底路径在 `:7534` 起。这是新版把脚本注入 MAIN world 的原因——读 DOM 本不需要 MAIN world。

**旧版**：grep `getHistoryMsgs` / `imEngine` / `imSDK` / `getTimeline` → **零命中**。读历史只有一条路：`.im-timeline .im-message__bubble` 选择器（`zhilianClientBridge.ts:789`）。

### 4.2 实测：每次调用 1:1 触发一条神策上报

**【实测】** 三段实验：

| 实验 | HTTP 请求数 |
|---|---|
| 静置 12 秒（基线） | **0** |
| 调 3 次 `getHistoryMsgs` | **3 条 `sa.gif`** |

严格 1:1（与 `batch_send: false` 吻合）。旧版此数字为 **0**。

### 4.3 调用量的大头在哪

**【代码事实】** `chat.readThread` 不只用于巡检，还兼任**每次 effectful 动作后的验证读**：

- `contract.v1.json:1435`（发文本）、`:1453`（换微信）、`:1462`（邀面卡）：`verification: { primitive: "chat.readThread", maxRounds: 3 }`
- 多气泡一次最多 5 条，**每条独立验证** → 一轮回复可能打出十几次历史查询
- 单次上限 `readThreadMaxItems: 64`（`contract.v1.json:1519`），手侧 `:12437` 是持续翻页的 while 循环

**【推断】** 服务端视角还有一个组合信号：注释写明刻意"不调用 `sendMsgReceipt`/`sendLastMsgRead`"（为了不让候选人看到已读），所以呈现为**大量拉历史、几乎不产生已读回执**。真人打开会话必然产生回执。

**【代码事实】** 注释中另有一条自证：

> 真机 2026-07-28：现网 `session.scene` 为 undefined……传入非法值会让 API 主路径 **100% 被拒**

说明调参期间向服务端打过一整批被拒请求。参数校验失败率异常是服务端侧的强信号，且精确记录。

**这是本次唯一一条"实测坐实 + 新有旧无"的差异。**

## 6. 点击事件的性质：合成 vs 真实

### 6.1 实测对比

**【实测】** 对同一位置分别做两种点击，页面侧全局监听记录：

| | 合成点击（`element.click()` / `dispatchEvent`）<br>**= 本产品插件** | 真实点击（CDP 注入） |
|---|---|---|
| 事件数量 | **1 个**（孤立 `click`） | **7 个**完整序列 |
| 序列 | `click` | `focus → pointerdown → mousedown → pointerup → mouseup → click → mousemove` |
| `isTrusted` | **false** | **true（全部）** |
| `screenX` | **0** | 941（真实屏幕坐标） |
| `detail` | **0** | 1 |
| `pointerType` | `null` | **`"mouse"`** |
| 按压时长 | 无 | pointerdown→pointerup 间隔 23ms |

### 6.2 技术原理

- **content script 造的事件**：`isTrusted` 恒为 `false`，这是浏览器写死的安全属性，页面内任何手段都改不了。
- **CDP（`Input.dispatchMouseEvent`）**：事件从浏览器内核注入，与真实硬件输入同一条路径，页面侧无法分辨。

**【推断】** 浏览器扩展要产生 `isTrusted: true`，据现有认知只有 `chrome.debugger` API 一条路，代价是 Chrome 顶部会出现"正在调试此浏览器"横幅。**未经确证。**

**可选路径备忘**（若将来立案）：本产品已有 Electron 外壳 + Go 本地服务，具备做系统级鼠标注入（如 Windows `SendInput`）的现成通道，比 CDP 更底层且无横幅；代价是窗口必须前台、坐标需处理缩放对齐、执行期抢占用户真实鼠标。**此项属能力扩张，需单独立案。**

### 6.3 关键：这条不构成新旧差异

**【代码事实】** 旧项目点击方式：

```
sendButton.click();        // zhilianMinimumCollect.ts:7569
```

全文 grep `new MouseEvent` / `PointerEvent` → **零命中**。`.click()` 出现在 1317、1405、1712、2036、2065、2476、2491、2533、2628、2679、2718、2736、2962、2994、3037、3142、3157 等数十处。

**两代产品在点击性质上完全相同，都是 `isTrusted: false` 的合成点击。**

**【推断】** 若智联确实在查 `isTrusted` 或 xpath 层级，则旧版本现在拿去跑**应同样被封**。这指向"平台侧检测在这期间加强了"的可能，但**未经验证**。

## 7. `__vue__` 可用性调研（真机实测）

### 7.1 分场景结果

| 场景 | 元素自身暴露 | 祖先查找 | 载荷 |
|---|---|---|---|
| **IM 会话列表行**（20 个真实行） | **0 / 20** | **20 / 20** | `session`，85–86 字段 |
| **IM 消息 timeline**（打开会话后） | **直接可用** | — | `_props.data`，31 字段/条 |
| **推荐流候选人卡片** | 直接可用（`virtual-list-item`） | — | `source`，含完整简历 |

页面 `__vue__` 元素总数：推荐页 1128 个，IM 页 337 个。

### 7.2 三条要点

**（1）暴露性是动态的。** 同一批会话行，一次测得 0/20 全靠祖先查找；中途点开一个会话后再测，第 0 行变为**直接暴露**。这印证了 `zhilian.ts:3968` 的注释「智联实时插入新会话后，行节点上的 `__vue__` 可能不再暴露」。

**结论：三级兜底（元素 → 后代 → `$nuxt` 组件树 BFS，`zhilian.ts:3960-3995`）是必需的，不能因某次测到直接可用就简化为单路径。**

**（2）timeline 直接可用，代码注释是错的。** `zhilian.ts:7543` 写着「生产页面不暴露 Vue2 `__vue__`」，实测 `timeline.__vue__._props.data` **直接就能拿到**。这条错误注释导致 DOM 路径退到了 SSR 快照（`__INITIAL_STATE__.im.timelineMap`），而快照是页面加载时的静态数据、不随新消息更新，用于发后验证读不可行。**这是一个纯粹由错误注释造成的能力损失。**

**（3）结构同构。** `_props.data` 与 `getHistoryMsgs` 返回的是同一批消息对象。两条路径在 `zhilian.ts:7597` 的 `const rows = history as AnyRecord[]` 处汇合，**之后所有归一化代码（105/259 换微信、355 邀面卡、313 在线简历的字段识别、`clean`/`digest`/`toMillis`）完全共用，一行不用改**。

### 7.3 重要边界：不能改用真解析 DOM 气泡节点

**【代码事实】** 渲染后的 DOM 里没有 `userWeChat`、`staffWeChat`、`interviewId`、`startTime`、`originType` 等字段，卡片只剩一句文案。改用 DOM 节点解析会**直接报废换微信与邀面的识别能力**。

**【实测佐证】** 一次观测中 `_props.data` 为 15 条，而 DOM 气泡节点只有 10 个（虚拟滚动只渲染可见部分）。**DOM 节点数不可靠，`_props.data` 才是。**

### 7.4 补充实测（2026-08-03 第二轮，专项验证兜底链）

**（1）两条路是同一份数据，不是"同构"。**

```
store.getters['im/timeline']  ===  timeline.__vue__._props.data     // sameArrayRef: true
两者最后一条也是同一个对象                                          // sameLastObjRef: true
```

getter 是上游，`_props.data` 是它传下去的 prop。字段数 38，含 `status` / `flow` / `idServer`。

**（2）没有任何不依赖元素 `__vue__` 的入口。**

| 候选入口 | 实测 |
|---|---|
| `window.$nuxt` | **不存在** |
| `window.__NUXT__` / `app` / `vm` | 不存在 |
| `#app` 根元素 | **元素本身不存在** |
| `__VUE_DEVTOOLS_GLOBAL_HOOK__` | 不存在 |
| `window.Vue` | 存在，但只是构造函数，拿不到实例 |

**推论一**：Vuex getter **不比** `_props.data` 更稳——取 store 同样要先找一个带 `$store` 的 Vue 实例。此前"store 是全局单例故更稳"的说法**错误，已更正**。

**推论二**：getter 仍应进兜底链，但理由换成**冗余度**——`_props.data` 只能通过 timeline 那一个特定元素，getter 可通过页面上任意一个带 `$store` 的组件（数百个）。

**推论三（重要）**：`zhilian.ts:3970-3990` 的 `$nuxt` 组件树 BFS 兜底，**在当前页面是死代码**。它服务的是会话列表 `rowSource`，不是 timeline，需单独立项处理。

**（3）`__vue__` 暴露性高度动态，同页面两次观测完全相反。**

| 观测 | 会话行自身暴露 | 靠祖先 |
|---|---|---|
| 第一轮（页面 navigate 后） | **0 / 20** | 20 / 20 |
| 第二轮（用户手动打开会话后） | **24 / 24** | 0 |

timeline 元素则三次观测**全部直接可用**。**不稳的是会话行，不是 timeline。**

**（4）数组引用会被整体替换，禁止缓存。**

发消息采样中 `t=27ms` 处捕获到 `REFNEW`——新消息到达时 Vuex 用**新数组**替换，不是原地 push。

**工程约束**：轮询验证必须**每轮重新读 getter/props**。若持有一次引用循环轮询，会永远盯着旧数组、等不到新消息，最终超时误判"未确认"→ 转人工。症状具有迷惑性。

**（5）第二次发送时序样本**（与第 8 节的 504ms 互为对照）：

| 时刻 | 状态 |
|---|---|
| t = 27ms | 新消息出现，`status: sending`，无 `idServer`，**引用被替换** |
| **t = 281ms** | `status: success`、`flow: out`、`idServer` 到手 |

**两次样本 281ms / 504ms，波动明显，等待上限须留足（建议 3–5 秒）。**

### 7.5 修正后的兜底链

1. `timeline.__vue__._props.data` —— 最直接
2. **扫描任意带 `$store` 的元素 → `getters['im/timeline']`** —— 冗余度高得多
3. SSR `timelineMap` —— **必须显式标记为非实时，禁止用于发后验证读**

判据：`flow === 'out' && status === 'success' && idServer 存在 && 文本匹配`。

### 7.6 未验证项

长会话滚动翻页时 `_props.data` 是否增长——测试会话只有 13 条、已到顶（"90 天"边界标志已出现、`scrollHeight - clientHeight = 0`），未测到。**代码中的滚动翻页逻辑（`zhilian.ts:7568-7583`）目前无真机证据支撑。** 此项只影响深度历史回溯，不影响发后验证读。

## 8. 发后验证读时序（真机实测）

**实验**：按生产路径发送（native setter 写入 → `InputEvent('input')` → `Event('change')` → 点击发送），从点击时刻起每 20ms 采样 `_props.data`。

| 时刻 | 页面数据状态 |
|---|---|
| **t = 0ms**（点击返回） | 无变化，仍是原条数 |
| **t = 82ms** | 新消息出现，但 `status: sending`、**无 `idServer`**，只有本地 `sendMessageId` |
| **t = 504ms** | `status: success`、`flow: out`、**`idServer` 到手** |

**与 API 对照**（同一条消息）：

| | 页面 `_props.data` | API `getHistoryMsgs` |
|---|---|---|
| 最后一条 | `flow: out` / 文本匹配 / `status: success` | `flow: out` / 文本匹配 |
| **`idServer`** | **两者完全相同** | |
| 条数 | 15（当前渲染窗口） | 26（可拉更远历史） |
| 字段数 | 37（API 的超集，多 UI 状态） | 30 |
| 成本 | 本地读，**0 网络、0 埋点** | 67ms 往返 + **1 条埋点** |

**结论**：

1. 页面数据**自带 `status` 状态机**，能区分 `sending` / `success`——这正是"无失败标志"判据所需，而 `getHistoryMsgs` **没有**这个实时状态。**页面数据比 API 更适合做发后验证。**
2. "立刻读"要拆开看：0ms 读不到；82ms 读到的是本地回显，**不能当成功**；**约 500ms 才是可信的成功正证**。
3. 条数差异支持分层：验证读只需最后几条，页面绰绰有余；深度历史回溯才需要 API 或滚动加载。

## 8A. 老项目的读法与其失败处理缺口

### 8A.1 读法与新项目 DOM 路径完全一致

**【代码事实】** `zhilianMinimumCollect.ts:4242-4252`：

```js
mainWorldUtil.getDomPathResult({
  selector: '.im-timeline__wrapper .km-list',
  path: '__vue__._props.data',
}, { timeoutMs: 3000 })
```

同选择器、同取值路径。**老项目不解析 DOM 气泡节点。** 区别仅在于：老项目只有这一条路，新项目把它排在 API 之后当兜底。

### 8A.2 发后确认的三点优良设计（值得照抄）

**【代码事实】** `confirmOutboundPosted`：

1. **每轮重新调用** `collectOutboundTextTimeline()` —— 跨 world 通信天然不缓存引用，**恰好躲开 7.4(4) 的 REFNEW 陷阱**
2. **400ms 轮询间隔**，超时 6000ms
3. **三态而非二元**：`posted` / `switched`（会话切走）/ `unverifiable`（采集不可用）/ `sent_unmatched` / `not_sent`

其中 `sent_unmatched` 的原注释值得引用：

> 增长了(sent_unmatched) = 有己方消息落地但内容对不上（多为平台把号码/链接改写打码，或迟到的别条），说明本次很可能已发出，**绝不再重发**以免候选人收到两条

### 8A.3 缺口：「读不到」被误判为「确实没发出」

**【代码事实】** MAIN world 侧 `handleGetDomPath`（`xq-resume-base/src/content-main/index.ts:139`）的失败语义：

| 情况 | MAIN world 返回 | 调用侧 | 最终 |
|---|---|---|---|
| 通信超时 | — | reject | `ok:false` → `unverifiable` → **不重发** ✓ |
| selector 缺失 / 元素不存在 | `success:false` | reject | 同上 ✓ |
| **元素存在但 `__vue__` 不暴露** | **`success:true, data:undefined`** | resolve | **`ok:true` + 空数组** ✗ |

最后一行是缺口：`getValueByPath` 取不到值仍返回 `success: true`，而 `collectZhilianImTimelineMessages` 写的是 `Array.isArray(response.data) ? response.data : []`——**取不到即当空数组**。

于是 `sawCleanRead = true`、`outCount = 0`，超时后判 `0 > baseline` 为假 → 返回 **`not_sent`**（其注释为"确实什么都没发出去，可安全重发"）→ **重发**。

**「读不到」与「确实 0 条」没有被区分开，这是一条真实的多发路径。**

### 8A.4 它为何仍然跑通

**【实测】** timeline 元素的 `__vue__` 三次观测**全部直接可用**；不稳定的是**会话列表行**（0/20 ↔ 24/24）。

**结论：老项目是踩在一个恰好成立的前提上跑通的，而不是因为其失败处理正确。「生产验证过」在这一点上不构成正确性证据。**

### 8A.5 对新项目的结论

- **读法照抄**（同选择器、同 path，已验证）
- **每轮重取 / 400ms 轮询 / 三态结果照抄**
- **失败处理必须保留新项目的**：安全内核要求"读不到 → 不确认 → 转人工"，配合 WAL/idemKey/证词/原语内不重试，正好堵住 8A.3 的缺口
- **必须区分"取不到数据"与"确实 0 条"** —— 这正是老项目缺的一刀
- 新项目判据（`status === 'success' && idServer` 存在）强于老项目（仅数量增长 + 文本匹配），**该优势保留**

### 9.1 现状（此前判断有误，此处更正）

if len(ledger) > 0 && !ListPreviewMatches(...) { hintDirty = true }   // 列表预览与账本末条不符

## 10. 建议与优先级（均需另行立案，本文档不构成授权）

### 优先级 1 —— 有实测支撑，收益最大

- 约束：必须保留三级兜底，不得简化为单路径
- 合规性：不违反「成功=发后页面可见」（2026-07-29 裁决），该裁决要求的本就是回读页面

**（2）简历详情停留与滚动**

- `zhilian.ts:2584`、`:2628` 的 `randomDelayMs(2_000, 2_500)` 放宽

### 优先级 2 —— 减量，无实测紧迫性

**（3）持久化已完结集**，借鉴旧版 `finishedImUserIdList`，减少巡检基数。

### 优先级 3 —— 押后

**（4）巡检整体改 DOM** —— 指纹跳过已在起作用，收益不如预期，而代价（每个会话都要真打开）很大。

**（6）真实事件注入**（`chrome.debugger` 或 Go 侧系统级注入）—— **在第 11 节的对照实验出结果前不建议投入**，因为它赌的是一个尚未证实的因果。

   - 不会 → 确系新版行为造成，回到本文清单继续排

   这个实验比继续读代码有价值得多。

2. **风控表现的精确描述** —— 平台提示原文、被限制的具体能力、首次发生时刻。不同表现指向完全不同的原因（限简历查看 → 第 5.1 节；限发消息 → 第 4 节与话术内容；要求人脸/短信验证 → 登录环境与 IP，与本文基本无关）。

3. **时间线对齐** —— 把风控发生时刻与 `brain.db` 的动作时间线对齐，看前 30 分钟处于哪个阶段（采集 / 打招呼 / 沟通 / 换微信）。

4. **内容取证** —— 从 `brain.db` 导出最近一批已发送正文，算相似度；统计换微信发起率与候选人拒绝比。填补 11.1 的盲区。

5. **账号维度旁证** —— 是否换了新账号？新号在任何平台的阈值都远严于老号。装机机器、网络出口有没有变？同 IP 下是否有多个招聘账号在跑？

6. **因果实验** —— 测试账号分两支：A 支只采集不发消息，B 支只发消息不采集。哪支先触发，就锁定哪一侧。

## 附录 A：实验方法（可复现）

所有实验在甲方测试账号的真实登录页面执行，均为只读或经授权的可控动作。

**A.1 原生函数检测**
```js
const nat = f => /\[native code\]/.test(Function.prototype.toString.call(f))
```
对照组：在 `example.com` 上跑同一段，排除浏览器扩展干扰。

**A.2 埋点频率基线**
清空网络记录 → 静置 12 秒 → 读（得 0）→ 清空 → 执行 N 次目标动作 → 读，比较增量。

**A.3 神策配置读取**
从 `window.sa.para` 读 `heatmap` / `batch_send` / `use_client_time`。

**A.4 `security/environment` 载荷捕获**
在同一次脚本内包装 `XMLHttpRequest.prototype.open` / `send`（透传不改内容，仅记录），触发一次发送，`finally` 中还原。**注意**：智联自身已包装 fetch/XHR 并持有原生引用，故 prototype 层拦截仅在业务代码每次从 prototype 取值时生效；实测 XHR 路径可捕获。

**返回值必须只取结构（字段名、类型、长度），不取值** —— 否则会被工具侧安全过滤整体拦截。

**A.5 xpath 跟随 target 验证**
对同一容器的父/子/孙三级分别 `dispatchEvent(new MouseEvent('click'))`，比较上报 xpath 的长度与末端。零副作用。

**A.6 点击性质对比**
装全局 capture 阶段监听器记录 `isTrusted` / `screenX` / `detail` / `pointerType` 及事件序列 → 先合成点击 → 再真实点击同一坐标 → 比较 → 卸载监听器。

**A.7 发后时序采样**
记录 `_props.data` 基线长度 → 按生产路径写入并点击 → 每 20ms 采样，记录 `(长度, flow, status, idServer 有无, sendMessageId 有无)` 的变化点。
