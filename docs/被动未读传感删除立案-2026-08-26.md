## 一、一句话

未读角标的**被动上报链**在 2026-08-10 之后只剩一个用途(正数拉前下一轮巡检),
而该用途**最多值 60 秒**[数据];`pageNavigated` 事件里的 `pageKind` 字段则**从头到尾
没人读**[已核]。建议一次性删掉这两段,顺带订正一处已经失效的注释。

## 二、旧约束

### 2.1 契约

```json
"PingSensors": { "fields": { "unreadTotal": { "ref": "SensorReading", "nullable": true } } }
"PingBody":    { "fields": { ..., "sensors": { "ref": "PingSensors", "optional": true, "nullable": true } } }
"PageNavigatedEventData": { "fields": { "pageKind": {...}, "at": {...} } }
```

### 2.2 规格

《协议规格-v1》§12 与 §4.6 描述 ping 搭载传感快照。同规格 790 行已记 2026-08-10
裁决:「`unreadBadge` 传感事件保留,但其用途收窄为巡检拉前提示,不再参与未读子轮
的进入判定。」

### 2.3 一处**已经失效**的注释 [已核]

`client/service/internal/session/registry.go:129-132` 写着:

> 未读读数是插队判定的唯一输入,而它走"手主动推送、脑不得反向拉取"的提示通道

2026-08-10 之后此句不成立,且与另外三处正确注释直接矛盾:
- `client/service/internal/patrol/round.go:1922-1925`「替代被动传感基线判定」
- `client/service/internal/patrol/manager.go:455-457`「角标事件只剩一个用途」
- `client/service/internal/appbridge/patrol.go:438-441`「unread awareness now flows
  through the chat.readUnreadTotal command path (2026-08-10)」

过时而自洽的描述比缺失更危险——读它的人不会怀疑自己看到的是错的。

## 三、当前可达场景:这两段今天在干什么

### 3.1 未读数值上脑:四个消费点,全是展示或日志 [已核]

| # | 位置 | 性质 |
|---|---|---|
| 1 | `session/registry.go:135-156` | 写内存缓存 `HandState.Sensors` + 派生 `SensorHealth` |
| 2 | `session/registry.go:157-164` | 变化沿日志「未读读数变化」 |
| 3 | `adminhttp/m2.go:91-94` | `/admin` accounts 的 `unreadTotal` 字段 |
| 4 | `client/ui/src/console/pages/AccountPage.tsx:115,222` | 诊断台角标数字 |

唯一写入点 `registry.go:119 HeartbeatReport`,调用方只有 `session/hub.go:548`。

**没有任何业务判断读它。** 巡检 actor 拿到的手状态里构造性地没有 sensors 字段
(`appbridge/patrol.go:438-441` 注释明说)。插队判据来自主动命令:
`patrol/round.go:1935-1937` 派发 `chat.readUnreadTotal` → `:1954` 取 total →
`:1978-1991` 打「未读插队判定 current=N」。

### 3.2 `PingContext.ready` / `PageHealth`:同样只到展示 [已核]

`sensorBridge.ts:240-274 contextHealth` → ping.contexts → `registry.go:134
capabilityPageHealth` → **唯一消费者 `adminhttp/m2.go:89`**。

**关键核对:命令派发的就绪判定不读它。** `session/hub.go:194 readyLocked` 走
`registry.go SessionHealth`,返回的是心跳到达时设置的 `s.Health`,与 contexts 无关。
即删掉 pageKind 不会卡住派发。

### 3.3 `pageNavigated` 事件里的 `pageKind`:解出来但没用 [已核]

`patrol/manager.go:468-477`:

```go
case protocol.EventPageNavigated:
    var data protocol.PageNavigatedEventData
    if err := json.Unmarshal(event.Data, &data); err != nil { return err }
    return m.store.MutateAccount(key, func(account *store.Account) error {
        account.DirtyHint = true
        m.pullForward(account, now, m.config.CoalesceWindow)
        return nil
    })
```

`data` 只用于反序列化的错误检查,`data.PageKind` 一次都没读。

**不要与 `EventManualInteraction` 搞混**:那一个**确实读** `data.PageKind`
(`manager.go:483`,判 `Recommend` → `InvalidateSourcingFeed`),但它由
`sensorBridge.ts:276-285 emitRecommendationFeedReload` 发射,数据源是 SW 侧
`chrome.webNavigation`,**不经 content script**。那条是活的业务硬闸,本次不动。

### 3.4 唯一还活着的用途:拉前巡检,值多少 [已核 + 数据]

`patrol/manager.go:450-467`:角标事件正数 → `DirtyHint=true` + `pullForward`。

| 参数 | 值 | 位置 |
|---|---|---|
| 正常轮间隔 `PatrolInterval` | **2 分钟** | `patrol/types.go:333`(2026-08-04 甲方由 5 分钟调快) |
| 拉前目标 `CoalesceWindow` | 25 秒 | `types.go:338-340` |
| 最小轮距 `MinimumRoundGap` | 60 秒,**拉前跨不过去** | `types.go:342-343`,实现见 `manager.go pullForward` |

最坏情况(消息在一轮刚结束时到达):

- 有拉前:目标 `now+25s`,被 60 秒下限顶住 → 下一轮在 上轮 +60 秒
- 无拉前:下一轮在 上轮 +120 秒

**拉前买到的上限是 60 秒**,且随时间接近自然轮迅速衰减到零(消息在 +90 秒到达时
只快 5 秒)。

## 四、拟议改动

### 4.1 契约(两处,均为删除)

1. 删 `PingSensors` 及 `PingBody.sensors`
2. 删 `PageNavigatedEventData.pageKind`(保留 `at`)

同 commit 重跑 `go run ./contract/codegen` 并提交两端生成产物;规格 §12/§4.6 相应
段落同步修订。按「悬置决策·契约 append-only 冻结点」,当前开发阶段允许破坏性修订,
但须逐项证明无生产者、无消费者、无持久化/恢复路径引用——本文第三节即该举证。

### 4.2 插件端删除面

- `plugin/src/base/contentDom.ts` **整个文件消失**。其中:
  - `readZhilianUnreadTotal:12-17` 删除(生产唯一消费者是 `content.ts:54`)
  - `ZHILIAN_UNREAD_BADGE_SELECTOR:10` 与 `parseZhilianUnreadBadgeText:21-37`
    **迁入智联平台模块** —— 主动路径 `zhilian.ts:5034,5036` 仍在用,**解析口径
    一个字节不改**
- `contentSensor.ts:91-132 armBadge` 及其状态位删除
- `content.ts` 的 `readUnreadTotal` 环境项、`pageKind()` 与 `PageNavigated` 载荷里
  的 pageKind 删除
- `sensorBridge.ts`:`CachedUnread:49-52`、`ContentTabState.unread`、`:155` 写入、
  `:217-230` 中三处 `setSensorSnapshot`、`UnreadStable` 分支整体删除
- `connection.ts`:`:75`、`:104`、`:153-168 setSensorSnapshot`、`:553`、
  `:756-768 currentPingSensors` 删除

### 4.3 脑侧与 UI 删除面

- `session/registry.go`:`Sensors`/`SensorHealth`/`LastSensorAt` 字段(`:51-54`)、
  `:133-178` 相关分支、`unreadReadingText`、`capabilityPageHealth`、
  `:245,263` 的拷贝
- `adminhttp/m2.go`:`:49-51` view 字段、`:79`、`:89-94`

### 4.4 顺带订正

`session/registry.go:129-132` 的失效注释(第 2.3 节)。

### 4.5 **必须保留**——删过头会掉业务能力

| 保留项 | 位置 | 理由 |
|---|---|---|
| 角标选择器与文本解析 | 迁入平台模块 | 主动路径 `zhilian.ts:5034,5036` 在用 |
| 登录态解析全链 | `content.ts:22-40` → `contentSensor.ts:134-154` → `sensorBridge.ts:167-182` → `manager.go:496-525` | **唯一的即时掉登录停机通道**;主动路径要等下一轮巡检 |
| content script 的探测应答 | `content.ts:93-96` | `contentScriptOk` 的唯一来源(`zhilian.ts:851-858`);它是 `appbridge/account_resolver.go:83-86` 的硬前置,删了产品 UI 解析不出账号,**整体停摆** |
| webNavigation 接线与推荐流换代 | `sensorBridge.ts:120-133,276-285` | 与 content script 无关,是「推荐页运行连续性」的实现,**删被动传感时不要顺手带走** |

### 4.6 **两个坑**

**坑一:`resyncStaleSensors` 只能删一半。** `sensorBridge.ts:325-331` 的条件是
「未读缺失 **或** 登录态未知 → 重新索要快照」。未读那一半随本次删除去掉,
**登录态那一半必须留**:`lastCanonicalLogin` 要先拿到一个非 unknown 的采样,
登录态变化事件才可能触发(`sensorBridge.ts:170-179` 要求 `previous !== null &&
previous !== Unknown`)。删过头 → 即时停机通道永久失效,而且**没有任何症状**。

**坑二:`UnreadStable` 消息整条删除,不是只删 value。** 该消息同时承载 ping 快照的
`value` 与事件用的 `emitEvent/prev`(`contentSensor.ts:124-130`);事件本身随本次
裁决一并废止,故整条删。若甲方只批准删快照、保留拉前,则 `armBadge` 与
`readZhilianUnreadTotal` 必须保留,`contentDom.ts` 不能消失——**收益随之减半**,
见第五节。

## 五、收益与成本

### 5.1 收益

| 项 | 说明 |
|---|---|
| content script 的平台特定面 **4 件 → 1 件** | 只剩登录态解析;认站点退化为一个字符串,而 `hostMatch` 已在适配器上声明,白拿 |
| `contentDom.ts` 整个文件消失 | base 层不再持有该块平台 DOM 知识 |
| 多平台批 B 的一等危险消失 | 该文件有 2026-08-03 真机事故先例(选择器要求双类 → 零未读被读成读不到 → 插队被 `unreadRetryDeferred` 锁死);删除后剩下的选择器+解析是纯搬家,不再有两个消费者要协调 |
| 契约减两个字段,脑侧减一份缓存与一个派生健康度 | |
| 清掉一处会误导人的失效注释 | |

### 5.2 成本

| 项 | 量级 |
|---|---|
| **候选人回消息后最多晚 60 秒被看见** | 上限 60 秒,平均更小;**不丢消息**,只是晚看见 |
| 诊断台失去未读数与 `sensorHealth`/`pageHealth` | 排障少一个眼睛。这两个数今天不参与任何判断,但**确实是真实损失** |
| **一次部署硬切换** | 契约变 → `contractHash` 变 → 按《协议规格-v1》§14:暂停派发 → 重启脑 → 重载插件 → 确认哈希一致 → 恢复 effectful。mismatch 状态禁发 effectful |
| 一批测试要跟着改 | 单元测试与端到端夹具里涉及 sensors/pageKind 的断言 |

### 5.3 风险与失效方向

- 删除面全部是「没有消费者的数据通道」,**不触碰任何安全内核**(账本闸、证词闸、
  平台回读闸、原语内不重试、发后正证一律不动)
- 坑一若踩中,失效方向是**掉登录后不能即时停机、要等下一轮巡检**——仍是「少做」
  方向,但会静默,故列为实施时的阻断级核对项
- 拉前废止后,新消息响应变慢属**时效**损失,不影响正确性
