# 里程碑 4 · 主动建联闭环实施与验收计划

> 状态：已获甲方批准，2026-07-20。附带裁决：沟通逻辑规格补齐“人工指定当前候选人 → selected 建档”入口跃迁；`GREETING_REJECTED` 的归档语义按本计划收窄文本落地。
> 上游约束：`AGENTS.md`、`contract/协议规格-v1.md`、`docs/沟通逻辑规格-v4.md`、`docs/协议设计/E-首个真实副作用安全轨道.md`、M2/M3 计划与验收报告。
> 真机许可：见 `docs/真实账号测试授权记录.md`。当前 Chrome 已登录真实账号，可在授权范围内做普通招呼与聊天测试；仓库与报告不得记录候选人姓名、账号、平台用户 ID、会话 ID、聊天正文或可还原身份的截图。
> 验收剖面：首个真实客户安装前、开发者模式本地加载、同机可信通信、有人值守；只覆盖智联一个真实账号、一个真人选定候选人、一次自然招呼。

## 一、里程碑结论与边界

M4 只交付一条最窄主动建联竖切：

`真人打开一个当前候选人 → 脑正式读取并持久化候选人×职位档案 → 真人确认一次招呼意图 → 手执行 chat.sendGreeting@1 → 观察到同一候选人的稳定新会话和唯一服务端招呼 → 脑原子绑定候选人/档案/会话并自动 adopted → 新会话进入既有巡检与 chat.sendMessage 路径`

候选人来源只做“真人在智联页面打开当前候选人，脑下发正式 readonly 原语读取最小身份”。M4 不遍历搜索结果、不自动选择候选人、不抄写平台 ID、不接受测试注入作为产品入口。若当前页面无法提供经真机确认的稳定平台用户 ID 或稳定职位引用，本里程碑停在事实门，不得以姓名、职位名、`resumeNumber`、DOM 路径或 URL 参数拼接身份。

`chat.sendGreeting` 与 `chat.sendMessage` 是两个原语。前者从“尚无会话”建立关系并发送首条招呼；后者只向已经 adopted 的既有会话发送。发现候选人已经存在会话时，`sendGreeting` 必须在动作前停止，不得顺手改派 `sendMessage`，也不得把既有会话冒充本次建联成功。

本里程碑不做：

- 自动搜简历、批量采集、AI 打分、选人、自动招呼调度、配额与频控；
- AI 生成招呼语、自动回复、确定性沟通状态机、冷催/跟催；
- 邀面卡、换微信卡、主动联系候选人的补采简历流程；
- 自动打开、滚动或切换候选人，自动切既有会话后发送；
- 第二平台、第二账号、云端、授权、运营通知、远程 JavaScript 或 program 交付机制裁决；
- 无人值守转正、通用平台适配框架或通用 effect target/verification DSL。

## 二、出口宣言（批准后冻结）

### 1. 本轮最小可交付出口

一个真人当前打开的未联系候选人，经正式 `candidate.readCurrent@1` 进入候选人和档案账本；一个稳定招呼意图经正式 `chat.sendGreeting@1` 产生至多一次平台动作；成功时同时观察到同一候选人的稳定 `conversationRef` 与唯一服务端确认的我方招呼。脑在一个 SQLite 事务中完成意图终局、档案推进、会话绑定、自动 adopted 和唯一 `origin=self` 招呼事实。脑重启、手重连和恢复对账后没有第二次招呼或账本增生；该新会话可直接进入现有巡检并满足 `chat.sendMessage` 的 adopted 前置条件。

完成还要求：适用的全量门禁绿色、一次有人值守真实 Chrome 验收通过、形成《里程碑4-验收报告》。最窄生产竖切的自动冒烟一绿即先提交，不等待后续故障矩阵、独立审查或真机验收。

### 2. 必须立即阻断的损害

- 同一招呼意图或同一档案产生两次候选人可见招呼；
- 招呼发给错误候选人或错误职位；
- 以 `resumeNumber`、姓名、职位名、列表序号或其他启发式身份绑定；
- 已有沟通关系仍再次打招呼；
- 覆盖真人已经输入但未发送的内容，或改变平台默认招呼语/账号级配置；
- 只观察到点击、跳转、弹窗消失或乐观记录就记成功；
- 候选人、档案、意图、会话、tracked/adopted 与消息事实半事务错绑；
- 部署硬切换尚未完成、账号身份/cap/witness 不就绪或账号域已有 suspect 时仍越过不可逆动作；
- 动作后结果不明时再次点击、换正文、换 `intentId` 或换 `msgId` 自动补发。

这些是阻断级。任何一项出现都必须停止当前真实测试并修复；不得用“有人值守”放宽 M3 已冻结的安全内核。

### 3. 允许重试或人工兜底的失败

页面未打开或被切走、当前候选人/职位身份读不到、零个或多个目标匹配、控件不唯一、已有会话、真人仍在操作、证词写失败、平台风控、验证码、动作前上下文丢失和普通 UI 瞬时失败，均可 fail-closed；少发、等待页面恢复、真人重新打开页面均可接受。

真实 effectful 的 `failed/sideEffect=none` 与任意 receipt rejection 仍终局化原意图。需要再试时只能由真人重新确认后另铸新意图；M4 不新增自动 effectful 重试。动作后无法唯一确认新关系或招呼时，只进入配套验证和 suspect，人工判断之前不得再发。

当前有人值守阶段允许可恢复的页面体验瑕疵、需要重新读取当前候选人或重新打开页面；不为它们创建通用迁移、恢复或兼容框架。

### 4. 独立审查预算与明确后置

最窄冒烟 commit 之后最多一轮独立审查。审查只举证当前可达问题；阻断项修复后只做该 diff 的定向复核，不重开全量审查。优化项只有在常见、边际价值明确且修复成本低时才以独立 commit 纳入；其余登记后停止。

以下义务明确后置，不得在 M4 中顺手实现：

> 派发层 mismatch 禁 effectful 构造闸，触发条件=首个自动 effectful 派发入口上线前。

M4 的招呼入口仍由真人逐次确认，不是自动 effectful 派发入口，故本里程碑不触发该截止点。真实验收仍必须按现有部署硬切换程序确认脑手 `contractHash` 一致后才开始。

## 三、AGENTS.md 第 12 条规范修改立案

本节只请求修改授权，不把拟议文本当作既有依据。甲方批准后，实施必须按“可信规范先行 → `contract.v1.json` → codegen 产物 → 双端实现”的顺序落地；若批次 0 的真机事实推翻任一拟议语义，立即停止并重新提交修订，不允许实现反向塑造规范。

### 3.1 现有约束

1. `chat.sendGreeting@0` 只是未来占位，不能上报 capability 或派发；协议规格 §16 与 E 文 §7 都把新会话验证闭环推迟到阶段四。
2. `chat.sendMessage@1` 只接受 adopted `conversationRef + expectedTail`，明确不能建立新会话。
3. 每个真实 effectful 必须有 guards、evidence 和配套验证读；现有唯一配套读是按既有 `conversationRef` 寻址的 `chat.readThread@1`。
4. M2 没有候选人来源；当前脑只有会话列表里的 `platformUserRef`，不能据此选择一个未联系候选人。
5. §12.8 的驱动 canonical 只覆盖既有 IM 页面；当前有人打开的候选人页面尚无窄例外。
6. 真实 SX 的唯一自动恢复仍是同一 `witnessStoreId` 下 `report=unknown` 时重投原 `msgId`；其他失败或歧义不得自动补动作。

### 3.2 当前可达场景与修改必要性

M4 的目标候选人在动作前没有 `conversationRef`。以下时序在当前范围内可达：

```text
候选人/职位 preflight 通过
→ journal=attempting
→ 唯一招呼动作已经让平台建立会话并发出招呼
→ SW 在 committed/result 前死亡
```

此时脑只有候选人和职位身份，现有 `chat.readThread` 无法寻址；盲目再发违反安全内核，永久只转人工又不满足“新会话验证闭环”的到期义务。因此需要一个只返回结构化正证的候选人键验证读。

同时，没有正式候选人读取入口时，只能让真人抄平台 ID、走测试注入或把 DOM/URL 细节塞进脑，三者均违反产品入口与平台中立约束。

### 3.3 请求授权的规范变化

同批激活三个原语：

| 原语 | class | 作用 |
|---|---|---|
| `candidate.readCurrent@1` | readonly | 读取真人当前打开且唯一的候选人、职位和关系状态；不搜索、不滚动、不驱动页面 |
| `chat.sendGreeting@1` | effectful | 对已持久化、尚未建立关系的候选人×职位发送一条脑指定文本并建立新会话 |
| `chat.readGreetingOutcome@1` | intrusive / `idempotentReadReceipt` | 按候选人、职位和正文 hash 取得“关系已建立且招呼已服务端确认”的结构化正证 |

另外新增一个机器可读执行错误 `GREETING_REJECTED`：只表示平台明确拒绝该候选人/职位的招呼且可证明 `sideEffect=none`。它是 `docs/沟通逻辑规格-v4.md` 中“招呼发送失败 → 已结束（招呼失败）”的唯一自动映射。route、guard、identity、witness、receipt、页面解析或结果不明等技术失败不推进档案主线；否则一次页面抖动会永久结束一个候选人。

这项解释会同步写入沟通逻辑规格。`sideEffect=confirmed` 或验证取得正证时一律按已发出收束，不能归档为“招呼失败”。

### 3.4 拟议协议规格文本

拟在 §4.3、§4.5、§7.4、§7.5、§8.3、§9、§12、§16–§18 分别加入或同步以下规范性文本：

> `candidate.readCurrent@1` 只读取真人当前已经打开且界面上唯一可判定的候选人。成功 data 为 `{platformUserRef, displayName, positionRef, positionTitle, contactState}`；两个 `*Ref` 都是不透明稳定引用，脑只作相等比较。`contactState` 为 `unestablished | established | unknown`。该原语不得滚动候选人列表、自动选择目标、打开候选人或返回 `resumeNumber`、URL、selector、tabId、平台原始对象；零个或多个当前目标必须响亮失败。

> `chat.sendGreeting@1` 只对脑已持久化的候选人×职位执行一次，args 固定为 `{platformUserRef, positionRef, text}`，guards 固定为 `{expectUnestablished:true}`。正文使用 §4.5 的 NFC/空白规范化与 SHA-256 算法。平台 program 必须在 `attempting` 前和第一个可能发送招呼的标准动作前，以字面同一份 greeting evaluator 核对账号身份、唯一候选人、职位、尚未建立关系、硬截止、真人输入所有权和唯一公开动作表面；任何变化都以 `sideEffect=none` 停止。

> 该原语不得修改平台默认招呼语、以后不再弹出等账号级配置，也不得覆盖动作前已经存在的真人输入或招呼弹窗。若当前平台模式下第一次“打招呼”动作可能直接发送，则它就是本命令唯一允许的发送动作，不得随后再点击弹窗发送；只有真机证明第一次动作在当前公开状态下纯粹打开本命令拥有的编辑器时，才可继续写入精确正文并执行一次最终发送。无法在公开世界边界内区分时转人工，不向框架私有实现追证。

> `attempting` 成功持久化后，program 对候选人可见的招呼动作至多调用一次，原语内部不得重试。系统信任平台一次标准招呼动作至多产生一次候选人可见副作用且作用于界面所示对象；不以 Vue owner、组件树、SDK、VNode、listener 或事件接线互证授权。

> `chat.sendGreeting@1` 的 ok 必须同时观察到：同一 `platformUserRef + positionRef` 唯一绑定一个稳定 `conversationRef`；该会话中相对“关系未建立”基线恰有一条新的、服务端确认成功的我方文本，其 `contentHash` 等于待发正文。平台自动追加的职位提示或其他 system 行不计作第二条招呼。按钮状态、页面跳转、弹窗消失、编辑器清空、乐观消息或本地临时 ID 均不构成成功。

> 成功 data 固定为 `{platformUserRef, positionRef, conversationRef, contentHash, observedAt}`；evidence 类型固定为 `outboundGreetingObserved`，data/evidence/journal/outbox 均不得回抄招呼正文。目标换绑、已有会话、零个或多个会话、零条或多条匹配招呼、服务端确认不足或读取失败，均不得触发第二次动作。

> `chat.readGreetingOutcome@1` 按 `{platformUserRef, positionRef, contentHash}` 读取关系正证。只有候选人、职位、唯一稳定会话和唯一服务端招呼四者同时匹配时，返回 `confirmed=true` 及 `{conversationRef, contentHash}`；`confirmed=false` 只表示本轮没有取得充分正证，绝不表示“确认未发送”。它是 `chat.sendGreeting@1` 的唯一配套验证读，最多三轮；只有正证可自动补记成功，其他结果全部转 suspect。

> `chat.sendGreeting` 成功终局时，脑在一个 SQLite 单写事务中终结 effect intent、推进档案为 `greeted`、绑定候选人与新会话、创建 adopted `Conversation/TrackedIntent`（`adoptedBoundarySeq=0`）并追加唯一 `origin=self` 招呼消息。重复 result、迟到 result、验证正证或人工裁决必须收敛到同一唯一事实，不得增生关系、会话或消息。

> 有人值守 `candidate.readCurrent@1` 与 `chat.sendGreeting@1` 可使用真人当前打开的唯一候选人页面作为命令级动作表面。该窄例外不改变 IM 传感 canonical，不授权自动搜索、滚动、打开或切换候选人，不把 tab/window/route 写入协议；零个或多个目标匹配均在不可逆动作前失败。

> `GREETING_REJECTED` 只允许在平台给出明确业务拒绝且手能证明候选人可见副作用为零时返回，`retryable=no`、`sideEffect=none`。其他动作前技术失败保留档案 `selected`，由真人决定是否另铸新意图；动作后歧义进入验证/suspect。

拟将 `docs/沟通逻辑规格-v4.md` 第一节的例外补充为：

> “招呼发送失败直接归档「招呼失败」”仅指平台明确业务拒绝并收到 `GREETING_REJECTED/sideEffect=none`。身份、页面、守卫、证词、receipt、超时或解析等技术失败不推进主线；`sideEffect=possible` 进入 suspect，`sideEffect=confirmed` 或配套验证取得正证按已招呼处理。

拟在“主线状态跃迁表（全部跃迁，无其他）”补入 M4 有人值守入口：

> `人工指定当前候选人（M4 有人值守入口） | → 已选中`

> 只有 `candidate.readCurrent` 返回稳定候选人/职位身份且真人明确确认时，脑才创建或收编 `selected` 档案；单纯读取不建档。该入口是 M4 对自动“采集 → 打分 → 选人”前段的有人值守替代，不伪造“已采集/已打分”历史。

- E 文只追加 M4 增量，不改写 M3 历史：witness schema/version 不变，基线由既有会话尾变为候选人关系未建立，阴性不授权第二次招呼；
- codegen 对 verification 的门禁从只认 `chat.sendMessage` 改为遍历所有已激活真实 effectful；不趁机设计通用验证 DSL。

### 3.6 收益、成本与替代方案

收益：形成正式候选人入口与新会话恢复出口；完整复用 M3 的 brain ledger、idemKey、journal/outbox、query/report、suspect 与单写事务，不新增手侧业务状态；成功 data 足以让脑平台无关地绑定候选人、职位、会话和消息。

成本：增加两个读取原语、若干 schema、一个业务错误码和 greeting 专用 verifier，均成为契约负债；智联 program 需要一套与既有会话不同的动作 evaluator；真实页面若无法稳定关联候选人、职位、新会话与服务端招呼，本能力不得激活。

已否决的替代方案：

- 把 `sendGreeting` 塞进 `sendMessage`：动作前没有 `conversationRef/expectedTail`，语义不成立；
- 真人抄 `platformUserRef` 或测试注入：不是普通用户可用产品入口；
- 用 `resumeNumber`、姓名或职位名定位：身份会漂移或碰撞；
- 只靠现有 `chat.readThread` 恢复：失联时尚无 `conversationRef`；
- 让手在结果不明时再点一次：直接违反安全内核；
- 先造通用 effect target/verification DSL：当前只有第二个真实 effectful 用例，直接实现三个窄原语即可。

## 四、候选人表结构设计（悬置决策到期）

### 4.1 `Candidate`：人的平台身份根

```text
Candidate
  Platform             TEXT      NOT NULL  PK(1)
  PlatformUserRef      TEXT      NOT NULL  PK(2)
  DisplayName          TEXT      NULL
  FirstSeenAt          DATETIME  NOT NULL
  LastSeenAt           DATETIME  NOT NULL
  CreatedAt            DATETIME  NOT NULL
  UpdatedAt            DATETIME  NOT NULL
```

裁决：候选人主键固定为 **`(Platform, PlatformUserRef)`**。`PlatformUserRef` 的值必须来自经真机确认的稳定平台 userId，但在脑手协议和脑内只是不透明等值引用；任何一端不得解析其格式。

明确排除：

- `resumeNumber` 不进入 `Candidate`，不作主键、唯一键、外键、幂等键或关联兜底；
- `AccountRef` 不进入人的主键；招聘账号是动作上下文，不是候选人身份；
- `DisplayName` 是可变展示快照，改名只更新字段，不新建人；
- 姓名、职位、手机号、简历编号和会话编号均不参与人的相等判断。

未来若采集确需保留 `resumeNumber`，只能进入带来源与采集时刻的简历/来源快照表，且不得有指向 Candidate 身份的唯一语义。本次不提前建该表。

### 4.2 `CandidateProfile`：人 × 职位档案

沟通规格的状态主体是档案而不是人，因此状态不能塞进 `Candidate`：

```text
CandidateProfile
  ProfileID                  TEXT      NOT NULL  PRIMARY KEY
  Platform                   TEXT      NOT NULL
  AccountRef                 TEXT      NOT NULL
  PlatformUserRef            TEXT      NOT NULL
  PositionRef                TEXT      NOT NULL
  PositionTitle              TEXT      NULL
  MainStatus                 TEXT      NOT NULL
  EndReason                  TEXT      NULL
  SuccessfulGreetingIntentID TEXT      NULL
  ConversationRef            TEXT      NULL
  GreetedAt                  DATETIME  NULL
  CreatedAt                  DATETIME  NOT NULL
  UpdatedAt                  DATETIME  NOT NULL
```

约束：

- `ProfileID` 是脑生成的内部稳定引用，供 effect intent 的 `TargetRef` 使用；它不是候选人身份；
- 外键 `(Platform, PlatformUserRef) → Candidate`；
- 唯一键 `(Platform, AccountRef, PlatformUserRef, PositionRef)`，同人同职位重复读取只更新展示快照，不重置状态；
- `ConversationRef` 非空时，`(Platform, AccountRef, ConversationRef)` 唯一；绑定冲突必须整事务回滚；
- 人级建档闸由事务检查并以部分唯一索引兜底：同一 `(Platform, PlatformUserRef)` 最多一个 `MainStatus != eliminated` 的档案；已结束同样阻止换职位重新追求，只有已淘汰者未来可建立其他职位档案；
- M4 只产生 `selected → greeted`，以及明确 `GREETING_REJECTED` 时的 `selected → ended/endReason=greetingFailed`；其余完整状态机留待后续里程碑。

`PositionRef` 是招聘账号上下文内的不透明稳定职位引用。M4 只保存当前职位最小身份与标题快照，不提前建设完整职位管理表；若真机无法提供稳定 `PositionRef`，不得退化为只用职位标题。

### 4.3 `CandidateGreetingHead`：招呼意图 CAS

招呼前没有 conversation，不得把 `ConversationEffectHead` 硬套到候选人，也不为两个用例泛化通用 effect target：

```text
CandidateGreetingHead
  ProfileID       TEXT      NOT NULL  PRIMARY KEY
  LatestIntentID  TEXT      NOT NULL  UNIQUE
  Generation      INTEGER   NOT NULL
  CreatedAt       DATETIME  NOT NULL
  UpdatedAt       DATETIME  NOT NULL
```

脑在创建 `EffectIntent + CmdRecord` 的同一个 SQLite 单写事务中，对 `LatestIntentID/Generation` 做 CAS。UI 多标签、响应丢失或重复 POST 只能收编 current，不得生成第二个招呼意图。`EffectIntent.TargetRef = ProfileID`，idemKey 从 `ProfileID + IntentID` 确定性派生。

不新增第二套 effect intent 或 witness 表；`CandidateGreetingHead` 只解决“招呼前没有 conversation head”的业务最新意图锚点。

### 4.4 成功事务

`chat.sendGreeting` 的首次合法成功、重复 result、验证正证或迟到终局最终都必须进入同一个幂等事务。事务同时完成：

1. 校验 result 的候选人、职位、正文 hash 与原意图一致；
2. `EffectIntent → ok`，保存唯一 `conversationRef` 和发送 fingerprint；
3. `CandidateProfile selected → greeted`，写成功 intent、conversation 和 `GreetedAt`；
4. 创建或核对 `Conversation(platform, accountRef, conversationRef)`，其 `PlatformUserRef` 必须等于 Candidate 主键；
5. 创建 `TrackedIntent(requestedBy=system:greeting, status=adopted)`，会话直接 `TrackingState=adopted`、`AdoptedBoundarySeq=0`；
6. 追加唯一 `Message(seq=1, direction=out, kind=text, origin=self, outboundIntentId=intentId)`；
7. 任一唯一键、身份或已有绑定冲突时整事务回滚并转人工，不允许覆盖旧关系。

`adoptedBoundarySeq=0` 表示该会话没有被系统收编前的存量业务历史；系统亲自发出的招呼是边界后的第一条已发消息与后续时钟锚。平台自动加入的 system 行不冒充招呼，后续 `readThread` 仍可按既有对账规则观察。

### 4.5 现有数据与迁移口径

- 不把现有列表索引中的数百个 untracked `Conversation` 批量转换为 Candidate；它们是感知索引，不是选人或建档事实；
- 只有真人经 `candidate.readCurrent` 明确收编的候选人和系统本次亲生会话进入新表；
- 既有 adopted/M3 会话继续按现有模型工作，不要求 M4 为其猜造职位档案；
- 当前尚无真实客户，物理建表沿用首客前既有迁移入口，不在 M4 引入通用 migration framework；但 Candidate 复合身份、Profile 唯一键和 resumeNumber 禁令自本计划批准后视为正式设计，后续改变必须显式迁移，不能静默重解释已有行；
- 首个真实客户安装前仍须单独完成正式 schema migration 机制与冻结审查，本条列入后置项。

## 五、安全不变量与恢复收敛

1. **一个档案只有一个 current greeting head。** 重复 UI 请求只收编 current；成功、suspect 或未裁决会冻结新招呼。
2. **动作目标只认稳定平台用户 ID + 职位引用。** 姓名、标题、卡片序号、`resumeNumber` 和 DOM 路径不得兜底。
3. **关系已存在即不招呼。** 脑账本已绑定或手观察到 established 任一成立都在动作前停止；M4 不自动改派现有聊天。
4. **M3 安全内核原样复用。** idemKey、attempting→committed、outbox、query/report、域冻结、原语内不重试和结果未知不重发均不改 schema、不降级。
5. **先确定第一个发送能力边界。** 如果候选人卡第一次标准动作可能直接发送，它就是唯一发送动作；不能再补第二次弹窗发送。
6. **不覆盖输入、不改全局设置。** 原语只拥有自己本次创建的编辑器状态；发现已有弹窗/草稿或需改变平台默认配置时转人工。
7. **成功是三项正证。** 同一候选人职位、稳定新会话、唯一服务端招呼缺一不可；system 行不算招呼。
8. **阴性不能证明未发送。** `readGreetingOutcome.confirmed=false`、读取失败、零/多匹配都只会继续有限验证或 suspect，永不授权第二次动作。
9. **成功事实原子化。** 候选人、档案、意图、会话、tracked/adopted 和消息要么一起提交，要么一个都不推进。
10. **脑不读 evidence 做业务分支。** 自动推进只读契约 data；DOM、selector、tabId、平台原始 ID 和私有对象只可进入脱敏 evidence/日志。
11. **有人值守不是测试分支。** UI 和未来调度器都必须经同一产品服务、同一 effect intent、同一命令信封、同一 Dispatcher 和同一 program 原语。

恢复矩阵：

| 观察 | 脑侧处置 |
|---|---|
| outbox/done 含合法 `chat.sendGreeting ok` | 走同一成功事务；重复只回 duplicate，不增生 |
| 同 witness store 且 report=unknown | 仅允许重投原 msgId/body/idemKey/guards 一次 |
| attempting / possible / store 换代 / result 丢失 | 最多三轮 `chat.readGreetingOutcome` |
| 验证唯一正证 | 补记同一原意图成功并执行同一成功事务 |
| 验证 false、零/多关系、身份/职位不清 | suspect；不再次招呼 |
| `GREETING_REJECTED/none` | 原意图失败；档案 ended/greetingFailed |
| 其他合法 failed/none 或 receipt rejected | 原意图终局；档案保持 selected，真人可另铸新意图 |
| failed/confirmed | 冻结并验证/人工；不得归档招呼失败或另发 |

## 九、停止条件

出现以下任一情况立即停止当前真实测试，不尝试“修一下再点一次”：

- 无法从公开页面事实稳定取得 platform userId 或 positionRef；
- 候选人身份跨轻刷新变化、候选人/职位只能靠姓名标题或 resumeNumber 猜；
- 当前候选人已经有会话，或 unestablished 无法机器判定；
- 无法判断第一次“打招呼”是否可能直接发送，或 custom text 必须改变平台默认配置；
- 账号身份不一致、contract/cap/witness 不就绪、域冻结、真人输入未清、验证码、风控或平台限制；
- 自动故障矩阵、全量回归、事务回滚测试或隐私扫描未通过；
- 第一次候选人可见动作后，新会话、目标绑定或服务端招呼任一不能唯一确认；
- 真机事实与第三节拟议文本冲突。

动作前失败可由真人修复页面后另铸新意图；动作后失败只进入验证/suspect。最后两项必须回到裁决或人工，绝不第二次招呼。

## 十一、M4 完成定义

以下条件缺一不可：

- 第三节规范立案获批并按规格先行落地，契约、codegen、实现一致；
- Candidate 主键正式固定为 `(platform, platformUserRef)`，resumeNumber 未进入身份/关联链；
- 人工当前候选人入口、profile greeting head、sendGreeting 与配套验证读均走正式 Dispatcher；
- 自动故障矩阵证明任意覆盖故障下候选人可见招呼 ≤1，脑侧关系与消息事实 ≤1；
- 最窄冒烟已提交，后续采纳项各自提交，最多一轮独立审查且当前阻断项为零；
- 一次真实“你好”观察到同候选人新会话和唯一服务端招呼，脑账本原子 adopted；
- 脑重启、手重连和对账后零增生，新会话可进入现有巡检/`chat.sendMessage`；
- 全量门禁、隐私扫描和 M4 验收报告完成；
- 后置项保持后置，没有第二平台、AI、自动调度、卡片、云端或交付机制混入。

达到以上出口即停止 M4。继续增加样本、守卫、恢复机制或自动化范围，必须由真实失败证据、本文已列触发条件或甲方新授权重新立项。
