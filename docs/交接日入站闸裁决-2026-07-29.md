# 交接日入站建档闸裁决（2026-07-29 甲方裁决）

本文件固化甲方对"主动来聊候选人入站建档"范围的收窄裁决。它只收窄 `adoptInboundConversationProfiles` 的建档准入条件，不修改契约、不修改插件、不新增持久化状态，也不改变任何已建档候选人的既有处理。

## 背景

本产品是对旧产品"智联招聘自动化"的全新重构。首个客户从旧产品迁移过来时，其智联账号里仍留有旧产品时代产生的会话。这些会话对新产品而言与"陌生候选人主动来聊"在列表上无法区分：同样有 `platformUserRef`、`displayName` 和可匹配的职位标题。

甲方指定 **2026-07-29 为新老产品交接日**。

## 旧约束（被本裁决收窄的部分）

入站建档只要求三项页面身份事实齐备且无冲突：`platformUserRef` 非空、`displayName` 非空、`positionTitle` 存在且唯一匹配本机后台职位。会话年龄不参与判定。

## 当前可达场景（本裁决要阻断的链）

1. `chat.readList(filter=all)` 携带 `stopOlderThanDays=8`，返回 8 天内有活动的会话；`filter=unread` 按协议规格禁带该字段、**不设年龄截止**，老会话只要有未读气泡即可进入窗口。
2. `adoptInboundConversationProfiles` 位于 filter 分支之前，普通通道与未读通道共用同一处建档判定。
3. 建档成功（`main_status=selected`）后，`prepareInboundConversationProfile` 打开候选人简历页并采集简历快照，随即 `EnsureInboundConversationV4Root` 建立 V4 根。
4. 建根后进入 `processCommunicationV4Profile`：AI 生成回复，产生候选人可见动作。因为 `readThread` 已把旧对话历史读入，AI 拿得到上下文，会**接着旧对话继续推进**（索要微信、邀约面试）。

实际损失：对旧产品已经聊过、可能已经约过面、已经谈崩或已明确拒绝的候选人，新产品重走一遍完整沟通流程。这是对真实候选人的骚扰，且发生在我方无感知的自动链路里。

## 新裁决（权威文本）

1. **入站建档新增交接日判据。** 会话行的最后活动时间早于交接日本地 00:00 时，不予建档；记 `status=skipped reason=beforeHandover` 审计后跳过。判定位于既有三项身份事实判定的同一处，普通通道与未读通道共用。
2. **判据取列表行已有的 `ConversationSummary.lastActivityTs`**，不新增任何页面读取、不新增原语、不新增命令。时间戳缺失（`null`）时同样不予建档，方向保守。
3. **闸只作用于尚无档案的会话。** 已建档候选人在此判定之前即已返回，其既有处理、状态机与动作链完全不受影响。
4. **闸不落任何持久拒绝状态。** 被跳过的会话下一轮巡检重新评估；误挡的代价是"晚一轮"，不是永久丢失。
5. **交接日默认 `2026-07-29`，可由环境变量 `RECRUITHELPER_INBOUND_HANDOVER_DATE` 覆盖**，规格见下节。

## 环境变量规格

- **变量名**：`RECRUITHELPER_INBOUND_HANDOVER_DATE`
- **值格式**：`YYYY-MM-DD`，按脑进程的客户端本地时区解释，取该日 `00:00:00` 为界。早于该时刻的最后活动时间不予建档。
- **默认值**：`2026-07-29`（变量缺失或为空时生效）。
- **非法值拒绝启动**，不静默回落到默认。理由：格式打错一位（例如 `2026-8-1`）若悄悄回落，会放进一批本应挡住的旧会话，正是本裁决要阻断的方向；启动即失败让错误立刻可见。
- **只在脑进程启动时读取一次**，不持久化，不进契约，不经产品 UI、管理 API、旧后台或插件配置写入。
- **启动日志打印生效日期**。该值不是 PII，须可被一眼确认。
- **不设独立开关。** 需要让新产品接管全部历史时，把日期设早即可；日期本身足以表达全部意图。

## 明确接受的缺口

**旧产品的候选人若在交接日之后主动发来新消息，仍会被当作新入站候选人接管。** `lastActivityTs` 是"最后活动时间"，会被新消息刷新，因此拦不住"旧关系复活"这一类。

甲方 2026-07-29 明确在两个方案间选择接受此缺口：

- 已否决的备选：在 `prepareInboundConversationProfile` 建根前，复用本来就会发生的那次 `readThread`，按会话最早一条 external 消息的 `ts_approx_ms` 判定会话年龄（该判据单调、不随新消息漂移，且实测页面读到的 external 消息 100% 携带时间戳）。否决理由是甲方判断旧产品候选人在交接后主动冒泡者极少，且愿意人工处理这几例，不值得为此多一段判定逻辑与一批终态档案行。

若真机出现旧候选人复活并被自动接管的实例，该备选方案可作为后置项重新立案。

## 不变式（本裁决不触碰）

- 契约、`contract.v1.json`、协议规格与两端 codegen 产物一律不改。
- 插件端不改：不新增原语、不新增页面读取、不改变 `stopOlderThanDays` 语义。
- 不新增表、列、迁移路径、恢复路径或自动重试。
- 已建档候选人的建档事实、状态机、动作链、WAL/idemKey、手证词与平台正证等安全内核完全不变。
- 业务事实禁止物理 `DELETE` 不受影响：本闸在建档发生**之前**拦截，不产生需要删除或回滚的业务事实行。

## 成本

- **误挡真实新候选人**：仅当列表行 `lastActivityTs` 缺失或平台时钟异常时发生。实测本机现有 741 个会话全部携带该值，缺失概率极低；且下一轮巡检自动重新评估。
- **交接日当天的新候选人**：默认值 `2026-07-29` 放行当日活动，不产生此项成本。若部署时把日期设为次日，当天新来的候选人会被挡到次日巡检捡回。
- **无存量清理成本**：本机现有 333 个候选人档案最早建于 2026-07-21，全部由新产品自身招呼或收编产生，无需回填或清理。

## 后置项（本轮明确不做）

- 旧关系复活后被接管（上文"明确接受的缺口"）。
- 交接日期的产品 UI 配置面。
- 被跳过会话的产品页可视化（当前只落审计）。
