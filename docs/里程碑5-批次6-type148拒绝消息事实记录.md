## 四、正式巡检补充事实

部署硬切换后，第一次正式巡检在连续八个列表协议页成功后遇到一次页面注入空结果；账号立即恢复 `userPaused`，消息、AI 调用与自动动作计数均未变化。按既有 `afterRecovery` 语义重载插件及页面后，第二轮完整列表分页成功，证明该次列表失败属于可恢复瞬态，本批不据此修改列表页码或重试语义。

第二轮随后在 `/app/im` 基础路由读取目标线程时得到脱敏阶段码 `read_history_dom_fallback:history_api_rejected_on_base_route`：页面引擎能从会话列表唯一解析目标，但历史接口在未选中目标 route 时拒绝，DOM 也没有目标线程证词。该事实推翻 program 中“稳定列表页可直接读取任意会话历史”的旧假设。处置仍限定在智联 program：目标尚未选中时，先经完整 `conversationRef` 唯一定位、空草稿与账号/route 复核后点击一次会话行，确认目标 route 就绪，再执行原历史读取；任何歧义转人工。`chat.readThread` 的既有 `intrusive + idempotentReadReceipt` 分类已经覆盖打开会话可能产生的已读效果，machine contract 不变。

两轮均未读取到可入账的目标线程结果；既有 `system/system` 行未修正，DialogueTurn、AIInvocation 与 CommunicationAction 仍为零。账号保持 `userPaused`，待上述最窄 program 修正通过门禁后再验收。

## 五、第三轮对账事故与恢复

会话选择修正部署后，第三轮正式巡检成功取得完整四行页面快照。按平台枚举面事实门交叉核对，快照的脱敏形状依次为：

| 顺序 | 平台类型 | 脱敏形状 | 本批处理 |
|---:|---:|---|---|
| 1 | `104` | 当前沟通上下文；候选字段为 `job/resume/sessionOriginType` | 未新增映射，仍按 `system/system` 保守保存 |
| 2 | `169` | 沟通职位系统提示；候选字段为 `jobNumber/jobTitle/rootOrgId/title` | 未新增映射，仍按 `system/system` 保守保存 |
| 3 | `131` | 招聘方已发招呼 | 既有 `out/text` 映射 |
| 4 | `148` | 候选人拒绝反馈 | 本批严格 `in/text` 映射 |

旧检测器错误要求“活动账本长度必须等于完整页面快照长度”。因此活动账本只有两行、快照带两行前置历史时，专用分类修正没有进入；随后普通 deep 零重叠路径把四行快照误收编为历史基线。恢复前的六条物理事实如下，表中不含正文、消息身份或摘要原文：

| seq | 方向 / 类型 / 来源 | `sourceKey` | 事实解释 |
|---:|---|---:|---|
| 1 | `out/text/self` | 无 | 原始招呼，保留 |
| 2 | `system/system/external` | 无 | 被误分类的拒绝行 |
| 3 | `system/system/external` | 有 | 错误基线收编的 type 104 前置历史 |
| 4 | `system/system/external` | 有 | 错误基线收编的 type 169 前置历史 |
| 5 | `out/text/external` | 有 | 错误基线重复收编的招呼 |
| 6 | `in/text/external` | 有 | 正确的 type 148 拒绝行，保留 |

脱敏等值核验结果：seq1/seq5 的正文与内容摘要相等；seq2/seq6 的正文、内容摘要与平台时间相等；seq3..seq6 属于同一个 `oldTail=2 / historicalFrom=3 / historicalThrough=6 / imported=4` 基线轮。seq1 的 `tsApprox` 仍是第三节记录的已知旧错误，本次不回写。恢复前 DialogueTurn、AIInvocation、CommunicationAction 均为零，账号已置为 `userPaused`。

检测器修正后只在“快照尾存在唯一严格候选”时生成分类修正；允许快照携带任意数量的前置历史。多候选、候选不在尾、预期尾缺失或替换均响亮停止；原 `system` 尾仍存在且后接不同入站时仍走普通追加。

恢复提交前又通过正式 patrol 取得一次 fresh `chat.readThread`：`reachedTop=true`、快照四行、尾部唯一，且尾行的 `sourceKey`、`contentHash`、方向、类型、正文和平台时间与 seq6 全部匹配。因执行时早于产品的 08:00 日常开启窗口，本轮使用执行后即删除的一次性本地维护探针，只在“唯一账号仍为 `userPaused` 且无 active M5 试运行”时临时打开只读巡检窗并留下脱敏审计；命中目标 `chat.readThread` 后立即经正式 pause 入口恢复 `userPaused`。该探针没有进入提交、HTTP API、巡检代码或产品能力。

数据恢复使用事故专用本地 CLI，在一个 SQLite 事务内复用既有业务消息撤回路径；没有物理 `DELETE`，也没有裸 SQL 改行业务事实：
