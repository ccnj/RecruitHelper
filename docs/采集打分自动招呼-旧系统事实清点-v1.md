### 6.2 详情字段 fallback

旧 `parseDetailModal` 的顺序：

- 姓名：`.resume-basic-new__name` → 卡片姓名。
- 年龄：元信息中首个含“岁”的文本 → 卡片年龄。
- 工作年限：元信息中含“应届/年/经验”且不含“岁”的文本 → 卡片工作年限。
- 学历：元信息中匹配“博士/硕士/本科/大专/高中/中专/学历” → 卡片学历。
- 求职状态：元信息中匹配“在校/离校/在职/求职/看看机会” → 卡片求职状态。
- 城市：元信息中匹配“现居/户口” → 卡片城市。
- 最近投递：`.resume-section-purposes` → 卡片 `.talent-basic-info__extra`。
- 工作、教育、自评、证书分别取对应区块；缺区块时得到空字符串。
- `detailText` 为弹框全文加证书，截 12,000 字符；`rawText` 为卡片原文加弹框全文，截 2,000 字符。

旧身份字段 fallback：

1. `resumeNumber/resumeK/resumeT/userId` 先取当前 URL query。
2. 再对“当前 URL + 详情弹框 outerHTML 前 160,000 字符”按字段名正则扫描。
3. 再回落到卡片基础对象已有值。
4. 推荐采集主路径随后用列表节点 Vue 私有 `_props.source` 的 `userMasterId` 和 `resumeNumber` 覆盖上述身份；两者缺一即报错。
5. 详情 URL 的 `resumeNumber` 必须存在并与列表 source 的 `resumeNumber` 相等，否则该候选人采集失败。

Vue 私有 source 路径是旧代码声明，本次真机没有读取该私有对象；当前只真机确认 URL 确实随详情加入 `resumeNumber`。`__vue__/_props/source` 属平台内部、版本脆弱的考古线索。

### 6.3 展开与阅读

- 若 `.new-work-experiences__expand` 可见且文字为“展开全部”，旧代码点击并等待最多 2.5 秒直到文字出现“收起全部”。
- 随后只在工作经历区查找精确文本“展开”，最多 8 轮、每轮最多 16 个。
- 本次样本没有“展开全部”节点，故该分支未真机触发。
- 详情阅读时间随机 3–8 秒。代码寻找弹框内可滚动元素，选择可滚空间最大的一个；滚动步数为 `floor(seconds/12)`，下限 1、上限 5。以当前 3–8 秒配置实际为 1 步。
- 关闭详情首选 `.new-shortcut-resume__close, .new-shortcut-resume__close i`；找不到时发送 Escape。

### 6.4 通用弱 fallback 采集

推荐详情主路径之外，旧代码另有两个通用函数：

- `collectCandidateFromElement`：拼接节点 attributes、outerHTML 前 12,000 字符、文本；正则找 `resumeNumber`、`resumeK/k`、`resumeT/t`、`userId/userMasterId`。姓名先找 `.talent-basic-info__name--inner`，再找任意 class 含 `name/Name` 的后代。
- `collectOneZhilianCandidate`：URL query → 最多扫描 2,500 个 DOM 节点相关 attributes（总量上限 200,000 字符）→ local/session storage（上限 300,000 字符）→ `body.innerText`；姓名再走宽泛 name selector。

两条只属于旧代码声明；15 份数据库没有记录使用了哪条 fallback，当前推荐主流程也不调用它们作为详情身份 fallback。

## 7. 翻页、频控、停止与去重

### 7.1 采集批次与上限

- 推荐批次默认 3 人；调用参数被归一化为 2–5，只有传入 `<=1` 时允许单人批。
- 测试模式每轮上限 50；正式模式上限 150。
- 测试和正式的详情阅读、候选间隔、批间隔完全相同：3–8 秒、3–15 秒、5–12 秒。
- 两模式 `candidateInteractionIntervalMs` 都写成 `3 * 15 * 1000`，即 45 秒。
- 业务 tick 只接受 `reason=alarm_tick`，先查 45 秒间隔；本地小时必须 `>=8`，因此代码覆盖 08:00–23:59，没有单独的晚间上限常量。
- tick 还要求旧客户端返回任务可运行、客户端可用、用户已授权。

### 7.2 列表滚动即旧“翻页”

旧推荐页没有页码点击；以虚拟列表滚动作为翻页：

1. 从首张卡片祖先和 `.page-view__content, .app-view, .talent-recommend, .km-scrollbar__wrap, [class*="scroll"], [class*="list"]` 中筛可滚节点。
2. 选 `scrollHeight-clientHeight` 最大者；没有则用 document scroller。
3. 向下滚 `window.innerHeight × 0.75..1.0`，smooth，并派发 scroll 事件。
4. 固定等 1.2 秒，再最多 3 秒、每 500ms 轮询可见边界签名。
5. 边界签名是“可见 listitem 数量 + 首/中/尾三个 listitem 的 Vue source `userMasterId`”。scrollTop 或签名任一变化即记为 moved。
6. 单次采集函数最多进行 3 轮“扫当前卡片并尝试滚动”。

旧批量招呼另有反向寻找：把当前首个 listitem `scrollIntoView(block=end)`，等待 8 秒，再比较首项 `userMasterId`。这段属于招呼找卡片，不是推荐采集的向下翻页。

### 7.3 停止与客户端确认

- 当前批次没有新候选人且列表不能移动时，返回 `exhausted`。
- 总采集在 `exhausted` 或达到 50/150 上限时停止。
- 完成上报 reason 只有 `no-next-page`、`max-candidates-reached`。
- 每批发送 `ZHILIAN-CANDIDATE-BATCH-COLLECTED`；只有客户端业务响应被判定 accepted 后，插件才把本批 user ID 加入全局已采集集合。
- 结束另上报 `ZHILIAN-RECOMMEND-COLLECTION-FINISHED`，携带首屏第一个 `userMasterId` 作为后续招呼回找锚点。

## 8. 入库、打分调用与错误行为

### 8.1 入库

- `store_candidates` 接受对象或数组；非对象、缺 `resumeNumber/resume_number` 的条目跳过并做聚合日志。
- 落库字段包含 resume K/T、姓名、性别、年龄、工作年限、学历、求职状态、城市、期望职位/薪资、活跃标签、采集来源。
- 整个插件候选对象另存为简历 detail；同一 `resumeNumber` 再采集时覆盖 detail。
- 候选人初始主状态 `已采集`，微信状态 `未邀微信`。

### 8.2 评分输入

旧 `extract_scoring_input` 生成：

```text
基本：姓名、性别、年龄、工作年限、最高学历、求职状态、现居
期望：期望职位、期望薪资、最近投递
自评：最多 1,500 字符
工作经历：最多 1,500 字符
教育经历：最多 500 字符

```

它把结构化 JSON 的 `{resume_json}` 全量替换进评分模板。请求只有一条 `user` message，`response_format=json_object`、`temperature=0.3`、`max_tokens=2500`、单请求 timeout 120 秒。

模型配置可用逗号或换行表示顺序链；前一模型非配置错误失败后尝试下一模型，401/403、缺 key、缺 model 直接停止模型链。普通单次评分默认 `retries=2`；采集批次调用传 `llm_retries=0`，外层只对 `deepseek_error` 最多尝试 5 次，每次间随机等待 1–3 秒。若 `finish_reason=length`，内层独立允许一次 token 预算翻倍，最高 8,192；该次不计入外层 `llm_retries`。

运行时默认 `AI_SCORING_MAX_WORKERS=5`，每轮最多取当前 active batch 中 200 个“已采集、有 detail、无 score”的候选人，按 `last_collect_at, id` 排序；并行模式每次实际只提交前 `max_workers` 个，循环续取。

评分 JSON 接受键别名：`score/分数/评分`、`reason/理由`、`match_points/匹配点`、`concerns/顾虑点`。`score_version` 由实际模型名去掉 `-` 和 `.` 得到；表主键是 `(candidate_id, score_version)`，但评分入口的缓存查询只按 candidate 取第一条，已存在任一评分即不再评分。成功后主状态从 `已采集` 进 `已打分`。

网络错误使批次返回 `paused/network_retry`；配置错误使评分能力标为 blocked；其它最终失败会记录 `score_failed` 并调用旧库的候选人 purge。这里是旧代码实际行为陈述。

## 9. 阈值、确定性选人和招呼前状态

### 9.1 阈值与配额

旧默认值：

| 参数 | 默认 | 配置归一化 |
|---|---:|---|
| `targetMin` | 80 | 0–150 |
| `targetMax` | 90 | 0–150；若小于 min 则交换 |
| `minScore` | 5 | 1–10 |
| `maleRatioLimit` | 50% | 0–100 后除以 100 |

未指定目标数时，在 80–90 间随机取整数。男性上限为 `floor(targetCount × maleRatioLimit)`。

选人池只取本批 `main_status=已打分` 候选人，按评分降序、`lastActiveTime` 降序；同一候选人多版本评分取最新 `scored_at`。只有 `score>=minScore` 进入 eligible。遍历 eligible 填满剩余名额，男性达到上限则跳过。所有未被选中的池中候选人都进入淘汰：低于阈值写 `低分<5`，其余写 `落选(名额满)`。

库中 2,980 条选中记录的最低分为 5，且 1,015 条低分淘汰原因精确为 `低分<5`，与默认阈值相互印证。另有 765 条名额淘汰，最高分达到 8。

### 9.2 状态枚举

旧状态机主状态全集：`已采集`、`已打分`、`已选中`、`已招呼`、`沟通中`、`已邀面`、`已淘汰`、`已结束`、`已约面`。

15 库实际见：`已采集`、`已选中`、`已招呼`、`沟通中`、`已约面`、`已结束`、`已淘汰`。数据库快照中未见 `已打分` 和 `已邀面`，但代码有这两个中间态。

微信状态全集：`未邀微信`、`已邀微信`、`已加微信`。它是独立于主状态的另一条状态轴。

### 9.3 “合格”之后不是直接自动招呼

旧当前链路中，确定性选中会：

1. 把候选人主状态推进到 `已选中`。
2. 创建 `selection_review` pending。
3. 客户端 interaction state 在“选人待复核、招呼待复核、招呼生成中”等情形返回 `waiting_user_confirm`。
4. 只有复核通过且招呼内容准备好，状态才返回 `greeting_confirmed`。
5. 插件看到 `greeting_confirmed` 后才进入推荐页并领取 `ZHILIAN-GREETING-TODO-LIST-REQUEST`。

因此旧代码与日志所证明的链路是“采集 → 打分 → 确定性选中 → 人工确认/招呼准备 → 批量招呼”，不是“达到 5 分立即自动招呼”。
