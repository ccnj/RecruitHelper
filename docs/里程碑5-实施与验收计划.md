# 里程碑 5 · 确定性沟通状态机与 AI 建议层实施与验收计划

> 状态：待甲方裁决，2026-07-21。批准前只提交本计划，不修改可信规范、机器契约、数据库结构或生产代码。
> 上游约束：`AGENTS.md`、`contract/协议规格-v1.md`、`docs/沟通逻辑规格-v4.md`、`docs/协议设计/E-首个真实副作用安全轨道.md`、M4 计划与验收报告。
> 真机许可：见 `docs/真实账号测试授权记录.md`。当前 Chrome 已登录真实账号，可在授权范围内做普通聊天测试；仓库、报告、AI 调用日志与未来上报不得记录候选人姓名、平台账号/用户/职位/会话原始引用、聊天正文、完整 prompt、API key 或可还原身份的截图。
> 验收剖面：首个真实客户安装前、开发者模式本地加载、同机可信通信、真人每日开启巡检且全程值守；只覆盖智联一个真实账号、一个显式选定档案、一个普通文本对话轮、一次自动文本回复。

## 一、里程碑结论与边界

M5 不一次性吞下 `docs/沟通逻辑规格-v4.md` 的卡片、微信、运营通知和整套时刻表。当前缺少邀面卡、换微信卡及相应后置条件的稳定真机样本；拒绝流程、催 2、已邀面、跟催、卡片事件和服务态都依赖这些能力。把它们写进状态枚举并不能形成可验收的生产闭环，反而会制造一批没有生产者的状态和猜测性语义。

M5 只交付一个“对话核心”最窄竖切：

`M4 已绑定 profile/conversation 的档案收到一轮普通候选人文本 → 既有巡检先完成消息对账 → 脑冻结唯一 DialogueTurn → 确定性短路或 AI 三分类建议只落一次 → AI 只生成纯文本建议 → 确定性代码核对状态、输入边界和动作白名单 → 自动复用 chat.sendMessage@1 发送至多一次 → 唯一服务端正证 → 原子完成动作与消息事实`

候选人第一条真实文字一经正式账本观察，档案即由 `greeted` 进入 `communicating`，不以 AI 成功或回复成功为前提。AI 只回答“建议分类”和“建议文本”；它不能推进主状态、选择重试、扣预算、创建 effect intent、派发命令或把失败解释成成功。

M5 是首个自动 effectful 派发入口。自动的含义是：真人当天开启巡检并显式把一个档案加入 M5 试运行后，该档案的一个合格普通文本轮不再逐条弹出“确认发送”，由确定性脑代码自动构造一次 `chat.sendMessage` 业务意图。试运行范围固定为一个档案、最多一个自动发送成功；成功或进入任何 `manualRequired/suspect` 后自动退出试运行，不扩大到账号下其他档案。

本里程碑不做：

- 自动搜索、采集、AI 打分、选人、招呼调度、配额或平台风控节律；
- 拒绝分支自动挽留、换微信邀请、催 2、收号和运营通知；
- 邀面卡、换微信卡、跟催组、接受/拒绝卡事件和服务态；
- 冷催、36 小时归档、7 天兜底或跨日集中任务；
- 图片、语音、文件的自动理解；这些消息仍按“真实文字”推进 `communicating`，但转人工，不自动回复；
- 招呼前候选人主动来信的补采简历、完整简历采集或职位管理；
- 自动匹配平台职位标题与后台职位名；职位配置必须由真人显式绑定，禁止字符串猜测；
- 新脑手原语、新消息 kind、新 contract 字段、AI 专用命令通道或手侧 AI/调度逻辑；
- 运行时接入旧后台授权、bind/heartbeat/job-config；M5 只证明自有类型可由旧整包无损填充，并以本地配置运行；
- 第二平台、第二账号、无人值守转正、客户交付、远程 program、更新器或正式 schema migration 框架。

## 二、出口宣言（批准后冻结）

### 1. 本轮最小可交付出口

一个 M4 正式 `greeted + adopted` 且显式绑定职位 AI 上下文的档案，在既有巡检读到一轮普通候选人文本后：

1. 脑以消息账本的不可变边界创建唯一 `DialogueTurn`，重复巡检和相同消息重放不增生第二轮；
2. 前置确定性短路与 AI 三分类只得到一个持久结果；分类失败按既有规格固定落 `neutral`，不反复改判；
3. AI 生成的纯文本只作为建议持久化，确定性代码独立决定该轮是否允许 `replyText`；
4. 自动入口只从 `CommunicationAction` 的稳定主键确定性派生一个 `EffectIntent`，复用既有 head/CAS、WAL、mismatch 双闸、witness、`chat.sendMessage@1`、验证读与 suspect；
5. 只有唯一服务端发送正证才能把 action 记为 `sent`，并由既有成功事务追加唯一 `origin=self` 消息；
6. 脑重启、手重连、重复 patrol、AI 回包重放和 result/outbox 重放后，turn、action、effect intent 和候选人可见消息都不增生；
7. 一次有人值守的真实普通文本自动回复通过后，试运行自行停止，并形成《里程碑5-验收报告》。

最窄生产竖切自动冒烟一绿立即提交，不等待完整故障矩阵、独立审查或真实 Chrome 验收。

### 2. 必须立即阻断的损害

- 同一对话轮产生两条候选人可见回复，或重复巡检/重启另铸第二个自动意图；
- 回复错人、错职位、错会话，或以姓名、职位标题、列表位置等启发式绑定 AI 上下文；
- AI 直接推进状态、扣预算、创建命令、选择重试或输出未在白名单内的业务动作；
- 未真正发出的消息滑动时钟、记为固定话术已用、消耗打扰预算或把 action 记成 `sent`；
- 新候选人消息或真人出站消息已经改变消息尾，旧建议仍越过条件写发送；
- 覆盖真人草稿、绕过 `chat.sendMessage` evaluator、WAL、witness、验证读或 suspect；
- `contractMatch=false`、账号身份/hand/cap/witness 不就绪、账号域已有 suspect 时仍构造或写出 effectful；
- 把真实 SX 的 `failed/sideEffect=none`、receipt rejection 或阴性验证当成自动另铸新意图的授权；
- API key、候选人明文身份、聊天正文或完整 prompt 出现在普通日志、审计 detail、管理 API 返回、验收报告或未来云端上报；
- 物理删除 turn、action、AI 调用、配置修订或状态事实。

以上均为阻断级，真实测试立即停止。M3/M4 已冻结的安全内核不因“自动回复”而放宽。

### 3. 允许重试或人工兜底的失败

以下失败允许少发、延后或转人工，不为追求自动恢复扩大机制：

- job-config 真实响应与预期不符、配置缺文档、未知 placeholder、职位上下文未显式绑定；
- LLM 本地配置缺失、provider 超时/限流/余额不足、返回非法 JSON、空文本或输出越界；
- 完整历史超过本轮批准的 token 上限；
- 当前轮含图片、语音、文件、卡片、主动换微信、拒绝或其他 M5 未激活场景；
- 对账读不清、目标换绑、消息尾变化、真人先回复、草稿存在、控件不唯一、平台风控或验证码；
- 自动入口构造 effect intent 之前失败：保留 turn/分类/建议事实，后续是否重试 AI 只按本计划批准的次数与 token 预算；
- effect intent 一旦构造：严格服从协议安全内核。`failed/none` 与 receipt rejection 把 action 置 `manualRequired`；possible/confirmed/超时进入既有验证与 suspect；调度器不自动另铸新意图。

人在场可重新绑定配置、清理页面、人工回复或裁决 suspect。M5 不以“自动回复率 100%”为出口。

### 4. 独立审查预算与明确后置

冒烟 commit 后最多一轮独立审查。阻断项修复后只复核对应 diff，不重开全量审查；优化级发现必须同时证明常见、边际价值明确且修复成本低，否则登记后停止。

以下已清偿项不重做：派发层 contract mismatch 双闸、出站消息 `retracted` 显式事实、M3 witness/验证/suspect 轨道、M4 Candidate/Profile/Conversation 绑定。

卡片、微信、拒绝自动流程、时刻表、媒体、运营通知、旧后台运行时接入、第二平台和无人值守全部后置，见第十四节。达到一个档案一次自动回复的出口后必须停止，不顺手开始 M5-B 或 M6。

## 三、AGENTS.md 第 12 条规范修改立案

本节只请求修改授权，不把拟议文本当作既有依据。批准后仍先完成批次 0 事实门；事实推翻拟议语义时停止并重新立案，不得让实现反向塑造规范。

### 3.1 现有约束

1. `AGENTS.md` 当前写明本仓库“现阶段完全不连云端”，授权/旧后台接入后置；真实 LLM provider 是新的出站信任边界。
2. `docs/沟通逻辑规格-v4.md` 已规定 AI 是建议者、状态由确定性代码裁决；一轮只判一次，动作失败时重放未完成动作、不重判。
3. 同一规格又笼统写“招呼后的生成或发送失败，下轮巡检自然重试”；协议规格则明确真实 SX 的 `failed/none` 与 receipt rejection 终局化原意图，只能由人决定是否另铸。两者在自动入口到来前尚未冲突，M5 必须消解。
4. 对话轮定义了“判后新来的消息属于下一轮”，但没有裁定旧轮建议尚未派发时遇到新消息或真人先回复如何处理。
5. 协议规格已经允许“测试页、调度器、运营工具都是脑内命令生产者”，`chat.sendMessage@1` 与全部安全轨道不依赖生产者是人还是自动状态机。
6. 当前 contract 不包含 AI、职位配置、对话轮或业务状态，也不应包含；这些都是脑内领域语义。

### 3.2 当前可达场景与修改必要性

M5 的正常链路会出现：

```text
巡检对账到候选人文本
→ 分类与回复建议落库
→ 自动状态机创建 chat.sendMessage effect intent
→ 手在动作前明确 failed/sideEffect=none，或 receipt rejected
→ 下一轮巡检再次看见同一个未完成业务动作
```

如果照沟通规格的笼统“自然重试”另铸意图，就绕过协议安全内核；如果把所有 AI 阶段失败也当真实 SX 终局，又会无谓放弃无候选人副作用的可恢复计算。必须在规范中以“effect intent 是否已经构造”为分界。

另一个可达场景是：建议已冻结但尚未构造 effect intent，候选人又发一条消息或真人先行回复。继续发送旧建议可能答非所问、与真人抢话；自动合并并重新生成又会扩大本轮机制。M5 最窄裁决应是：旧 action 显式 `superseded/manualRequired`，该档案停止自动化，不自动重写或补发。

### 3.3 请求授权的规范变化

本批请求授权：

- 将“完全不连云端”收窄为“不连接旧业务后台；只允许 Go client 按本地显式配置直连一个 LLM provider”；
- 明确 provider 请求与本地业务数据、普通日志/未来上报之间的隐私边界；
- 明确 AI 只产出结构化建议，确定性 reducer 是状态与动作唯一裁决者；
- 按 effect intent 构造点分开 AI 计算重试与真实 SX 恢复；
- 明确旧轮建议遇到新入站或真人出站时不得自动继续发送；
- 明确 M5 只激活普通非拒绝文本回复，未激活分支转人工；
- 明确自动状态机是既有 `chat.sendMessage` 的合法命令生产者，但不获得任何安全内核豁免；
- 不修改 `contract.v1.json`，不新增 brain-hand schema、原语、枚举、capability 或 codegen 产物。

### 3.4 拟议 `AGENTS.md` 文本

拟将首段“本仓库现阶段完全不连云端”改为：

> 旧后台（xq-resume-backend）在客户交付前仍不改动，本仓库运行时仍不接 bind/heartbeat/job-config 等旧业务接口。M5 起唯一获准的云端出站是：Go client 按客户端本地显式配置直连一个 LLM provider；model/base_url/key 不由插件或旧后台下发，插件永远不接触 key。职位 AI 上下文使用本仓库自有类型，须能由旧 job-config 整包无损填充，但兼容证明不等于运行时接入授权。除此之外仍视为不连云端。

拟在全局约定加入：

> AI provider 请求只携带完成当前建议所需的职位上下文、消息角色/正文与状态事实，不携带 platformUserRef、accountRef、conversationRef、resumeNumber 或候选人 displayName。候选人自由文本可能自含身份，系统不承诺内容级脱敏。普通日志、审计 detail、管理 API、验收报告和未来上报只允许 invocation/turn/action 随机引用、用途、provider/model、配置 hash、输入输出 hash、token 数、延迟、状态、错误分类与估算费用；禁止记录 API key、base request/response、聊天正文、完整 prompt 或候选人明文身份。业务数据库为完成重放而持久化的消息与建议正文不属于“日志/上报”，仍受本地数据边界与业务事实禁止物理删除约束。

### 3.5 拟议《沟通逻辑规格-v4》文本

拟在第五节“他说话了”前加入 AI 权限边界：

> AI 是纯建议层。判意向 AI 只能返回 `interested | rejected | neutral` 建议；回复 AI 只能返回候选文本与允许的建议元数据。主线状态、微信线、预算、话术标记、轮边界、动作种类、是否发送、何时重试及 effect intent 均由确定性代码根据已持久化事实裁决。AI 输出不得直接解释为状态跃迁或命令；未知字段、未知动作、非法结构或越界文本一律丢弃并转保守分支。

拟把“发过”条目中招呼后的失败语义改为：

> 招呼后的沟通动作在**尚未构造真实 effect intent**的 AI 分类、建议生成或确定性计划阶段失败，可在后续巡检按持久轮边界继续计算；已落库的分类不得重判，已冻结的合法建议不得重新生成。**一旦真实 effect intent 已构造**，恢复与失败完全服从《协议规格-v1》：只有同 witness store 且 `report=unknown` 可重投原 `msgId`；`failed/sideEffect=none` 与任意 receipt rejection 均终局化原意图并把业务动作转人工，自动调度不得另铸；possible/confirmed/结果未知只进入验证、suspect 或人工裁决。只有唯一发送正证才算“发过”。

拟在“对话轮”条目后加入：

> 判定结果落库后、真实 effect intent 构造前若又观察到候选人新消息或真人出站消息，旧轮未发 action 不再自动执行，显式标记为 `superseded/manualRequired`；新消息属于下一轮，但 M5 试运行先冻结该档案等待真人，不自动合并、重写或连续发送。effect intent 已构造后的页面变化由既有 expectedTail/evaluator、验证与 suspect 收敛，业务层不得旁路取消后补发。

拟在第五节加入 M5 激活边界说明：

> M5 首个生产剖面只自动处理已正式绑定 profile/conversation/职位上下文的一轮普通文本，且只开放 `interested/neutral → replyText`。`rejected`、主动换微信、卡片、媒体、服务态、时钟动作或任何未激活能力均转人工；这只是阶段性能力削减，不改写本文完整目标行为，也不得用不完整动作冒充完整分支。

### 3.6 拟议《协议规格-v1》与 E 文文本

拟在协议规格 §7.4/§7.5 加入：

> 脑内命令生产者可以是真人确认入口，也可以是经批准的确定性自动状态机。自动生产者必须先持久化唯一业务动作事实，并从该事实主键确定性派生 `intentId`；重复巡检、进程重启或 AI 回包重放只能取回同一动作与同一 intent，不得按当前时间另造。生产者身份不进入线上协议，也不改变 WAL、head/CAS、idemKey、witness、guards、验证、suspect 与 contract mismatch 双闸。

拟在 §8.1/§8.2 的真实 SX 失败总则补一句事实同步：

> “只能由人确认后另铸新意图”同样约束自动业务调度器：调度器不得把 `failed/none`、receipt rejection、阴性验证或 `resolvedFailed` 当作再次自动发送的授权。业务层可在 effect intent 构造前重做纯 AI 计算，但不得把这条例外延伸到已经构造的真实 SX。

拟在 `docs/协议设计/E-首个真实副作用安全轨道.md` 的 X10 后追加：

> M5 自动生产者以持久 `CommunicationAction` 主键替代 M3 有人值守 UI 的一次确认作为上游稳定意图源；这只改变“谁创建意图”，不改变意图之后的任何安全轨道。一次 action 至多绑定一个 effect intent；动作失败后的自动另铸仍被禁止。

### 3.7 机器契约裁决

M5 不修改 `contract/contract.v1.json`。理由：

- AI provider 是脑的外部依赖，不是脑手协议参与者；
- `DialogueTurn`、`CommunicationAction`、职位上下文和模型用量是脑内业务事实；
- 自动调度器已经是协议明文允许的命令生产者；
- 真实发送继续使用 `chat.sendMessage@1` 的现有 args/guards/data/evidence 与 `chat.readThread@1` 验证读；
- 诊断所需 provider/model/token/latency 可进本地领域表和日志，不值得成为永久 contract 负债。

若批次 0 或实现证明必须让手理解 AI、职位配置或业务轮状态，视为架构方向错误，停止重提，不得新增 contract 字段迁就实现。

### 3.8 收益、成本与替代方案

收益：形成第一条真正由脑自动决策并复用既有安全轨道的业务闭环；AI 输出与状态裁决物理分层；一轮一次分类、动作一次意图和成功一次消息均由数据库唯一约束证明；未来卡片和时刻表可复用 turn/action，而不让模型直接操纵平台。

成本：新增 LLM 出站信任边界、本地 secret 配置、三类业务事实表和职位上下文修订；完整历史可能带来成本与上下文上限；一个档案的试运行范围降低了短期自动覆盖率。

否决的替代方案：

- 让 AI 返回“更新状态+执行动作”的自由 JSON：违反 AI 建议者红线；
- 在插件里直连 LLM：泄露 key，破坏脑主动和手无业务状态；
- 复用旧客户端大段 chat_reply 状态机：旧实现和 v4 目标不一致，且职位、固定话术与恢复链耦合严重；
- 把 job-config 原响应直接当领域类型：把旧后台 camelCase、DeepSeek 配置继承和历史化石永久带入新项目；
- 把职位标题自动匹配到后台职位名：可能给正确候选人使用错误职位事实，属于错靶；
- M5 先建通用工作流/事件溯源/多 provider 路由框架：当前只有两个 AI 用途和一个真实竖切，成本不成立；
- 自动 SX `failed/none` 后换 intent 再发：直接违反冻结安全内核；
- 等卡片和完整时刻表全部完成再做第一次自动回复：延迟最稀缺的真实反馈。

## 四、批次 0：job-config 与固定语事实门

### 4.1 立项前只读考古所得候选结论

这些结论只用于设计事实门，旧仓源码不是本仓库可信事实：

1. 旧后台源码同时实现 `POST /api/v1/client/job-config` 与 `POST /api/v1/client/job-configs`。单数返回当前职位整包；复数顶层为 `{currentJobId,jobs}`，每个 job 与单数同形并增加 `missingDocs`，且 `includeDocuments=false` 时原始 `documents` 会被清空。
2. “六种 doc_type”存在三个口径：
   - 初始表结构六种：`打分/招呼语/多轮沟通/固定语1/固定语2/固定语3`；
   - 当前旧后台领域常量十种：另有 `职位筛选/候选人筛选/意向判断/沉默追问/客户事实库/固定话术/固定规则` 等正式类型；
   - 沟通链路俗称六类：`多轮沟通/意向判断/沉默追问/客户事实库/固定话术/固定规则`，但后台 `missingDocs` 实际只把前五类非空作为硬条件，`固定规则` 可空。
3. 没有找到旧客户端把 `固定语1/2/3` 分别解释为三段稳定业务话术的生产证据。旧设计称三者为占位；迁移链只证明 `固定语1 → 礼貌结束话术 → 固定话术`，`固定语2/3 → 固定规则`，后两者有信息折叠。
4. 当前 `fixedPhrases` 是 `{content,scenes}` 场景包；源码候选场景包括 `rejectWechat/wechatAccepted/candidateAskWechat/meetingAccepted/silence48Wechat/meetingInvitePending`，但最后一项未找到生产消费者。
5. 单数/复数整包还携带 `apiKey/model/baseUrl`。M5 不继承这些字段，provider secret 与模型选择必须来自新客户端本地配置。

因此 M5 不会把“固定语 1/2/3”写成新领域枚举，也不会假定当前部署与源码一致。

### 4.2 获批后的真实只读采样

批次 0 使用旧系统现有授权上下文，只读调用真实部署：

1. 分别请求 `/api/v1/client/job-config`、`/api/v1/client/job-configs`；复数分别采 `includeDocuments=false/true`；
2. 只记录 HTTP 状态、JSON key、类型、null/空值口径、数组计数、每类文档字节数与 SHA-256；不记录 license token、API key、base_url、prompt/事实库/话术正文；
3. 确认复数端点是否真实部署、是否被止血开关返回空 jobs、`currentJobId` 是否存在于 jobs；
4. 对至少一个职位核对生效文档确实来自 `active_version_id`，不按反范化 `job_id` 混入历史版本；
5. 记录真实 doc_type 集合、各类空值计数，以及 `固定语1/2/3/礼貌结束话术` 是否仍有存量；只留聚合计数和 hash；
6. 枚举 `fixedPhrases.scenes` 的真实 key、值结构和启用状态，不记录具体文本；与旧客户端真实消费者集合做交集；
7. 盘点 `多轮沟通/意向判断` prompt 的 placeholder 名称和必填语义，只记 placeholder 名，不记 prompt；确认 M4 当前 Candidate/Profile/Message 数据能否填满；
8. 用脱敏 fixture 证明单数整包和复数 job 包均可映射到本仓库 `JobAIContextRevision`：`job_version_docs` 返回的**全部** `doc_type/content` 均逐项保留，导入前后集合与内容 hash 相等；M5 实际消费的沟通视图只允许从这份无损原包显式派生；
9. 考古报告明确写出固定语 1/2/3 的“可证映射、不可证映射、不得继承项”，不以迁移名推断业务话术。

产物为 `docs/里程碑5-批次0-job-config事实记录.md` 与一个不含正文、key、身份的测试 fixture，独立 docs commit。

### 4.3 事实门出口与停止条件

事实门通过必须同时满足：

- 至少单数真实整包形状已确认；若复数端点被关闭，可记录事实但不阻塞 M5 单职位试运行；
- 当前目标职位 `job_version_docs` 的完整文档集合可逐字节收进自有类型；批次 0 已根据真实 `doc_type` 和旧客户端消费者冻结 M5 沟通视图，未使用文档也没有丢失；
- `多轮沟通/意向判断` 的必填 placeholder 可由当前本地事实填充；
- 目标 profile 与一个本地职位上下文可由真人显式绑定；
- 固定语 1/2/3 没有被伪造成三个新业务场景。

任一以下情况立即停止并重提立案：

- 真实回包形状无法被拟议类型无损表达；
- 目标 prompt 强依赖当前不存在的简历字段，无法安全填充；
- 真实配置只有历史固定语槽位且语义无法证实；
- 必须结构性修改旧后台才能提供 M5 所需信息；
- 需要按职位标题猜测配置归属；
- 采样会把 secret、prompt 正文或候选人身份写入仓库。

加法式小改（例如未来增加一个明确 doc_type 或响应可选字段）只可另行立案；结构性重做旧后台默认不做。

## 五、AI 上下文、provider 与兼容设计

### 5.1 本仓库自有职位 AI 上下文

领域类型由“无损来源包”和“可执行语义视图”两层组成，不把旧响应 DTO 直接当领域模型，也不因 M5 暂时不用某类文档而丢掉它：

```go
type JobAIContextRevision struct {
    ContextID       string
    RevisionHash    string
    SourceKind      string // localImport；未来才可能是 legacyJobConfig
    SourceJobRef    string // 可选，只作来源审计，不参与 profile 身份
    DisplayName     string
    Environment     string
    SourcePackage   JobConfigDocumentPackage
    Communication   CommunicationView
    CreatedAt       time.Time
}

type JobConfigDocumentPackage struct {
    Documents []JobConfigDocument // 按 doc_type 排序后的完整原包；未知/未使用类型也保留
}

type JobConfigDocument struct {
    DocType string
    Content string
}

type CommunicationView struct {
    ConversationPrompt string
    IntentPrompt       string
    SilencePrompt      string // M5-A 不消费
    CustomerFacts      string
    FixedPhrases       string
    FixedRules         string // 经事实门确认后可为空
    MappingVersion     string // 批次 0 冻结的显式映射，不靠名字猜测
}
```

`RevisionHash` 由完整 `SourcePackage` 和稳定元数据的 canonical JSON 计算。同一 `doc_type` 重复、空缺口径不明或结构化区与原始 `documents` 冲突时 fail-closed。`CommunicationView` 只是批次 0 证实后的派生投影；解析固定话术只产生更下游的临时视图，原包永远保留。坏 JSON 不丢原文，但对应自动分支不可用。配置更新产生新 revision，不原位改写历史轮使用的 revision。

M5 运行时不连接旧后台。批次 0 只实现纯映射函数和脱敏 fixture；真实试运行使用本地导入的一份 context revision。未来接旧后台时，只新增 adapter，不改状态机、AI 输入或 action 表。

### 5.2 兼容判据

“能被旧后台 job-config(s) 整包无损填充”具体定义为：

1. 单数整包或复数 `jobs[i]` 对应活动版本的 `job_version_docs` 文档集合，必须按 `doc_type + UTF-8 content` 一一进入 `SourcePackage`；导入前后类型集合、空值口径与逐项字节 hash 相等，M5 不消费的打分、招呼或未知加法类型也不得丢失；
2. `job.id/name/environment` 能进入来源元数据，但不成为平台候选人或职位身份；
3. `CommunicationView` 只能由批次 0 冻结的显式映射从 `SourcePackage` 派生；`fixedPhrases.scenes` 只作一致性校验或派生缓存，不反向覆盖原包；
4. 旧整包的 `apiKey/model/baseUrl` 是 provider 凭据而非 `job_version_docs` 业务文档，按甲方约束明确不继承；这三个字段的舍弃必须由 adapter 测试显式断言，provider 配置走本地独立类型；
5. `documents` 未返回时，只能从整包结构化区**可逆重建**同一来源包；两条来源同时存在时逐项类型/content hash 必须一致，不一致 fail-closed。若结构化区不足以还原全部文档，`includeDocuments=false` 的回包只能用于形状验证，不能创建 context revision；
6. 原始六占位时代的 `固定语1/2/3` 只有经真实数据和消费代码共同证实语义后才可写入 `MappingVersion`；默认只在 `SourcePackage` 中无损保留，拒绝猜测它们分别对应什么业务话术。

### 5.3 profile 与职位上下文绑定

M4 的 `positionRef` 是平台不透明职位引用，旧后台 job id 是客户配置引用，二者没有天然等价关系。M5 增加真人显式绑定：

- 一个 profile 在试运行前选择一个 `ContextID`；
- 绑定记录保存 `profileId/contextId/revisionHash/boundAt/boundBy/status/reason`；
- 改绑以新显式事实表达，旧绑定标 `superseded`，不物理删除；
- 每个 DialogueTurn 冻结实际使用的 `revisionHash`；中途配置更新不改变已判轮；
- 禁止按 `PositionTitle == job.name` 自动绑定或兜底。

### 5.4 provider 接口与本地配置

脑内只定义一个窄 provider 接口：

```go
type LLMProvider interface {
    CompleteJSON(ctx context.Context, request CompletionRequest) (CompletionResponse, error)
}
```

`AIAdvisor` 在 provider 之上定义 `SuggestIntent` 与 `SuggestReply` 两个业务用途。provider 只负责 HTTP、认证、超时、JSON 响应抽取与用量；不理解 CandidateProfile、状态跃迁或发送动作。

首批只实现一个 OpenAI-compatible Chat Completions adapter，足以覆盖 DeepSeek 与支持该接口的 OpenAI 模型；不做多 provider 自动路由、fallback、熔断集群或 SDK 抽象。以后确需 Responses API 或本地模型时，新增 adapter，不改业务层。

本地配置为：

```text
provider
model
base_url
api_key
request_timeout
max_input_tokens
max_intent_output_tokens
max_reply_output_tokens
```

配置只保存在客户端 data 目录，不提交仓库、不经插件、不从旧 job-config 继承。管理 UI 对 key 只显示“已配置/未配置”，读取 API 不回传原值；日志只记录 provider/model，不记录 base_url、key 或请求认证信息。当前同机可信剖面不引入操作系统钥匙串或远程 secret 服务；首客前按交付威胁模型重新裁决本地 secret 存储。

同一物理 provider 调用不在 HTTP adapter 内自动重试，避免一次逻辑调用产生不可见的双计费。后续巡检重试必须新建一条 `AIInvocation` 事实并受每 turn 次数与 token 预算约束。

### 5.5 AI 输入与输出

provider 请求使用本仓库自有 `AIAdviceInput`，包含：

- 当前 profile 主状态与仅供裁决的布尔/枚举事实；
- 当前职位标题和从冻结 `SourcePackage` 显式派生的 M5 沟通视图；
- 完整活动消息历史（role、kind、text 或媒体占位符）及本轮消息边界；
- 当前只允许 `replyText` 的动作白名单；
- 禁止声称“已加上/已通过”、禁止虚构系统会执行的后续动作等已冻结约束。

请求不携带 platform/account/conversation/user 原始引用、resumeNumber 或 displayName。完整历史若超过批准 token 上限，不静默截断，转人工；以后是否做可证明的摘要另行立案。

AI 输出固定为：

```go
type IntentSuggestion struct {
    Label string // interested | rejected | neutral
}

type ReplySuggestion struct {
    Text string
}
```

模型不返回 `send=true`、状态、预算或 action list。确定性代码先做拒绝模板/简历标记/空轮短路，再在需要时调用意向模型；分类结果持久后不重判。`rejected` 在 M5-A 只转人工；`interested/neutral` 才可进入纯文本建议。建议文本经过非空、UTF-8/长度、无未知结构、当前能力白名单和必要禁承诺规则校验；失败不构造 effect intent。

## 七、领域数据模型与唯一约束

M5 不建通用事件溯源或工作流引擎，只增加当前竖切有真实生产者和消费者的事实。

### 7.1 `JobAIContextRevision`

保存第五节自有类型。主键 `revisionHash`，`contextId + revisionHash` 唯一；完整 `job_version_docs` 来源包及派生沟通视图是本地业务配置，不进入日志。历史 revision 不删除、不原位改写。

### 7.2 `ProfileAIContextBinding`

保存真人把一个 profile 绑定到一个 context revision 的事实：

```text
bindingId
profileId
contextId
revisionHash
status = active | superseded
reason
boundBy
boundAt
supersededAt
```

每个 profile 最多一个 active binding；替换以显式 `superseded` 表达。

### 7.3 `DialogueTurn`

```text
turnId
profileId
conversationRef
inputDigest
historyThroughSeq
inboundFromSeq / inboundThroughSeq
contextRevisionHash
status = collected | classified | adviceReady | dispatching | completed | manualRequired | superseded
intentLabel
intentSource = codeShortCircuit | llm | llmFailureFallback
classifiedAt
createdAt / updatedAt
```

`profileId + inputDigest` 唯一。`inputDigest` 由 profile、上一条活动出站边界、当前轮有序活动消息 seq/kind/contentHash 和 historyThroughSeq 确定性计算，不使用 wall clock。重复平台观察、巡检和脑重启只能取回同一 turn。

### 7.4 `CommunicationAction`

```text
actionId
turnId
kind = replyText
text
contentHash
status = planned | effectPending | sent | manualRequired | superseded
effectIntentId
failureReason
plannedAt / effectStartedAt / sentAt / updatedAt
```

M5 每 turn 只允许一个 `replyText`，`turnId + kind` 唯一；`effectIntentId` nullable unique。`actionId` 是自动 `intentId` 的稳定派生源，不能按当前时间重造。建议正文必须持久化后才能构造 effect intent；重启复用同一 text/hash。

### 7.5 `AIInvocation`

每次真实 provider 调用追加一行：

```text
invocationId
turnId
purpose = intent | reply
attempt
provider / model
contextRevisionHash
inputHash / outputHash
inputTokens / cachedInputTokens / outputTokens
latencyMs
status = ok | transportFailed | providerRejected | invalidOutput | budgetBlocked
errorClass
estimatedCostMicros
createdAt / finishedAt
```

`turnId + purpose + attempt` 唯一。表中不保存 key、base request/response、候选人身份、正文或完整 prompt；raw 输出中合法建议文本只进入 `CommunicationAction`，分类只进入 `DialogueTurn`。估算费用是观测值，不参与状态裁决。

### 7.6 `CandidateProfile` 增量

只新增当前可生产的 `communicating` 主状态及首次真实文字时间/轮引用。M5 不提前加入 `invited/interviewed`、微信线、冷催余额、固定话术标记或卡片组字段；这些没有当前生产者。

档案 `greeted → communicating` 的触发是正式消息账本中新出现候选人真实文字，不等待分类或回复。已经 `ended/eliminated` 的档案不纳入 M5-A，避免提前实现唤醒和已淘汰不回复语义。

### 7.7 业务事实删除纪律

上述表均不使用 `gorm.DeletedAt`，不物理 DELETE。错误 AI 输出、过期建议、改绑和人工接管分别以 `invalidOutput/superseded/manualRequired` 明示；查询必须按业务语义显式选择活动行。

## 八、确定性处理顺序与事务边界

### 8.1 每档案处理顺序

巡检仍先完成 M2 消息对账，再交给沟通 reducer；传感事件不直接调用 AI 或发消息。M5-A 单档案顺序：

1. 根据正式 profile↔conversation 绑定读取活动账本；
2. 若第一条未处理候选人真实文字存在，原子推进 `greeted → communicating`；
3. 若存在真人出站消息，先以它滑动“我方最后已发”边界，不与真人抢话；
4. 从上一条活动出站消息之后收集候选人的全部新消息，冻结一个 turn；
5. 非普通文本、拒绝/换微信/卡片等未激活语义标 `manualRequired`，不进入 AI 回复发送；
6. 运行确定性意向短路；需要模型时只调用一次意向建议并持久化分类；失败固定 neutral；
7. `rejected` 转人工；`interested/neutral` 调用回复建议；
8. 合法建议原子创建唯一 action；
9. 构造 effect intent 前重新核对 profile/context/conversation 绑定、turn 输入尾、是否新增消息、是否真人已回复、action 是否 current、账号域是否可派发；
10. 由 action 主键确定性创建一个 effect intent，并走既有 `chat.sendMessage`；
11. 唯一正证使 action `sent`；其他终局按安全内核映射，不自动另铸。

M5-A 不执行事件层和时刻表动作；遇到相关事实只转人工，不假装已处理。

### 8.2 事务边界

至少四个明确事务，不跨网络持锁：

1. **轮冻结事务**：确认账本边界、推进首次 `communicating`、创建/复用 DialogueTurn；
2. **分类/建议事务**：provider 调用在事务外；回包后以 turn 状态 CAS 写 AIInvocation 和分类或 action，输入边界已变化则只记 invocation、action 不转正；
3. **意图构造事务**：核对所有脑侧前置，CAS `action planned → effectPending`，创建唯一 EffectIntent/Cmd 并推进现有 ConversationEffectHead；
4. **发送成功事务**：复用 M3 已有成功入账，并在同一 SQLite 单写事务把 action 置 `sent`；若现有结构无法同事务扩展，先停下重提，禁止先 sent 后补 action。

网络调用、模型延迟和手执行期间不持 SQLite 事务或 actor 长锁。

### 8.3 失败与恢复映射

| 失败点 | M5 处置 |
|---|---|
| 意向 provider 失败/非法 | 分类一次落 `neutral + llmFailureFallback`；不重判 |
| 回复 provider 失败/非法 | 不构造 action/effect intent；按批准的 AI 次数预算后续巡检再试，耗尽转人工 |
| 建议后新增候选人消息 | 旧 action `superseded/manualRequired`；M5-A 冻结档案 |
| 建议后真人先回复 | 同上；真人消息成为新出站锚 |
| effect intent 构造前脑重启 | 取回同一 turn/action/text，不重新分类或生成 |
| contract mismatch | WAL 前零 effectful；既有审计；action 保持可见但不旁路发送 |
| receipt rejection / failed none | 原意图终局，action `manualRequired`；自动调度不另铸 |
| report unknown、同 store | 只允许既有轨道重投原 msgId |
| possible/confirmed/超时/阴性验证 | 验证/suspect；不第二次发送 |
| 唯一正证 | 同一事务 action=sent + 唯一 self Message |

## 九、安全、隐私与自动化范围

1. 自动入口只对一个显式试运行 profile 生效，成功或任何人工态后自行退出；其他档案仍只巡检对账。
2. 每 profile 同时最多一个未终局 CommunicationAction；每账号仍受既有 effectful/intrusive 串行域约束。
3. AI 无权绕过已有 expectedTail。建议生成时的历史尾和派发前的活动尾必须一致；最终动作前仍由手的同一 evaluator 条件写。
4. 当前范围不新增动作前平台守卫；M3 `chat.sendMessage` 发送栈原样复用。若发现新守卫需求，仍须过 AGENTS.md 三问与信任边界。
5. provider base_url/key 只在 Go client；插件、contract、evidence、journal/outbox 与 Chrome 页面均不出现。
6. 管理 UI 可显示建议文本给现场人员观察，但普通状态 API 不返回候选人原始引用；开发诊断导出默认只含 hash/计数。
7. AI provider 必然接收聊天正文和职位内容；这属于甲方批准后的明确数据出站。平台 ID、displayName 不发送；自由文本自含姓名/电话的残余风险在验收报告如实记录。
8. 不记录模型推理内容；只消费最终结构化字段。provider 返回额外 reasoning/trace 时丢弃，不落库、不上报。

## 十三、真实 Chrome 最小验收

### 13.1 前置条件

- 甲方已批准 provider/model/预算，客户端本地 key 配置完成；
- 真实 job-config 事实门通过，目标职位 context 已本地导入并由真人显式绑定；
- 选择一个 M4 正式 profile/conversation，存在尚未由我方回应的一轮普通候选人文本；若没有合格样本，等待或由甲方另行指定，不主动多发消息制造样本；
- 目标轮不是拒绝、换微信、卡片、媒体或服务态；
- 真人确认平台 composer 空、无验证码/风控，账号身份 current；
- `contractMatch=true`、`witnessReady=true`、outbox/journal/suspect 均无阻断；
- M5 试运行只选该 profile，自动成功上限为 1；
- 浏览器控制不直接点击发送，真实动作只经脑→手正式通道。

### 13.2 验收动作

1. 记录脱敏前置计数：profile 状态、turn/action/invocation/effect intent/self Message 数；
2. 真人当天开启巡检并启用该 profile 的一次性 M5 试运行；
3. 巡检自动对账、分类、生成建议、确定性批准并派发，不逐条人工确认；
4. 页面观察到同一会话唯一自然回复，正式 `chat.sendMessage` 取得唯一服务端正证；
5. 试运行自动退出，不处理第二档案或第二轮；
6. 再跑一次巡检，确认无重复分类、调用、意图和发送；
7. 重启脑、等待手重连，再跑对账，确认页面与账本零增生；
8. 检查 provider 用量与本地 AIInvocation 元数据一致，日志/报告无正文和身份。

### 13.3 通过判据

- profile 从 greeted 进入 communicating 恰一次；
- DialogueTurn、CommunicationAction、成功 EffectIntent、`origin=self` Message 各恰一份；
- 候选人可见回复恰一条；
- AI 只产生建议，状态/意图/发送均能追到确定性代码决策；
- 复跑与重启没有第二次 provider 调用（已有合法建议时）、第二 intent 或第二消息；
- 真实 SX 任一歧义只少发/转人工；
- 试运行范围没有扩散；
- 隐私扫描与全量门禁绿色。

| 中间消息 retracted ABA 极窄窗 | 真实错投/投影证据或无人值守前 | 沿 M4 后置 |
| 自动搜索/采集/打分/选人/招呼调度 | 漏斗前段里程碑 | 不做 |
| 其他平台 | 用户取得真实账号 | 完全不做 |
| 无人值守与多档案扩量 | 足量真实 cohort、人工率和守卫假阳性数据 | M5 只有单 profile 一次性试运行 |
| program 交付、append-only 冻结、草稿保护 | 第一次给真实客户安装插件前 | 沿既有截止点重新裁决 |
| 正式 migration、Windows 真机、安装包、更新链 | 客户交付里程碑 | 仅保持交叉构建常绿 |

## 十五、停止条件与待甲方裁决项

### 15.1 停止条件

同时满足以下条件即完成 M5：

1. 批次 0 真实配置事实门通过；
2. 规范按批准文本先行落地，machine contract 保持零改动；
3. 自有 AI context 可由真实旧整包无损填充，profile 显式绑定；
4. DialogueTurn/Action/AIInvocation 与确定性 reducer 自动化矩阵通过；
5. 最窄自动 effectful 冒烟已绿并即时提交；
6. 一轮独立审查结束，当前可达阻断项为零；
7. 一次真实普通文本自动回复通过，复跑与重启零增生；
8. 全量门禁、token/成本记录和隐私扫描通过；
9. 《里程碑5-验收报告》独立提交。

达到后停止，不继续做拒绝、卡片、时刻表、第二模型或第二档案。

### 15.2 甲方本次需裁决

1. 是否批准 M5 只做“单 profile、单普通文本轮、一次自动 replyText”的最窄出口；
2. 是否批准第 3 节拟议规范文本，尤其：LLM 唯一云端出站、SX 构造点前后重试分界、新消息/真人回复使旧 action 转人工；
3. provider/model 方案：第 6.2 节 A/B/C 及具体模型；是否额外启用正交的 D 影子评测与对比模型；
