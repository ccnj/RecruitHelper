## 一、里程碑结论与边界

M5 不一次性吞下 `docs/沟通逻辑规格-v4.md` 的卡片、微信、运营通知和整套时刻表。当前缺少邀面卡、换微信卡及相应后置条件的稳定真机样本；拒绝流程、催 2、已邀面、跟催、卡片事件和服务态都依赖这些能力。把它们写进状态枚举并不能形成可验收的生产闭环，反而会制造一批没有生产者的状态和猜测性语义。

M5 只交付一个“简历补采 + 对话核心”最窄竖切：

`M4 已绑定 profile/conversation 的档案收到一轮普通候选人文本 → 既有巡检先完成消息对账 → 若该档案尚无简历快照则经新原语从当前 IM 会话补采一次并冻结来源快照 → 重新读取消息边界并冻结唯一 DialogueTurn、简历、历史和默认全选推荐时段 → 渲染现网原 prompt → 确定性短路或一次独立 AI 三分类只落一次 → rejected 转人工，interested/neutral 再作一次独立回复调用 → 回复模型返回旧格式话术序列 → 脑丢弃模型动作建议并把多段话术合并为一条文本 → 确定性代码核对状态、输入边界和动作白名单 → 自动复用 chat.sendMessage@1 发送至多一次 → 唯一服务端正证 → 原子完成动作与消息事实`

候选人第一条真实文字一经正式账本观察，档案即由 `greeted` 进入 `communicating`，不以 AI 成功或回复成功为前提。AI 只回答“建议分类”和“建议文本”；它不能推进主状态、选择重试、扣预算、创建 effect intent、派发命令或把失败解释成成功。

M5 是首个自动 effectful 派发入口。自动的含义是：真人当天开启巡检并显式把一个档案加入 M5 试运行后，该档案的一个合格普通文本轮不再逐条弹出“确认发送”，由确定性脑代码自动构造一次 `chat.sendMessage` 业务意图。试运行范围固定为一个档案、最多一个自动发送成功；成功或进入任何 `manualRequired/suspect` 后自动退出试运行，不扩大到账号下其他档案。

同一个显式试运行选择在批次 2A 先只启用简历预采：即使候选人尚未回复，巡检也可对这个已有 adopted 会话、无快照的唯一 profile 补采一次；它不推进 `communicating`、不调用 AI、不发送消息。后续收到普通文本时直接冻结该快照；若尚未预采成功，回复链在任何 AI 前执行同一补采闸。不存在第二套测试入口。

首轮事实门已经证明旧后台 10 类文档集合可以无损收编，但现网 `多轮沟通` 需要本地尚不存在的简历。甲方最终裁决为：旧后台零改动、不新增 `doc_type`、不建本地 sidecar；继续原文使用 `多轮沟通 → 回复生成`、`意向判断 → 意向分类`、`客户事实库 → 事实上下文`。M5 因此吸收“IM 会话内补采简历”的最小采集竖切；它只服务当前已绑定档案，也为未来“候选人主动打招呼后补采简历”提供前置能力，不在本里程碑开启后者。

意向层另吸收旧生产的三类确定性短路候选：投递简历直接有意向、拒绝模板正则、不超过 25 字的短拒词表。它们不因旧代码存在就自动变成新系统事实；批次 0B 必须在当前真实页面与现网消息语义上逐条核对，只启用被证实的条目，无样本或存疑的保持禁用。

本里程碑不做：

- 漏斗前段的自动搜索、搜索页/简历库批量采集、AI 打分、选人、招呼调度、配额或平台风控节律；
- 拒绝分支自动挽留、换微信邀请、催 2、收号和运营通知；
- 邀面卡、换微信卡、跟催组、接受/拒绝卡事件和服务态；
- 冷催、36 小时归档、7 天兜底或跨日集中任务；
- 图片、语音、文件的自动理解；这些消息仍按“真实文字”推进 `communicating`，但转人工，不自动回复；
- 搜索页/简历库批量采集、独立简历详情页爬取、持续刷新简历或职位管理；
- 招呼前候选人主动来信的自动回复；本轮只交付其可复用的 IM 会话内补采简历前置能力；
- 自动匹配平台职位标题与后台职位名；职位配置必须由真人显式绑定，禁止字符串猜测；
- 除 `candidate.readResume@1` 外的新增脑手原语、新消息 kind、AI 专用命令通道或手侧 AI/调度逻辑；
- 运行时接入旧后台授权、bind/heartbeat/job-config；M5 只证明自有类型可由旧整包无损填充，并以本地配置运行；
- 第二平台、第二账号、无人值守转正、客户交付、远程 program、更新器或正式 schema migration 框架。

## 二、出口宣言（批准后冻结）

### 1. 本轮最小可交付出口

一个 M4 正式 `greeted + adopted` 且显式绑定职位 AI 上下文的档案，在既有巡检读到一轮普通候选人文本后：

1. 脑在消息对账确认该 profile 有待处理普通候选人文本、且没有成功简历快照时，只创建一次持久补采事实，并经正式 `candidate.readResume@1` 从当前已绑定 IM 会话读取同一候选人的五段式简历；重复巡检不增生第二次补采，失败转人工；
2. 成功结果以来源、采集时刻、内容 hash 和结构化正文形成不可变 `CandidateResumeSnapshot`；身份仍锚 M4 `platformUserRef`，`resumeNumber` 不作身份、不作 profile 关联键；
3. 补采结束后脑重新读取活动消息边界，再创建唯一 `DialogueTurn`，冻结该简历快照、历史边界和推荐时段文本；重复巡检和相同消息重放不增生第二轮；
4. `多轮沟通`、`意向判断`、`客户事实库` 原文进入各自既定用途；`多轮沟通` 只支持 `{简历}{推荐时段}{对话历史}`，`意向判断` 只支持已证实仍在生产使用的 `{回复}{招呼语}`，各文档识别到自身白名单外模板占位符即响亮失败；意向请求仍按沟通规格携带本轮全部消息与轮前最近 20 条活动历史，但通过固定数据信封而非新模板 token 表达；
5. 批次 0B 逐条证实后启用的确定性短路优先；未短路才用原 `意向判断` 做一次独立三分类调用。两条路径都只得到一个持久结果；意向调用失败按 v4 固定落 `neutral + llmFailureFallback`，不反复改判；
6. `interested/neutral` 另做一次独立回复生成调用，不与意向判断合并；回复模型必须返回旧格式 `话术_序列` 数组，脑丢弃 `动作`，把非空话术按顺序用换行合并为一条候选文本建议，不实现多气泡；
7. AI 建议只作为事实持久化，确定性代码独立决定该轮是否允许 `replyText`；AI 对推荐时段的文字约定不代表卡片已发，当前由真人跟进；
8. 自动入口只从 `CommunicationAction` 的稳定主键确定性派生一个 `EffectIntent`，复用既有 head/CAS、WAL、mismatch 双闸、witness、`chat.sendMessage@1`、验证读与 suspect；
9. 只有唯一服务端发送正证才能把 action 记为 `sent`，并由既有成功事务追加唯一 `origin=self` 消息；
10. 脑重启、手重连、重复 patrol、AI 回包重放和 result/outbox 重放后，补采、快照、turn、action、effect intent 和候选人可见消息都不增生；
11. 一次有人值守的真实简历补采与普通文本自动回复通过后，试运行自行停止，并形成《里程碑5-验收报告》。

最窄生产竖切自动冒烟一绿立即提交，不等待完整故障矩阵、独立审查或真实 Chrome 验收。

### 2. 必须立即阻断的损害

- 同一对话轮产生两条候选人可见回复，或重复巡检/重启另铸第二个自动意图；
- 回复错人、错职位、错会话，或以姓名、职位标题、列表位置等启发式绑定 AI 上下文；
- 从错误会话/候选人采集简历，或把 `resumeNumber`、姓名、职位标题、DOM 位置当作候选人身份；
- 简历面板只覆盖部分字段、内容超限或目标绑定无法确认时仍伪造完整快照并调用 AI；
- prompt 出现未批准模板占位符仍静默留空、猜值或发送；
- AI 直接推进状态、扣预算、创建命令、选择重试或输出未在白名单内的业务动作；
- 执行模型返回的 `动作`，或把一个 `话术_序列` 自动拆成多次 `chat.sendMessage`；
- 未真正发出的消息滑动时钟、记为固定话术已用、消耗打扰预算或把 action 记成 `sent`；
- 新候选人消息或真人出站消息已经改变消息尾，旧建议仍越过条件写发送；
- 覆盖真人草稿、绕过 `chat.sendMessage` evaluator、WAL、witness、验证读或 suspect；
- `contractMatch=false`、账号身份/hand/cap/witness 不就绪、账号域已有 suspect 时仍构造或写出 effectful；
- 把真实 SX 的 `failed/sideEffect=none`、receipt rejection 或阴性验证当成自动另铸新意图的授权；
- API key、候选人明文身份、聊天正文、简历正文或完整 prompt 出现在普通日志、审计 detail、管理 API 返回、验收报告或未来云端上报；
- 物理删除补采、简历快照、turn、action、AI 调用、配置修订或状态事实。

以上均为阻断级，真实测试立即停止。M3/M4 已冻结的安全内核不因“自动回复”而放宽。

### 3. 允许重试或人工兜底的失败

以下失败允许少发、延后或转人工，不为追求自动恢复扩大机制：

- job-config 真实响应与预期不符、配置缺文档、未知 placeholder、职位上下文未显式绑定；
- IM 简历入口不存在/不唯一、必须切换到未绑定目标、字段覆盖不足、身份回读不一致、页面变化、payload 超限或读取失败；
- LLM 本地配置缺失、provider 超时/限流/余额不足、返回非法 JSON、空文本或输出越界；
- 按冻结格式组装后的历史、简历与 prompt 超过本轮批准的 token 上限；
- 当前轮含图片、语音、文件、卡片、主动换微信、拒绝或其他 M5 未激活场景；
- 对账读不清、目标换绑、消息尾变化、真人先回复、草稿存在、控件不唯一、平台风控或验证码；
- 自动入口构造 effect intent 之前失败：保留已有事实；intent 失败只落一次 `neutral + llmFailureFallback`，之后仍执行一次独立 reply 调用；reply 失败在 P 档直接转人工，不重试、不产生第三次 provider 调用；
- effect intent 一旦构造：严格服从协议安全内核。`failed/none` 与 receipt rejection 把 action 置 `manualRequired`；possible/confirmed/超时进入既有验证与 suspect；调度器不自动另铸新意图。

人在场可重新绑定配置、人工查看/录入简历、清理页面、人工回复、跟进模型提到的面试时段或裁决 suspect。M5 不以“简历补采率/自动回复率 100%”为出口。

### 4. 独立审查预算与明确后置

冒烟 commit 后最多一轮独立审查。阻断项修复后只复核对应 diff，不重开全量审查；优化级发现必须同时证明常见、边际价值明确且修复成本低，否则登记后停止。

以下已清偿项不重做：派发层 contract mismatch 双闸、出站消息 `retracted` 显式事实、M3 witness/验证/suspect 轨道、M4 Candidate/Profile/Conversation 绑定。

多气泡、卡片、微信、拒绝自动流程、可配置时刻表、媒体、运营通知、旧后台运行时接入、第二平台和无人值守全部后置，见第十四节。达到一个档案一次补采、一次自动回复的出口后必须停止，不顺手开始 M5-B 或 M6。

## 三、AGENTS.md 第 12 条规范修改立案

本节只请求修改授权，不把拟议文本当作既有依据。批准后仍先完成批次 0B 重开事实门；事实推翻拟议语义时停止并重新立案，不得让实现反向塑造规范。

### 3.1 现有约束

1. `AGENTS.md` 当前写明本仓库“现阶段完全不连云端”，授权/旧后台接入后置；真实 LLM provider 是新的出站信任边界。
2. `docs/沟通逻辑规格-v4.md` 已规定 AI 是建议者、状态由确定性代码裁决；一轮只判一次，动作失败时重放未完成动作、不重判。
3. 同一规格又笼统写“招呼后的生成或发送失败，下轮巡检自然重试”；协议规格则明确真实 SX 的 `failed/none` 与 receipt rejection 终局化原意图，只能由人决定是否另铸。两者在自动入口到来前尚未冲突，M5 必须消解。
4. 对话轮定义了“判后新来的消息属于下一轮”，但没有裁定旧轮建议尚未派发时遇到新消息或真人先回复如何处理。
5. 协议规格已经允许“测试页、调度器、运营工具都是脑内命令生产者”，`chat.sendMessage@1` 与全部安全轨道不依赖生产者是人还是自动状态机。
6. 当前 contract 不包含 AI、职位配置、对话轮或业务状态，这些仍是脑内领域语义；但也没有任何原语能从已绑定 IM 会话读取候选人简历，M4 `candidate.readCurrent@1` 只读取真人当前已打开候选人的身份/职位/关系三态。
7. M5 原计划承诺 machine contract 零改动；首轮事实门已证明现网原 prompt 强依赖 `{简历}`，甲方随后裁决由 M5 吸收最小 IM 补采能力，因此该承诺已经作废，新增原语必须按本节获批后规格先行。

### 3.2 当前可达场景与修改必要性

M5 的正常链路会出现：

```text
巡检对账到候选人文本
→ 分类与回复建议落库
→ 自动状态机创建 chat.sendMessage effect intent
→ 手在动作前明确 failed/sideEffect=none，或 receipt rejected
→ 下一轮巡检再次看见同一个未完成业务动作
```

如果照沟通规格的笼统“自然重试”另铸意图，就绕过协议安全内核；如果把所有 AI 阶段失败也当真实 SX 终局，又会无谓放弃无候选人副作用的可恢复计算。必须在规范中以“effect intent 是否已经构造”为分界。

另一个可达场景是：建议已冻结但尚未构造 effect intent，候选人又发一条消息或真人先行回复。继续发送旧建议可能答非所问、与真人抢话；自动合并并重新生成又会扩大本轮机制。M5 最窄裁决应是：旧 action 显式 `superseded/manualRequired`，该档案停止自动化，不自动重写或补发。

首轮事实门还证明了第三条当前可达链：

```text
巡检对账到已绑定 profile 的候选人普通文本
→ profile 没有简历快照
→ 现网多轮沟通原 prompt 要求 {简历}
→ 脑若填空串/旧标题/姓名等替代值，会把不存在的事实送给 provider
→ 脑若自行切换候选人或按 resumeNumber 寻址，又会制造错靶身份链
```

旧后台零改动、不新增文档槽位且不建本地 sidecar 后，唯一能完整闭合这条链的最窄能力是：脑只对已正式绑定的 IM 会话下发一次平台中立简历读取意图，手在同一候选人绑定下返回结构化快照；读不全、读错或读不到即转人工。该读取是否只读页面，还是会打开详情面板并可能产生 read-receipt/页面侵入，必须由重开的批次 0B 真机事实决定 class，不能在计划阶段猜。

### 3.3 请求授权的规范变化

本批请求授权：

- 将“完全不连云端”收窄为“不连接旧业务后台；只允许 Go client 按本地显式配置直连一个 LLM provider”；
- 明确 provider 请求与本地业务数据、普通日志/未来上报之间的隐私边界；
- 明确 AI 只产出结构化建议，确定性 reducer 是状态与动作唯一裁决者；
- 按 effect intent 构造点分开 AI 计算重试与真实 SX 恢复；
- 明确旧轮建议遇到新入站或真人出站时不得自动继续发送；
- 明确 M5 只激活普通非拒绝文本回复，未激活分支转人工；

### 3.7 机器契约增量立案

原“machine contract 零改动”裁决作废。M5 修改 `contract/contract.v1.json`，但范围只到 `candidate.readResume@1`：

- 原语名固定，沿用现有 X batch，不新增 feature、hello 字段、消息 kind、witness/evidence 版本或 effectful 语义；
- args 固定以既有平台中立不透明 `conversationRef + platformUserRef` 锁定目标；不发送脑内 `profileId`，不出现 resumeNumber、URL、tab/window、selector 或平台对象；
- data 用平台中立的五分区结构表达。批次 0B 按 IM 面板事实冻结每个分区的子字段与空值、数组、字符及总 payload 上限；当前候选实现是 `basic/expectations` 的 label-value 集合与三个文本分区，不把旧 DOM 形态永久写入契约；
- class 由批次 0B 在 `readonly` 或 `intrusive` 两条已批准分支中选定，机器契约中不得保留“待定”；两类都不设 effectful evidence；
- AI provider、`DialogueTurn`、`CommunicationAction`、职位配置、简历快照表和模型用量仍是脑内领域语义，不进入脑手 contract；
- 真实回复继续原样复用 `chat.sendMessage@1` 与 `chat.readThread@1` 的既有安全轨道。

批次 0B 只能在下表两条预授权 metadata 分支中选一条，不能自创第三种：

| metadata | 已渲染只读分支 | 打开面板分支 |
|---|---|---|
| class | `readonly` | `intrusive` |
| preconditions | `context.platform/accountRef/expectedPrincipalFingerprint`、`surface.im`、`login.in`、`conversation.tracked` | 左列全部 + `manualQuiet` |
| execBudget / deadline | `10s / 30s` | `60s / 120s` |
| lease | 无 | `30s` |
| platformSideEffect | 不声明 | 由真机写死 `none` 或 `idempotentReadReceipt` |
| idemKey / guards / evidence / verification | 全部无 | 全部无 |
| 物理重派 | 沿 readonly 既有封顶；仍只对应一个 profile logical capture | 沿 intrusive 既有封顶并占账号串行域；仍只对应一个 profile logical capture |

失败只复用既有通用错误：坏参数/超帧用 `PROTO_BAD_ARGS/PROTO_MSG_TOO_LARGE`；页面/登录/身份未就绪用 `CTX_NOT_READY`；执行中页面或已绑定目标丢失/换绑用 `CTX_LOST_DURING_EXEC`；当前登录主体与 `expectedPrincipalFingerprint` 不符才用 `ACCOUNT_MISMATCH`；命令受理时指定的候选人/会话绑定已确定不存在用现有非 `chat.*` 目标码 `TARGET_NOT_FOUND`，`CONVERSATION_NOT_FOUND` 仍只供 `chat.*`；入口/五分区结构不唯一或无法解析用 `ELEMENT_UNRESOLVED`；完整合法 data 超限用 `PAYLOAD_LIMIT`；超时/内部异常沿 `EXEC_TIMEOUT_HAND/INTERNAL_HAND`。候选人/peer 不符不得污染 `ACCOUNT_MISMATCH` 的账号主体语义；不为页面细节新增错误枚举，也不允许任何失败返回部分 resume data。

规范先行 commit 必须同时修改协议文本、机器契约和 Go/TS codegen 产物并通过 `go run ./contract/codegen -check`。capability 只有在 program handler 与脑侧消费者同批闭合后才可上报。contractHash 改变后，按 §14 硬切换：暂停派发、重启脑、重载插件、确认 hash/caps 一致后恢复；mismatch 期间既有双闸继续禁止 effectful。

若实现证明必须让手理解 AI、职位配置、业务轮状态或自动选择候选人，视为架构方向错误，停止重提，不得继续扩 contract 迁就实现。

### 3.8 收益、成本与替代方案

收益：形成第一条“真实简历事实 → 脑自动建议 → 复用既有安全轨道”的业务闭环；AI 输出与状态裁决物理分层；一次补采、一轮一次分类、动作一次意图和成功一次消息均由数据库唯一约束证明；同一简历能力是未来候选人主动来信支持的前置，但不提前开启该行为。

成本：新增一个永久脑手原语及 contractHash 硬切换、插件 IM 页面读取、简历快照高敏事实、巡检补采接线、LLM 出站信任边界、本地 secret 配置、沟通事实表和职位上下文修订；冻结历史窗口与简历会增加 token/64KB 上限压力；一个档案的试运行范围降低了短期自动覆盖率。

否决的替代方案：

- 让 AI 返回“更新状态+执行动作”的自由 JSON：违反 AI 建议者红线；
- 在插件里直连 LLM：泄露 key，破坏脑主动和手无业务状态；
- 复用旧客户端大段 chat_reply 状态机：旧实现和 v4 目标不一致，且职位、固定话术与恢复链耦合严重；
- 把 job-config 原响应直接当领域类型：把旧后台 camelCase、DeepSeek 配置继承和历史化石永久带入新项目；
- 把职位标题自动匹配到后台职位名：可能给正确候选人使用错误职位事实，属于错靶；
- 给 `{简历}` 填空串、摘要猜值或删掉占位符：改变现网 prompt 输入事实；
- 新增旧后台 `doc_type` 或本地 sidecar prompt：甲方已裁决后台零改动且既有槽位原文照用；
- 按 resumeNumber、姓名或 IM 列表位置找简历：违反 M4 身份锚并制造错靶；
- 一并搭建批量简历采集/刷新框架：当前只需一个已绑定档案补采一次，跨层成本不成立；
- M5 先建通用工作流/事件溯源/多 provider 路由框架：当前只有两个 AI 用途和一个真实竖切，成本不成立；
- 自动 SX `failed/none` 后换 intent 再发：直接违反冻结安全内核；
- 等卡片和完整时刻表全部完成再做第一次自动回复：延迟最稀缺的真实反馈。

2. `固定语1/2/3` 没有三个可继承的稳定业务场景，不进入 M5 可执行视图。
3. 现网 `多轮沟通` 原文需要简历、推荐时段和对话历史；本地消息账本已有历史，但首轮没有简历和推荐时段实现。
4. 现网职位配置与 M4 profile 没有天然外键，仍必须真人显式绑定，禁止按标题猜测。
5. 旧后台运行时接入、旧 provider 字段继承、新 `doc_type` 与本地 sidecar 均不在最终方案内。

首轮“事实门未通过”的历史结论保持不改。本次是甲方改变范围、批准 M5 吸收简历补采后的新事实门，产物另建 `批次0B`，不改写旧报告来伪装第一次已经通过。

### 4.2 旧代码提供的候选口径（不是平台事实）

旧五仓只进入候选方案池。本批已找到以下可供真机/fixture 核对的生产实现：

- 历史：最近最多 20 条按时间正序；空正文跳过；每行 `候选人(消息):正文`、`我(消息):正文` 或 `我(招呼语):正文`，行间换行；入站单条最多 1000 字、出站最多 300 字，超长追加固定截断提示。
- 默认推荐时段：不是 7×24，而是周一至周五 `[09:00,18:00)` 窗口内整点默认全选；取未来 14 天，当天排除已过去整点，结束时刻不包含。旧 renderer 不只是把 token 换成概览：无 `【可约面时间】` 块时把全部 token 换成短指针并在文末追加一次“当前时间 + 约束提示 + 中文压缩概览”数据块；已有块时只在块内首个 token 注入，其余换短指针。单日概览形如 `M月D日(周X) 09:00-17:00 的整点`。
- 回复：旧生成结果以 `话术_序列` 数组为主；旧账本曾用换行合并，旧页面另有多气泡路径。M5 明确只保留前者，一次数组只产生一条 `chat.sendMessage`。
- 动作：旧实现曾在确定性动作为空时回退 AI `动作`；M5 明确不继承该行为，字段无条件丢弃。
- 沟通简历：顶层口径为 `基本`、`期望`、`自评`、`教育经历`、`工作经历`；其中基本/期望为键值集合，后三项为文本。旧 IM 右侧已有“打开详情面板”的动作零件和已删除的历史采集实现，但没有当前端到端生产事实。
- 意向：现生产代码仍会把本轮最后一条入站正文替换到 `{回复}`、把最后一条已发招呼替换到 `{招呼语}`，并把旧中文 `有意向/拒绝/中性` 映射为内部分类。故“三项占位符”只能指 `多轮沟通`，不能全局覆盖 `意向判断`。
- 意向短路候选清单（仅是旧生产代码考古，尚未获得新系统启用资格）：
  - 简历投递 marker：`发送了在线简历`、`附件简历`、`简历请查收`、`简历,请查收`、`简历已发送`、`已发送简历`、`投递简历`、`已投递简历`、`简历发您`、`简历发你`、`发您简历`、`发你简历`，及同时包含 `简历` + `查收` 的兜底；命中后候选分类为 `interested`。
  - 拒绝模板候选正则：`(很抱歉|抱歉)[，,]?\s*我(暂时)?\s*(不|觉得这个).{0,20}(考虑|不匹配|不感兴趣|不合适)`；命中后候选分类为 `rejected`。
  - 短拒词候选表：`不考虑`、`不感兴趣`、`不需要`、`不合适`、`勿扰`、`别发`、`不找工作`、`已入职`、`已经入职`、`找到工作了`、`不找了`；只在去空白后正文长度≤25 且不含 `?/？` 时候选命中 `rejected`。

这些格式可以被新项目有判断地采用，但 IM 入口、字段覆盖、目标绑定、页面副作用与真实 prompt token 仍以本批真机证据为准。

### 4.3 批准后的真机与脱敏核对

1. 在真人显式选择、已由 M4 绑定的单个 IM 会话上，只读核对右侧简历入口与详情面板；不发送消息、不切换候选人、不搜索、不滚动候选人列表。
2. 证明面板在整个打开/展开/关闭链中始终绑定命令指定的 `conversationRef + platformUserRef`；只允许沿用已被当前页面事实证实的身份源，禁止姓名、职位标题、resumeNumber、DOM 位置或列表首项兜底。
3. 逐区核对 `基本/期望/自评/教育经历/工作经历` 是否可完整读取，并区分“页面明确为空”与“解析不到”。特别核对期望职位、最近投递与我方沟通职位没有被旧 parser 混为一项。
4. 观察是否必须点击/展开、是否改变路由、是否产生读回执或其他候选人可感知事实，据此把原语 class 冻结为 `readonly` 或 `intrusive`，并冻结 intrusive 的 `platformSideEffect`、lease 与 `manualQuiet`。
5. 在内存中测量五分区 canonical JSON 的 UTF-8 大小；事实记录只保存分区覆盖、空值状态、条目数与分桶大小，不保存正文、原始身份、截图、无盐正文 hash 或可反推摘要。
6. 对同一生产配置只在内存重读 `多轮沟通/意向判断` 原文，结合旧生产替换调用核对“活模板 token”而不是用任意花括号正则：前者恰只替换 `{简历}{推荐时段}{对话历史}`，后者恰只替换 `{回复}{招呼语}`；同时只记录 prompt 声明的输出 key 集，明确 `{话术_序列}` 若属于输出示例就不是输入 token。若事实不同，停止重提，不扩白名单猜测。
7. 用完全 synthetic 消息 fixture 固化历史文本口径；只消费正式活动消息，排除 retracted，最后 20 条按时间正序，截断规则与 speaker/label 字面固定。
8. 用冻结时钟 fixture 固化完整旧时段 renderer：周一至周五 09:00–18:00 窗口内整点全选、未来 14 天、当天排除过去时刻；分别覆盖 prompt 无/有 `【可约面时间】` 块、一个/多个 token、短指针、当前时间/约束提示和中文压缩概览的字面 golden。生成结果在 turn 创建时冻结，重启/重试不随当前时间漂移。
9. 用 synthetic 文档固化 provider 消息组装：原 prompt 只作上述冻结 renderer，`CustomerFacts` 原文只在末尾以一份固定不可配置分隔块追加；意向请求另以不含行为指令的固定数据信封携带本轮全部消息与轮前最近 20 条历史，并冻结字段、角色、顺序与去重口径。除这两块之外不追加本地提示词。若甲方不批准事实库组装提议，删除事实库输入而不是暗建 sidecar。
10. 用 synthetic 模型回包固化输出：`话术_序列` 是必有非空字符串数组；`动作` 及批次 0B 从生产 prompt 证实的纯元数据 key（例如若真实存在的 `策略`）只允许忽略，不进入业务。数组逐项 trim、丢空，以 `\n` 合并为一条；白名单外顶层字段、非法类型或合并后越过 `chat.sendMessage` 上限均响亮失败。不继承旧 `reply/content/text/话术` 宽松回退。
11. 对上述每个简历 marker、拒绝正则各分支与每个短拒词做现网真机语义核对：只读已有消息，不为造样本发送任何内容；事实记录只保存规则 ID、命中/未见/反例状态和计数，不保存原消息或可反推摘要。只有当前真机命中含义与目标分类一致的条目进入“已启用”清单；未见样本、有反例或含义不稳定的条目保持禁用，不阻塞其他已证实条目。
12. 用 synthetic 意向 fixture 固化“已启用”短路清单的空白压缩、长度、问号、优先级与中文到内部 `interested/rejected/neutral` 映射；分类输入的招呼只能来自唯一已发送的 M4 消息事实，不能用草稿、失败招呼或展示字段。
13. 意向 provider 只按已裁决的“本轮全部消息 + 轮前最近 20 条”入参固化 fixture；不对最后一条/无历史/其他窗口另发 provider 请求，不做入参 A/B 或影子对照实验。
14. 在尚未新增绑定表/UI 的前提下，真人只确认一个未来拟绑定的 `profile × context revision` 对，事实记录仅写“可明确选择/不可明确选择”与脱敏随机标签；正式持久绑定在批次 2B 实现后完成，界面不得按标题预选。

产物为 `docs/里程碑5-批次0B-IM简历与模板事实记录.md`、不含真实正文/身份的页面形状 fixture 与格式 fixture，独立 docs commit。

### 4.4 重开事实门出口与停止条件

通过必须同时满足：

- IM 五分区能在同一稳定候选人绑定下完整表达，明确空值与读失败可区分；
- 原语 class、动作表面、账号串行/lease 需求已经由真机事实写死，不存在非幂等候选人可见副作用；
- 合法真实样本低于现有 64KB inline hard limit；
- 两份现网 prompt 各自只出现获批白名单 token，三个 renderer 与意向数据信封 fixture 完全确定性；
- 三类意向短路的每个候选条目都得到“已启用/未见样本/有反例禁用/账本不可表达”之一的显式结论；已启用条目的匹配对象、归一化、长度、问号、跨消息扫描和优先级均已冻结；
- 一份无身份的合成五分区快照可无损通过拟议 contract DTO；
- 真人能明确指出一个未来拟绑定的 profile/context 对，不依赖标题猜测；本批不伪称已经持久绑定。

任一以下情况立即停止并再次重提，不修改规范或实现：

- 详情不能稳定绑定 `conversationRef + platformUserRef`，或只能靠 resumeNumber/姓名/DOM 位置猜；
- 必须产生非幂等、候选人可见副作用才能读取；
- 任一分区无法区分明确为空与读取失败，期望字段语义仍混淆，或只能截断/伪造才能形成快照；
- 真实合法 payload 超过 64KB；此时按既有到期条款另立 `blob/1`，不得偷塞新分页机制；
- 生产 prompt 出现白名单外活 token，或旧格式输出/历史/时段无法确定性复刻；
- 甲方要求某项短路必须在 M5-A 启用，但对应的简历投递或拒绝事实只存在于当前账本无法稳定表达的卡片/系统事件；此时停下重提感知/契约立案，不得在脑侧改为解析 DOM 文案或暗中新增消息 kind。未被要求强制启用的无样本/不可表达条目按上文保持禁用，不阻断其他已证实条目；
- 真机核对会把简历正文、身份、prompt 正文、secret 或可反推摘要写入仓库。

事实门通过只授权进入批次 1；不会自行扩成搜索/批量采集、旧后台修改或通用简历框架。

## 五、AI 上下文、provider 与兼容设计

### 5.1 本仓库自有职位 AI 上下文

领域类型由“无损来源包”和“可执行语义视图”两层组成，不把旧响应 DTO 直接当领域模型，也不因 M5 暂时不用某类文档而丢掉它：

```go
type JobAIContextRevision struct {
    ContextID       string
    RevisionHash    string
    SourceKind      string // localImport；未来才可能是 legacyJobConfig
    SourceJobRef    string // 可选，只作来源审计，不参与 profile 身份
    DisplayName     string
    Environment     string
    SourcePackage   JobConfigDocumentPackage
    Communication   CommunicationView
    CreatedAt       time.Time
}

type JobConfigDocumentPackage struct {
    Documents []JobConfigDocument // 按 doc_type 排序后的完整原包；未知/未使用类型也保留
}

type JobConfigDocument struct {
    DocType string
    Content string
}

type CommunicationView struct {
    ReplyPrompt    string // 多轮沟通原文
    IntentPrompt   string // 意向判断原文
    CustomerFacts string // 客户事实库原文
    MappingVersion string // 批次 0B 冻结的显式映射，不靠名字猜测
}
```

`RevisionHash` 由完整 `SourcePackage` 和稳定元数据的 canonical JSON 计算。同一 `doc_type` 重复、空缺口径不明或结构化区与原始 `documents` 冲突时 fail-closed。`CommunicationView` 只按甲方冻结映射读取三份原文；`沉默追问/固定话术/固定规则` 以及打分、招呼等未激活文档仍完整留在来源包，但不进入 M5-A 可执行视图。配置更新产生新 revision，不原位改写历史轮使用的 revision。

M5 运行时不连接旧后台。批次 2 只实现纯映射函数、脱敏 fixture 与本地导入；真实试运行使用本地导入的一份 context revision。未来接旧后台时，只新增 adapter，不改状态机、AI 输入或 action 表。

### 5.2 兼容判据

“能被旧后台 job-config(s) 整包无损填充”具体定义为：

1. 单数整包或复数 `jobs[i]` 对应活动版本的 `job_version_docs` 文档集合，必须按 `doc_type + UTF-8 content` 一一进入 `SourcePackage`；导入前后类型集合、空值口径与逐项字节 hash 相等，M5 不消费的打分、招呼或未知加法类型也不得丢失；
2. `job.id/name/environment` 能进入来源元数据，但不成为平台候选人或职位身份；
3. `CommunicationView` 只能由批次 0B 冻结的显式映射从 `SourcePackage` 派生：`多轮沟通→ReplyPrompt`、`意向判断→IntentPrompt`、`客户事实库→CustomerFacts`；其他文档不因未使用而丢失，也不得覆盖这三份原文；
4. 旧整包的 `apiKey/model/baseUrl` 是 provider 凭据而非 `job_version_docs` 业务文档，按甲方约束明确不继承；这三个字段的舍弃必须由 adapter 测试显式断言，provider 配置走本地独立类型；
5. `documents` 未返回时，只能从整包结构化区**可逆重建**同一来源包；两条来源同时存在时逐项类型/content hash 必须一致，不一致 fail-closed。若结构化区不足以还原全部文档，`includeDocuments=false` 的回包只能用于形状验证，不能创建 context revision；
6. 原始六占位时代的 `固定语1/2/3` 只在 `SourcePackage` 中无损保留，不进入本次已冻结 `MappingVersion`；未来若要消费必须另立案，拒绝猜测其业务话术。

### 5.3 profile 与职位上下文绑定

M4 的 `positionRef` 是平台不透明职位引用，旧后台 job id 是客户配置引用，二者没有天然等价关系。M5 增加真人显式绑定：

- 一个 profile 在试运行前选择一个 `ContextID`；
- 绑定记录保存 `profileId/contextId/revisionHash/boundAt/boundBy/status/reason`；
- 改绑以新显式事实表达，旧绑定标 `superseded`，不物理删除；
- 每个 DialogueTurn 冻结实际使用的 `revisionHash`；中途配置更新不改变已判轮；
- 禁止按 `PositionTitle == job.name` 自动绑定或兜底。

### 5.4 provider 接口与本地配置

脑内只定义一个窄 provider 接口：

```go
type LLMProvider interface {
    CompleteJSON(ctx context.Context, request CompletionRequest) (CompletionResponse, error)
}
```

`AIAdvisor` 在 provider 之上定义 `SuggestIntent` 与 `SuggestReply` 两个业务用途。provider 只负责 HTTP、认证、超时、JSON 响应抽取与用量；不理解 CandidateProfile、状态跃迁或发送动作。

首批只实现一个 OpenAI-compatible Chat Completions adapter；M5-A 生产配置已经冻结为 DeepSeek V4 Pro。意向与回复虽使用同一模型，但是两个独立业务用途和两次独立 HTTP 调用：分别建立 `purpose=intent|reply` 的 AIInvocation，禁止共用一个 prompt、request 或 response 合并完成。D 影子评测与 V4 Flash 整体后置到 M5-B 立项前，M5-A 不调用、不配置、不计费、不产出其评测证据。M5 不做多 provider 自动路由、熔断集群或 SDK 抽象；以后确需其他 API/本地模型时新增 adapter，不改业务层。

本地配置为：

```text
provider
model
base_url
api_key
request_timeout
max_input_tokens
max_intent_output_tokens
max_reply_output_tokens
```

生产调用固定显式发送 `thinking={"type":"disabled"}`，不允许本地配置把它改成思考模式。配置只保存在客户端 data 目录，不提交仓库、不经插件、不从旧 job-config 继承。管理 UI 对 key 只显示“已配置/未配置”，读取 API 不回传原值；日志只记录 provider/model，不记录 base_url、key 或请求认证信息。当前同机可信剖面不引入操作系统钥匙串或远程 secret 服务；首客前按交付威胁模型重新裁决本地 secret 存储。

同一物理 provider 调用不在 HTTP adapter 内自动重试，避免一次逻辑调用产生不可见的双计费。P 档每 turn 的 intent/reply 各最多一次：未短路时先独立调 intent；intent 失败仅落一次 `neutral + llmFailureFallback`，然后仍进入一次独立 reply 调用；reply 失败直接转人工且不重试。两个用途都不在后续巡检再次调用。批次 5 dry-run 必须核对两条独立 invocation 的 `usage.completion_tokens_details.reasoning_tokens` 均为 0；字段缺失或非零都停止，不自行切模型、改开关或放宽预算。

### 5.5 AI 输入与输出

provider 请求使用本仓库自有 `AIAdviceInput`，包含：

- 原样的 `IntentPrompt` 或 `ReplyPrompt` 与原样 `CustomerFacts`；本计划提议把事实库在渲染后的原 prompt 末尾以一个固定、不可配置分隔块追加，批次 0B 用 synthetic fixture 冻结字面组装。它不反写旧文档、不新增可编辑 prompt，也不是本地 sidecar；
- `IntentPrompt` 的 `{回复}` 为本轮最后一条正式候选人普通文本，`{招呼语}` 为唯一成功招呼消息正文；同一请求另携带本轮全部有序活动消息与本轮之前最近 20 条活动历史的固定数据信封；旧中文模型信号再映射为内部枚举；
- `ReplyPrompt` 的 `{简历}` 为 turn 冻结的五分区快照 JSON，`{推荐时段}` 由批次 0B 冻结的旧单份注入协议渲染（含短指针/数据块/默认全选时段概览），`{对话历史}` 为消息账本按批次 0B 口径渲染的最近 20 条；
- 不另加 profile 状态、动作白名单或本地“禁承诺”行为提示；除冻结的模板替换、`CustomerFacts` 分隔块和上述无指令数据信封外零附加文本。动作与状态安全由输出 parser 和确定性 reducer 保证。

请求不携带 platform/account/conversation/user/profile 原始引用、resumeNumber 或 displayName；但甲方已知情授权简历和自由文本本身可能自含身份。历史的“最近 20 条 + 单条固定上限”是本次兼容格式，不是按 token 临时静默裁剪；组装后若仍超过 P 档输入上限，整轮转人工。

AI 输出固定为：

```go
type IntentSuggestion struct {
    Label string // interested | rejected | neutral
}

type ReplySuggestion struct {
    Phrases []string // 旧回包字段：话术_序列
}
```

意向 adapter 只接受旧 JSON 的 `信号`（兼容已证实的 `signal`）并将 `有意向/拒绝/中性` 显式映射为内部枚举；可读 `理由/reason` 只供当前调用判错，不持久化模型推理。回复 adapter 只消费必有 `话术_序列:string[]`；`动作` 与批次 0B 从真实 prompt 冻结的纯元数据 key 解析后立即丢弃，白名单外字段、旧 `reply/content/text/话术` 回退和自由 action list 均不支持。数组逐项 trim、丢弃空项并以换行合并；结果必须非空且满足 `chat.sendMessage` 正文上限，否则不构造 action。

确定性代码先按批次 0B 冻结的启用清单和顺序执行“简历投递→`interested`、拒绝模板正则→`rejected`、≤25 字短拒词→`rejected`”，再处理既有空轮语义；未短路才调用一次独立意向模型。本轮全部消息 + 轮前最近 20 条的入参已裁决，M5-A 不另发其他入参版本、不做对照实验。分类结果持久后不重判。`rejected` 在 M5-A 只落 `codeShortCircuit|llm` 分类并转人工，不调回复模型、不创建 action；`interested/neutral` 才可进入一次独立回复建议调用。模型任何 `动作`、时段承诺或未知结构都不能推进状态、扣预算、创建 effect intent 或触发多次发送。

### 7.1 `JobAIContextRevision`

保存第五节自有类型。主键 `revisionHash`，`contextId + revisionHash` 唯一；完整 `job_version_docs` 来源包及派生沟通视图是本地业务配置，不进入日志。历史 revision 不删除、不原位改写。

### 7.2 `ProfileAIContextBinding`

保存真人把一个 profile 绑定到一个 context revision 的事实：

```text

contextId
revisionHash
status = active | superseded
reason
boundBy
boundAt
supersededAt
```

每个 profile 最多一个 active binding；替换以显式 `superseded` 表达。

### 7.3 `CandidateResumeSnapshot` 与 profile 补采闸

成功简历是不可变业务事实，不覆盖写进 Candidate/Profile：

```text
snapshotId
profileId
sourceKind = imConversation
sourceConversationRef
sourceLogicalDispatchId
observedAt / capturedAt
schemaVersion
contentHash
resumeJSON
createdAt
```

`sourceLogicalDispatchId` 唯一；result 重放只能收编同一快照，同一 logical dispatch 出现不同 content hash 必须冲突转人工。`contentHash` 只做本地一致性，不是身份或候选人唯一键。插入前事务必须核对 profile 当前的 platform/account/conversation/platformUserRef 绑定与原命令一致。快照不更新、不物理删除、不用 `gorm.DeletedAt`；未来重新采集只能追加新行。

`CandidateProfile` 增加最小补采闸：

```text
resumeCaptureState = unattempted | inFlight | captured | manualRequired
resumeCaptureLogicalDispatchId
activeResumeSnapshotId
resumeCaptureAttemptedAt
resumeCaptureFailureReason
```

巡检只有在“无 active snapshot 且 state=unattempted”时 CAS 生成一个稳定 logical dispatch；重复 patrol/重启取回同一事实。成功后绑定 snapshot；最终失败置 `manualRequired`，不会因为仍然“无简历”在下一轮另造补采。真人若要重试必须走未来显式入口，本里程碑不提供自动 reset。`resumeNumber` 不进入表、唯一键、索引、外键或绑定兜底。

既有 M4 profile 迁移时显式初始为 `unattempted`，不伪造补采历史；升级回归必须覆盖已有行。该闸可由批次 2A 的唯一试运行 profile 在尚无入站时预先触发，也可在首个合格入站到来后触发；两者共用同一状态、logical dispatch 与恢复规则，不是两套采集入口。

`resumeJSON` 使用批次 0B 冻结的五分区自有 DTO。正文可存在本地业务库和正式命令 result，但所有普通管理列表、日志、审计 detail 与报告必须只返回随机 ID、状态、分区覆盖和大小，不回传正文。

### 7.4 `DialogueTurn`

```text
turnId
profileId
conversationRef
inputDigest
historyThroughSeq
inboundFromSeq / inboundThroughSeq
contextRevisionHash
resumeSnapshotId
recommendedTimeText
renderFormatVersion
status = collected | classified | adviceReady | dispatching | completed | manualRequired | superseded
intentLabel

classifiedAt
createdAt / updatedAt
```

`profileId + inputDigest` 唯一。`inputDigest` 由 profile、上一条活动出站边界、当前轮有序活动消息 seq/kind/contentHash 和 historyThroughSeq 确定性计算，不使用 wall clock。重复平台观察、巡检和脑重启只能取回同一 turn。

`recommendedTimeText` 在 turn 创建时按冻结时钟生成并持久化；重启/延迟不得按新的“现在”重算。只有 profile 已有 active snapshot 才能创建自动沟通 turn，创建时冻结 snapshot ID；补采期间不预造半成品 turn。历史通过冻结 seq 与格式版本重建，不能绕过 retracted 过滤或换成实时消息尾。

### 7.5 `CommunicationAction`

```text
actionId
turnId
kind = replyText
text
contentHash
status = planned | effectPending | sent | manualRequired | superseded
effectIntentId
failureReason
plannedAt / effectStartedAt / sentAt / updatedAt
```

M5 每 turn 只允许一个 `replyText`，`turnId + kind` 唯一；`effectIntentId` nullable unique。`actionId` 是自动 `intentId` 的稳定派生源，不能按当前时间重造。建议正文必须持久化后才能构造 effect intent；重启复用同一 text/hash。

### 7.6 `AIInvocation`

每次真实 provider 调用追加一行：

```text
invocationId
turnId
purpose = intent | reply
attempt
provider / model
contextRevisionHash
inputHash / outputHash
inputTokens / cachedInputTokens / outputTokens / reasoningTokens
usageShape = complete | reasoningFieldAbsent
latencyMs
status = ok | transportFailed | providerRejected | invalidOutput | budgetBlocked
errorClass
estimatedCostMicros
createdAt / finishedAt
```

`turnId + purpose + attempt` 唯一。生产 dry-run 与运行都要求 `reasoningTokens=0` 且 usage shape 可核对；字段缺失记 `reasoningFieldAbsent` 并阻断 M5 真机发送，不伪造 0。表中不保存 key、base request/response、候选人身份、聊天/简历正文或完整 prompt；raw 输出中合法合并文本只进入 `CommunicationAction`，分类只进入 `DialogueTurn`。估算费用是观测值，不参与状态裁决。

### 7.7 `CandidateProfile` 沟通状态增量

除第 7.3 节补采闸外，只新增当前可生产的 `communicating` 主状态及首次真实文字时间/轮引用。M5 不提前加入 `invited/interviewed`、微信线、冷催余额、固定话术标记或卡片组字段；这些没有当前生产者。

档案 `greeted → communicating` 的触发是正式消息账本中新出现候选人真实文字，不等待分类或回复。已经 `ended/eliminated` 的档案不纳入 M5-A，避免提前实现唤醒和已淘汰不回复语义。

### 7.8 业务事实删除纪律

上述表均不使用 `gorm.DeletedAt`，不物理 DELETE。补采失败、错误 AI 输出、过期建议、改绑和人工接管分别以 `manualRequired/invalidOutput/superseded` 明示；查询必须按业务语义显式选择活动行。

## 八、确定性处理顺序与事务边界

### 8.1 每档案处理顺序

巡检仍先完成 M2 消息对账，再交给沟通 reducer；传感事件不直接调用 AI 或发消息。对批次 2A 已显式选定的唯一 adopted profile，巡检可先走 profile 级预采分支：无 active snapshot 时只执行同一补采闸，不创建 turn、不推进 `communicating`、不调用 AI、不发消息。普通对话主链为：

1. 根据正式 profile↔conversation 绑定读取活动账本；
2. 若第一条未处理候选人真实文字存在，原子推进 `greeted → communicating`；
3. 若存在真人出站消息，先以它滑动“我方最后已发”边界；若已无待回复入站则停止，不与真人抢话；
4. 预判当前待处理集合；媒体、主动换微信、卡片等未激活且现有账本无法稳定表达的语义标 `manualRequired`，不补采、不进入 AI。普通文本中的拒绝表达不在此处提前拦截，必须进入 turn 后由确定性短路落正式 `rejected` 分类；
5. 若 profile 已有 active resume snapshot 则继续；否则 CAS 补采闸并下发唯一 `candidate.readResume` logical dispatch，成功原子收编不可变快照，失败把 profile 置 `manualRequired`；任何 AI 调用都在这一步成功之后；
6. 补采网络返回后重新读取 profile/context/conversation 绑定与活动消息账本：真人已回复则停止；新候选人文本尚未冻结，可并入即将创建的同一轮；
7. 从上一条活动出站消息之后收集全部候选人新消息，创建唯一 turn，并冻结 active snapshot、历史边界、格式版本与默认推荐时段文本；
8. 按批次 0B 冻结的启用清单与顺序扫描本轮全部消息：先判简历投递 `interested`，再判拒绝模板正则 `rejected`，再判≤25 字短拒词 `rejected`；命中即以 `intentSource=codeShortCircuit` 持久化一次分类，不调意向 provider。未命中时以 `{回复}{招呼语}` 渲染原 `意向判断`，同时交付本轮全部消息与轮前最近 20 条历史的固定数据信封，作一次独立意向调用；失败固定落 `neutral + llmFailureFallback`；
9. `rejected` 立即转人工，不调回复 provider、不创建 action；`interested/neutral` 才进入回复准备；
10. 用冻结快照、推荐时段和账本历史只替换原 `多轮沟通` 的三个白名单 token，附加原样客户事实数据块；渲染不完整或出现未知 token 即停止；
11. 只调用一次与意向判断物理独立的回复建议；解析 `话术_序列`、丢弃获批忽略字段、按顺序合并为一条合法文本，原子创建唯一 action；
12. 构造 effect intent 前重新核对 profile/context/conversation 绑定、turn 输入尾、resume snapshot、是否新增消息、是否真人已回复、action 是否 current、账号域是否可派发；
13. 由 action 主键确定性创建一个 effect intent，并走既有 `chat.sendMessage`；
14. 唯一正证使 action `sent`；其他终局按安全内核映射，不自动另铸。

M5-A 不执行事件层和时刻表动作；遇到相关事实只转人工，不假装已处理。

### 8.2 事务边界

至少七个明确事务，不跨网络持锁：

1. **补采计划事务**：CAS profile `unattempted→inFlight` 并冻结 logical dispatch；已有快照、非本试运行 profile 或绑定不合格时不派发。预采分支不改沟通状态；`greeted→communicating` 只在正式账本观察到首条真实入站时由独立状态/轮冻结事务推进；
2. **补采结果事务**：result 回来后重新核对绑定，原子插入/复用 snapshot 并推进 profile。同 logical dispatch 不同 hash 冲突；
3. **轮冻结事务**：重新确认账本边界，创建/复用 DialogueTurn 并冻结 snapshot/时段/历史格式；
4. **分类事务**：短路分类不调 provider，以 turn 状态 CAS 直接写唯一 `codeShortCircuit` 结果；未短路时 provider 调用在事务外，回包后以同一 CAS 写独立 intent AIInvocation 和分类，输入边界变化则只记 invocation、turn 转人工；
5. **回复建议事务**：provider 调用在事务外；回包后以 turn 状态 CAS 写 AIInvocation 和唯一 action，输入/快照边界变化则只记 invocation、action 不转正；
6. **意图构造事务**：核对所有脑侧前置，CAS `action planned → effectPending`，创建唯一 EffectIntent/Cmd 并推进现有 ConversationEffectHead；
7. **发送成功事务**：复用 M3 已有成功入账，并在同一 SQLite 单写事务把 action 置 `sent`；若现有结构无法同事务扩展，先停下重提，禁止先 sent 后补 action。

网络调用、模型延迟和手执行期间不持 SQLite 事务或 actor 长锁。

### 8.3 失败与恢复映射

| 失败点 | M5 处置 |
|---|---|
| 意向 provider 失败/非法 | 分类一次落 `neutral + llmFailureFallback`；不重判，仍进入一次独立 reply 调用 |
| 简历读取失败/不全/换绑/超限 | 不创建自动沟通 turn、不调用 provider；profile `manualRequired`，不自动另造补采 |
| 简历 result 重放 | 同 logical dispatch + 同 hash 只复用一个 snapshot；不同 hash 冲突转人工 |
| prompt 未知 token/缺输入 | 不调用 provider 或不构造 action；响亮失败转人工 |
| 回复 provider 失败/非法 | 不构造 action/effect intent；P 档无第二次调用，直接转人工 |
| 话术数组多项 | 按冻结顺序用换行合并为一个 action；不得拆成多 intent |
| 模型返回动作/时段承诺 | `动作` 丢弃；时段只保留在候选文本，状态与卡片事实不推进 |
| 建议后新增候选人消息 | 旧 action `superseded/manualRequired`；M5-A 冻结档案 |
| 建议后真人先回复 | 同上；真人消息成为新出站锚 |
| effect intent 构造前脑重启 | 取回同一 turn/action/text，不重新分类或生成 |
| contract mismatch | WAL 前零 effectful；既有审计；action 保持可见但不旁路发送 |
| receipt rejection / failed none | 原意图终局，action `manualRequired`；自动调度不另铸 |
| report unknown、同 store | 只允许既有轨道重投原 msgId |
| possible/confirmed/超时/阴性验证 | 验证/suspect；不第二次发送 |
| 唯一正证 | 同一事务 action=sent + 唯一 self Message |

## 九、安全、隐私与自动化范围

1. 自动入口只对一个显式试运行 profile 生效，成功或任何人工态后自行退出；其他档案仍只巡检对账。
2. 每 profile 同时最多一个未终局 CommunicationAction；每账号仍受既有 effectful/intrusive 串行域约束。
3. AI 无权绕过已有 expectedTail。建议生成时的历史尾和派发前的活动尾必须一致；最终动作前仍由手的同一 evaluator 条件写。
4. 当前范围不新增动作前平台守卫；M3 `chat.sendMessage` 发送栈原样复用。若发现新守卫需求，仍须过 AGENTS.md 三问与信任边界。
5. `candidate.readResume` 只核对命令指定会话与平台用户的世界状态，不以 Vue/SDK/DOM 私有层互证授权任何动作；数据源可按真机选择，但失效方向固定为“读不到→不确认→转人工”。
6. provider base_url/key 只在 Go client；插件、contract、evidence、journal/outbox 与 Chrome 页面均不出现。简历 DTO 必然进入 contract result data，但不得进入 evidence、普通错误或泛用诊断文本。
7. 管理 UI 可显示建议文本给现场人员观察，但普通状态/命令查询 API 不返回候选人原始引用、简历 result data 或快照正文；开发诊断导出默认只含随机 ID、hash、分区覆盖、大小和计数。
8. AI provider 必然接收聊天正文、职位内容与简历正文；这属于甲方批准后的明确数据出站。平台 ID、displayName 不作为独立字段发送；简历/自由文本自含姓名电话的残余风险在验收报告如实记录。
9. 不记录模型推理内容；只消费最终结构化字段。provider 返回额外 reasoning/trace 时丢弃，不落库、不上报；usage 中 reasoning token 只记录数值并必须为 0。

## 十二、确定性故障矩阵

| 场景 | 必须结果 |
|---|---|
| 一条合格非拒绝候选人文本 | 一个 turn、一个分类、至多一个建议、至多一条回复 |
| 巡检前连续多条文本 | 合并同一轮，意向数据信封包含全部有序消息，只分类一次 |
| 命中已启用简历投递规则 | `interested + codeShortCircuit`，零 intent provider；之后可有一次独立 reply |
| 命中已启用拒绝正则/短拒词 | `rejected + codeShortCircuit` 后转人工，零 provider、零 action |
| 同一平台消息重复观察 | 不增生 turn/action |
| 无简历快照且有待处理普通入站 | 创建 turn 前只创建一个 logical capture；任何 AI 等待成功快照 |
| 重复 patrol/脑重启于补采中 | 复用 profile 上同一 logical dispatch，不另造补采 |
| 简历入口零个/多个、目标换绑或字段读不全 | 不落部分快照、不创建 turn，profile manualRequired |
| 简历 payload 超限 | PAYLOAD_LIMIT 后转人工，不截断、不分页；真实样本超限则停止另立 blob |
| 简历 result 重放 | 同 logical ID+同 hash 只产生一个 snapshot；不同 hash 冲突转人工 |
| 分类后脑重启 | 复用分类，不重判 |
| 建议后脑重启 | 复用同一 text/hash，不重生成 |
| 未短路正常轮 | 先 intent、后 reply 两条独立 invocation，不合并 |
| 分类 provider 失败 | 一次 `neutral + llmFailureFallback`，然后仍独立调用一次 reply；日志无正文 |
| 模板缺输入或出现白名单外活 token | 不调用 provider，响亮失败转人工 |
| 回复 provider 失败 | 不构造 action/effect intent；P 档无重试，直接转人工 |
| `话术_序列` 多项 | 按顺序换行合并，只产生一个 replyText action/intent |
| provider 回 `动作` 或已证实忽略元数据 | 字段值不产生业务动作；只消费合并话术 |
| provider 回未知字段/非法序列 | invalidOutput 转人工，不调用手 |
| reasoning 字段缺失或非零 | dry-run/生产阻断，不自行切模型或改预算 |
| 候选人又发新消息 | 旧建议不得发送，档案转人工 |
| 真人先回复 | 自动 action 作废并转人工，真人消息滑锚 |
| `rejected`、主动换微信、媒体、卡片 | M5-A 转人工，不发固定话术或换微信邀请，不发不完整流程 |
| profile/context/conversation 换绑 | effect intent 构造前失败，无错靶 |
| contract mismatch | WAL 前零 effectful，审计可见 |
| hand/cap/witness 不就绪 | 不构造/不派发，少发可见 |
| 重复 tick 并发 | DB 唯一键/CAS 只允许一个 action/intent |
| result/outbox 重放 | action/message 只完成一次 |
| `failed/none` 或 receipt rejection | action manualRequired，不自动另铸 |
| possible/超时/正证歧义 | 验证/suspect，绝不第二次发送 |
| 同 store report unknown | 只重投原 msgId，不建新 intent |
| 成功 | action=sent 与唯一 self Message 同事务收敛 |
| 脑重启、手重连 | capture/snapshot/turn/invocation/action/intent/message 均零增生 |
| 配置 revision 更新 | 已有 turn 继续使用冻结 hash，新轮才可显式绑定新版 |

### 13.2 验收动作

1. 记录脱敏前置计数：profile resumeCapture 状态、snapshot、turn/action/invocation/effect intent/self Message 数；
2. 真人当天开启巡检并启用该 profile 的一次性 M5 试运行；

4. 补采后巡检重新核对消息边界，冻结 turn 的 snapshot、历史格式与推荐时段，再完成唯一分类和一次回复建议；未短路时分类与回复是两次独立 provider 调用，若自然命中简历投递 `interested` 短路则只有一次 reply 调用；
5. parser 丢弃模型动作/获批元数据，把 `话术_序列` 合并为一条文本；确定性 reducer 批准并派发，不逐条人工确认；
6. 页面观察到同一会话唯一自然单气泡回复，正式 `chat.sendMessage` 取得唯一服务端正证；
7. 试运行自动退出，不处理第二档案或第二轮；
8. 再跑一次巡检，确认无重复补采、快照、分类、调用、意图和发送；
9. 重启脑、等待手重连，再跑对账，确认页面与账本零增生；
10. 检查 provider usage 与本地 AIInvocation 元数据一致、reasoning tokens 为 0，日志/报告无正文和身份。

### 13.3 通过判据

- profile 从 greeted 进入 communicating 恰一次；
- M5 验收证据中至少有一次正式 patrol `candidate.readResume` 成功；对应 profile 只有一个 logical capture 和一个不可变 snapshot，重复巡检/重启不增生；
- DialogueTurn 冻结正确 snapshot/时段/历史格式；CommunicationAction、成功 EffectIntent、`origin=self` Message 各恰一份；
- `话术_序列` 无论几项，候选人可见回复都恰为一个自然文本气泡；
- AI 只产生建议，状态/意图/发送均能追到确定性代码决策；
- AI `动作`/忽略元数据没有产生业务动作，模型文字中的时段没有被记成卡片/邀面成功；
- 实际发生的每次生产调用 reasoning tokens 均为 0；非短路真实轮必须恰为两条独立 invocation，若真实轮自然命中 `interested` 短路，则由批次 5 dry-run 另行提供两次独立调用证据；
- 复跑与重启没有第二次补采/provider 调用（已有合法事实时）、第二 intent 或第二消息；
- 真实 SX 任一歧义只少发/转人工；
- 试运行范围没有扩散；
- 隐私扫描与全量门禁绿色。

## 十五、停止条件与待甲方裁决项

### 15.1 停止条件

同时满足以下条件即完成 M5：

1. 首轮 job-config 事实继续有效，批次 0B IM 简历/模板重开事实门通过；
2. 规范按批准文本先行落地，`candidate.readResume@1` 机器契约与 Go/TS 产物一致；
3. 完成部署硬切换并确认 contractHash/cap；正式 patrol 对一个 profile 只补采一次并形成一个不可变 snapshot；
4. 自有 AI context 可由真实旧整包无损填充，profile/context 显式绑定，三个 renderer/两个 parser golden 通过；
5. DialogueTurn/Action/AIInvocation 与确定性 reducer 自动化矩阵通过；
6. 最窄自动 effectful 冒烟已绿并即时提交；
7. 批次 5 V4 Pro 非思考 dry-run、意向/回复两次独立调用证据与一轮独立审查结束，所有实际 invocation 的 reasoning tokens 为 0，当前可达阻断项为零；
8. 一次真实普通文本自动单气泡回复通过，复跑与重启对 capture/snapshot/turn/action/intent/message 全部零增生；
9. 全量门禁、token/成本记录和隐私扫描通过；
10. 《里程碑5-验收报告》独立提交。

达到后停止，不继续做拒绝、卡片、可配置时刻表、多气泡、简历刷新、第二生产模型或第二档案。

### 15.2 已冻结裁决与唯一开工门

以下事项已由甲方与执行方对齐，本计划不再重复请问：

- 最窄出口为单 profile、一次 IM 简历补采事实、单普通文本轮与一次自动单气泡 `replyText`；批次顺序为 `0B→1→2A/2B→3→4→5→6`，批次 2A/6 的真实证据可组合验收，不为连续演示删除业务事实；
- 旧后台零改动，不新增 `doc_type`/sidecar；既有文档原文固定映射，历史/默认时段/话术序列按本计划兼容口径冻结，模型 `动作` 丢弃；
- 简历正文属于已授权 provider 出站；模型文字中的时段当前由真人跟进发卡，不推进 `invited`/卡片成功；
- `多轮沟通` 的模板 token 为 `{简历}{推荐时段}{对话历史}`；现网 `意向判断` 另保留 `{回复}{招呼语}`，并以固定数据信封使用本轮全部消息 + 轮前最近 20 条；不做其他入参版本或对照实验；
- 旧生产“投简历→有意向、拒绝模板正则、≤25 字短拒词表”纳入 M5 候选迁移清单，批次 0B 逐条真机核对后才启用；
- M5-A 生产仅用 V4 Pro 非思考 + P 档；意向判断与回复生成保持两次独立调用、不合并；意向失败落 `neutral + llmFailureFallback` 后仍进入一次独立回复调用；
- M5-A 的 `rejected` 只转人工；固定挽留/收场话术 + 换微信邀请等完整拒绝分支待卡片真机样本与邀请原语就绪后另行立案；
- D 影子评测整体后置到 M5-B 立项前，届时使用 M5-A 积累的脱敏 fixture 与真实计量数据重新比较；M5-A 不跑 V4 Flash；
