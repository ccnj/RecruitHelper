## 一、结论摘要

能做，而且比预想的近。当前缺的**不是**一套自动更新系统，而是三段已有能力之间的两个接头
和一个分发面：

- 安装器（`scripts/installer.nsi`）已经是 per-user、无 UAC、可静默、覆盖安装天然安全；
- 插件换代（`client/electron/pluginSeed.js`）已经是指纹比对 + 原子替换 + 失败回滚；
- 插件激活（`client/service/internal/adminhttp/reload.go`）已经有完整判据：手就绪、能力
  声明、**无未收束命令**、终止旧推荐流、等新 bootId、校验 contractHash、超时不自动重派。

缺口只有三处：新版包从哪来（分发）、谁在什么时候装（时机裁决与执行）、装完谁去点那一下
Chrome 重载（激活触发器）。

**其中第三处独立于前两处，且现在就在花人工成本**——每次人工装包后仍要交代“去
`chrome://extensions` 点一次刷新”。它不需要任何云端出站、不碰任何冻结规范，建议先做、单独
交付。真正需要甲方裁决的是前两处。

## 二、现状盘点

### 2.1 老项目怎么做的（考古，非依据）

`../AutoZhilian/xq-resume-client-main` 的更新链是 electron-updater + generic provider：

| 环节 | 老项目做法 |
|---|---|
| 分发 | ECS `8.153.161.25` 的 nginx `/updates/` 静态目录 |
| feed | electron-builder 生成的 `latest.yml`（版本 + sha512 + blockmap） |
| 拉取 | `electron-updater` 的 `autoDownload = true`，启动后与周期检查 |
| 安装 | `autoInstallOnAppQuit = false` + 主动 `quitAndInstall`，NSIS oneClick + 差分包 |
| 发布 | `scripts/release-win.sh`：打包 → scp 上传 → curl 验证 feed 版本 |
| 插件代码 | 另一条线：远程 program.js 下发（`PROGRAM_JS_URL_PREFIX`） |

老项目的客户端是被动应答方，没有“正在跑批次”这种状态，所以“下载完就能装”。**新项目脑是
主动方，这条前提不成立**，时机裁决是本次规划里最实的一块，不能照抄。

老项目的远程 program 下发被本仓库明确否决（2026-07-25 决策第四节），不在讨论范围。

### 2.2 本仓库已有的拼图

| 能力 | 位置 | 状态 |
|---|---|---|
| 版本号单点升级 | `scripts/bump-version.sh` | 五处同步，客户端与插件永远同号 |
| 构建 | `scripts/build-win.sh` | 交叉编译脑 → UI → 插件 → dir 包 → makensis |

| 插件换代 | `client/electron/pluginSeed.js` | 壳启动时按目录指纹比对，tmp 目录校验 manifest 后 rename，失败回滚保旧版 |

### 2.3 三处缺口

1. **分发面**：没有任何“新版在哪”的通道。目前靠人工把 `setup.exe` 传给客户。
2. **拉取与安装**：客户端没有任何自更新代码。`client/electron/package.json` 无
   electron-updater 依赖，`build.publish` 未配置。
3. **激活触发器**：`reload.go` 的判据是现成的，但只有人工入口。升级后插件文件已换代、
   Chrome 里仍跑旧代码，此时 `contractMatch` 挡住 effectful——**安全，但业务静止**，
   直到有人去点那一下。

## 四、技术方案

### 4.1 分发面

最小形态：一个静态目录，两类文件。

```
/rh-updates/<客户标识>/latest.json
/rh-updates/pkg/RecruitHelper-<版本>-setup.exe
```

`latest.json`：

```json
{
  "version": "0.3.0",
  "url": "/rh-updates/pkg/RecruitHelper-0.3.0-setup.exe",
  "sha256": "…",
  "size": 95443968,
  "minFrom": "0.2.0",
  "notes": "一句话说明"
}
```

要点：

- **按客户分目录做灰度**。系统里已有客户标识（运营 webhook 正文携带客户名），复用即可。
  一个客户一个 `latest.json`，先放一家观察，再逐家推。成本几乎为零，是本方案里性价比最高
  的一项。
- **停发与降级**：把某客户的 `latest.json` 版本改回旧号即止血。已升级的机器需要人工远程
  装回旧包（NSIS 是全量覆盖，装旧版可行），但**降级只在数据库 schema 未变更时安全**——
  schema 变更过的版本不可降级，这一条必须写进发布清单。
- `minFrom` 用于将来出现不可跨越的迁移时挡住过旧版本，当前恒为占位。
- 托管位置见第七节裁决点 1。

### 4.2 为什么不用 electron-updater

推荐**自研最小更新器**，不引入 electron-updater。四条理由，前两条是硬成本：

1. **它要求 electron-builder 的 NSIS 安装器约定**（`/S` 之外的 `--updated` 标志、卸载器
   提取、blockmap 差分格式）。本仓库用的是自有 `installer.nsi`，正是因为
   electron-builder 的 nsis target 在 Apple Silicon 上编不出来（需要运行 32 位 exe 提取卸载
   器，wine/qemu/Rosetta 都不覆盖，见打包 skill 第六节）。改去迎合它，等于把已经绕开的坑
   重新踩一遍，而且只能在 Windows 上验证。
2. **它的自动行为必须全部关掉**。更新时机的裁决权在脑（谁在跑批次、有没有未收束命令，它
   一概不知）。关掉 autoDownload、autoInstallOnAppQuit 之后，它剩下的价值就只有“下载、
   校验 sha512、启动安装器”三件事——自研不到 300 行。
3. 差分包省下的是每次约 90MB 的下载。低频更新场景下这不是瓶颈。
4. 不引入依赖，也就不需要在提案 B 里放宽 `AGENTS.md` 的字面约束。

### 4.3 客户端侧：脑裁决，壳执行

分工按“主动权在脑”：

**脑**（Go，参照 `notify` 的发件箱范式）：

1. 周期检查（建议 6 小时 + 启动后延迟一次）拉 `latest.json`；
2. 版本高于当前则下载到 `%LOCALAPPDATA%\RecruitHelper\updates\`（**不能放安装目录**，
   会被 `RMDir /r` 清掉；也不放业务数据目录），校验 sha256，落一条更新记录；
3. 裁决“现在能不能装”，全部满足才置为 ready：
   - 没有运行中的工作流（漏斗批次与沟通轮均非活跃）；
   - 该手没有未收束命令（`NonTerminalCmdsForHand`，`reload.go` 已有）；
   - 没有未终局的 effectful WAL；
   - 落在业务运行窗口之外，或用户已显式暂停，或用户显式点了“立即更新”；
4. 暴露 `GET /admin/update/pending`（或产品 API 等价物）。

**壳**（Electron，只做两件事）：

1. 轮询该端点；
2. ready 时 `spawn(setup.exe, ['/S'], {detached:true, stdio:'ignore'}).unref()` 然后
   `app.quit()`。必须 detached——安装器会 `taskkill /F /IM RecruitHelper.exe`，非 detached
   的子进程会被一起带走。

`[00:00, 08:00)` 是天然的安装窗口：业务窗口关闭，不可能有新链，只可能有跨点收尾的尾巴。
建议把它作为无人值守时的默认安装时机。

### 4.4 安装器要补的三处

1. **静默模式下装完自启**。当前脚本装完什么都不做，自动更新会在此断掉——客户端关了，
   用户不知道要去点桌面图标。需加 `IfSilent` 分支 `Exec "$INSTDIR\${APP_EXE}"`。
2. **写入已装版本供反查**。已有 `WriteRegStr HKCU … DisplayVersion`，够用，无须新增。
3. 保持纯 ASCII（skill 第六节的硬约束，macOS makensis 是 ANSI-only 构建）。

### 4.5 重启后：确认与防循环

新版启动时对照更新记录：

- 版本 == 期望版本 → 标记成功，保留该安装包一份作为回滚材料，清理更早的；
- 版本仍是旧的 → 安装失败，**记录并退避**（同版本失败 2 次后停止自动重试，转人工，
  产品 UI 提示“自动更新失败，请联系支持”）。没有这道闸就会形成装-崩-装的循环。

### 4.6 装完自动激活插件（可独立先做）

新版壳启动 → `pluginSeed` 把新插件写进固定目录 → 脑发现在线手的 `contractHash` 与自身不
一致 → **自动走一次 `reload.go` 的既有编排**（判据一条不减）→ Chrome 重读磁盘上已经换代
的文件 → 新 bootId + contractHash 匹配 → effectful 恢复。

这条链现在就是通的，只差自动触发器。约束照旧：

- 一旦 `debug.reload` 已派发，超时或歧义**不得**进入通用自动重派链（协议规格 §14.1），
  转人工；
- 自动触发只在“无未收束命令 + 无活跃批次”时进行，与 4.3 同一套判据；
- 自动重载同样会作废旧推荐流，因此绝不能在批次中途触发。

**这一块不依赖提案 A 与 C，也不需要任何云端出站**，可以立即立项。收益是每次人工装包后
省掉一次远程指导，且消除“客户装了新版但业务不动、也不知道为什么”的静默停滞。

## 五、需要真机验证的未知事实

按“页面事实发现顺序”与文档信任边界，以下四条是推测，**实现前须在 Windows 真机验证**，
不得当作已知：

1. **Chrome 开着时能否替换插件固定目录**。`pluginSeed.js` 的注释已预留失败分支，但从未验证
   过 Chrome 持有 unpacked 扩展目录时 `rename` 在 Windows 上是成功还是 `ACCESS_DENIED`。
   若失败，自动更新链在此断裂，需要改为逐文件覆盖或调整顺序。**这是整条链的最大单点未知。**
2. **静默安装是否被 SmartScreen 拦**。判断是不会：SmartScreen 的信誉检查依赖文件的
   Mark-of-the-Web，而 MOTW 由浏览器等下载方写入，Go/Node 直接写文件不产生 MOTW。但这是
   关键路径，必须实测。Defender 实时扫描对未签名 exe 的误报另算，属人工兜底范围。
3. **taskkill 自己的父进程后安装器能否正常完成**。detached spawn 理论上不受影响，需实测。
4. **装完自启后能否正确重新拉起脑进程**。涉及 `BRAIN_DATA_DIR` 等环境，实测为准。

### 8.1 本轮最小可交付出口

Windows 真机上：人工装新版包 → 托盘退出旧客户端 → 安装 → 新客户端启动 → **全程不碰
Chrome** → 脑自动完成一次插件重载，观察到新 bootId、`contractHash` 与脑一致、effectful 恢复
可派，业务能继续。

若插件文件因 Chrome 占用而未换代成功（第五节未知 1），则出口改为观察到：自动重载后仍不
匹配 → **停止自动、留下明确诊断、不出现循环**。这一分支同样算通过——它正是本批要保证的
失败形态，并且顺带把未知 1 的答案带出来。

范围内的改动：把 `reload.go` 的编排核心从 HTTP handler 抽成可复用函数（admin 按钮与自动
触发器共用同一条路径、同一套判据），加一个触发器与一道防循环闸。**不改 `pluginSeed.js`、
不改安装器、不碰协议契约、不新增任何云端出站。**

触发条件，全部满足才自动重载（判据一条不减，全部复用现有实现）：

1. 手 online + ready + 声明 `debug.reload@1`；
2. `contractMatch == false` 或 `contractHash != protocol.ContractHash`；
3. 该手无未收束命令（`NonTerminalCmdsForHand`）；
4. 无活跃工作流（`ActiveProductWorkflowRun` 不处于 `StatusRunning` / `StatusAwaitingConfirmation`）；
5. 当前 `(handId, bootId)` 尚未自动重载过。

### 8.2 必须立即阻断的损害

- **批次中途重载**——重载会作废旧推荐流并丢掉当批进度。由判据 3、4 阻断，二者缺一不可。
- **自动重派维护命令**——协议规格 §14.1 红线。重载超时或歧义一律转人工，**绝不**进入通用
  重试链。
- **重载循环**——以 `(handId, bootId)` 为键至多自动一次。重载后新 bootId 若仍不匹配，停止
  自动并记录，不再触发。
- **判据放宽**——自动路径不得比现有人工路径宽松哪怕一条。

### 8.3 允许重试 / 人工兜底的失败

- 判据不满足（有批次在跑）→ 本次不做，下次评估时重来。不算失败。
- 自动重载超时或歧义 → 保持 effectful 禁派（这本身就是安全态），转人工，诊断台按钮照旧可用。
- 换代后 `contractHash` 仍不一致 → 停止自动、记录、转人工。
- 抽取重构引入的回归 → 由 Go 单测与既有 `reload_test.go` 覆盖。

复核发现，按纪律第 6 条分流后**登记不阻塞**的一项：
