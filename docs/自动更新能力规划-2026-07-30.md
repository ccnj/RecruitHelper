# 自动更新能力规划（2026-07-30）

本文件是**规划与待裁决提案**，不是已获批的实施授权，也不修改任何现有规范。按 `AGENTS.md`
增量交付纪律第 12 条，其中第三节的规范修订须经甲方逐条裁决后，才可按“规范先行 → 实现同步”

## 一、结论摘要

能做，而且比预想的近。当前缺的**不是**一套自动更新系统，而是三段已有能力之间的两个接头
和一个分发面：

- 安装器（`scripts/installer.nsi`）已经是 per-user、无 UAC、可静默、覆盖安装天然安全；
- 插件换代（`client/electron/pluginSeed.js`）已经是指纹比对 + 原子替换 + 失败回滚；
- 插件激活（`client/service/internal/adminhttp/reload.go`）已经有完整判据：手就绪、能力
  声明、**无未收束命令**、终止旧推荐流、等新 bootId、校验 contractHash、超时不自动重派。

缺口只有三处：新版包从哪来（分发）、谁在什么时候装（时机裁决与执行）、装完谁去点那一下
Chrome 重载（激活触发器）。

**其中第三处独立于前两处，且现在就在花人工成本**——每次人工装包后仍要交代“去
`chrome://extensions` 点一次刷新”。它不需要任何云端出站、不碰任何冻结规范，建议先做、单独
交付。真正需要甲方裁决的是前两处。

## 二、现状盘点

### 2.1 老项目怎么做的（考古，非依据）

`../AutoZhilian/xq-resume-client-main` 的更新链是 electron-updater + generic provider：

| 环节 | 老项目做法 |
|---|---|
| 分发 | ECS `8.153.161.25` 的 nginx `/updates/` 静态目录 |
| feed | electron-builder 生成的 `latest.yml`（版本 + sha512 + blockmap） |
| 拉取 | `electron-updater` 的 `autoDownload = true`，启动后与周期检查 |
| 安装 | `autoInstallOnAppQuit = false` + 主动 `quitAndInstall`，NSIS oneClick + 差分包 |
| 发布 | `scripts/release-win.sh`：打包 → scp 上传 → curl 验证 feed 版本 |
| 插件代码 | 另一条线：远程 program.js 下发（`PROGRAM_JS_URL_PREFIX`） |

老项目的客户端是被动应答方，没有“正在跑批次”这种状态，所以“下载完就能装”。**新项目脑是
主动方，这条前提不成立**，时机裁决是本次规划里最实的一块，不能照抄。

老项目的远程 program 下发被本仓库明确否决（2026-07-25 决策第四节），不在讨论范围。

### 2.2 本仓库已有的拼图

| 能力 | 位置 | 状态 |
|---|---|---|
| 版本号单点升级 | `scripts/bump-version.sh` | 五处同步，客户端与插件永远同号 |
| 构建 | `scripts/build-win.sh` | 交叉编译脑 → UI → 插件 → dir 包 → makensis |

### 2.3 三处缺口

1. **分发面**：没有任何“新版在哪”的通道。目前靠人工把 `setup.exe` 传给客户。
2. **拉取与安装**：客户端没有任何自更新代码。`client/electron/package.json` 无
   electron-updater 依赖，`build.publish` 未配置。
3. **激活触发器**：`reload.go` 的判据是现成的，但只有人工入口。升级后插件文件已换代、
   Chrome 里仍跑旧代码，此时 `contractMatch` 挡住 effectful——**安全，但业务静止**，
   直到有人去点那一下。

## 四、技术方案

### 4.1 分发面

最小形态：一个静态目录，两类文件。

```
/rh-updates/<客户标识>/latest.json
/rh-updates/pkg/RecruitHelper-<版本>-setup.exe
```

`latest.json`：

```json
{
  "version": "0.3.0",
  "url": "/rh-updates/pkg/RecruitHelper-0.3.0-setup.exe",
  "sha256": "…",
  "size": 95443968,
  "minFrom": "0.2.0",
  "notes": "一句话说明"
}
```

要点：

- **按客户分目录做灰度**。系统里已有客户标识（运营 webhook 正文携带客户名），复用即可。
  一个客户一个 `latest.json`，先放一家观察，再逐家推。成本几乎为零，是本方案里性价比最高
  的一项。
- **停发与降级**：把某客户的 `latest.json` 版本改回旧号即止血。已升级的机器需要人工远程
  装回旧包（NSIS 是全量覆盖，装旧版可行），但**降级只在数据库 schema 未变更时安全**——
  schema 变更过的版本不可降级，这一条必须写进发布清单。
- `minFrom` 用于将来出现不可跨越的迁移时挡住过旧版本，当前恒为占位。
- 托管位置见第七节裁决点 1。

### 4.2 为什么不用 electron-updater

推荐**自研最小更新器**，不引入 electron-updater。四条理由，前两条是硬成本：

1. **它要求 electron-builder 的 NSIS 安装器约定**（`/S` 之外的 `--updated` 标志、卸载器
   提取、blockmap 差分格式）。本仓库用的是自有 `installer.nsi`，正是因为
   electron-builder 的 nsis target 在 Apple Silicon 上编不出来（需要运行 32 位 exe 提取卸载
   器，wine/qemu/Rosetta 都不覆盖，见打包 skill 第六节）。改去迎合它，等于把已经绕开的坑
   重新踩一遍，而且只能在 Windows 上验证。
2. **它的自动行为必须全部关掉**。更新时机的裁决权在脑（谁在跑批次、有没有未收束命令，它
   一概不知）。关掉 autoDownload、autoInstallOnAppQuit 之后，它剩下的价值就只有“下载、
   校验 sha512、启动安装器”三件事——自研不到 300 行。
3. 差分包省下的是每次约 90MB 的下载。低频更新场景下这不是瓶颈。
4. 不引入依赖，也就不需要在提案 B 里放宽 `AGENTS.md` 的字面约束。

### 4.3 客户端侧：脑裁决，壳执行

分工按“主动权在脑”：

**脑**（Go，参照 `notify` 的发件箱范式）：

1. 周期检查（建议 6 小时 + 启动后延迟一次）拉 `latest.json`；
2. 版本高于当前则下载到 `%LOCALAPPDATA%\RecruitHelper\updates\`（**不能放安装目录**，
   会被 `RMDir /r` 清掉；也不放业务数据目录），校验 sha256，落一条更新记录；
3. 裁决“现在能不能装”，全部满足才置为 ready：
   - 没有运行中的工作流（漏斗批次与沟通轮均非活跃）；
   - 该手没有未收束命令（`NonTerminalCmdsForHand`，`reload.go` 已有）；
   - 没有未终局的 effectful WAL；
   - 落在业务运行窗口之外，或用户已显式暂停，或用户显式点了“立即更新”；
4. 暴露 `GET /admin/update/pending`（或产品 API 等价物）。

**壳**（Electron，只做两件事）：

1. 轮询该端点；
2. ready 时 `spawn(setup.exe, ['/S'], {detached:true, stdio:'ignore'}).unref()` 然后
   `app.quit()`。必须 detached——安装器会 `taskkill /F /IM RecruitHelper.exe`，非 detached
   的子进程会被一起带走。

`[00:00, 08:00)` 是天然的安装窗口：业务窗口关闭，不可能有新链，只可能有跨点收尾的尾巴。
建议把它作为无人值守时的默认安装时机。

### 4.4 安装器要补的三处

1. **静默模式下装完自启**。当前脚本装完什么都不做，自动更新会在此断掉——客户端关了，
   用户不知道要去点桌面图标。需加 `IfSilent` 分支 `Exec "$INSTDIR\${APP_EXE}"`。
2. **写入已装版本供反查**。已有 `WriteRegStr HKCU … DisplayVersion`，够用，无须新增。
3. 保持纯 ASCII（skill 第六节的硬约束，macOS makensis 是 ANSI-only 构建）。

### 4.5 重启后：确认与防循环

新版启动时对照更新记录：

- 版本 == 期望版本 → 标记成功，保留该安装包一份作为回滚材料，清理更早的；
- 版本仍是旧的 → 安装失败，**记录并退避**（同版本失败 2 次后停止自动重试，转人工，
  产品 UI 提示“自动更新失败，请联系支持”）。没有这道闸就会形成装-崩-装的循环。

### 4.6 装完自动激活插件（可独立先做）

新版壳启动 → `pluginSeed` 把新插件写进固定目录 → 脑发现在线手的 `contractHash` 与自身不
一致 → **自动走一次 `reload.go` 的既有编排**（判据一条不减）→ Chrome 重读磁盘上已经换代
的文件 → 新 bootId + contractHash 匹配 → effectful 恢复。

这条链现在就是通的，只差自动触发器。约束照旧：

- 一旦 `debug.reload` 已派发，超时或歧义**不得**进入通用自动重派链（协议规格 §14.1），
  转人工；
- 自动触发只在“无未收束命令 + 无活跃批次”时进行，与 4.3 同一套判据；
- 自动重载同样会作废旧推荐流，因此绝不能在批次中途触发。

**这一块不依赖提案 A 与 C，也不需要任何云端出站**，可以立即立项。收益是每次人工装包后
省掉一次远程指导，且消除“客户装了新版但业务不动、也不知道为什么”的静默停滞。

## 五、需要真机验证的未知事实

按“页面事实发现顺序”与文档信任边界，以下四条是推测，**实现前须在 Windows 真机验证**，
不得当作已知：

1. **Chrome 开着时能否替换插件固定目录**。`pluginSeed.js` 的注释已预留失败分支，但从未验证
   过 Chrome 持有 unpacked 扩展目录时 `rename` 在 Windows 上是成功还是 `ACCESS_DENIED`。
   若失败，自动更新链在此断裂，需要改为逐文件覆盖或调整顺序。**这是整条链的最大单点未知。**
2. **静默安装是否被 SmartScreen 拦**。判断是不会：SmartScreen 的信誉检查依赖文件的
   Mark-of-the-Web，而 MOTW 由浏览器等下载方写入，Go/Node 直接写文件不产生 MOTW。但这是
   关键路径，必须实测。Defender 实时扫描对未签名 exe 的误报另算，属人工兜底范围。
3. **taskkill 自己的父进程后安装器能否正常完成**。detached spawn 理论上不受影响，需实测。
4. **装完自启后能否正确重新拉起脑进程**。涉及 `BRAIN_DATA_DIR` 等环境，实测为准。

## 七、甲方裁决结果（2026-07-30）

1. **更新源托管**：复用 `8.153.161.25` 的 nginx，加一个静态目录。不新建基建。
2. **安装自动程度**：先做“下载完在产品 UI 提示、用户点‘立即更新’才装”；跑顺后再放开到

### 8.8 批 0 增补二：手就绪即评估（2026-07-30 甲方确认后落地）

真机那 30 秒延迟全是在等 ticker——手 15:39:20 就连上了，评估却要等到 :35。给
`session.Hub` 加一个 ready 钩子，手一就绪立刻捅醒评估；ticker 保留，兜住提醒被合并或丢弃
的场合（`fd708bc`）。

三个位置是刻意的，都不是风格问题：

- **钩子挂在 `activate` 之外、`h.mu` 已释放之后**。那里锁序固定为 `h.mu → Registry.mu`，
  回调进去会把这条纪律撕开；到调用点时注册表已登记新 session/boot，观察者读到的是最终态。
- **回调只做非阻塞 channel 发送**。它跑在手的读循环上，一旦同步发起编排就当场自锁：
  `Reload` 要等下一次 hello，而那个 hello 正需要这个读循环去处理。
- **wake 缓冲 1、满则丢弃**。提醒不带 handID，每次评估全量扫描注册表，所以合并或丢弃都
  不会漏掉任何一只手。

并发上：tick 与 wake 共用一个 goroutine，`EvaluateOnce` 永远串行；两者撞在一起只是连着评估
两次，第二次必被 `staleReason`/`halted`/`attempted` 挡成空转。

**顺带修掉一处不对称**（`f38a2c0`）：增补一只加了触发条件，漏了对称的成功判据——`Reload`
换代后只查契约，手若仍报旧版本照样判成功，于是下一轮又派发一次重载，白白多一次推荐流

此时重复重载不会有不同结果，磁盘上的插件根本不是期望的那一版。这个缺陷是写“撞车时第二次
评估应空转”那条测试时暴露的。

### 八之三、检查节奏与下载风暴（2026-07-30，`2a60404`）

甲方定的基数：**首检 30 秒、周期 15 分钟**（原为 2 分钟 / 6 小时）。清单只有几百字节，查得勤
几乎不花什么；真正的负载是那 96MB 的包，而它下好校验过就不再重下。

**抖动是重点。** 固定间隔会把本来分散的客户端**同步化**：这是个上班时间用的工具，客户多半在
同一个早晨时段开机，固定首检延迟就意味着他们在同一分钟一起来取 96MB。更糟的是失败之后——
所有人同一刻超时、又在同一刻重试，同步性反而被强化。现在两个时间点都散成 0.75~1.25 倍，
期望频率不变。

**实测更新源出口约 1.5 MB/s**（96MB 单客户 64 秒）。据此的容量判断：

| 并发客户数 | 每客户下载耗时 |
|---|---|
| 10 | 约 11 分钟 |
| 25 | 约 27 分钟 |
| 30 | 约 32 分钟 → 撞上 30 分钟下载超时 |

**抖动治的是“撞在一起”，治不了带宽本身。** 25–30 个客户这个临界点由出口带宽决定，与检查周期
无关；缩短周期反而让涌入窗口更窄。客户数再上一个量级时该把包挪到 OSS/CDN、服务器只留清单，
那是另一个量级的事，现在做是浪费。

周期缩短的副作用一并处理：一台断网的机器一天要走近百轮，同一句失败刷上百条会把真正的异常
埋掉。改为只在“由通转不通”或失败原因变化时说一次，恢复后再失败重新说。

### 换代延迟：14.4 秒 → 27 毫秒

装 0.2.4（客户机原为 0.2.3），Chrome 全程开着、装完不碰：

| 时刻 | 事件 |
|---|---|
| 18:23:09.811 | 客户端启动 |
| 18:23:09.886 | `[plugin] 已更新插件到 …`（pluginSeed 换代成功） |
| 18:23:10.028 | 会话建立（旧插件 0.2.3 连上） |
| **18:23:10.055** | **触发换代**——距会话建立 **27 毫秒** |
| 18:23:10.269 | `插件已自动换代 extVersion=0.2.4` |

首验时这一步等了 14.4 秒（干等 ticker），ready 钩子把它压到了 27 毫秒；整个换代
18:23:10.028 → 10.269，**241 毫秒**。

同一条日志也验证了 8.8 修的那处文案：

```
插件需要换代，自动重载 reason=版本落后于磁盘上的插件
  handVersion=0.2.3 diskVersion=0.2.4
  handContract=sha256:e75e80c0… brainContract=sha256:e75e80c0…
```

两个 contract hash **一模一样**，而 reason 正确指向版本。修之前这里会写“契约不一致”。

## 八之五、批 2 真机验收（2026-07-31，先失败后通过）

### 第一次：失败，根因是安装器把自己杀了

0.2.6 上点更新装 0.2.7。脑侧裁决、下载校验、交出安装器都正常，`[service] 退出
code=1`，九分钟后机器回来仍是 0.2.6。

根因：`installer.nsi` 清场时用了 `taskkill /F /IM RecruitHelper.exe /T`。`/T` 是终止
进程树，而自动更新路径下安装器正是客户端 `spawn` 出来的子进程——它把自己一起杀了，
死在清场那一步，根本没走到文件覆盖。**Node 的 `detached: true` 救不了：在 Windows 上
它只断开控制台，ParentProcessId 照样记录在案。**批 2 出口里"detached 理论上不受影响"
那条推测是错的。

当时安装器侧一行日志都没有，只能反推：安装目录若被 `RMDir /r` 清过，客户端就起不来，
而它起来了且仍是 0.2.6 → 没走到那一步。

修复（`8b47b4d`）三处：去掉那个 `/T`（客户端唯一要紧的子进程是脑，前一行已按名字杀
过）；安装器补四条 `install.log` 痕迹，刻意放在不会被 `RMDir /r` 清掉的 updates 目录；
`IfSilent` 的相对跳转改成命名标签——加日志后 `+n` 会数错，而数错的后果是"静默安装不
重启客户端"。

### 第二次：0.2.8 全线通过

| 时刻 | 事件 |
|---|---|
| 00:32:22 | 客户端启动（0.2.6） |
| 00:34:01 | `新版客户端已下载并校验通过 version=0.2.8`——启动后 1 分 39 秒（30 秒首检带抖动 + 约 69 秒下载） |
| 00:35:49 | 用户点"立即更新"→ `准备安装新版客户端，即将退出` → 交出安装器 |
| **00:35:59** | **新版自己起来了**——距交出安装器 **10 秒**，全程无人操作 |
| 00:36:00 | `上次自动安装已生效 version=0.2.8 from=0.2.6` |
| 00:36:02.123 | 旧插件（0.2.6）连上 |
| 00:36:02.153 | 触发换代——距会话建立 **30 毫秒** |
| 00:36:02.389 | `插件已自动换代 extVersion=0.2.8`——换代耗时 **236 毫秒** |

**三条 Windows 侧真机未知一次性全部有了答案：**

1. **SmartScreen/Defender 不拦静默运行的未签名 exe。** 与 5.2 的推测一致——MOTW 由浏览器
   写入，Go 直接写的文件没有这个标记。
2. **taskkill 自身父进程后安装器能跑完**——去掉 `/T` 之后。这一条以第一次失败的形式给出
   了答案。
3. **`IfSilent` 自启分支正确。** 10 秒后客户端自行启动，无人碰过。

顺带验到的：

- 这次插件换代是**契约触发**（`reason=契约与当前脑不一致`，两个 hash 确实不同：
  `e75e80c0` vs `ba63438e`），而 8.7 那次是版本触发。8.8 修的那处文案在两条路径上都报对了；
- `pending-install.json` 的成功判定与清理正常：装成后 `上次自动安装已生效`，此前 0.2.7 那次
  失败留下的 `attempts=1` 记录被新版本的记录覆盖，未误伤。

**批 2 至此完成。** 从点击到新版跑起来、插件换代完毕，总计约 13 秒。

## 九、明确不做

- 远程 JS 热更、动态 program 下发、独立于客户端的插件更新通道（沿用 2026-07-25 决策）；
- CRX、Chrome 扩展私有 update URL、Chrome Web Store；
- 客户自助安装向导（首装仍人工远程）；
- 差分包与增量下载；
- 自动回滚（回滚 = 人工远程装旧包 + 改 feed 止血，且仅限 schema 未变更时）；
- 把更新决策交给壳或插件——时机裁决只在脑。
