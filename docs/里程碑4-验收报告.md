# 里程碑 4 · 主动建联闭环验收报告

> 对照 `docs/里程碑4-实施与验收计划.md`。记录日期：2026-07-21（Asia/Shanghai）。
> 本报告不记录候选人姓名、账号明文标识、平台用户/职位/会话原始引用、Cookie、token、聊天正文或可还原身份的截图。
> 真机许可见 `docs/真实账号测试授权记录.md`；许可不放宽“结果未知不重发”的安全红线。

## 1. 当前结论

状态：**通过（M4 首客前、开发者模式、同机可信、有人值守剖面）。**

真人当前打开的未建联候选人已经通过正式 `candidate.readCurrent@1` 建档；正式 `chat.sendGreeting@1` 对一个候选人执行一次候选人可见动作；页面最终出现唯一新会话和唯一服务端确认的自然问候。第一次结果收敛遇到新会话服务端视图短暂分叉，系统没有补发，而是按设计进入验证与 `suspect`。平台事实固化和最窄读取修复分别提交后，正式 `chat.readGreetingOutcome@1` 取得唯一正证；脑在单个 SQLite 事务中把意图、档案、会话、adopted 跟踪和唯一 `origin=self` 消息收敛为成功。

随后脑优雅重启、手自动重连。重启前后目标账本与全库业务计数完全相同；`contractHash` 一致，`witnessReady=true`，`outboxPending=0`、`journalOpen=0`、`suspect=0`，页面自然问候没有增生。新会话已经具备既有巡检与 `chat.sendMessage` 所要求的 adopted 前置条件，本轮没有向该候选人发送第二条测试消息。

验收只覆盖智联一个真实账号和一次候选人可见招呼，不能外推无人值守成功率、第二账号或第二平台。

## 2. 范围与明确不做

本里程碑交付的最窄竖切为：

`真人打开当前候选人 → 正式只读身份 → 真人确认 selected 档案 → 稳定招呼意图 → 一次最终动作 → 唯一新会话/服务端招呼正证 → 原子 adopted → 接回既有巡检与 sendMessage`

没有混入自动搜索、批量采集、AI 打分、自动选人、自动招呼调度、配额/频控、AI 回复、确定性沟通状态机、邀面/换微信卡、第二平台、云端、授权、更新器、远程 JavaScript、program 交付机制或无人值守转正。插件仍构建到 `plugin/dist`，由 Chrome 开发者模式本地加载。

## 3. 批次 0 事实门

### 3.1 当前候选人与身份

- 推荐列表没有可靠的“当前项”；只有真人已经打开且唯一可见的详情定义当前候选人。
- 未建联候选人的稳定平台用户引用来自获批的一次性 MAIN-world 脱敏探针。代表值同页两次一致、轻刷新后唯一命中；原始值没有离开函数局部或进入持久记录。
- URL/DOM 不能直接提供平台用户引用。`resumeNumber` 只在同一次 MAIN-world 读取中把唯一详情瞬时连接到唯一来源卡，不返回、不持久化、不作身份或失败降级。
- 该私有感知源属于高脆数据通道，失效方向固定为“读不到 → 不确认 → 转人工”；禁止降级到姓名、头像、列表序号或 DOM 位置，也不参与动作接口授权互证。

### 3.2 职位、动作与正证

- 职位引用由当前 URL、来源卡 owner route 与同一 owner 的 active job 三者相等确定；标题只展示，不作身份。
- 未建联关系由唯一当前详情中的唯一标准招呼按钮确认。关系不清只返回 `unknown`，不得发送。
- 招呼为两步公开拓扑：第一步只打开编辑器；最终发送按钮才是候选人可见动作。自定义项已经选中但编辑入口样式隐藏时，DOM 中仍存在唯一可逆入口；它只能在 attempting 前展开，仍须观察到唯一可见编辑器才继续。默认招呼配置永不修改。
- 服务端正证要求同一候选人、职位和唯一会话，同时存在唯一稳定消息身份、成功状态、我方方向、招呼消息类型和正文 hash。按钮变化、配额变化、弹窗消失或乐观气泡都只是旁证。
- 首次真实建联证明新会话的 history、live timeline 与刷新后的初始化 timeline 可短暂分叉。它们现在只提供正证候选，按稳定服务端消息身份去重汇合；正证并集恰为一个才确认，零个或多个均为阴性且不授权补发。

批次 0 的临时探针与路径诊断没有进入 contract/capability 或生产代码；动态键持久化偏差已原位脱敏，最终仓库残留扫描为零。

## 4. 契约、能力与数据模型

### 4.1 三个正式原语

| 原语 | class | 当前语义 |
|---|---|---|
| `candidate.readCurrent@1` | readonly | 只读真人当前打开的唯一候选人、职位和关系三态；不搜索、不滚动、不自动打开 |
| `chat.sendGreeting@1` | effectful | 对已持久化且关系未建立的人×职位执行一次脑指定自然招呼；attempting 后候选人可见动作至多一次 |
| `chat.readGreetingOutcome@1` | intrusive / idempotentReadReceipt | 按候选人、职位与正文 hash 读取唯一新会话和唯一服务端招呼正证；`false` 不表示未发送 |

规范文本、`contract.v1.json`、Go/TS codegen、脑侧实现、手侧注册与真实 hello capability 已一致。`GREETING_REJECTED` 只映射平台明确业务拒绝且 `sideEffect=none`；身份、页面、guard、witness、receipt、超时、解析或结果不明都不能借此归档候选人。

### 4.2 候选人和档案

- `Candidate` 主键固定为 `(platform, platformUserRef)`；`resumeNumber` 不进入主键、唯一键、外键、幂等键或关联兜底。
- `CandidateProfile` 以内部 `profileId` 为主键，并有 `(platform, accountRef, platformUserRef, positionRef)` 身份唯一约束。
- 同一个平台用户同一时刻最多一个非 `eliminated` 档案；conversation 绑定在 `(platform, accountRef, conversationRef)` 上唯一。
- `CandidateGreetingHead` 每个 profile 唯一、`latestIntentId` 唯一，以 generation CAS 串行化多标签、响应丢失与重复 POST。
- 业务事实不物理删除。两个动作前安全失败的档案仍以显式 `selected` 状态保留，没有通过 DELETE 隐藏历史。

### 4.3 成功事务

唯一正证进入一个 SQLite 单写事务，同时完成：

1. 根命令与 greeting intent 终局为 `ok`；
2. profile 从 `selected` 推进到 `greeted`；
3. profile 绑定唯一 conversation；
4. 创建或收编 adopted `Conversation/TrackedIntent`，`adoptedBoundarySeq=0`；
5. 追加唯一 `origin=self` 消息并绑定 `outboundIntentId`。

任一约束、写点或状态 CAS 冲突都整事务回滚；重复/迟到 result、验证正证与人工裁决不能增生第二份事实。

## 7. 确定性故障矩阵

脑侧与手侧矩阵共同覆盖：

- 重复 POST、响应丢失、多标签 generation CAS 和 latest 恢复；
- 候选人/职位变化、零个/多个当前目标、已有关系、关系 unknown、已有编辑器或真人输入；
- 两种首击拓扑、隐藏可逆编辑入口、最终动作调用次数不超过一；
- attempting 前失败、attempting 后动作前死亡、动作后观察前死亡；
- committed/outbox/result/ACK 丢失、Service Worker 重生、脑重启、witness store 换代；
- 正证、阴性、零/多会话、零/多同 hash 招呼、职位错配和跨视图不同服务端身份；
- 明确业务拒绝与普通技术失败的档案分流；
- 成功事务每个写点回滚、重复/迟到 result、验证/result 竞态和人工裁决竞态；
- M3 `chat.sendMessage` 与 M2 巡检全量回归。

共同断言为：候选人可见招呼不超过一次，成功 greeting intent、`origin=self` 招呼和 profile↔conversation 绑定都不超过一；读不清只能少发或转人工。

## 8. 真实 Chrome 验收

### 8.1 发送前

- 硬切换按“暂停派发 → 重启脑 → 管理端一键重载插件 → 新 hello”完成；脑手 `contractHash` 一致，三个 M4 capability 和 `witness/1` 就绪。
- `outbox=0`、`journalOpen=0`、账号域无 suspect，账号身份 current；页面没有验证码、风控或真人草稿。
- 真人通过产品 UI 读取并确认当前候选人，Candidate/Profile 各唯一；目标关系明确为未建立。
- 产品编辑器只包含获准自然问候，产品确认只发生一次。浏览器控制没有直接操作智联输入框或最终发送按钮。

### 8.2 两次动作前安全失败

前两个真实 greeting intent 都在不可逆动作前以 `ELEMENT_UNRESOLVED / sideEffect=none` 终局：

1. 当前自定义项已经选中，编辑图标因未悬停只在样式层隐藏；初版实现错误地把“样式不可见”当成“入口不存在”。
2. 第一笔修复又假定重新点击已选项会产生 hover；真实标准 click 不会制造指针悬停，仍未打开编辑器。

两次均没有最终发送 click、没有新会话、没有消息、没有 suspect。对应事实和修复分别提交；失败档案继续保留为 selected，未物理删除。

### 8.3 唯一候选人可见动作与页面差分

第三个 intent 的 prepare/preflight 通过并写入 attempting，最终标准动作只调用一次。结果帧在租约窗口内没有形成即时终局，脑没有补发，而是依次进入三轮自动验证和 suspect。

页面旁证为：目标关系从“未建联动作”变成“继续沟通”，当日可用配额从 100 变为 99。随后在 IM 中观察到同一候选人/职位的唯一新会话和唯一自然问候。刷新后的服务端初始化快照进一步给出唯一稳定消息身份、成功状态、我方方向和相同正文 hash；最终正式配套验证读也取得同一唯一正证。旁证没有单独授权成功，账本只由正式正证收敛。

### 8.4 验证、人工裁决与读取修复

该根命令共有六条正式 `chat.readGreetingOutcome` 子命令：一条在页面切换期 canceled，四条合法返回 `confirmed=false`，最后一条在平台读取修复与插件硬切换后返回唯一正证。所有阴性均没有触发招呼动作。

第一次真人 `resolvedOk` 还受协议的迟到结果窗口约束，窗口结束前返回 409，没有提前裁决。窗口结束后，真人裁决只授权只读验证。动态 IM 上下文持续阴性时系统保持 suspect；确认两个可见 composer 均为空后轻刷新目标会话，脱敏诊断证明完整服务端正证存在。事实文档和读取修复分别提交、自动门禁绿色并重载插件后，最后一次正式只读验证成功。

### 8.5 脑账本差分

相对第三次发送前，业务事实恰增加：

- greeting intent `+1`，最终成功 `1`；
- profile↔conversation 绑定 `+1`；
- adopted tracked conversation `+1`，`adoptedBoundarySeq=0`；
- `origin=self` 且绑定该 intent 的消息 `+1`；
- suspect 最终回到 `0`。

目标成功事务结束时，Candidate/Profile/Intent/Conversation/TrackedIntent/Message 均各为一份，没有重复绑定或第二条消息。

### 8.6 脑重启、手重连与零增生

成功后先记录目标计数：Candidate/Profile/Intent/Conversation/TrackedIntent/Message 均为 `1`，根命令加六条正式验证子命令共 `7`。全库聚合基线为 Candidate `4`、Profile `4`、EffectIntent `10`、Cmd `330`、Conversation `488`、TrackedIntent `4`、Message `11`。

脑随后优雅退出并以同一最终代码和数据库重启；手自动重连，无在途 effectful 被恢复或重派。重启后上述目标计数和七项全库聚合逐项完全相同，页面仍显示同一唯一自然问候；手侧仍为 `witnessReady=true`、`outboxPending=0`、`journalOpen=0`，全局 `suspect=0`。

正式正证读在最终插件上已经完成。重启后没有为了形式上强迫一条额外 `chat.readThread` 而新增管理旁路、篡改 `lastSyncedAt` 或唤醒账号下其他 pending 会话；这会扩大真实页面动作面，且不增加“不双发”证明。新会话已经是 adopted、边界为 0，既有 `chat.readThread`/`chat.sendMessage` 路径继续由 M2/M3 真机事实和本轮全量回归覆盖。本报告把该停止判断显式记录，不伪称执行了未执行的命令。

## 9. Guard cohort 与人工成本

开发期真实 greeting cohort 为：intent `n=3`、动作前技术失败 `2`、候选人可见动作 `1`、最终成功 `1`、进入 suspect 的动作 `1`。两个动作前失败均已证实为页面实现缺陷，不计作守卫假阳性，也不能据此计算逐守卫假阳性率。

候选人可见动作 cohort 只有 `n=1`。该样本经历一个人工介入案例，案例内先后授权三次只读裁决验证；按案例口径为 `1/1`，按操作次数为 `3/1`。这些只是真实原始计数，禁止折算或外推为无人值守每百次长期介入率。账号身份、唯一当前候选人、职位、关系未建立、唯一编辑器、默认设置、最终动作表面和动作窗口在唯一可见动作中均曝光并通过；当前没有经人工确认的守卫假阳性样本。

## 10. 隐私与架构边界

- 对仓库执行真实候选人姓名、已知账号/用户/职位/会话/命令原始引用和常见长标识扫描，命中为零；报告只写“自然问候”和 hash 是否一致。
- 真机诊断没有把原始身份、正文、Cookie、token、截图或服务端消息 ID 写入仓库。
- program 没有新增 Chrome listener、业务定时器、业务 storage、远程代码执行或第二平台分支；监听仍只在 base，业务节奏仍只在脑。
- 旧项目只提供候选线索；身份、动作拓扑和正证均以当前真实页面与本仓库事实文档重新裁决。
- “死代码三件套与 witness 两缺陷”匿名债务已由甲方撤销；未来只有找到原始实名证据时才独立立项，不恢复匿名挂账。
