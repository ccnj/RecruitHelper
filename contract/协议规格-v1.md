## 1. 模型与公理

1. **脑是唯一账本。** 手随时失忆(SW 空闲约 30 秒被杀、页面导航杀 content script、浏览器重启),失忆是常态。手侧一切存储只能是"证词"——丢了只准退化为"更多转人工",不准导致错误的自主行为。
2. **语义方向永远脑→手;传输连接方向手→脑。** 手主动拨号、重连、发心跳,但协议语义上手没有主动权:只执行命令、只上报传感提示。
3. **语义传输无关。** 任何正确性不押在 WebSocket 特性上(连接即会话、帧有序、断开即边界都不作为正确性依据)。验收思想实验:换 MQTT 5 承载,语义零修改(A 卷 §13.2 已逐条核过)。
4. **外部副作用极贵。** 重复给候选人发消息=骚扰=封号风险。纪律:宁可少发;一切歧义不自动重发,只转人工。协议目标:让"多发"在自动逻辑下机制性不可能,让"少发+人工"成为歧义唯一归宿。
5. **契约单一源头。** 两端协议类型与运行时校验全部出自 `contract/` codegen(Go/TS 类型、常量、validator),禁止手写;关联字段在生成类型里非可空。CI 校验全部生成物一致。
6. **单一命令通道。** 测试页、调度器、将来的运营工具都只是脑体内的命令生产者;协议中不存在"测试命令"概念。手侧唯一入口是命令分发器。
7. **平台无关。** 命令与结果的语义字段一律意图级;DOM/selector/tabId/windowId/平台专有 id 只许出现在 evidence 与日志,脑逻辑不得读取 evidence 内容做分支。
8. **业务节奏全在脑。** 巡检、调度、重试、超时判定只存在于脑;分钟级延迟是业务规格明文允许的(`docs/沟通逻辑规格-v4.md` 巡检模型:每日真人手动开启,数分钟一轮,最晚至 24:00),协议不为秒级实时付复杂度。

环境基线:Chrome ≥ 116(活跃 WS 收发重置 SW 30 秒空闲计时);chrome.alarms 最小约 30 秒;脑=Electron 内常驻 Go 服务+SQLite。

## 2. 传输绑定与本地握手

### 2.1 连接 [M1]

- 端点 `ws://127.0.0.1:{port}/v1/channel`;默认端口 **17872**(明确不复用 17321),脑侧配置文件与手侧扩展 options 页均可改。文本帧,UTF-8,一帧一条 JSON 消息,不批量不拼接。
- 单帧硬上限 `limits.maxMsgBytes`(默认 256 KB,welcome 下发),按**完整 envelope 的 UTF-8 字节数**计算;通用 body 内联建议线 `inlineBytes`=32 KB。感知批次另冻结:单条消息内联文本 ≤2 KB、内联 `result.data` ≤64 KB、证据文字 ≤2 KB;更大完整内容只可走 `blob/1` Claim Check。未协商 blob 时必须在执行前或组装结果时响亮失败(PAYLOAD_LIMIT),禁止静默截断;收到超硬帧一律 PROTO_MSG_TOO_LARGE。
- 手侧重连退避:1s 起 ×2,封顶 30s,±30% 抖动;连接稳定 60s 后退避归零。chrome.alarms 看门狗(60s)发现"未连接且无在途尝试"即发起——它只是复活闹钟,不是心跳。runtime.onStartup/onInstalled 立即尝试。

### 2.2 本地可信握手与连接边界 [M1, 2026-07-17 修订]

威胁模型:用户明确把同机本地环境视为可信。协议防网页脚本误连与跨站 WebSocket,不试图防恶意本地进程;如果未来出现远程手、不可信本地多用户或云端监听,必须重新设计传输鉴权,不能把本节直接外推。

1. **只监听回环地址**:脑只在 `127.0.0.1` 监听固定端点,不得监听 `0.0.0.0`、局域网或公网地址。
2. **Origin 前置校验**:升级 WebSocket 前,脑只接受 `Origin` 以 `chrome-extension://` 开头的请求,其余请求直接拒绝。这是网页侧边界,不是对本地进程或某个特定扩展的身份证明。
3. **手自己出生身份**:插件首次运行以密码学安全随机源生成稳定、不透明的 `handId`(长度 1..128),写入 `chrome.storage.local`。每个 Chrome profile 天然拥有不同的本地实例 ID;SW/浏览器重启复用,清除扩展数据或重装后生成新值。`handId` 只用于手注册表、路由和单活接管,不是凭据,也不等于招聘账号绑定。
4. **零配对、零握手身份 token**:hello 的 `handId` 必填且不可空,没有 `auth`;welcome 不签发 `handId`、共享 token 或其他手身份凭据。不存在配对窗口、待确认连接、配对码、`paired_hands` 凭据表或配对管理 UI。§13 推迟的 `blob.token` 是会话作用域的 HTTP 数据面 capability,不参与 hello 身份判定,不得被当作配对机制。
5. **10 秒握手**:手发送 hello 后,脑完成 Origin、主版本和结构校验并立即回 welcome/bye;10 秒未收到响应,手关闭连接并进入正常重连退避。没有等待人工确认,因此没有握手期 pre-session ping 或 70 秒特殊超时。
6. **单活连接**:同 `handId` 的新 hello 顶掉旧连接(旧连接收 bye(SUPERSEDED));非当前物理连接来的任何消息丢弃并审计。当前物理连接上只有已 accepted 命令的 `progress/result` 可保留该命令创建时的旧 `session`;`ack/ping/event` 仍必须与当前会话一致。
7. **协议摘要不是签名**:`contractHash` 是契约文件公开字节的 SHA-256 摘要,在线握手层只用于漂移告警。它没有秘密材料,不是签名、MAC、口令或身份凭据;不匹配不得硬拒连接,连接建立及 readonly/intrusive 的在线兼容门禁是主版本与逐项 caps/features。effectful 另受 §14 常备部署一致性双闸约束;首客前破坏性硬切还须暂停派发,直至重启脑、重载插件并确认哈希一致。
8. 显式不做(防回潮):人工配对、共享 token、一次性配对码、二维码、旧扩展 ID 白名单、Native Messaging 发现、动态端口发现。若威胁模型改变,以新安全设计和相应协议版本处理,不得悄悄恢复旧字段。

本地明文 ws 可接受,依据是回环监听和用户声明的本地可信边界;wss 自签证书在该边界内零收益高摩擦,不做。

## 3. 消息信封 [M1]

信封 7 字段,冻结;扩展只发生在 body 内。

```json
{
  "proto": 1,
  "kind": "cmd",
  "msgId": "01JB2K3G8XF5N7Q9R0S1T2U3V4",
  "session": "s-01JB2K1AAAAAAAAAAAAAAAAAAA",
  "ts": 1768546201345,
  "attempt": 1,
  "body": { }
}
```

| 字段 | 类型 | 语义 |
|---|---|---|
| proto | int | 协议主版本。首客前可按 AGENTS.md 在同一主版本内硬切清理;兼容冻结后,跨原语的不兼容变更才递增主版本且当前主版本内只做加法。接收方始终必须忽略不认识的字段(must-ignore)。 |
| kind | string | 消息种类(§4)。不认识的 kind:命令方向 ack 拒绝(PROTO_UNSUPPORTED_KIND),上报方向记日志丢弃。 |
| msgId | string | 消息逻辑身份:唯一不透明串(建议 ULID,手侧 crypto.randomUUID 亦可),接收方不得解析其内容。**重传时不变**,是去重键与关联锚点。 |
| session | string\|null | 当前发送尝试所属会话(welcome 分配)。hello/welcome/bye 为 null。命令只在 session=手当前会话时可执行;已 accepted 命令在旧会话断开后仍可完成，首次产生的 progress/result 可以携带该命令的创建会话；同一上行信封跨会话补投时按下方重传纪律更新为当前会话。两者都只在该手当前物理连接上受理。 |
| ts | int64 | 发送方毫秒时钟,仅诊断;重传时更新。**永不**用于去重、排序或状态裁决。 |
| attempt | int | 同一 msgId 第几次发送,仅诊断(>1 说明投递层在重传)。 |
| body | object | kind 专属载荷。 |

所有线上 `int/int64` 都限制在 JSON/TypeScript 可精确表示的 safe-int53 范围(±9,007,199,254,740,991);Go/TS validator 使用同一 `safeInteger` 规则,防止跨端四舍五入后关联、deadline 或排序值分裂。

命名纪律:线上字段一律 camelCase;所有"指向另一条消息"的字段只有一个名字 **`ref`**,在生成类型里非可空——别名漂移与"回执丢关联 id"从构造上灭绝。

重传纪律:同一 msgId 重传时,信封可变字段为 ts、attempt、**session(跨会话重投时更新为手当前会话)**;msgId 与 body 不可变。

## 4. 消息种类

全集 13 种;M1 激活 8 种,S 批再激活 progress/event/cancel,X 批激活 query/report,至此 13 种全部激活。首客前破坏性清理规则见 §14;未知字段 must-ignore 的接收纪律不因冻结点前后而改变:

| kind | 方向 | 需对方 ack | 批次 | 用途 |
|---|---|---|---|---|
| hello | 手→脑 | 以 welcome/bye 作答 | M1 | 自报身份、bootId、能力、版本 |
| welcome | 脑→手 | 否 | M1 | 握手完成:分配会话、下发参数 |
| bye | 脑→手(手→脑方向 [远] 预留:优雅下线;v1 手侧终止一律直接关连接) | 否 | M1 | 拒绝握手/宣告关闭/顶替,带原因码 |
| cmd | 脑→手 | 是 | M1 | 下发命令 |
| ack | 双向 | 否 | M1 | 收妥回执:对 cmd=已解析入队;对 result=脑已持久化 |
| result | 手→脑 | 是 | M1 | 命令终局,唯一携带 data/error/evidence 之处 |
| ping | 手→脑 | 以 pong 作答 | M1 | 会话内心跳:SW 保活+半开检测+就绪度 |
| pong | 脑→手 | 否 | M1 | 心跳应答,带脑侧时钟 |
| progress | 手→脑 | 否(可丢) | S | 长命令阶段汇报,兼执行期活性;stage 为自由文本,禁止程序分支 |
| event | 手→脑 | **否(可丢)** | S | 传感提示。QoS0:无 ack、无重发、丢了无害(正确性在对账层) |
| query | 脑→手 | 以 report 作答 | X | 脑询问命令在手侧状态(歧义消解) |
| report | 手→脑 | 否 | X | 按手侧 journal/内存作答(state: unknown/queued/executing/attempting/done) |
| cancel | 脑→手 | 是 | S(随租约) | 尽力而为取消;ack 只确认请求收妥,与目标 result 赛跑时 result 赢 |

### 4.1 hello(手→脑)[M1]

```json
{ "body": {
  "handId": "h-7f3ak2m9qwe8rty0uiop", // 插件本地随机生成并稳定保存;不是凭据
  "bootId": "b-a83kd02m",         // SW 内存随机值,SW 每次出生新生成——手记忆连续性的唯一指示器
  "protoSupported": [1],
  "contractHash": "sha256:...",   // 公开摘要,仅漂移告警;不是鉴权签名
  "app": { "extVersion": "0.1.0", "browser": "chrome/126" },
  "caps": ["debug.ping@1", "chat.readThread@1", "chat.sendMessage@1"],
  "features": ["progress/1", "lease/1", "cancel/1", "witness/1"], // 独立协议特性开关(非原语)
  "witnessStoreId": "w-7d2f...", // [X] chrome.storage 证词库世代;清库后必须换值
  "outboxPending": 2,             // [X] 本次 hello 快照中等待补投的 SX result 数
  "journalOpen": 1                // [X] attempting 证词数;仅诊断,不承载业务判断
} }
```

**caps 会话不可变**:program 热更后手必须断线重连、以新 hello 重报能力(localhost 重连毫秒级,换来"会话内能力恒定"强不变量)。脑派发前查会话 caps,无能力的命令不派发、意图挂起并在 UI 呈现(能力缺口是运营事件,不是错误循环)。

**`witness/1` 是真实 SX 的硬门禁**:声明该 feature 时 `witnessStoreId/outboxPending/journalOpen` 三字段必须齐备;任一缺失即协议不就绪,脑不得派发真实 effectful。`witnessStoreId` 跨 SW/浏览器重启稳定,仅证词库首次初始化或整体丢失后换代;脑把派发时的值写入命令账本。换代后 `report=unknown` 不能证明零副作用,只能验证后转 suspect。三个字段也随 ping 搭车用于健康诊断,必须全有或全无;它们不使心跳变成业务账本。

### 4.2 welcome(脑→手)[M1]

```json
{ "body": {
  "session": "s-01JB2K1AAA...",
  "proto": 1,
  "hb": { "intervalMs": 20000, "graceMs": 50000 },
  "limits": { "maxMsgBytes": 262144, "inlineBytes": 32768 },
  "contractMatch": true,
  "now": 1768546200449,
  "sensors": { "badgeDebounceMs": 800, "badgeMinEmitIntervalMs": 5000,
               "navSettleMs": 500, "manualQuietMs": 45000 },  // [S] 传感参数由脑下发,手无自带策略数值
  "blob": { "endpoint": "http://127.0.0.1:17872/v1/blobs", "token": "bt-...", "maxBytes": 20971520 }  // [X→2026-07-28 激活] blob/1 就绪时必发;缺席=本会话未协商 blob
} }
```

握手拒绝或会话关闭走 bye:`PROTO_INCOMPATIBLE` / `SUPERSEDED` / `SHUTTING_DOWN`。Origin 不合格在 WebSocket 升级前直接拒绝,不会进入协议帧。

### 4.3 cmd(脑→手)[M1]

```json
{ "body": {
  "name": "chat.sendMessage",
  "ver": 1,
  "context": { "platform": "zhilian", "accountRef": "acc-01",
               "expectedPrincipalFingerprint": "opaque-v1-..." }, // debug.* 或首次绑定前 probe.platform 可缺省;指纹只许相等比较
  "args": { "conversationRef": "c-5f6a", "text": "..." },
  "idemKey": "ik1:zhilian:acc-01:chat.sendMessage:cand-98a7:int-01JB2K2Z",  // 仅 effectful 携带
  "deadline": 1768546801345,      // 绝对过期时刻(脑钟):手出队时与不可逆动作前一刻双查,过期即回 result(expired)
  "execBudgetMs": 60000,          // 手侧单次执行预算,超时自行中止回 EXEC_TIMEOUT_HAND;上限 240000(MV3 5 分钟强杀留余量)
  "leaseMs": 30000,               // [S] 需 lease/1;5s..120s;progress 按脑接收时刻续租,绝不越过 deadline
  "guards": { "expectedTail": [ { "direction": "in", "contentHash": "..." } ] }
} }
```

`chat.sendMessage@1` 的 guards 词汇只冻结一项:`expectedTail` 为 1..5 条 `MessageAnchor`。手在**写 journal attempting 之前**定位指定会话并冻结一份当前线程窗口,又在**不可逆动作前最后一刻**以字面同一份 evaluator 重读当前世界;两次都必须核对账号身份、路由与 `conversationRef→peer` 目标绑定,任一变化即 `GUARD_FAILED/sideEffect=none`。

**消息基线降为观测模式(2026-08-04 甲方裁决)**:`expectedTail` 与有序消息 source keys 的比对照常执行,但**结果不再拒绝发送**——比对不上时把"基线已变、尾部实际是哪几行、每行的方向"记入手侧运行日志,然后照常进入发送。本降级**不新增任何协议字段**:`data`、`evidence` 与错误码一律不动,漂移场景的事后还原依赖账本消息序列(多出来的行会被下一次读取收进账本)。本降级统一适用于全部复用本 guards 的发送原语(`chat.sendWechatInvite@1`、`chat.sendInviteCard@1`、`chat.acceptWechat@1`),只降其中一条会让多气泡链在下一步的卡片上照样断掉。降级的只有"消息基线不符即拒发"这一条判断:身份/路由/目标绑定与下句的 `composer.empty` 都是硬前置,原样拒绝;journal attempting→committed、脑账本 idemKey 去重(§7.3)、原语内不重试与发后正证一律不变。裁决依据、接受的两项后果与首客前复核义务见 AGENTS.md「防护成本预算」第 9 条末段。`composer.empty` 同为硬前置条件:页面已有用户未发送输入时必须在 attempting 前回 `USER_ACTIVE` 或 `GUARD_FAILED`,不得覆盖草稿;写入正文后还须确认当前唯一可见输入框的值精确等于待发正文。

动作前硬闸只核对两类对象:预期世界状态,以及被直接调用动作接口的公开标准语义。控件层只要求当前页面存在唯一可见 detail、输入框和发送按钮,三者满足 DOM containment;发送按钮若关联 form,其有效标准 `type` 必须为 `button`,避免一次 click 额外触发标准 submit/reset。原生 `disabled` 只会让标准 click 无效,`aria-disabled` 又不定义 click 抑制语义,二者均不作为多发/错靶/覆盖输入的安全硬闸。框架组件 owner/model、页面 SDK、渲染节点、监听器注册表、事件接线或 DOM 对象跨重绘恒等性等平台私有实现不得参与动作授权或降级为观测守卫。系统构造性保证自己的逻辑至多调用一次不可逆动作,并信任“一次标准 click 至多产生一次副作用且作用于界面所示对象”;若不接受该平台动作契约,只能削减能力或转人工,不得继续向私有实现内部追证。

preflight 与 attempting 后的 commit 必须调用字面同一 evaluator 和同一组冻结参数;commit 写入正文后仍由该 evaluator 重新核对世界状态。最后一份绿色结果后不得再读取页面、时钟或控件属性,必须立即执行唯一一次冻结的标准 click。guards 是条件写闸,不是验证结果;后置条件核验、配对 `chat.readThread@1` 与 suspect 只负责判定结果和收敛歧义,可以捕获并升级已经发生的伤害,不能补救或反向取代合法预防守卫。

M4 另激活以下三个主动建联原语，仍使用同一信封、队列与命令分发器，不新增 kind 或 feature：

- `chat.sendGreeting@1` 的 args 固定为 `{platformUserRef,positionRef,text}`，guards 固定为 `{expectUnestablished:true}`。它只对脑已持久化且关系未建立的候选人×职位执行一次；preflight 与最终动作前必须字面调用同一 greeting evaluator，核对账号、按两项不透明引用唯一绑定的可见目标、职位、关系未建立、deadline、真人输入所有权与唯一公开动作表面。任何变化都在不可逆动作前失败，不得覆盖既有弹窗，不得修改平台默认招呼设置。

**编辑器准备阶段不监听真人操作（2026-08-11 甲方裁决）**：prepare 段不得注册任何真人输入探测，一律以本命令正文覆盖编辑器当前内容。原实现在打开弹窗后于 document 上 capture 监听 `pointerdown`/`keydown`/`input`，以 `event.isTrusted` 判定真人并在命中时中止准备（失败码 `existing_editor`）；该探测整体移除。**降级的只有 prepare 段这一条判断**：打开前的弹窗计数闸、写入正文后至发送前由同一 evaluator 以正文精确相等核对的“真人输入所有权”、账号/目标/关系未建立/deadline/唯一公开动作表面与默认招呼设置核验，一律原样拒绝。因此“把真人写的正文替他发给候选人”仍不可能发生——编辑器内容与本命令正文不精确相等即失败。裁决理由有二：一是该守卫从未被真机数据证明拦到过真人（客户机 696 次招呼中 11 条 `USER_ACTIVE` 全部归因于平台拒绝后弹窗未关，即打开前的弹窗计数闸；两个来源共用同一错误码与同一错误文本，账本无法区分，只能取上界）；二是它与 CDP/OS 级鼠标输入根本不兼容——那类输入的 `isTrusted` 恒为 true，守卫会被我方自己的第一次点击触发，招呼将一条也发不出。甲方知情接受的代价：真人在“打开弹窗→选中自定义→点开编辑→写入正文”这一窗口（约 3~5 秒）内敲进同一弹窗的草稿会被静默覆盖且不可恢复，由人自行重打。本降级不改变手侧证词 journal、脑账本 idemKey 去重、原语内不重试与发后正证的任何一条。

主动建联动作仍只信任公开标准动作语义。候选人身份的私有感知通道只回答“当前是谁”，不得与组件树、SDK、VNode、listener 或事件接线互证动作授权；感知失败只能少发、转人工。

2026-07-24 的《智联主动微信请求接受事实记录》使候选人主动请求分支到期：

- `chat.acceptWechat@1` 的 args 固定为 `{conversationRef,requestSourceKey}`，guards 复用 `expectedTail`。它只接受由稳定 `sourceKey` 锚定的 `105 + in + originType=2 + success` 请求；preflight 与唯一标准 click 前必须字面调用同一 evaluator，核对账号、目标、消息基线、请求仍是唯一可见 pending 微信卡、卡片未进入 done 且唯一“同意”动作可用。成功正证是**同一张请求卡上的可见后置状态**：该卡的标准同意动作消失、卡片转入已完成形态（按可见文本判定，样式类名只作定位提示），此形态天然幂等，是 §4.5“观察到稳定后置条件”在 AGENTS.md「可见后置状态原则」下的合法实例。`259 + out + originType=2 + success` 服务端消息是**可选加成**而非成功前提：若在原语执行窗口内已到达、方向与 originType 正确且候选人与招聘方微信字段都存在，则一并返回其 `exchangeSourceKey` 与候选人 `peerWechat`；未到达不影响成功判定，号由 `chat.readWechatExchangeOutcome@1` 延迟收编。data 固定为 `{conversationRef,requestSourceKey,exchangeSourceKey?,peerWechat?,observedAt}`，其中 `exchangeSourceKey` 与 `peerWechat` 要么同时出现、要么同时缺席，且只返回候选人微信。
- `chat.readWechatExchangeOutcome@1` 是 readonly 微信交换结果专门读面，也是上述动作的配套验证读，args 为 `{conversationRef,requestSourceKey?}`。它只读真人当前已经打开且公开路由精确匹配的实时消息源，不定位、不滚动、不点击、不发送。**两种形态共用同一条结果消息判据**：`259 + success`、`from` 与 `originType` 构成两种已证实配对之一（`from=候选人 + originType=1`，或 `from=招聘方 + originType=2`）、且双方微信字段齐全；即结果消息恒归属**点同意的一方**，`originType` 恒等于**发起方**（2026-07-28 生产页面双样本直读）。
  - **带锚形态**（`requestSourceKey` 存在）是 `chat.acceptWechat@1` 的配套验证读专用形态：`requestSourceKey` 只允许锚定两种已证实请求：`105 + in + originType=2 + success` 后唯一的 `259 + out + originType=2 + success`，或 `105 + out + originType=1 + success` 后唯一的 `259 + in + originType=1 + success`；匹配结果必须在下一条 `105` 之前，且窗口内恰好一条。
  - **无锚形态**（`requestSourceKey` 缺省）是独立 ContactAsset 收编读面：不锚请求卡、不划请求窗口，在当前会话可见消息中取满足上述判据的**最新一条**。它**不得用于任何 effectful 动作的成功判定或补记**，只服务 ContactAsset 收编。立法依据（2026-08-06 甲方裁决）：平台会话面板只挂载尾部一段消息且同时报告 `reachedTop/complete`，我方无从翻页；请求卡随对话变长必然滚出该窗口，而带号的结果消息始终在尾部附近，因此锚请求卡会使收号随对话增长从延迟恶化为永久失败。真机实证一例延迟 4 小时 42 分、耗 15 次读取，其间号每一次都在窗口里。放弃的「号属于哪次请求」绑定在 235 个真实会话中零反例（每会话恰好一张请求卡）。
  两种形态匹配成立均返回 `{confirmed:true,exchangeSourceKey,peerWechat,observedAt}`，否则只返回 `{confirmed:false,observedAt}`。

`chat.acceptWechat` 的 result/evidence 只证明一次接受动作的后置状态，不追加我方出站 Message，也不得被再次投影为“候选人接受我方邀请”。可见后置状态读不到、读不清、目标换绑、路由或身份复核失败都只进入未确认/专门 outcome 读/suspect，绝不授权第二次 click。可选的 259 加成另有更严的收编闸：零匹配、多匹配、方向或 originType 不符、双微信字段不全时一律**不取号**（`exchangeSourceKey` 与 `peerWechat` 一并缺席），但这些只影响取号，不推翻已经成立的可见后置状态正证。

冒烟冲刺新增 `candidate.readSourcingResume@1`，用于漏斗前段一次读取一位采集候选人。命令 args 固定为 `{excludePlatformUserRefs}`，其中排除列表最多 32 项且脑只作不透明值回传；成功 data 固定为 `{platformUserRef,displayName,positionRef,positionTitle,contactState,observedAt,basic,expectations,selfEvaluation,education,workExperiences}`，展示字段 nullable 且不参与身份或动作判定，五个简历分区与 `candidate.readResume` 同义。原语可在当前明确的采集页面打开一个未排除目标，因此 class 为 `intrusive`、`platformSideEffect=idempotentReadReceipt`；读取完整并再次核对目标绑定后，必须关闭本命令使用的详情，确认弹框消失且 URL 不再携带 `resumeNumber` 才可返回 ok。关闭无法确认时整体失败且不返回部分 data。它不得点击招呼、电话、筛选确认或任何候选人可见动作。身份与职位必须来自已经真机证明的稳定不透明来源，`resumeNumber` 只可在手内瞬时连接列表与详情；缺失、重复、换绑、结构不完整、载荷超限或没有可采目标均整体失败，不返回部分 data，也不得以姓名、`resumeNumber`、列表序号或 DOM 位置降级。

M6 正式批采不再用扩大 `excludePlatformUserRefs` 的办法承载全批去重，并新增采集前职位与筛选对齐能力，共四个平台无关原语：

- `job.takeOffline@1` 的 args 固定为 `{jobName}`，成功 data 固定为 `{jobName,offlineVisible,verifyRounds,platformFeedback,observedAt}`，guards 固定为 `{expectOnlineOnPlatform:true}`，evidence 为 `platformPostingOffline`，配对验证读为 `job.readPublishedList@1`（最多 3 轮，脑侧验证器按「该职位名是否已不在『在线中』分区」判定，与幂等口径共用同一套归一化；它不读会话尾部、也不比对发送指纹）。它把一个已在线的职位**下线**，立案于甲方 2026-08-13 裁决「发布完之后立刻下线」。它与 `job.publishDraft@1` 是**两条独立原语、两条独立意图**：发布成功而下线失败时，已发布那笔账原样成立、不受下线结果影响。甲方同日明确本动作**只是锦上添花、失败记一笔即可**，因此它是全部 effectful 原语里**唯一不产人工票据**的一个——脑侧收束不进 suspect 队列、不冻结人工裁决，未确认即终局失败并留审计。这不放宽任何其他原语的失效方向：下线失败的后果是职位仍在线，方向是「少做了下线」而非多做副作用，且平台上重复下线不可能发生（已下线的行根本没有下线入口），与消息类原语的多发风险不是一类。执行顺序固定为「导航到职位管理页 → 切到『在线中』分区并等其渲染完整 → 按 `jobName` 在该分区内找**唯一**匹配行 → 点该行的下线入口 → 等二次确认弹层出现 → 点弹层的确认 → 回读列表取正证」。真机事实（2026-08-13 只读考古加一次真实下线，测试职位）：行是 `div.job-list > div.job-item`、职位名在 `a.job-item__title--jobname`（与 `job.readPublishedList@1` 同一套选择器），下线入口是行内 `a[zp-stat-id=job-action-offline]`；**点它只打开弹层、不产生任何副作用**；弹层是全局单例 `.km-modal.km-modal--open.km-modal--message-box`，文案「确定要下线该职位吗？」**不含职位名**，确认按钮是 `button.km-button--primary`（文案「下线」）。页面里同时存在数十个 `.km-modal` 且数量随操作增减，判别弹层是否打开**只能靠 `km-modal--open` 且可见**，绝不能靠存在性或计数。**弹层不含职位名意味着确认层做不了目标绑定**：绑定必须在点下线入口那一刻凭同一个 DOM 行锁死，点开弹层到点确认之间不得重读列表、不得重新定位；这道口子由「『在线中』分区内同名职位唯一」这条硬前置封住——匹配到两条同名一律干净失败，绝不猜。**点确认按钮之前的任何失败一律 `sideEffect=none`**（职位仍在线，可安全重来），点确认之后一律 `possible`；原语内绝不重试、绝不第二次点击，弹层不按预期出现即按 `none` 干净失败。成功正证是点击后回读职位管理页、`jobName` **不再出现在『在线中』分区**——不要求它出现在「未上线」，下线后落哪个分区是平台的事，不在线才是本原语的目标；真机实测下线后在线中计数减一、未上线计数加一、该行带「手动下线」标签，标签纯诊断、不作判据。读不到正证只记未确认，不得推断失败、不得再次点击。`platformFeedback` 只收录下线后页面可见的提示原话，纯诊断，不参与判定。
- `candidate.readSourcingTargetResume@1` 的 args 固定为 `{platformUserRef,positionRef}`，data 与 `candidate.readSourcingResume@1` 相同。它只读取当前推荐窗口中唯一匹配两项不透明引用的目标，不搜索、不滚动、不改筛选；目标零个、多个或任一引用换绑均整体 failed。成功仍须读取完整五分区、再次核对目标绑定、关闭本命令使用的详情，并确认弹框消失且 URL 清除 `resumeNumber`。打开详情可能产生幂等已查看记录，但不得产生候选人可见消息。

批次 0B 已把 `candidate.readResume@1` 写死为 `intrusive/platformSideEffect=none`：preconditions 为账号上下文、`surface.im`、`login.in`、`conversation.tracked` 与 `manualQuiet`，进入账号串行域，执行预算 60s、deadline 120s、lease 30s；不设 idemKey、guards、evidence 或 verification。平台 program 可使用经真机事实确认的数据通道，但失败方向只能是“不确认→failed→人工”。合法完整 data 必须落在现有 64KiB 内联上限内；超限使用 `PAYLOAD_LIMIT` 并转人工，不截断、不分页，也不在 M5 偷渡 blob。

`account.readWechatSetting@1` 是空 args 的账号配置读面(2026-08-18 甲方裁决立案),固定 `intrusive/platformSideEffect=none`、30s/60s/30s,成功 data 固定为 `{configured,observedAt}`,preconditions 为完整账号上下文、`login.in` 与 `manualQuiet`。它读取招聘方账号在平台上的**微信号联系配置是否已填**,供脑在用户显式开始工作流(全流程/只回复)前裁决放行:平台换微信链路把个人中心配置的微信号发给同意交换的候选人,配置空着时邀请发出后无号可给,候选人被无效打扰——此前该项只存在于《新用户开机手册》的人工 checklist。智联实现:导航平台页到个人中心,条件轮询等「微信号」栏渲染(最长约 10 秒,遵守条件等待纪律),按**可见文本**判定——值非空且非「暂未添加」占位即 `configured=true`,占位、为空或该栏存在可见「去添加」动作即 `false`。判据依据 2026-08-18 真实登录页面考古:同组件的未配置形态(以邮箱栏实测)值元素**依然存在**、仅显示占位文本,故「元素出现与否」不构成判据,必须读文本;栏已渲染但值区尚未呈现任何决定性形态时继续轮询,不把渲染中间态误读成未配置。栏渲染等不到、页面/路由不可达、读取异常一律整体 failed,不返回猜测;脑侧对 failed 与 `configured=false` 同向处理(拒绝本次开始),失效方向永远朝少做,误拦由用户按提示在平台补配置后重试收敛。**data 刻意只含布尔,绝不携带微信号本身**——招聘方自己的微信号不进契约、不进 evidence、不进日志的既有禁令原样适用。本原语唯一页面动作是导航,不点击、不滚动、不打开弹层、不修改任何配置;读完不负责导航回原页面,后续页面需要由既有恢复路径(`nav.ensureSurface`)重建。它的读数只授权「本次开始请求放行与否」这一个裁决,不得复用为任何 effectful 动作的前置正证、验证读或业务状态依据。不新增消息 kind、feature、event、错误码、guards/evidence、witness 版本或领域持久化。

手侧执行模型:**全局严格串行**,先 ack 入队,FIFO,深度 16,满则 ack 拒绝 QUEUE_FULL(背压)。只有协议/session/caps/schema/队列类问题走 ack(rejected)。命令在收帧时已经过 deadline 仍先 ack(accepted),随后从队列的“不可执行终局”分支回 result(expired),**绝不调用原语 handler**;accepted 后才发现页面、账号、用户或目标问题一律 result(failed)。

### 4.4 ack(双向)[M1]

```json
{ "body": { "ref": "01JB2K3G8X...", "status": "accepted" } }
```

- status:`accepted` / `rejected`(附 §10 错误对象,此层错误恒 sideEffect=none)/ `duplicate`。
- 对 cmd:accepted=已解析、schema 过验、已入执行队列(**不是**开始执行,更不是完成)。
- 对 result:accepted 与 duplicate **等价**——皆表示脑侧已持有该终局,手删除队列条目(否则补投会循环到 SW 死亡,挤占队列)。
- **去重不等于沉默**:重复到达必须重新 ack(duplicate);若该 cmd 已有终局,补发一份 result(replayed=true)——Stripe 式结果重放。

### 4.5 result(手→脑)[M1]

```json
{ "body": {
  "ref": "01JB2K3G8X...",
  "status": "ok",                  // ok | failed | canceled | expired(四者皆终局;拒收在 ack 层)
  "data": { },                     // ok 时与 dataBlobRef 恰有一个;内联按原语 dataSchema
  "dataBlobRef": null,             // blob/1:完整 data JSON 的 sha256 内容引用,取回验哈希后再跑 dataSchema
  "error": null,                   // failed 时必填,§10
  "evidence": [ { "type": "outboundMessageObserved" } ],  // chat.sendMessage ok 必填;对脑不透明
  "replayed": false,
  "execMs": 6890
} }
```

effectful 的 ok 定义为**观察到稳定后置条件**,"我触发了动作"、编辑器清空、乐观渲染或只有平台本地临时 ID 的缓存记录都不算(宪法原文)。生成的 `validatePrimitiveResult` 按具体原语强制 data/evidence schema;`chat.sendMessage@1` 必须在动作前冻结当前目标绑定的服务端消息基线,后续每轮观察仍须匹配该目标。只有相对基线**恰好新增一条**服务端确认记录,且该唯一记录为我方 `text`、`contentHash` 与发送正文相等时才可 ok。零新增、多新增、并发入站、明确失败与成功并存、目标换绑或读不清均只算阴性;歧义恢复只使用配套 `chat.readThread@1`。

目标绑定证词只表示本轮各次读取仍指向同一界面所示会话,不证明平台私有框架、SDK 或事件接线正确。系统构造性保证自己的逻辑对公开标准动作接口至多调用一次;平台把一次标准动作重复执行或送往其他目标属于被信任动作契约的违约。即时 observer、配对验证读与 suspect 可以发现并升级阴性结果,但不能撤销已经发生的伤害,因此任何阴性都禁止第二次动作。

正文 hash 与 `ThreadMessage` 文本采用同一算法:Unicode NFC、trim、所有 Unicode 空白串折叠为单个 ASCII 空格,再做 SHA-256 小写 hex。除契约明确声明、只作等值比较的不透明 `platformUserRef/positionRef/conversationRef` 与下述 `sourceKey` 唯一例外外，平台私有 ID 只在手内用于证词判定或脱敏 evidence，不进入脑侧业务 data；result/data/evidence 与手侧证词均不得回抄消息正文。

`ThreadMessage.sourceKey` 是 optional 的不透明平台消息等值键，只允许在平台已经取得稳定服务端消息身份时产生。配方冻结为该身份原始字节串前加 ASCII 版本域 `source-v1|` 后作 SHA-256 全量摘要，输出 64 个小写 hex 字符，即 `sha256("source-v1|" + 平台稳定消息身份)`；配方改变必须换版本前缀，旧 key 不迁移。原始平台消息身份永不离开手。脑不得解析、反推或把 `sourceKey` 写入日志、evidence、管理接口、UI、报告或其他对外面，只能在同一 `platform+accountRef+conversationRef` 内作相等比较与持久化；数据库唯一范围固定为 `(platform,accountRef,conversationRef,sourceKey)` 的 nullable 唯一索引，不得全局唯一。合法用途只包括消息去重、存量历史收编、同会话卡片事实/回执关联、同会话文本发送回执关联与认领，以及卡片原语参数或结果的本地持久等值比较；字段名可为 `sourceKey/requestSourceKey/exchangeSourceKey`，均表示同一种不透明键。禁止跨会话比较、充当候选人身份或平台 ID 替代、独立动作授权、wire `idemKey` 或对外诊断字段。相同 `sourceKey` 的 `direction/kind/cardType/contentHash` 任一冲突时必须立即转人工，禁止追加消息或进入零重叠重建；可变 `cardState` 不参与冲突判定。`kind=system` 的行不作语义证词（2026-08-11 甲方裁决）：同 key 行对中任一侧为 `kind=system` 时不参与本句冲突判定——system 是「未能识别」的自白而非对平台事实的声明，其 `text/contentHash` 由手侧兜底拼装，随解析实现演进而变化属预期，不构成平台事实变化的证据（立案实例：2026-08-10 插件换代使同一条系统消息的兜底文本从抄邻行变为 `[系统消息:99]`，同 key 异 hash 触发本闸，一个活跃会话自此每轮对账整体作废、新入站消息永不入账）。该类行仍凭 `sourceKey` 参与去重与已知身份判定，同 key 的后续观察（含解析改进后呈现为 text/card 形态）不追加新行、不改写既有账本行；既有的尾行误归类修正路径不受影响。

卡片 `contentHash` 只覆盖平台无关的不可变业务投影，不含微信号、cardState、平台消息身份或 `sourceKey`。M5-B 当前开放的精确配方如下，所有字面片段、分隔符和十进制格式均为 ASCII；时间戳使用无前导零的 Unix epoch 毫秒十进制：

- 已可靠归一化的 `wechatExchange`：`sha256("card\x1fwechatExchange")`；
- 已可靠归一化的 `interviewInvite`：`sha256("card\x1finterviewInvite\x1f" + startsAt + "\x1f" + endsAt + "\x1f" + method)`，其中 `endsAt` 缺席时投影为空串（分隔符位数不变），`method` 取实际归一化值。`wechatVideo` 卡的投影结果与本条改写前的旧配方逐字节相同。

平台无法可靠映射完整业务投影的旧卡或未知卡不得用于新卡片动作的成功正证；其历史兼容 hash 只作本地账本锚，不得冒充上述规范配方。[M5-A/2026-07-22、M5-B/2026-07-23 甲方裁决]

`ThreadMessage.interview` 是 optional 的平台无关邀面参数 `{startsAt,endsAt?,method}`，只可用于 `kind=card && cardType=interviewInvite`；时间为 Unix epoch 毫秒。`endsAt` 本身也是 optional：平台明确给出结束时间时必须填写且 `endsAt > startsAt`；平台对该形态不提供结束时间（当前已知：线下到场面试，平台恒返回 `0`）时必须省略，不得由 `startsAt` 合成。当前 `method` 开放 `wechatVideo` 与 `onsite`。旧消息或无法从真实平台事实可靠映射其余参数的卡片必须整体省略该字段，不得猜值。`peerWechat` 不进入 `ThreadMessage`，也不参与 `contentHash`。

候选人微信号属于本地业务资产。获准的交换结果原语可在 result data 中返回 trim 后非空且有界的 `peerWechat`，但不得返回招聘方自己的微信号；它只允许继续存在于手侧既有 journal/outbox 生命周期、不可变 `CmdRecord.ResultBody` 审计快照和脑内权威 `ContactAsset`，不得进入 evidence、错误、stdout、普通日志、审计 detail、管理 API/UI、报告或 AI 请求。脑收编成功后以 `ContactAsset` 为业务权威，不解析命令审计快照来重建资产。

`chat.sendGreeting@1` 的 ok 接受事先定义且与本次目标明确绑定的可见业务后置状态：动作前同一 `platformUserRef+positionRef` 唯一处于“关系未建立”，唯一标准动作后同一目标明确变为“关系已建立”。智联已验证的具体形态是：同一稳定身份目标的唯一“打招呼”变为唯一“继续沟通”；M4 历史入口位于候选人详情，M6 正式入口位于推荐列表卡片。一次命令只能使用当前里程碑批准的一个动作表面，不得在两者间猜测切换。该目标变化本身足以确认招呼动作成功；稳定 `conversationRef` 与服务端消息行是可用时的丰富正证和后续会话收编材料，不再是动作成功前置。页面跳转、弹窗消失、输入清空、配额变化、无关按钮变化、乐观消息或本地临时 ID 仍不足以成功。

其成功 data 固定为 `{platformUserRef,positionRef,conversationRef?,contentHash,observedAt}`，每个 evidence item 固定为 `{type:"outboundGreetingObserved"}`；`contentHash` 表示本命令唯一受控动作携带正文的指纹，不声称必然从 IM 消息行回读，正文不得进入 data、evidence、journal 或 outbox。`chat.readGreetingOutcome@1` 按 `{platformUserRef,positionRef,contentHash}` 复读同一目标的关系后置状态：`confirmed=true` 时 `contentHash` 必须存在并匹配，`conversationRef` 仅在同次观察可稳定取得时返回；`confirmed=false` 时二者必须同时不存在。页面无变化、目标消失或状态读取失败只能表示本轮未取得充分正证，绝不证明未发送，也绝不授权第二次动作。

`chat.sendMessage@1`、`chat.sendWechatInvite@1` 与 `chat.sendInviteCard@1` 的成功 data 另可携带 optional 的 `tsApprox`（Unix epoch 毫秒，2026-08-06 立案）：它是本次唯一命中的出站消息在平台消息视图中展示的时间戳，与 `ThreadMessage.tsApprox` 同源同义，仅当平台数据提供可解析时间时携带；缺失即表示无平台时间证据，手不得以本机时钟合成。该字段只作账本时间维度的事实收编，不参与成功判定、验证比对或任何发送授权；`observedAt` 语义不变，仍是手完成观察的本机时刻。`chat.sendGreeting@1` 不携带此字段：其成功正证来自推荐页关系状态变化，该表面没有消息视图，无平台时间证据可采。

`chat.sendMessage@1` 的成功 data 另可携带 optional 的 `sourceKey`（2026-08-09 立案）：它是本次唯一命中的出站消息按本节配方派生的不透明等值键，与 `ThreadMessage.sourceKey` 同源同义。即时观察路径命中唯一新增行时必须携带；2026-08-03 乐观判定例外路径无页面观察，不携带，故字段为 optional。该字段只作回执与既有账本行的等值关联、认领与持久化，不参与成功判定、验证比对，也不构成任何发送授权；验证读的成功判据不变。`chat.sendGreeting@1` 不携带此字段：其成功正证来自推荐页关系状态变化，该表面没有消息视图，无消息身份可采（与 `tsApprox` 同款排除）；招呼消息行的身份由后续 `chat.readThread` 收编时从快照取得。

`chat.sendWechatInvite@1` 的成功 data 固定为 `{conversationRef,contentHash,sourceKey,observedAt}`，evidence 只含 `{type:"outboundWechatInviteObserved"}`；`chat.sendInviteCard@1` 另回显 `interview`，evidence 只含 `{type:"outboundInterviewInviteObserved"}`。两者的 `contentHash/sourceKey` 都只作不透明等值比较；正文、微信号、平台消息身份与私有卡片 ID 不得进入 data/evidence。`chat.acceptWechat@1` 的 evidence 只含 `{type:"candidateWechatRequestAcceptedObserved"}`，`peerWechat` 只允许出现在该原语或专门 outcome 读的 typed result data，并受本节 ContactAsset 边界约束。验证读阴性只表示未确认，服从与 `chat.sendMessage` 相同的“绝不补动作”语义。

### 4.6 ping / pong [M1]

```json
{ "kind": "ping", "body": {
  "queueDepth": 1,
  "inFlight": "01JB..." ,          // 正在执行的命令 msgId,无则 null
  "contexts": [],                  // [S] 各账号上下文就绪度 { platform, accountRef, ready, reason }
  "sensors": null,                 // [S] 只运缓存现货(如 unreadTotal),禁止心跳到点反向拉取 DOM
  "witnessStoreId": "w-7d2f...", "outboxPending": 0, "journalOpen": 1 // [X] 仅计数诊断
} }
{ "kind": "pong", "body": { "now": 1768546220003 } }
```

ping 由完成握手的手发起,间隔 `hb.intervalMs`(默认 20s)±20% 抖动,一石三鸟:WS 活动保活 SW(<30s);手凭 pong 缺失(连续 2 次)检测半开连接并主动重连;携带就绪度供脑健康模型。**心跳不携带业务数据**——sensors 只是缓存读数转发,心跳变胖=健康信号失真。hello/welcome 之前没有会话心跳;握手由独立的 10 秒 helloTimeout 约束。

### 4.7 progress / 租约 / cancel [S]

三项分别用 `progress/1`、`lease/1`、`cancel/1` 协商;脑不得因手只支持其中一项就推断另两项。`chat.readList`、`chat.readThread` 等声明 `leaseMs` 的原语只有在三项所需能力齐备时才可派发。

```json
{ "kind": "progress", "body": { "ref": "cmd-msg-id", "stage": "page 3", "pct": 40 } }
{ "kind": "cancel", "msgId": "cancel-msg-id", "body": { "ref": "cmd-msg-id", "reason": "leaseExpired" } }
{ "kind": "ack", "body": { "ref": "cancel-msg-id", "status": "accepted" } }
```

- 租约从脑收到目标命令的 ack(accepted) 的本地单调时刻开始;每条**schema 合法、ref 指向仍在途命令、来自该手当前物理连接**的 progress 以脑接收时刻续到 `now+leaseMs`,但永不越过绝对 deadline。该 progress 可保留目标命令创建时的旧 session;旧物理连接、迟到、未知 ref、已终局命令的 progress 只记审计,不复活命令。`stage` 仅人读,`pct` 可缺省且范围 0..100,二者都禁止用于程序分支;合法 progress 与 ping 一样刷新手的 lastSeen。
- 租约 gap 到期代表本次物理尝试失联,不是业务终局:脑先发唯一 cancel,保留 1000ms 的有界 result 竞态窗;窗内目标 result 先到则 result 赢。竞态窗后仍无 result,readonly/intrusive 才按 §8 作废并进入 replacement chain,effectful 进入 suspect。竞态窗不延长绝对 deadline,progress 不能把 deadline 后移。
- cancel.body.ref 指向**目标 cmd**;cancel 自己的 ack.ref 指向**cancel 帧 msgId**。queued 目标直接移出执行候选并回目标 result(canceled);executing 目标在取消安全点前协作中止并回 result(canceled);越过安全点只记录取消请求,照常完成目标 result。ack(accepted) 只表示请求已收妥,不证明取消成功;无论竞态顺序,目标 cmd 的首个合法 result 赢并成为唯一终局。
- cancel.reason 是机器枚举:`leaseExpired | deadlineImminent | superseded | operator | shutdown`;不得用自由文本决定行为。`leaseExpired` 是当前自动生产值,`operator` 为未来显式人工取消来源预留,其余三值为 deadline 临界、命令替代和服务退出的确定性生命周期来源预留;手不按 reason 分叉取消语义,但日志保留来源。因此五值都是 cancel 控制面的正式词汇,不是可删化石。

### 4.8 query / report [X]

```json
{ "kind": "query", "msgId": "query-msg-id", "body": { "ref": "target-cmd-id" } }
{ "kind": "report", "msgId": "report-msg-id", "body": {
  "ref": "target-cmd-id", "witnessStoreId": "w-7d2f...", "state": "attempting",
  "result": null,
  "journal": { "ref": "target-cmd-id", "idemKey": "ik1:...", "state": "attempting", "startedAt": 1768546203000 }
} }
```

query/report 是 base 投递层对账,不是 program 原语,不进业务 FIFO、不触碰页面。query 的 `ref` 指向要询问的 cmd;report 的 `ref` 仍指向该目标 cmd而非 query 消息。report 可丢且无 ack;脑未收到可重新 query,手每次从当前内存/journal 重新构造 report。两者必须使用当前 session 和当前物理连接,不得跨连接采信。

| state | 强制字段 | 可以推出的事实与唯一动作 |
|---|---|---|
| `unknown` | `result=null,journal=null` | 当前内存和指定 `witnessStoreId` 的 journal 均无目标。**仅当 storeId 与派发时一致**才是“未越过 attempting 写点”的零副作用证明,允许安全重投原 msgId;storeId 换代/未知则不能证明,走验证后 suspect |
| `queued` | `result=null,journal=null` | 同一 boot 内仍排队、尚未写 attempting;等待原执行或 cancel,不得并发另发 |
| `executing` | `result=null,journal=null` | handler 正执行但尚未越过 attempting 写点;继续等待 result/下一轮 query,不得重发 |
| `attempting` | `result=null,journal.state=attempting` | 已持久写提交前证词,是否发生副作用不确定;命令未终态期间占用串行域并走验证,绝不重发 |
| `done` | 完整 `ResultBody` + `journal.state=committed` | 直接按 result 终局入账;ref 与账本命令、journal.idemKey 与账本 idemKey 必须逐项相等,不等即证词损坏并转人工 |

生成 validator 强制 `done` 的 result/journal 非 null、`attempting` 的 journal 非 null且状态匹配、其余状态禁止夹带二者,并强制所有内嵌 `ref` 等于 report.ref。attempting journal 只含 `ref/idemKey/state/startedAt`,**不得含 args、消息正文、guards 或业务决策输入**。

## 5. 确认层级:每层能推出什么 [M1]

| 层 | 信号 | 能推出 | 不能推出 |
|---|---|---|---|
| L0 | WS write 返回 | 字节进本端缓冲 | 对端收到 |
| L1 | ack(accepted) | 手收到、过验、入队 | 会被执行、会成功 |
| L2 | result 终局 | 手的终局判断+副作用标注+证据 | 平台真把消息投给了候选人 |
| L3 | 脑的业务核验(readonly/intrusive 对账回读)[X] | 逼近平台侧真相 | 绝对真相 |

端到端论证:低层确认永远不能替代高层核验。L1 缺失按投递问题处理(§7);L2 缺失按执行问题处理;L3 不通过**不自动重发,只转人工**。

## 6. 命令分类学 [M1 定义,S/X 逐批启用]

三类,契约静态声明,**按最坏实现定级**(声明从紧无害,从宽踩页面):

| class | 定义 | 重试/重派 | 排队 | idemKey | evidence |
|---|---|---|---|---|---|
| `readonly` | 不驱动页面、无平台侧效果的纯探测 | 自由重派(新 msgId 同 args),有轮次封顶 | 不进账号串行域 | 禁止 | 不需要 |
| `intrusive` | **业务只读或声明式幂等**,但驱动/占用页面;平台侧效果至多是一次性幂等的(已读回执、页面就位) | 同 readonly:自由重派安全 | **进账号串行域**(与 effectful 同队互斥,跨手生效) | 禁止 | 不需要 |
| `effectful` | 不可回滚、可叠加的外部副作用(发消息、发卡) | **永不自动重派**;只有 journal 在同一 storeId 下明确 `unknown` 的提交点前零副作用证明允许重投原物理命令;其余歧义→验证→suspect | 账号串行域 | 必填 | ok 必填且按原语 schema 强制 [X] |

归类判据(litmus,写进契约注释):执行两次与一次对候选人可感知世界无任何额外差别、且不发出任何业务内容→看是否驱动页面:驱动=intrusive,不驱动=readonly;否则=effectful。**拿不准=effectful**(与 sideEffect"拿不准标 possible"同一保守方向)。

intrusive 原语须另声明 `platformSideEffect: "none" | "idempotentReadReceipt" | "idempotentPhoneReveal"` 供审计(第三值 2026-08-07 甲方裁决新增,语义见「候选人电话揭示契约增量」)。intrusive 单列的原因(C 卷 §4.2):判成 readonly,重派会踩掉同账号在途发送的页面;判成 effectful,"结果未知态的验证读"陷入循环依赖。

原语注册六要素:`name、ver、class、argsSchema、dataSchema、preconditions`;真实 effectful 另强制 `guardsSchema、evidenceSchema、verification{primitive,ver,maxRounds}`。这些元数据与 Go/TS 的 guards/evidence/result validator 一并由 codegen 生成,两端不得手写旁路。外加纪律第七条:**原语实现内部禁止自主重试**——原语=单次尝试+观察后置条件+诚实上报,重试决策归脑(旧系统"点击后重试一次"的修复移植时必须剥离内部重试,否则两层重试相乘)。

**debug 串行域**:debug.* 的 intrusive/effectful 命令进该手专属的 `debug` 串行域(每手一个,与账号域平行,规则同款);测试页命令同样经脑铸造意图行,idemKey 照常派生(§7.4 debug 形态)。

## 7. 投递保证、重传与幂等

### 7.1 选型 [M1]

- 命令通道:**至少一次投递 + 手侧去重 = 有效一次入队**。
- 执行语义:readonly/intrusive 至少一次(可重派);effectful **在歧义处降为至多一次**(宁可少发)。
- 上报通道:result 至少一次(内存队列重发直到脑 ack;[X] 起 SX 的 result 另有持久 outbox)+ 脑按 msgId 持久去重(processed 表 30 天)。
- 不追求恰好一次:两将军定理;QoS2 只保 broker-client 报文不重,应用崩溃照样重复,纯付费迷信。

### 7.2 重传规则(同 msgId)[M1]

**同一条存活的 localhost TCP 连接上永不重发帧**——loopback 不丢包;送达了没 ack 说明手内部卡死,再塞一帧只是多一条日志(B 卷 1.2)。规则:

1. ackTimeout(3s)内**无任何应答**(连 rejected 都没有)→ 判连接可疑 → **脑主动关闭连接**,触发手侧重连。本规则与反模式 19 只约束"无应答的帧"。
2. 帧重发只发生在**重连之后**,且仅当新 hello 的 `bootId` 与派发时记录一致(手记忆连续,去重表有效,重复投递被吸收);重发帧的 session 更新为新会话(§3 重传纪律)。
3. bootId 变了:readonly/intrusive 重新派发(新 msgId);无 `witness/1` 的 effectful 一律 suspect。真实 SX 按 §9 四阶段对账:只有 `witnessStoreId` 与派发记录一致且 report=unknown 时才获得“attempting 写点前死亡”的零副作用证明,可重投**原 msgId**;attempting、storeId 换代、report 缺失/损坏均先验证后 suspect,绝不盲重发。
4. **ack(rejected) 是应答,不是歧义**:对 readonly/intrusive,瞬态拒绝(QUEUE_FULL 退避后、STALE_SESSION 换会话后)允许同 msgId 再投,同一连接亦可(它有应答,不属"无应答帧重发");协议性拒绝(PROTO_*)记 rejected 终局。**真实 SX 不使用这条瞬态重投通道**:任何 receipt rejected(包括 STALE_SESSION/QUEUE_FULL)都终局化物理命令与原意图,之后只能由人确认并另铸新意图。真实 SX 的唯一自动恢复通道是§9 在与派发时相同的 `witnessStoreId` 下得到 `report=unknown`,然后重投原 msgId。

### 7.3 手侧去重与队列 [M1]

- **收帧管线顺序(固定,不许重排)**:信封/body 结构校验 → **msgId 去重**(命中即 ack(duplicate),有终局则重放 result,**不再看 session**)→ session 校验(**仅受理时刻生效**:已 accepted 的命令跨会话继续执行,其首次 progress/result 即使携带命令创建会话也照常入账；持久信封跨会话补投则更新为当前 session；脑侧始终以当前物理连接为不可放松的来源围栏)→ caps/features/原语版本 → args + guards schema → **deadline 时间分支**:若已过期,直接写去重表、ack(accepted) 并进入不占 FIFO 容量的终局队列回 result(expired);否则检查队列容量 → 写去重表并 ack(accepted) → FIFO 执行候选。**只有 ack(accepted) 的命令才进去重表**,被拒命令不入表(只为 readonly/intrusive 瞬态拒绝后同 msgId 再投留路;真实 SX 在脑侧已终局化)。deadline 的字段类型仍在 schema 阶段校验;时间已过永不因 QUEUE_FULL 改成 rejected,handler 调用次数必须为 0。
- **去重表:内存 LRU 256,作用域=SW 一次生命(bootId)**,键=msgId(idemKey 冗余记录),值含终局 result 缓存。命中即 ack(duplicate)+必要时重放 result。**严禁把这张 LRU 写入 chrome.storage**——普通投递层的同 id 重发只发生在 bootId 未变时,由内存去重吸收；真实 SX 另有且仅有 §9 的跨 boot 例外：同一 `witnessStoreId` 的 report=unknown 给出 attempting 写点前零副作用证明后重投原 msgId。该例外不依赖旧内存 LRU，而由 journal 入队前闸与脑账本共同围栏，不能推广为一般同 id 重传。
- 断线不弃队:已 accepted 的命令在 SW 存活期间继续执行(deadline 出队双查防僵尸);R/I result 进内存有界队列(50 条,result 优先),重连即冲,SW 死即丢(由脑侧 WAL 兜底);真实 SX result 必须先进入持久 outbox,不得降级到仅内存队列。
- 去重先于一切副作用:msgId 表与真实 SX 的 idemKey journal 查询发生在入队前。journal 命中 attempting 时绝不再进 handler;命中 committed 且 ref 相同则重放缓存 result;同 idemKey 却 ref 不同是脑账本闸失效的严重告警,保证零新副作用并转人工。

### 7.4 幂等键(idemKey)[M1 格式,X 启用]

```
ik1:{platform}:{accountRef}:{primitive}:{targetRef}:{intentId}    业务形态
ik1:debug:{handId}:{primitive}:{targetRef}:{intentId}             debug 形态(测试页命令同样经脑铸意图行)
```

- **脑生成、从业务意图行确定性派生**(intentId=脑 SQLite 意图主键)。同一意图无论重发多少次、脑重启多少次,键恒同——比 Stripe 随机键更强:把"忘了复用"这种人祸也灭掉。
- 粒度=意图,不是"候选人+动作"全局唯一(隔天跟进是新意图新键);粒度裁决权在脑业务层。主动建联的具体形态为 `ik1:{platform}:{accountRef}:chat.sendGreeting:{profileId}:{intentId}`；`profileId` 是脑内 targetRef，不进入线上 args、data 或 evidence。
- 仅 effectful 携带;readonly/intrusive 禁止(避免假安全感)。

脑内命令生产者可以是真人确认入口，也可以是经批准的确定性自动状态机。自动生产者必须先持久化唯一业务动作事实，并从该事实主键确定性派生 `intentId`；重复巡检、进程重启或 AI 回包重放只能取回同一动作与同一 intent，不得按当前时间另造。一次业务动作至多绑定一个 effect intent。生产者身份不进入线上协议，也不改变 WAL、head/CAS、idemKey、witness、guards、验证、suspect 与 contract mismatch 双闸。

### 7.5 幂等三道闸 [X 全部就位]

1. **脑账本闸(权威)**:intents 表 UNIQUE(idemKey);派发前查账本,已有非失败终局或 suspect 冻结中的意图,拒绝铸造新命令。手侧全丢也拦得住。
2. **手证词闸(缩窗)**:§9 journal——SW 死于执行窗口的任意点,后果只可能是少发+人工,不可能多发。
3. **平台回读闸(L3)**:按真实 effectful 分支冻结基线并取得正证。`chat.sendMessage` 以 `expectedTail` 对当前目标绑定的服务端消息视图做条件写，歧义恢复用 `chat.readThread`；`chat.sendGreeting` 以候选人×职位“关系未建立”为基线，歧义恢复用 `chat.readGreetingOutcome` 确认同一目标已经明确变为“关系已建立”，会话引用与消息行可在后续巡检收编。动作前的账号身份、路由与目标绑定变化即停手；消息基线(`expectedTail`)变化自 2026-08-04 起只记录不停手(§4.3 `chat.sendMessage@1` guards 条款下的「消息基线降为观测模式」)；动作后按 2026-07-29「成功=发后页面可见」裁决补记成功(判据见 §9.4:方向、内容与本次动作一致、无失败标志、时间不早于本次派发,同文取最新一条)，阴性与读取失败只转人工，均不得授权动作。

重复发送需三道闸同时失效,而每道闸单独失效的后果都是"少发+人工"。

## 8. 命令生命周期、超时矩阵与 suspect [M1]

### 8.1 脑侧账本状态机(SQLite 持久)

**先记账后发送**:命令必先以 `queued` 落库(在途日志:msgId、name、class、idemKey、bootId@dispatch、deadline、状态)再进 socket。脑的账本永远是手所见命令的超集。

```
queued → sent → accepted → ok | failed | canceled | expired   (result 为准)
   sent --ackTimeout(无应答)--> (关连接,待重连按 §7.2 处置)
   sent --ack(duplicate)--> 视同 accepted
   sent --ack(rejected, 协议性 PROTO_*)--> rejected(终局)
   sent --ack(rejected, 瞬态 STALE_SESSION/QUEUE_FULL)--> readonly,intrusive: queued(待同 msgId 重投,非终局)
                                                         真实 effectful: rejected(终局;意图同步 failed)
   accepted --lease gap [S]--> readonly,intrusive: void(可铸 replacement)
                               真实 effectful: reconciliation gate(冻结,§9);无 witness: suspect
   任何非终局 --deadline+宽限 过 / bootId 换代 / 脑重启扫描--> readonly,intrusive: void(作废,巡检自然重派)
                                                            真实 effectful: reconciliation gate
   reconciliation --outbox/done--> result 终局
                  --same storeId + report=unknown--> 原 msgId 安全重投
                  --attempting/换代/缺报告--> 验证读唯一正匹配:ok;否则:suspect
人工裁决 suspect → resolvedOk | resolvedFailed(裁决即恢复:自动调度按最新状态重新规划,见 §8.4 通则后注)
```

**真实 SX 恢复的唯一性**:自动逻辑只能在同一 `witnessStoreId` 下收到 `report=unknown` 这一提交点前零副作用证明后,重投原 msgId。任何合法 `result=failed,sideEffect=none` 都终局化物理命令与原意图,`retryable=yes/afterRecovery` 只是手的建议值,不授权真实 SX 自动重投;任何 receipt rejected(包括瞬态 STALE_SESSION/QUEUE_FULL)同样终局化意图。若仍需发送,不得复活旧意图或铸 replacement,只能另铸新 `intentId`/`idemKey`:干净失败(合法 `failed/none` 与 receipt rejection)按下方 §8.4 通则由自动调度重铸,其余情形仍只能由人确认后另铸(2026-08-02 甲方裁决)。

自动业务调度器的再发授权自 2026-08-02 甲方裁决起按终局分类：`failed/none` 与 receipt rejection 按下段干净失败自动重试通则由调度器自动重铸；人工已裁决的 `resolvedFailed` 按“裁决即恢复”由调度器按最新世界状态重新规划新动作/新 `intentId`/`idemKey`，禁止重放原冻结文案、禁止复活原意图；阴性验证与未经人工裁决的 `suspect`/`possible` 仍不得当作再次自动发送的授权。业务层在 effect intent 构造前的纯计算（意向/回复/建议生成）失败不转人工：本巡检轮跳过该候选人，下轮巡检自然重试，节流为每巡检轮每档案至多一次意向调用与一次回复调用（替代原“每 turn 已批准 AI 调用预算”语义）；M5 P 档意向调用失败仍固定落一次 fallback 后继续回复调用。该纯计算语义不得延伸到已经构造的真实 SX。

**干净失败自动重试通则（§8.4，2026-07-29 以邀面卡例外立案，2026-08-02 甲方裁决推广为通则）**：任何 effectful 业务动作的 effect intent 终局为 `failed` 时，自动业务调度器可不经真人确认铸造带尝试序号的新业务动作（基础语义键不变，动作 ID 追加 `|try{n}` 后缀）与自该新动作 ID 派生的新 `intentId`/`idemKey`，由巡检轮按既有派发轨自然重试，次数不设上限。安全依据：`failed` 终局构造性蕴含副作用未发生——它只源于 `sideEffect=none` 结果、canceled/expired 结果或 receipt rejection（后者手未接受命令）；手在无法确证零副作用时上报 `sideEffectPossible`，落入 `possible`/验证轨而非 `failed`。每次尝试独立走完整 WAL/idemKey/手证词/页面正证安全轨，单次尝试内“至多一次标准点击”的保证不变。原意图与原动作照常终局留档（动作标 `retried`），不复活、不铸 replacement。原语可附加业务前置：`chat.sendInviteCard@1` 重铸前必须核对面试开始时间仍在未来，`startsAt` 已到期的动作不再重铸、按原语义转人工终局；该原语两段式实现（编辑器准备阶段失败时发送控件从未被点击，commit 点击之后的任何失败只进入 `possible`/验证轨）作为补充安全依据继续成立。本通则不适用于任何非 `failed` 终局：`suspect` 冻结该链等人工裁决；人工裁决 `resolvedFailed` 后由调度器按最新世界状态重新规划（上段“裁决即恢复”）；`possible` 与阴性验证的收敛语义一字不变。

**P 档输入预算与运输上限**：当前用途按 provider token 口径冻结为 `intent=8000`、`reply/scoring/greeting=16000`；provider 响应中的 `usage.prompt_tokens` 是输入 token 数及是否越过预算的唯一权威判据。请求正文 UTF-8 字节数、本地 tokenizer 估算或其他启发式都不得冒充 token 判据。调用前另有且只有一个相互独立的尺寸闸：完整序列化请求 JSON 的 UTF-8 运输硬上限首版为 256 KiB；命中记为请求运输失败（`requestPayloadTooLarge`），不是 `budgetBlocked`，此时 provider 未触达且 usage/成本为零。provider 成功响应缺少或携带非法 usage 必须作为响应无效响亮失败，其正文不得被消费为合法模型结果。若合法响应的 `usage.prompt_tokens` 超限，仍须如实保存该响应的真实 usage 与据此计算的成本，把 invocation 终局化为 `budgetBlocked/inputTokenBudgetExceeded`，且不得落分类、分数、招呼语、回复 action 或任何 effect。所有用途都禁止以截断输入、缩减既定投影、换档、换模型或自动重试来规避这两道边界。

**一次性历史误判纠偏（不是通用 retry）**：本许可只覆盖本文修订前已经发生、被旧“输入 UTF-8 字节数冒充 token 数”本地闸误记 `budgetBlocked`、且能由旧实现路径与全零 usage/成本共同证明 provider 从未触达的当前 M5 `reply` turn。只有真人经专用维护入口显式授权，才可在同一事务中保留原 `manualRequired` selection 与 `attempt=1` invocation 不变，并在同时满足以下全部事实时创建一条独立的新 `active` selection 和脱敏审计：账号仍处于人工停止；原 selection/turn 状态与失败原因精确匹配；turn 既有分类恰为 `interested/businessEvent` 且 `classifiedAt` 已存在；profile、conversation、context revision 绑定及冻结消息边界未变；不存在该 turn 的 action、effect intent、effectful command、自发消息或 `attempt=2` invocation。授权事务必须把当前投影 turn 从 `manualRequired` 精确恢复为 `classified` 并清空 failure，同时原样保留既有分类、`classifiedAt` 和所有冻结边界；除此不得改写 turn。任一前置不成立即零写入。获准的唯一 `attempt=2` 必须重新渲染并逐项核对 `inputHash/provider/model/contextRevisionHash` 与 `attempt=1` 完全相同；巡检、重启和普通 API 均不得自行触发。第二次无论因何失败都永久回到人工，不得再建 selection 或 invocation。该许可不适用于 intent、scoring、greeting、provider 已触达的调用、未来同形错误或任何真实 SX；审计只记随机引用、状态、hash 与原因，不得写入候选人 PII 或正文。唯一例外是下一段已发生事实的 2026-07-23 原始轨迹补验，不得据此类推其他失败。

**一次性原始轨迹补验（不是通用 retry）**：`ai-traces.db` 上线前，唯一 attempt 2 已触达 provider 并以 `invalidOutput` 终局，但旧隐私纪律未保存原始响应。甲方已显式授权仅对 turn `turn-20a94a0610113b8cc7c0e1e0b0972a9e35e8c3c67a16fcdf3351626d0b7da85a`、attempt 2 invocation `invocation-1a8eef7e0089c40d1bb1cf6e8f810b081265ca8ca528d2b6803974aa8273725d` 新铸恰好一次 attempt 3。专用本地维护入口必须先证明：账号仍由真人停止且无其他 active selection；turn、分类、绑定与冻结消息边界未变；attempt 1 仍是原零用量预算误判；attempt 2 仍是同 `provider/model/inputHash/contextRevisionHash` 的 `invalidOutput` 终局且旧 hash/usage/费用未被改写；没有 action、effect intent、effectful command、冻结边界后的 self Message、attempt 3 或本补验审计。授权只新增随机 active selection 与脱敏审计，并只把 turn 精确恢复为 `classified`、清 failure。attempt 3 调用前须重新渲染并与 attempt 2 核对同一 provider、model、input hash 与 context revision；调用后仍经过完整用量闸、严格解析、确定性 reducer、边界复核及既有 WAL/idemKey/正证轨。成功至多形成该 turn 的唯一 action；任何失败永久回人工；巡检、重启、普通 API 和其他 turn 均不得触发，禁止 attempt 4。该例外只增加一次 provider 调用和既有表中的 selection/invocation/audit 事实，不新增脑手契约或通用恢复机制。

**迟到帧总则**:任何终局/void 状态收到迟到的 ack/result,一律审计,不静默丢弃;suspect 收到迟到 result 按 §8.3 法条 6 自动核销;void 收到 result 只审计不改账(它是"脑账本是手所见超集"断言的观测点)。

**物理命令与逻辑派发链分层** [S]:每个 msgId 的 rejected/void/ok/failed/canceled/expired 都先独立持久化。readonly/intrusive 需要安全重派时才以新 msgId 建 `replacementOf` 链；真实 SX **禁止**进入这条新 msgId replacement 规则，只能在 §9 获得零副作用证明后重投原 msgId，否则验证后 suspect。对 R/I，单条物理命令终局不等于逻辑等待结束:等待者只在整条 replacement chain 最终成功、失败或达到重派上限时唤醒,不得因中间 void/expired 提前返回,也不得永远只等原始 msgId。cancel/result 竞态仍以目标物理命令的首个合法 result 为准。

**脑重启恢复**:启动即扫在途日志,未终态 readonly/intrusive 作废;无 `witness/1` 的 effectful 沿 M1 降级为 suspect。真实 SX 保留非终态账本并立即冻结 idemKey、占用账号域,进入 §9 reconnect reconciliation gate；先等 outbox 补投,再 query/report。只有完整对账无法给出终局或零副作用证明时才经验证落 suspect；进入 suspect 后释放账号域,仅继续冻结原 idemKey 与对应业务动作。这样脑重启不会制造自动重发,也不会在 outbox 即将补投前抢跑人工裁决。

**脑对离线的手不排队命令**:巡检 tick 现算现发,手不在线本 tick 跳过;命令是状态的投影,投影留在脑侧。deadline 取短值(巡检类 ≤ 2×execBudget)。

### 8.3 suspect 六法条 [M1 铺轨,X 已满负荷]

1. 触发:effectful 出现以下任一且 §9 对账/配套验证仍不能核销——deadline+宽限过仍无终局;result 带 sideEffect=possible，或 `chat.sendGreeting` 带 sideEffect=confirmed 但缺同一目标的可见关系后置状态正证;派发后 bootId 或 witnessStoreId 换代且无 result;脑重启扫描命中在途。冻结发生在对账前,但 suspect 终态只在对账结论后落下。
2. suspect 是**自动化的终态**:永不自动重试、永不静默;落审计,进客户端 UI 显著的 suspect 队列,有通知(v1 用 UI 告警面板+结构化日志;云端接入后加企微)。
3. **冻结幂等键**:人工裁决前,该 idemKey 拒绝签发任何新命令。
4. **释放串行域、隔离原动作**:未终态的 effectful 命令及其对账/验证过程继续占用账号串行域；一旦落为 suspect,该命令不再占用账号域。脑仅冻结原 idemKey 与对应候选人的业务动作,自动状态机跳过该动作并转人工；同一动作不得自动重发或另铸同义意图。其他会话的 effectful/intrusive 可继续按正常串行纪律派发 [X]。
5. 人工二选一裁决(确认已发生→补记完成;确认未发生→解锁允许**由人决定是否铸新意图**,自动逻辑不代劳),裁决落审计。**裁决入口前置条件**:手已重连且完成 outbox/query/report 与验证读仍无终局,或手离线持续 ≥ suspectManualDelayMs(默认 10 分钟)——对账未完成不许人裁,封死"人工误判与迟到 result 并发"的双发窗口。验证读封顶 3 轮；只有唯一正匹配自动核销成功,阴性不是“确认未发”,不得自动重发。
6. **迟到终局自动核销**:suspect 状态收到该命令的 result → 按 result 终局化、suspect 工单自动销案、落审计(与 cancel 的"result 赢"同构)——账本永远反映真相。

**配套立法**:今后任何业务 effectful 原语,必须与其配套验证读原语**同批交付**,缺验证读的 effectful 不准上线。

## 9. 手侧证词(journal / outbox)与恢复 [X 已激活]

### 9.1 存储形态与边界

chrome.storage.local 中只允许 base 投递层读写以下三类键；所有 DTO、枚举与 validator 均由 `contract.v1.json` 生成,plugin 不得另写接口:

```text
witness:meta       = WitnessStoreMeta{storeId,createdAt,schemaVersion=1,journalCount,outboxCount}
journal:{idemKey}  = JournalEntry{ref,idemKey,state,startedAt,committedAt?,result?,expiresAt}
outbox:{msgId}     = OutboxEntry{message:ResultEnvelope,createdAt,expiresAt}
```

`ResultEnvelope` 是完整的**已会话内** SX result 信封:`proto=1,kind=result,msgId,session(必填非空),ts,attempt,body:ResultBody`;outbox 的 key 必须等于 envelope.msgId,而 `body.ref` 指向原 cmd。`JournalEntry` 的 attempting 形态强制禁止 `committedAt/result`;committed 形态强制二者非 null且 `result.ref=ref`。`validateSchema` 在 Go/TS 两端执行条件字段与关联校验；时间字段之间的顺序关系**不由生成的 validator 表达**,而由手侧读回校验按 §9.5 分级处置。(2026-08-05 勘误:旧文称 `validateSchema` 一并执行"TTL 时间顺序校验",与实现不符——机器契约的 `JournalEntry/OutboxEntry` 从未定义时间顺序规则,该校验一直只存在于手侧读回路径。)

与宪法“手不持业务账本”的边界是四道栅栏,缺一不可:

1. 键值只含协议标识符、时间与 result 协议消息；**不存 args.text、候选人正文、guards 或业务决策输入**。attempting 尤其只是一张“这把手术刀可能已经举起”的证词。
2. 仅 base 可见；program 只能经过 `beforeSideEffect`/完成回调请求投递层写入,无法查询、删除或绕过。
3. journal TTL 14 天、outbox TTL 7 天、各上限 512。TTL 只是**未获 ack 条目的兜底清理**(脑长期失联、命令终局从未被确认时防止无限滞留)；正常生命周期终点是 §9.2.4 的 ack 收割,该删除不属于本条的“逐出腾容量”。TTL 清理仍只删已过期记录,绝不逐出未过期记录腾容量；**任一 TTL 条目实际删除前必须先旋转 storeId**，绝不能留下同世代 `unknown`；删除与计数更新之间的崩溃缝在下次读取时表现为"计数大于实际 key 数",按 §9.5 B 档旋转 `witnessStoreId` 后继续服务——读回时已无从区分它与真实丢失,一律保守按后者处理(2026-08-05 修订:旧文此处一律判 corrupt,把一个已换代、本可继续的状态升级成了整库熔断)。任一表已满即在 attempting 和 handler 不可逆部分之前回 `WITNESS_UNAVAILABLE{reason:capacityExceeded},sideEffect=none`。(2026-07-31 修订:此前 journal 无 ack 收割、只靠 TTL 清理,真实客户三天打满 512 后整机拒发;详见修订记录。)
4. 允许整体丢失,但丢失必须表现为新的 `witnessStoreId`。`journalCount/outboxCount` 与条目增删一同维护；每次启动和关键读写都须复核实际 key 数。单条丢失、崩溃在删除中间，以及**计数大于实际 key 数**(账面有、实物没有=可能有记录悄悄消失了)**一律不得在同一 storeId 下继续**,但按 §9.5 B 档旋转 `witnessStoreId` 后可以继续服务,不必整库熔断;**计数小于实际 key 数**(实物比账面多)不构成记录消失、只会让去重更保守,按 §9.5 C 档以实际 key 集为准修正计数并原样继续。脑看到换代只会增加验证/人工,绝不会把 unknown 当零副作用证明——**换代因此是一道完备的防多发闸,而不只是一次告警**。手证词永远不能反向覆盖脑账本。(2026-08-05 修订:旧文"计数不符一律判库损坏/换代"既未区分方向,也未说明何时选熔断、何时选换代;裁决见 §9.5。)

### 9.2 双写点与失败语义

真实 SX 的固定顺序如下,不得交换:

1. base 预检 feature、store 健康、journal/outbox 容量、idemKey 冲突；失败在动作前回 `WITNESS_UNAVAILABLE` 或相应 guard/context 错误。
2. program 完成页面、身份、`composer.empty` 与 `expectedTail` 核验后调用不可逆动作安全点；base 先写 `journal:{idemKey}=attempting` 并**等待 chrome.storage 写完成**。写失败回 `WITNESS_UNAVAILABLE{reason:writeFailed},sideEffect=none`,handler 的不可逆部分调用次数必须为 0。
3. 写成功后只允许一次物理动作。program 内部不得重试点击、键盘提交或网络发送。
4. 一旦越过 attempting 写点，本命令的**任何完整终局**（`ok`、`failed/none`、`failed/possible`或超时失败）都必须把 `journal=committed+完整 ResultBody` 与对应 `outbox=完整 ResultEnvelope` 放在**同一次 storage.set** 中再发送 result。`committed` 表示“该命令的终局已持久”，不等于“副作用已确认发生”；副作用真相仍由 ResultBody 的 `status/error.sideEffect` 表达。收到脑 ack(accepted/duplicate) 时，在**同一次 storage 删除操作**中收割 outbox 与该终局对应的 committed journal(按 `body.ref` 关联；越过 attempting 前的失败没有 journal，照旧只删 outbox)。ack 即脑账本已持久该终局，此后脑不再对该命令 query 或重投，journal 对它的对账价值归零；删除与计数更新之间的崩溃缝在下次读取时表现为"计数大于实际 key 数",按 §9.5 B 档旋转 `witnessStoreId` 后继续服务:Service Worker 重启后已无内存证据区分"我按计划删的"与"记录悄悄丢了",换代对两者都保守,且不必停机。ack 时若同 ref journal 仍为 attempting，即 committed/outbox 原子双写不变量已破，判库损坏。(2026-07-31 修订,旧文为“只删除 outbox，journal 保留至 TTL”。)越过 attempting 前的失败没有 journal，但仍须先进 outbox 再上报。
5. 后置条件未确认回 `POSTCONDITION_UNCONFIRMED/possible`，并按上一步原子持久这个失败终局。若 committed/outbox 双写失败，**不得用仅存于内存的任何终局绕过持久屏障**：保留 journal=`attempting`，熔断 dispatcher（不得继续 pump 已 accepted 队列），停止该连接的继续投递并由脑在重连 query 后进入验证读；同一 SW 内的重复 cmd 也只能回 duplicate ack，不能从内存重放易失 result。该分支既不得退回 `none`，也不得把易失事实伪装成可确认终局。恢复期只允许 query/report 与配套验证读推进；旧队列不得抢在恢复闸前重新获得页面执行权。

因此 SW 死于 attempting 写前=零副作用；死于 attempting 与 committed 之间=report attempting→验证/人工；死于 committed 后=outbox 补投或 report done。自动路径的方向始终是**可能少发,不能多发**。chrome.storage 回调与物理落盘之间是否仍有实现级窗口列入 §18 真机故障注入,不改变保守裁决。

### 9.3 重连四阶段(恢复闸)

手声明 `witness/1` 后,每次新会话在进入 normal 前严格经过以下四阶段；恢复期间脑冻结受影响账号的 intrusive/effectful 新派发,query/report 本身不占业务槽:

1. **outbox 补投**:手先按 hello 快照 `outboxPending=N` 补投这 N 条完整 result envelope,脑逐条持久去重并 ack。未收齐、损坏或**实际可投条目少于声明**即证词链异常,不得越过闸门；实际多于声明时照常补投全部条目并放行(多投只让脑多做一次幂等去重,不制造多发)。
2. **query**:脑对该手账本中每条非终局真实 SX 逐条发 query(ref=cmd msgId)。脑必须使用命令派发时持久记录的 `witnessStoreId` 作比较。
3. **report**:手按 §4.8 从内存/journal 回 report。done 直接入账；queued/executing 继续等原执行；attempting、storeId 换代、缺失/损坏报告进入配套验证；只有同一 storeId 的 unknown 可证明没有越过 attempting 写点。
4. **安全重投并 normal**:对上一步唯一获零副作用证明的命令,只更新 session/ts/attempt并重投**原 msgId 与原 body**；不得铸新 msgId。其余命令必须已经 result 终局、正在等原执行、验证中或 suspect。全部分类落库后才解除恢复闸进入 normal。

同 bootId 重连也走 outbox→query 的恢复闸；bootId 只说明内存连续,不能替代持久 result 补投。query/report 可安全重复,迟到 report 只在当前物理连接、当前 recovery generation、目标仍非终局时采信,否则仅审计。

### 9.4 真实 effectful 的配套验证读

#### 9.4.1 `chat.sendMessage@1`

验证原语固定为 `chat.readThread@1`,最多 2 轮(首轮+短暂间隔复读一轮)。脑使用原命令 `conversationRef` 构造最近窗口浅读;目标 hash 由原 args.text 按 §4.5 规范算法计算;不再要求 expectedTail 锚对齐、深分页或历史到顶判定,`guard.expectedTail` 仅保留动作前条件写用途。按 2026-07-29「成功=发后页面可见」裁决:窗口内观察到 `direction=out,kind=text,contentHash=目标`、无失败标志、时间不早于本次派发的消息,即自动补记 ok;同文多条匹配取满足条件的最新一条为本次。以下情况一律不能推出“未发送”:零匹配、页面/身份失败、证词库换代。它们全部落 suspect 转人工,**禁止自动重发**。

#### 9.4.2 `chat.sendGreeting@1`

验证原语固定为 `chat.readGreetingOutcome@1`，最多 3 轮。脑只从原命令重建 `{platformUserRef,positionRef,contentHash}`；手必须重新读取同一候选人、职位与可见关系状态。只有该目标明确处于“关系已建立”的合法 `confirmed=true` 才自动补记 ok；`conversationRef` 仅在同次观察稳定取得时一并收编，否则档案先进入 greeted、会话等待后续巡检绑定。`confirmed=false`、关系仍未建立或 unknown、身份/职位绑定不清、页面或读取失败、store 换代都不能推出“未发送”，全部落 suspect 转人工，禁止第二次招呼。

M4 原样复用 witness schemaVersion=1、attempting→committed/outbox、query/report 与“同 store 且 unknown 才重投原 msgId”的唯一安全恢复通道；不为招呼新增手侧业务状态。

#### 9.4.3 `chat.sendWechatInvite@1` / `chat.sendInviteCard@1`

两条卡片原语的验证读固定为 `chat.readThread@1`，最多 2 轮(首轮+短暂间隔复读一轮)。脑使用原命令 `conversationRef` 构造最近窗口浅读，不再要求 expectedTail 锚对齐、深分页或历史到顶判定。按「成功=发后页面可见」裁决，窗口内观察到一条符合下列全部条件、无失败标志、时间不早于本次派发的我方卡片即自动补记 ok(同类同参多条匹配取最新一条为本次)：

- 换微信：`direction=out,kind=card,cardType=wechatExchange,cardState=pending`，具有稳定 `sourceKey`，且 `contentHash` 等于 §4.5 的 `wechatExchange` 规范配方；
- 邀面：`direction=out,kind=card,cardType=interviewInvite,cardState=unknown`，具有稳定 `sourceKey`，`interview` 与原 args 的 `startsAt/endsAt/method` 逐项相等，且 `contentHash` 等于 §4.5 的 `interviewInvite` 规范配方。

`sourceKey` 只证明命中的平台消息具有稳定身份，不参与目标 hash 重建。零匹配、卡片状态或邀面参数不符、页面/身份失败、证词库换代均只进入 suspect 转人工，禁止第二次卡片动作。

#### 9.4.4 `chat.acceptWechat@1`

验证原语固定为 `chat.readWechatExchangeOutcome@1`，最多 3 轮，**且必须使用带锚形态**：
脑只从原命令重建 `{conversationRef,requestSourceKey}`，`requestSourceKey` 在本用途下
必填；§4.3 的无锚形态只服务独立 ContactAsset 收编，**不得为本动作补记成功**。验证读
不得搜索或切换会话，只在真人当前仍打开
同一会话时读取实时消息源。作为 `chat.acceptWechat` 验证器时，它只接受请求锚之后、
下一条 `105` 之前唯一存在一条 `259 + out + originType=2 + success`，且该行有稳定
`exchangeSourceKey` 和双方微信字段，才自动补记 ok 并把候选人 `peerWechat` 收编为
ContactAsset。`originType=1` 的另一种已证实形态只服务于“候选人接受我方邀请”的
独立只读收编，不得为本动作补记成功。

验证成功不追加我方 Message，也不物化微信成功固定回执；后续状态推进只消费同一个
已确认 action。路由不符、请求锚缺失、零匹配、多个匹配、字段缺失、读取失败或证词
库换代都不能推出“未接受”，全部落 suspect 转人工，禁止第二次 click。

### 9.5 读回校验的分级处置(2026-08-05 甲方裁决)

**判据。** 读回时发现任何不自洽,按顺序回答两个问题,答案决定处置档位:

- **问一:去重所需信息是否仍然完整可用?** 即每条 journal 的 `ref`、`idemKey`、`state` 能否被读出且互不矛盾。答"否"→ **A 档**。
- **问二:能否排除"有记录已经消失"?** 答"否"(即无法证明没丢)→ **B 档**;答"是"→ **C 档**。

只有"手在下次收到同一 idemKey 时误判我没做过"这一条链路会造成多发,而它的唯一入口是脑侧安全重投闸——**同一 `witnessStoreId` 下的 `report=unknown`**(§9.3 第 3 阶段)。因此换代(旋转 `witnessStoreId`)本身就是一道完备的防多发闸:换代后脑只会增加验证/人工,绝不会把 unknown 当零副作用证明。**B 档正是靠这一点做到既不停机、也不多发。**

**A 档 —— 判 corrupt(整库熔断、停止一切 effectful)。** 去重信息本身不可用或自相矛盾,继续服务等于蒙眼作答:

1. 同一 idemKey 的既有 `ref` 与当前命令不一致;多个 journal 复用同一命令 `ref`。
2. attempting 证词丢失却要写 committed;committed 的 `result.ref` 与 `ref` 不一致;同一 committed journal 出现不同终局;ack 时同 ref journal 仍为 attempting(§9.2 第 4 条末句)。
3. 运行中 `witness:meta` 消失;或出现**既非旧值、也非手自己刚写入之值**的第三个 `witnessStoreId`(手依本节第 2 条主动完成的 B 档换代不属于此列)。运行中已知 key 集缩小**不再列入本档**,改按 B 档第 6 条换代后继续——它正是"记录可能已消失"的典型形态,而换代已足以关闭安全重投闸,不必整库熔断。
4. `witness:meta` 违反 schema,或 `schemaVersion` 不受支持——meta 读不懂则全库无从解释。报错文本必须给出人可执行的处置(升级插件或清空证词库),不得只抛内部消息。
5. 内部不变量破坏:TTL 换代未能生成新 `storeId`、meta 未就绪、写入前自检 schema 违规。

**B 档 —— 旋转 `witnessStoreId` 后继续服务。** 全库其余条目仍可解释,但**无法证明没有记录消失**;换代把这份不确定如实告诉脑,再继续干活:

1. **单条** journal 或 outbox 违反 schema——这一条读不懂,但不影响其余条目。**但生成的 validator 里混有身份关联判据(当前唯一一条:`JournalEntry` 的"result.ref 必须等于 journal.ref",issue 的 `rule` 为 `correlation`),它命中时按 A 档第 2 条处理,优先于本条**:它证明的不是"这条读不懂",而是"这条的终局挂在别的命令身上",属身份被篡改。实现不得因为两者都表现为"schema 校验不通过"就一律归入本条。
2. journal/outbox 的键与内容不一致(键的 idemKey/msgId 与条目内字段对不上),或同一 idemKey/msgId 重复出现。
3. `journalCount/outboxCount` **大于**实际 key 数(账面有、实物没有)。**ack 收割(§9.2 第 4 条)与 TTL 清理(§9.1 第 3 条)删除已生效、meta 更新失败,落在的正是这一侧**:重启后内存证据已失,"我按计划删的"与"记录悄悄丢了"在存储层不可区分,一律按后者保守处理。
4. 终局 outbox 缺少唯一 committed journal;outbox 与 committed journal 的终局不一致;新 committed 的 outbox msgId 已存在;同一 outbox msgId 对应不同信封。
5. 一次读取整体失败(`readAll` 抛错)后恢复,无法确认期间的 key 集是否完整。
6. 运行中已知 key 集缩小(§9.1 第 4 条):内存视图里有、storage 里已不见。此处的"缩小"**以 storage 中实际存在的 key 为准**——因 B 档第 1、2、4 条被隔离而未装进内存视图的条目仍在 storage 里,不算缩小,不得因此升 A 档。

**C 档 —— 原样隔离后继续服务,不换代。** 记录都在、身份都对,只是附属字段不自洽:

1. journal/outbox 的时间字段关系不合法。
2. `journalCount/outboxCount` **小于**实际 key 数(实物比账面多)。
3. 出现未知的 `witness:` 前缀键。
4. 条目数量超过容量上限。

**处置纪律。** 以下十条是本裁决的实质,缺一即失去"不多发"的保证:

1. **不得删除记录。** 任何档位都不得把一条记录从 storage 里抹掉。丢弃一条 journal 等价于宣称"该动作从未发起过",会直接制造多发。能读懂的条目一律照常装载,继续参与 idemKey 去重与 query/report 应答,其 `ref/idemKey/state/result` 仍是权威事实。B 档中读不懂的条目**就地留在 storage**(留给 TTL 与人工排查),但**不装进内存视图,因而事实上不再参与去重**——这一点必须说破:它的安全性不再由它自己承担,而是由本档的换代承担(见第 9 条)。之所以仍不删除,是为可排查、且不制造既成删除,不是为了去重。
2. **B 档的换代必须先于任何其他动作完成并持久化**,顺序与 §9.1 第 3 条 TTL 换代一致:先写入新 `storeId`,确认落盘,再修正计数、装载条目、恢复服务。换代自身写失败即升级为 A 档。**手自己写入的新 `storeId` 不得触发 A 档第 3 条的"运行中 `witnessStoreId` 变化"**:该自检的基准是"手上一次自己持久化的值",凡是既非旧值、也非本次刚写入之值的第三个 `storeId` 才判 A 档。实现上等价于把自检放在换代动作之后重新取基准(现有 TTL 换代之所以能过关,正是因为它排在自检之后)。
3. C 档时间字段不合法时**只修正时间字段**,`ref/idemKey/state/result` 一律不得改动;修正只影响清理时机,不参与也不改变去重判定。修正后必须同时满足 `startedAt <= committedAt < expiresAt`(outbox 为 `createdAt < expiresAt`)**且 `expiresAt` 严格晚于当前时刻**——否则紧随其后的 TTL 清理会立刻删除它,把隔离变成删除。允许为此把 `expiresAt` 延长到 `当前时刻 + 原 TTL 长度`,不要求保持原值;该约束恒可满足,故不存在"修不动只好降档"的分支。
4. C 档计数偏小时以实际 key 集为准改写 meta,不动任何条目。
5. C 档未知键忽略:不读、不写、不删、不计入容量。
6. C 档容量超限只拒绝**新的** attempting/outbox 写入(仍回 `WITNESS_UNAVAILABLE{reason:capacityExceeded},sideEffect=none`,§9.1 第 3 条不变),已有记录照常提供去重与应答。
7. B/C 档均不得设 corrupt、不得停派 effectful、不得关闭连接(§9.6 第 1 条)。B 档换代后 outbox 仍须按 §9.3 第 1 阶段照常补投:result 是已持久的终局事实,补投只让脑多做一次幂等去重。
8. **本节三档已穷举当前读回校验的全部触发条件。** 实现中若出现本节未列的新判据,按"问一/问二"归档并补录本节,**不得默认归入 C 档**,也不得因"规格没写"而删除记录。
9. **换代闩锁按具体触发记账,不得按"我已降级"整体豁免。** B 档第 1、2、4 条的触发是**持久的**——条目就地留在 storage,下次读回原样再现。若每次 `reloadLocked` 都换一次代,脑侧派发时定格的 `WitnessStoreIDAtDispatch` 会在 report 回来前就已失效,全部 effectful 转验证/人工,人工介入率被顶满,比熔断更难诊断。因此**同一个触发只换代一次**:闩锁按触发的**身份**(键名 + 命中的判据)记账并**跨世代保留**,已换过代的同一触发再次读到时不再换代——若按"世代"记账,换代产生的新世代会把持久触发重新看成新触发,于是再换代,永不收敛。但**任何此前未记账的触发都必须各自再换一次代**,尤其"计数大于实际 key 数"每扩大一次差额都是一次新触发(差额数值参与身份构成)。记账表是内存态,随 Service Worker 生命周期,重启后至多多换一次代——这是可接受的,冷启动本就无法确认停机期间发生了什么。闩锁**绝不能写成"我已处于降级世代,故不再换代"**——那样此后每一次真实的记录丢失都会停留在旧 `storeId` 下,脑随即把 `report=unknown` 当成零副作用证明并安全重投,直接多发。本条与第 1 条互为条件:第 1 条允许把读不懂的条目排除出去重,唯一的代价补偿就是本条保证的换代。
10. **换代之所以是完备闸,依赖两条本节之外的不变量,放宽任一条都会使本档失效:** (一)真实 effectful 只经发送意图入口派发、因而必有 `IntentID`,重连时的同 bootId 盲重投据此跳过它们;(二)真实 SX 绝不铸造 replacement msgId(§8.4),因而不会经"继承同 `IdemKey` 与旧 `WitnessStoreIDAtDispatch`"的 replacement 链绕过 `storeId` 比较。任一条被放宽时必须重新论证本节。

**留痕。** 每次 B/C 档处置必须写入手侧运行日志,至少包含键名、命中的判据、原值与修正值。**不为此新增任何协议字段、枚举或事件类型**——按「防护成本预算」第 6 条"诊断辅助默认不进契约"。B 档另有脑侧天然可见性:`witnessStoreId` 换代会进入脑的审计与恢复分类,不依赖手侧日志。C 档只进手侧日志,脑无需知道:去重语义、report 应答与恢复闸行为都不因 C 档处置改变。同一理由下 hello/ping 的 witness 三字段语义不变。

**立案依据是真机数据。** 2026-08-05 客户机一条 committed journal 的 `startedAt` 比 `committedAt` 晚 1091ms(时间字段自身错乱,成因另案),整库因此判 corrupt 并永久熔断:13:23 至 14:35 全部 effectful 被拒派,一个 83 人批次发出 50 人后停摆、32 人未发,另有 1 条被迫由真人裁决为"未发送"。而该 journal 的 `ref/idemKey/state/result` 全部完好——去重所需信息一条不缺,被熔断的理由与去重无关。同库 232 条 journal 中仅此 1 条不合法。熔断且不可自愈:`state='corrupt'` 虽是内存标志,重启后仍会重新读到同一条毒记录再次熔断,而 TTL 自清理排在读回校验之后、永远轮不到执行,只能由人清空 chrome.storage。

**甲方知情接受的代价。** (一)失去"整库任何不自洽就立即停"的粗暴保险,安全性从此依赖三档分类判对与处置纪律第 1、8 条被严格执行;(二)B 档换代会让当时在途的 effectful 命令转入验证/人工,这是用少量人工票据换取整批不停摆,单次代价高于 C 档、远低于整机熔断;(三)**C 档的留痕事实上取不回来**——手侧只有 `console.*`(MV3 Service Worker 重启即失),且「现场数据上报」的诊断包白名单只含 `brain.log`/`brain.db`/`ai-traces.db`、不含插件日志,因此"日后靠日志复核 C 档分布"这条退路在当前设计下不存在,「防护成本预算」第 8 条要求的假阳性率数据也产生不出来;B 档因换代进入脑侧审计,不受此限;(四)本裁决不解决时间字段为何会错乱,该竞态仍会偶发,只是后果从整机停工降为一条日志。

### 9.6 证词库失败的表达形式(2026-08-05 甲方裁决)

证词库的任何失败都不得改用其他子系统的故障形态表达,否则脑只能看见症状、看不见原因:

1. **不得以关闭 WebSocket 表达存储失败。** result 无法先入持久 outbox、补投失败等情形一律按 §9.2 第 5 条在**本连接内**收敛(保留 attempting、熔断 dispatcher、停止继续投递),不得主动断链。断链会把存储问题伪装成网络问题,并使脑白白走完重连收编→query→租约超时→cancel→配套验证读→suspect 的全链路。
2. **证词库不可用时收到 query,必须如实回 report,不得静默丢弃。** 手明知自己的证词库不可用却沉默,会使脑必然等满租约才能收敛。该 report 沿用 §9.3 第 3 阶段既有分类,不新增状态。**但它携带的 `witnessStoreId` 必须与派发时不同**:`ReportBody.witnessStoreId` 是必填非空字段,而"`state=unknown` + 与派发时相同的 storeId"恰好是脑侧安全重投闸唯一认的零副作用证明(§9.3 第 3 阶段、§9.5 判据)——照字面"如实作答"而沿用旧 storeId,等于在证词库已不可信时伪造一份"我肯定没做过"的证明,直接制造多发。因此进入 A 档熔断或 B 档换代时,都必须先旋转并持久化新 `storeId`,其后所有 report 一律使用新值,使脑必然落入"storeId 换代 → 进入配套验证"分支。旋转自身也写不进去时(存储整体不可写),才允许沉默——此时任何应答都无法保证安全,让脑走租约超时反而是唯一保守的收敛。**该应答路径不得以"手已声明 `witness/1`"或"证词库健康"为前置条件**:证词库不可用恰恰意味着这两者都不成立,若沿用它们作门槛,本条在最需要它的重连路径上会整条落空(手不声明 `witness/1` → 会话不启用证词能力 → query 根本到不了应答逻辑)。此时脑侧因未见 `witness/1` 本就不会授权安全重投,应答只为让脑早于租约超时收敛,不改变任何裁决。
3. **hello/ping 中"未声明 witness 字段"与"声明为 0"必须可区分。** 手未声明表示"我没有可用证词库",脑不得将其读成"证词库正常且 `outboxPending=0`"而据此进入 outbox 补投判定(§9.3 第 1 阶段)。区分方式由两端实现选择,不新增协议字段。

## 11. 健康模型 [M1 两级,S 起三级]

三个正交问题,三个信号源,禁止互推:

## 12. 感知与同步 [S](裁决定稿,C 卷全文为实施细则;C 卷成文于沟通规格 v3,巡检"每日手动开启"门控以 v4 与本节为准)

1. **轮询循环归脑**:巡检节律(**每日真人手动开启**后数分钟一轮,最晚至 24:00——沟通逻辑规格 v4)只存在于脑的账号 actor;手零自主循环、零业务定时器(允许:重连退避、alarms 复活闹钟、心跳、传感去抖的一次性 setTimeout ≤3s)。手对"巡检开没开"零感知——开关只是脑侧调度器的一个闸。
2. **感知三层栈**:event 提示(秒级,可丢)→ ping.sensors 缓存搭车(≤25s,可丢)→ **巡检对账命令(分钟级,唯一正确性来源)**。层 1/2 的值禁止进入任何业务判断,唯一权力=把下一轮巡检拉前,并向巡检调度器提供经过既有稳定采样的侧栏总未读数。脑只在进程内按 `platform+accountRef+principalFingerprint` 保存“上一次完整未读子轮结束时的总未读数”：当前稳定值为正且没有结束基线、或与结束基线不同,才允许在下一候选人动作链收束后的安全边界插入未读子轮；与基线相同则不插入；稳定零值清除旧基线；缺失值不改变基线也不授权插入。该比较不授权中断在途命令、建档、状态推进或发送。拉前使用合并窗 25s、频控 ≥60s,且只有满足上述插入判据的提示才拉前;**巡检未开启时段拉前失效**——含夜间与"当日尚未手动开启",提示只落脏标记,开启后首轮收割,v4 明确"开机首日集中催与归档是预期行为"。事件是油门不是刹车,徽章清零/闪空永不取消或跳过普通巡检。
3. **事件五类**(unreadBadge / pageNavigated / loginStateChanged / manualInteraction / handLog):字段、去抖与两次一致规则按 C 卷 §6.2 入契约;manualInteraction 仅作巡检提示(DirtyHint),不再开手动静默窗(2026-07-27 甲方裁决废除;有人值守剖面下 45s 冻结每日误伤操作者本人,发送安全由草稿保护、发送前身份核验与页面正证承担)。**manualInteraction 收窄为推荐流换代信号(2026-08-11 甲方裁决)**:`kind` 只剩 `navigation` 一值,唯一发射条件是 Chrome `webNavigation.onCommitted` 公开确认的推荐页主框架 `reload`(`frameId=0` 且 `transitionType='reload'`);该信号不受 canonical 静音约束,脑侧据此作废推荐流。手侧不再监听真人 DOM 输入(pointerdown/keydown/click/popstate/hashchange 的 `isTrusted` 判定与命令导航归因窗口一并移除),`isTrusted` 自此不参与系统任何判断。裁决理由:真人插手的其余形态只带来"拉前巡检"这一加速效果,而拉前另有用户开启、未读角标、pageNavigated、登录态变化、巡检自身未扫完等来源覆盖,删除只损失名义延迟;而任何依赖 `isTrusted` 的判断都与甲方计划接入的 CDP/OS 级鼠标输入根本不兼容——那类输入 `isTrusted` 恒为 true,会让手把我方自己的操作误判成真人,进而作废我方正在使用的推荐流。甲方知情接受:真人点链接离开推荐页时推荐流不再当场作废,改由下一次扫描发现页面不可用时作废(慢数十秒,方向是少做);真人只点击/打字而未导致导航时,下一轮巡检晚约 1~1.5 分钟。
   **handLog 不是传感事件,是手侧自身的故障日志**(2026-08-06 随「日志上报」加入):它不参与本节 1/2 的感知三层栈,唯一去处是脑侧日志与日志上报队列,不得拉前巡检、不得改账号状态、不得触发任何业务命令。脑对它**不解析 context 查账号、不过 boundHandId 门禁**——手侧故障恰恰常发生在账号未绑定、掉登录或状态不正常时,按账号门禁拒收等于丢掉最该看的那一条。`EventBody.context` 因此自本次起为可选(与 `CmdBody.context` 同例,理由同为"绑定前尚无 accountRef");**除 handLog 外的事件缺 context 一律拒收**,该拦截落在脑的事件分流处而非 schema 层。手侧 `message`/`detail` 禁止携带任何候选人明文与页面文本,姓名与聊天正文一律由脑按引用自行补齐。
4. **同步机制**:脑持会话级账本锚尾(最近 ≤5 条 {direction, contentHash}),随 `chat.readThread` 首页下发,仅作滚动止损提示。单页最多 64 条且 compact data≤64KB;未到 anchor/顶部时回 `complete=false,nextCursor=opaque`,脑以相同 context/窗口参数带 cursor 续页,直至 `complete=true` 且 `anchorMatched || reachedTop`。各页内部按时间正序;首页是最新页,后续 cursor 页更老,聚合时依次**前插**且 cursor 保证页间不重不漏。手只在锚尾唯一命中时可裁掉锚前上下文;重复命中必须保留完整候选窗口。脑聚合成一份有界完整快照后,在快照任意连续片段中寻找账本后缀的最大重叠;同样最大长度有多解时取最靠后的起点(最少新增)并审计,随后才产出“本轮新增”投影,中间页不得入账或触发事件。零重叠→丢弃本轮聚合后 deep=true 从无 cursor 重启→仍零重叠按收编处理+审计,不静默吞。显式“处理当前会话”入口必须先用 `chat.identifyCurrentConversation@1` 锁定既有会话，并在该轮所有 `chat.readThread@1` 请求携带 `requireCurrent=true`；此模式禁止手调用会话定位器或产生会话切换，且每一页读取前后都必须复核 URL 仍为同一 `conversationRef`，漂移只失败、不自动切回。
5. **卡片=身份哈希+状态分离**:contentHash 只哈希卡片身份(cardType+关键参数),cardState(pending/accepted/rejected/expired/unknown)独立；邀面卡关键参数为 `startsAt+endsAt+method`，微信号永不进入 hash。按钮事件=以同会话 `sourceKey` 对齐的状态跃迁——旧卡跨轮重复触发机制性不可能,"已结束者点旧卡直进已约面"天然支持。平台没有可信状态映射时必须保留 `unknown`，不得把私有数值猜成业务状态。
6. **列表=变更检测不是账本**:`chat.readList` 不使用分页 cursor，也不把持续变化的虚拟列表冻结为跨命令快照。每次命令只返回当前平台列表已经加载、且可由同一会话定位器操作的稳定窗口，最多 32 会话且 compact data≤64KB。`move=reset` 必须选择并回读目标 filter、回到列表顶部后读取窗口，用于新完整扫描及 `all/unread` 切换；`move=next` 必须确认 filter 未变，向下移动小于一屏、等待窗口稳定后读取。脑必须先对当前窗口全部会话完成“跳过或处理”决定，才可派发下一次 `move=next`。跨窗口重复 `conversationRef` 是正常输入，由脑按 `conversationRef+fingerprint` 跳过；同一窗口内稳定身份重复仍是页面身份异常。`complete=true` 只表示到达当前物理底部，或 `filter=all` 命中年龄截止，不承诺平台历史永久穷尽。`filter=all` 的 `stopOlderThanDays` 省略默认 8；`filter=unread` 时禁止携带该字段、不设年龄截止，并须先把平台职位范围真实切为“全部职位”且回读确认，再把平台列表真实切为“未读”且回读确认，不得只在手内过滤普通列表。该公开筛选回读是未读视图的授权事实；筛选结果中单行 `unreadCount` 只是低保真变化提示，零值不得单独导致整窗失败，也不得由手静默过滤。`ConversationSummary.positionTitle` 是 optional/nullable 展示事实，只在同一会话行存在唯一公开可见职位标题时返回；缺失、空值或歧义必须省略或置 null，不得从当前默认职位、姓名、平台私有 ID 或 DOM 位置猜测。它只供主动来聊候选人按本机后台职位名称唯一精确匹配建档，不参与既有档案身份、会话身份或动作授权。

   列表的 unread 与 lastMessage 摘要都是低保真变更提示,不是账本。`tracking=pending`、消息账本为空或到期时钟命中时必须读取详情；除此之外,未经核对的 `unread>0` 或 lastMessage 摘要与账本尾不一致,触发一次详情读取。详情成功读取并完成账本事务后,脑可以按账号身份代际与会话作用域在内存中登记本次列表提示 fingerprint；未变化的同一 fingerprint 只抑制由 unread/摘要差异产生的重复读取,不抑制前述强制对账。fingerprint 任一输入变化后重新触发；详情读取、身份确认或账本事务失败不得登记。不脏且无强制对账条件时,本轮零详情页面动作。

   手上报的稳定 `unreadTotal` 是未读优先巡检提示。脑在 `filter=all` 的首次领取及每个新会话领取前,仅在上一候选人动作链已经收束的安全边界按本节第 2 条比较当前稳定值与上一次完整未读子轮的结束基线；正数且无基线或数值不同才进入未读子轮,正数同值、零值或缺失值都继续普通扫描。未读子轮内部不得递归插队，每次都以 `filter=unread,move=reset` 从顶部开始，逐窗口完整遍历一次；每个本轮唯一观察到的会话都必须至少打开一次，并以该子轮独立的已尝试集合保证每个 `conversationRef` 至多领取一次。可处理会话沿用 `chat.readThread@1` 读取并进入状态机；仅需消除未读、但不可建档或不可处理的会话使用 `chat.openConversation@1` 打开后跳过。同一窗口须继续处理尚未尝试的后续会话，窗口全部处理后才 `move=next`。单个会话的定位、读取或幂等打开失败只结束该目标尝试并继续后续会话；账号、身份、筛选与页面级失败仍服从既有停止语义。打开会话或产生候选人可见动作不会使已经取得的纯数据窗口失效，脑不得为未经证实的行消失假设在每处理一人后重读列表。

   未读子轮以“从顶部到 `complete=true` 遍历一次”为完成,不以列表行消失、列表为空或总气泡归零为完成条件。子轮完整结束后重新取得稳定总未读数：正数写为本主体的结束基线,零值清除基线；读取缺失、页面级失败或窗口未完整到达结束边界时不得伪造结束基线,并且不得在同一次普通扫描中围绕失败现场立即重入。随后切回 `filter=all,move=reset`。本次普通完整扫描已经决定过的 `conversationRef→fingerprint` 集合贯穿其间插入的未读子轮：提示未变化的会话直接跳过，期间产生新 fingerprint 的同一会话仍可重新领取。因此，插队期间曾处理的会话若又收到新消息，返回普通列表后不会被旧标记永久压掉。若旧未读消除与新未读到达恰好抵消、使总数与结束基线相同，本轮允许不再优先插队；普通全量扫描及 fingerprint 变化检测负责兜底,不为该低概率形态新增第二套版本机制。
7. **收编边界**:每会话 `adoptedBoundarySeq`,边界前消息不触发事件、不进对话轮,仅作语境。
8. **多标签仲裁**:SW 维护 canonical 平台标签页;驱动命令与传感只在 canonical 执行/发射(manualInteraction 例外:推荐页 reload 换代信号不论发生在哪个平台标签页都上报)。
9. **账号主体确证**:`probe.platform.data.principalFingerprint` 是平台无关、不透明、只许相等比较的登录主体指纹,不得暴露 Cookie/token/明文平台 userId,脑不得解析。首次真人绑定前尚不存在 `accountRef`,因此仅绑定流程发出的 `probe.platform` 可按原语元数据 `contextOptionalBeforeBinding=true` 省略 context；已绑定账号 actor 发出的 probe 仍必须携带完整 context,其余 [S] 原语无例外。真人绑定时脑保存指纹;之后每条 intrusive/effectful 命令在 context 携带 `expectedPrincipalFingerprint`。手在首次驱动页面前复读比较,并在返回任何账号数据或进入不可逆动作前再复核;不一致回 ACCOUNT_MISMATCH(sideEffect=none,manualOnly),不得交付跨账号数据。`nav.ensureSurface` 是 pageAbsent 时唯一恢复驱动例外,但身份一旦可见仍须在返回前复核。
10. **身份三态**:已绑定但 pageAbsent/contentScriptDead 暂不可观测时保留绑定,仅允许 probe/nav 恢复;新 session/boot 或健康过期时必须 fresh probe 一致后才放行驱动;明确 mismatch 或 logout→login 时绑定立即失效,只允许 probe,必须真人重新确认。登录态 `in` 本身永远不等于账号一致。
11. S 批基础原语四条:`probe.platform`(readonly,5s/30s)、`nav.ensureSurface`(intrusive,lease 30s)、`chat.readList`(intrusive,lease 60s)、`chat.readThread`(intrusive,lease 30s,兼任 [X] 验证读)。args/data 的 required、nullable、枚举、上下限均以 `contract.v1.json.schemas.types` 为唯一机器源；关键边界为列表窗口≤32、线程页≤64、每次 compact data≤64KB、分页 cursor≤2KB、anchorTail≤5、摘要≤200 Unicode 码点。列表 data 不含 cursor，`complete` 只陈述当前窗口遍历边界；线程 data 继续满足 `complete=false ⇔ nextCursor 非空` 与 `complete=true ⇔ anchorMatched || reachedTop`。opaque cursor 只许用于仍声明它的分页原语并原样回传，不得解析、跨账号/会话/参数复用；CURSOR_INVALID 时脑丢弃该原语未入账聚合并从无 cursor 重启。任一条目本身超限则 PAYLOAD_LIMIT,不准伪造 complete 或裁剪字段。M4 另激活 `candidate.readCurrent` 与 `chat.readGreetingOutcome`，其时限和字段仍以原语 metadata/schema 为准。

## 13. 大载荷(blob)[X→2026-07-28 部分激活]

简历 HTML、截图和不可分页的大载荷走同一 Go 进程的 localhost HTTP 内容寻址端点(`PUT /v1/blobs`,`sha256:<hex>` 引用,单件 ≤20MB,30 天无引用 GC,token 会话作用域经 welcome 下发);WS 消息只携带 ref。完整原语结果 JSON 用 `result.dataBlobRef`,取回后先验 sha256 与大小,再按该原语 dataSchema 校验;单条消息的大文本用 message.blobRef。`data` 与 `dataBlobRef` 在 status=ok 时恰有一个。S 批在 `blob/1` 未激活期间，列表按当前稳定窗口拆成独立命令、线程等真实分页结果使用 §12 的 cursor，单次 data 均≤64KB；单个不可再分条目超过 2KB 文本边界或单次结果仍无法表达时回 PAYLOAD_LIMIT,不准截断、发明字段或突破 256KB 帧上限。理由:控制面不被大帧队头阻塞(心跳纯度)、免 base64 税、传输无关(Claim Check 模式)。**blob 通道零协议语义**——不推进状态,不构成第二语义通道。

**2026-07-28 激活记录(触发条件「首个大载荷证据原语」到期,甲方裁决见成功取证截图立案)**:本次只激活手→脑上行子集——脑实现 `PUT /v1/blobs`(Bearer token 校验、逐字节 sha256 复核、单件 ≤`blobMaxBytes`、内容寻址落 `data/blobs/`,重复 PUT 幂等成功),welcome 携带 `blob{endpoint,token,maxBytes}`;token 为会话作用域随机值,连接换代即作废,不是配对或身份凭据(§4 注 4 不变)。脑读取 blob 走进程内文件读取,不开 HTTP GET;`result.dataBlobRef`/`message.blobRef` 的下行取回路径与 30 天无引用 GC 清扫继续保持未激活,列为显式后置项,触发条件不变。首个消费者是 `chat.captureThreadScreenshot@1` 与 `candidate.captureResumeScreenshot@1` 的 `imageBlobRef`(在各自 dataSchema 内引用 blob,属 §13 既定 Claim Check 用法,不新增语义);两原语以 `blob/1` 为 precondition,welcome 未携带 blob 时必须在执行前响亮失败(PAYLOAD_LIMIT),禁止内联或截断图像。

## 14. 版本与能力协商 [M1]

- **首客前例外**:第一次给真实客户安装前,可按 AGENTS.md 的四项删除举证、持久化兼容评估和硬切换程序,在当前 `proto`/原语版本内做破坏性清理。该许可只处理对外兼容形态,不允许削弱已经冻结的安全内核语义。
- `proto`:兼容冻结后的跨原语破坏性开关;兼容冻结后,当前主版本内一切变更是加法(must-ignore)。信封、kind 或跨原语公共结构不兼容时升级主版本并提供迁移/双栈方案。
- 原语粒度版本 `name@ver`:兼容冻结后,args/data/guards/evidence schema 不兼容变化=原语版本+1;脑按会话 caps 门控派发,支持双端灰度不同步。
- `contractHash`:在线握手仍仅作漂移告警,不因 mismatch 拒绝或关闭连接;连接建立及 readonly/intrusive 的兼容门禁仍是 `proto`/逐项 `caps`(哈希对合法加法也会变化,不得把无害灰度变成整手瘫痪)。**effectful 另有常备部署一致性硬闸**:脑在铸造 WAL 前必须确认当前 ready 手 `contractMatch=true`;Hub 在当前 active 代的线性化 socket 写点前,还须从 `cmd` 自身原语元数据判类并最终复核,覆盖 queued 同 `msgId` 重投与连接接管竞态。任一 mismatch 都明确拒绝并审计,且不得有 effectful 字节进入 socket;readonly/intrusive 与 query/report 等恢复读不受此闸阻断。这仍不是鉴权,也不取代 `proto`/`caps` 的兼容协商。首客前破坏性批次还须执行**部署硬切换程序**:暂停派发,重启脑并重载插件,确认哈希一致后才恢复 effectful。
- codegen:`contract/` → Go(类型+校验+状态机常量+合法转移表)与 TS(类型+常量+校验);CI 校验两端生成物一致;禁止手写协议类型。

### 14.1 部署硬切换中的插件重载握手 [X]

管理端以一次维护操作完成“重载插件→确认新版本就绪”,不另开命令通道,也不增加 hello 字段或消息 kind:

1. 新版文件可预先准备在当前扩展不会读取的独立暂存位置;若上层业务工作流仍依赖本次重载会刷新或失效的页面现场,部署编排不得改写正式插件目录或派发 `debug.reload`。进入上层定义的安全边界后,部署编排必须已按本节上文暂停派发;管理端记录目标手的 `handId`、旧 `bootId` 与本次期望的 `contractHash`,确认该手没有未收束命令后,才可原子替换正式插件目录并紧接着经正式命令通道派发 `debug.reload@1`。该原语为 `intrusive/platformSideEffect=none`,空 args、空 data,执行预算 5s、deadline 30s。维护命令尚未派发前,在后续安全边界重新评估上述条件属于部署编排延迟,不属于本节第 4 步禁止的自动重派。
2. 旧手完成重载前准备后回 `result(ok,data={})`。这个 result **只表示旧手已准备**,不表示插件已经重载或新版本已经就绪。旧手必须等该 result 收到脑的 `ack(accepted|duplicate)` 后,才调用一次 `chrome.runtime.reload()`;ACK 未到就沿既有 result 投递纪律补投,不得提前重载而丢失完成信号。
3. 新 SW 出生后刷新已经打开的平台标签页,使页面侧脚本与新扩展版本对齐,然后走既有连接与 hello 流程。脑只在观察到**同一 `handId`、不同于旧值的新 `bootId`、与本次期望值相等的 `contractHash`**,且该手通过脑侧既有 ready 判定后,确认“新版本已就绪”并允许部署编排继续；`ready` 是既有脑侧就绪状态,不是新增 hello 字段。
4. `debug.reload` 禁止进入 readonly/intrusive 的普通自动 replacement/重派链。命令、result ACK 或新 hello 任一步超时,本次维护操作保持未完成并继续禁止 effectful;是否另铸一次维护意图只能由管理端维护编排显式决定,不得由通用派发恢复逻辑代办。

当前剖面是首客前、有人值守。甲方显式接受插件重载与随后刷新平台页可能丢失未发送聊天草稿的风险;本批**不检测、不保存、不恢复草稿,也不为草稿增加协议字段或阻断守卫**。进入首个真实客户安装阶段前必须重新裁决该风险预算。

## 15. 反模式清单(明令禁止)[M1]

1. 两端手写协议字段/别名——唯一来源是 codegen,code review 见手写字段名即打回。
2. 回执不带 ref——生成类型非可空,构造上灭绝。
3. DOM/selector/tabId/windowId/平台 id 进语义字段——只许 evidence 与日志;脑读 evidence 做分支同罪。
4. 用时间戳做去重、排序或状态裁决。
5. 手自主重试 effectful;原语内部重试同罪。
6. 把"WS 连着"当"手健康"、把"心跳在"当"页面在"。
7. 自由文本承载语义(error.message、progress.stage 上做程序分支)。
8. 第二条命令通道(任何"顺手加个 HTTP 接口直接叫手做事"直接否决;blob 无语义不在此列)。
9. 追求协议级恰好一次(QoS2 迷信)。
10. 大载荷内联 base64 进 WS。
11. 过程式命令("点第 3 个会话")——命令必须声明式,这是 intrusive 可重派的构造前提。
12. 手侧批量聚合命令、自行排程——一 cmd 一 ack 一 result,节奏权 100% 在脑。
13. 无版本报文。
14. 心跳携带业务载荷/心跳到点反向采集。
15. 静默去重——重复到达必须重新 ack(+必要时重放 result)。
16. 把 chrome.storage 当账本——手侧持久数据只有证词地位,冲突以脑为准、疑义转人工。
17. fire-and-forget 下发 effectful——每条 SX 账本行必须走到终局或 suspect。
18. 未知原语/指令默认回成功——默认分支必须是显式拒绝。
19. 同一条存活 TCP 上重发帧——ackTimeout 的唯一动作是重建连接。
20. 事件直接触发业务命令——事件唯一权力是调整巡检开跑时刻/健康档(静默窗已于 2026-07-27 废除)。
21. retained 式"上线即收到陈旧命令"——脑对离线手不排队,命令现算现发。
